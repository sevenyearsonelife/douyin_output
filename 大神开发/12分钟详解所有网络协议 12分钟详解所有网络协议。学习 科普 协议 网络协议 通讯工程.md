IP stands for Internet Protocol and it is the absolute foundation of the entire internet. Every device connected to the internet has an IP address. Your phone has one, your laptop has one, the server hosting YouTube has one. An IP address is a numerical label that identifies a device on a network, exactly like a home address identifies a house on a street. IP was formally specified in September 1981 in a document called RFC 791 prepared for DARPA, the Defense Advanced Research Projects Agency. The engineers who built it were not building a commercial product. They were building a military communication system that could survive a nuclear attack by having no single point of failure and no central control. That decision is the reason the internet is decentralized today. IP takes your data and breaks it into small chunks called packets. Think of it like sending a book through the mail by tearing out each page, putting each page in a separate envelope, and mailing them all individually to the same address. Each packet contains a header with the source IP address, the destination IP address, a time to live value that limits how many routers the packet can pass through before being discarded, and a checksum to detect corruption. IPv4 addresses are 32 bits long, giving a maximum of 4. 3 billion possible addresses. In 1981 that seemed like an infinite number. By 2011, IANA, the organization that manages IP addresses, had distributed the last available IPv4 block. That is why IPv6 was created, using 128-bit addresses, giving us 340 undecillion possible addresses. That is 340 followed by 36 zeros. To put that in perspective, if you gave every single atom on the surface of the earth an IPv6 address, you would still have trillions of addresses left over. The most critical thing to understand about IP is that it is completely connectionless and unreliable by design. RFC 791 specifically states that IP limits its scope to delivering packets from source to destination. It does not guarantee packets arrive, it does not guarantee they arrive in order, it does not guarantee they arrive at all. IP routes and moves on. Everything reliable about the internet is built on top of IP by other protocols. TCP stands for Transmission Control Protocol, and its entire purpose is to fix everything IP does not guarantee. IP is connectionless and unreliable by design, meaning it drops packets, reorders them, duplicates them, and does not care at all. For real-time streaming that is acceptable, but for anything where data integrity matters, a missing byte in a firmware update can break a device, and a missing byte in a financial transaction can cost millions. TCP solves this by adding three things on top of IP. First, a connection, where before any data moves, both sides go through a handshake confirming they are ready to communicate. Second, sequencing, where every byte in the stream gets a sequence number, so the receiver knows exactly what arrived and what did not. Third, acknowledgement, where the receiver confirms every segment it gets, and if the sender does not hear back within the retransmission timeout, it resends that segment automatically. On top of that, TCP implements a sliding window for flow control, preventing a fast sender from flooding a slow receiver, and a congestion control algorithm that backs off when it detects packet loss on the network. The result is a guaranteed, ordered, reliable byte stream between two endpoints, and that guarantee is exactly why every protocol that cannot afford to lose a single byte, like HTTP, HTTPS, MQTT.和 WebSocket 运行在 TCP 之上。

UDP 代表用户数据报协议，它是 TCP 的故意相反。TCP 保证交付、顺序和完整性。UDP 故意抛弃了所有这些，原因比你想象的更重要。UDP 是在 RFC 768 中指定的，于 1980 年 8 月由 Jon Postel 发布，他是编写 TCP 的同一位工程师。它运行在 IP 之上，就像 TCP 一样，但移除了所有可靠性机制。没有握手，没有序列号，没有确认，没有重传，没有流量控制，没有拥塞控制。UDP 接收你的数据，将其包装在一个最小的 8 字节头中，只包含源端口、目标端口、长度和校验和，然后将其发送到目的地，而无需任何确认。TCP 头最小为 20 字节，UDP 头只有 8 字节。这种差异在大规模时非常重要，当服务器同时处理数百万个连接时。UDP 存在的真正原因是延迟。

TCP 的握手、确认和重传机制都引入了延迟。对于某些应用程序，这种延迟是完全不可接受的。想想一个实时视频通话。如果一个视频帧在发送方和接收方之间丢失，你不想让 TCP 停止一切来检测丢失的确认，等待重传超时，重传帧，并在半秒后将其传递到你的屏幕上。到那时，对话已经继续，显示旧帧会使一切变得更糟。你想要下一帧，现在，即使它稍微降级。人眼处理丢失的帧比半秒的冻结要好得多。这就是 UDP 的设计理念：接受不完美以换取速度。你会在视频流中找到 UDP，其中丢失的数据包会导致短暂的故障，而不是暂停；在在线游戏中，单个毫秒的额外延迟可以决定比赛的结果；在实时语音通话中，半秒的冻结比半秒的冻结更好；在 DNS 查询中，一个简单的查询和响应需要在不到 10 毫秒内完成。UDP DNS 查询只需要两个数据包。

相同的 DNS 查询通过 TCP 需要至少 7 个数据包。对于每秒处理 100,000 个 DNS 查询的服务器，这种差异是巨大的。DNS 代表域名系统，它就是你输入 google. com 而不是这个的原因。DNS 就像互联网的电话簿。你输入一个域名，你的设备向 DNS 解析器发送查询。解析器检查其缓存。如果有答案，它会立即返回。如果没有，它会查询根服务器，然后是顶级域名服务器，然后是该特定域名的权威名称服务器，直到找到正确的 IP 地址。整个过程在不到 50 毫秒内完成，每次你访问一个新网站。DNS 默认使用 UDP 端口 53，因为查询很小且快速。大多数人都不会想到的一个重要细节是，DNS 默认是完全未加密的，这意味着你的互联网服务提供商可以看到你查询的每个域名。

DNS over HTTPS 是为了解决这个问题，通过在正常 Web 流量中加密你的 DNS 查询。HTTP 代表超文本传输协议，它是你的浏览器与 Web 服务器通信的语言。它是由 Tim Berners-Lee 在 1989 年发明的。

At CERN. HTTP works on a simple request and response model. Your browser sends a request with a method: GET means "give me this resource", POST means "process this data", PUT means "update this resource", DELETE means "remove it". The server responds with a three-digit status code: 200 means success, 404 means not found, 500 means the server broke. HTTP/2 in 2015 allowed multiple requests simultaneously over one connection. HTTP/3 in 2022 replaced TCP with QUIC, reducing latency, especially on mobile networks. HTTPS stands for Hypertext Transfer Protocol Secure, and it is HTTP running inside an encrypted tunnel created by TLS. Without HTTPS, every byte you send travels as plain readable text. Every password, every credit card number, visible to anyone intercepting the traffic. HTTPS fixes this with a TLS handshake that does three things: it authenticates the server using a digital certificate, it establishes a shared encryption key between your browser and the server without ever transmitting that key over the network, and it encrypts all traffic using AES-256, making every byte completely unreadable to anyone in between. Over 85% of all web traffic is now encrypted with HTTPS, and it is the absolute minimum standard for any website handling user data. MQTT stands for Message Queuing Telemetry Transport, and it was built for a world HTTP was never designed for. It was created in 1999 by Andy Stanford-Clark of IBM and Arlen Nipper of Arcom to monitor oil pipelines in remote desert locations via satellite where connections were expensive, unreliable, and devices had almost no processing power. MQTT uses a publish-subscribe model. Devices publish messages to a central server called a broker. Other devices subscribe to the broker and receive only the messages they care about. Nobody talks directly to each other. MQTT's minimum packet size is just two bytes, compared to hundreds of bytes for HTTP. That tiny overhead is why MQTT became the standard for IoT devices. Your smart thermostat, your connected sensors, your industrial monitors are almost certainly using MQTT right now. WebSocket is the protocol that made real-time web applications possible. HTTP was never designed for applications that need data pushed instantly without asking. Live stock prices, chat messages, multiplayer games. All of these need something HTTP cannot provide. The old workaround was polling: your browser asking the server every second if anything changed. Wasteful, slow, and unnecessary. WebSocket was standardized in December 2011 in RFC 6455. It starts as a normal HTTP request, but asks the server to upgrade the connection. The server responds with status code 101, switching protocols. The connection is now a persistent full-duplex channel, where both sides send data at any time without waiting. The server pushes data the instant something changes. No polling, no delay, no wasted requests.
