I'm going to say something that might be controversial. Don't write prompts. I don't mean stop talking to your agent. I mean the big one, the giant instruction file at the root of your project that tries to explain everything. To see why, let's open one of the largest codebases on earth, Firefox. Tens of millions of lines of code, C++, Rust, JavaScript, Kotlin. You would expect its agent instructions to be enormous. The root file is 73 lines, and the very first rule in it, almost never add comments. So we're off to a good start. Here's a prompt most of us have written. One file, build steps, test commands, style rules, architecture, and a warning about that one flaky test. Every task pays for all of it. Fixing a typo in the docs, the agent still reads how the garbage collector works. Confidence does something different. The root file holds only what is true everywhere. Then it lists five directories and says, when you work in here, open the agent's file that lives in here. The JavaScript engine has one, layout has one, web render has one. Each is around a hundred lines or less, and each is only read when you step inside. It's the same move as extracting a function. The instruction didn't get shorter, it got a scope. Now look inside the layout one. It's 31 lines, and most of them say the same thing. Read this document first. It doesn't explain the frame tree, it points to the file that does. Because that document is maintained by the people who change the code, and a copy inside a prompt would be stale by Friday. The JavaScript engine's file goes one step further. It is a map, one line per directory in the order a script flows through the engine. Parser, interpreter, compilers, garbage collector. A map tells you where to look. It doesn't try to be the territory. And the Claude specific file?

It is one line. It imports the agent's file. One source of truth for every tool. Next problem, you can't grep Firefox. Well you can, but you'll wait. You could write a paragraph about that. Search carefully, restrict your paths, be patient. Or you can hand the agent a tool. Firefox ships a command line search that understands the code. Ask it for a definition and it answers. Four example commands replace a whole page of advice. This is the type system of prompting. A sentence asks the model to behave. A tool makes the right thing the easy thing. And there's a lovely line right below it. If you can't find something quickly, it is better to ask. But some knowledge really is long. Triageing a performance regression. Migrating translated strings. Splitting a commit for review. Firefox keeps 24 of these and calls them skills. Each one is a folder with its own instructions, scripts, and references. Here's the trick. Only the description is loaded up front. One paragraph. The other few hundred lines stay on disk until the task actually needs them. And the team is honest about the price. Their readme says every description carries an always-on cost. If a skill isn't useful to everyone, it doesn't belong in the tree. So the description becomes an interface. The good ones say when to use them and when not to. Not for running tests. Use the other skill. Some even declare which commands they are allowed to run. That's not a prompt anymore. That's a signature. One more layer. During code review, nobody should have to remember which guidance applies. So there is a small config file of rules. If a patch touches a web interface definition and a C++ file, load the web standards guide. If it touches front-end code but not tests, load the front-end guide. The prompt is selected by the diff, not by somebody's memory. Prompts have the same disease as comments. Nothing checks them. The compiler won't warn you when an instruction goes out of date. The agent will just follow it confidently. Firefox has a rule for this, and I love it. Reference a name, not a position. This text outlives the code it describes.所以没有行号，没有上面的函数，名称和固定到一个修订的链接。

所以你应该永远不要写一个提示吗？当然不是。写下代码不能告诉你的陷阱。像这个：默认截图不显示真实的渲染器输出，所以永远不要从截图中得出渲染错误已修复。或者这个：永远不要提交补丁而没有明确的批准。没有多少阅读源代码会教一个代理这个。这就是提示的作用。而这里是我没想到的部分。这些文件是学习一个大型项目最好的方式，对代理和人都是如此。从根开始，学习到处都成立的东西。进入一个模块，阅读它的映射，然后浏览技能描述，看看这里实际完成的工作。几百行，你就知道一切在哪里。所以在你给提示添加另一段之前，问一个不同的问题：它应该放在哪里？一个范围、一个指针、一个工具、一个技能或一个触发器。不要写提示，构建它们所属的地方。
