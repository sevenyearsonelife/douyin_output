两款应用功能完全相同，开发时间相差二十年。左边的这款你手指还没松开鼠标，它就已经打开了。它只占用一点五兆字节的内存。它是一九九八年由一个挤在一间会议室里就能装下的团队用 C 语言写出来的。右边的这款是今天早上刚下载的 Hello World 模板。光是画出窗口就要整整三秒，为了渲染 Hello 这个词，它分配了四百八十七兆字节的内存。光是输出一句问候就依赖了一千八百个第三方包。我们曾被许诺更快的硬件会让我们的工作更轻松，可事实恰恰相反，我们用硬件性能掩盖了一个事实，底层的代码早就不再追求优化了。这就是我们现在要做的去臃肿化。过去差不多四十年里，每一代软件都会耗尽下一代硬件带来的性能提升。这种现象在九十年代就有了名字，叫 Worth 定律。软件变慢的速度比硬件变快的速度还要快。

这是 Niklaus Wirth 在一九九五年提出的。他本来是想给行业敲个警钟，我们却把它当成了行业发展的路线图。真实的情况是这样的，大概在二零零五年，单线程 CPU 的性能就不再能每十八个月翻一番了，登纳德缩放定律失效了，CPU 主频卡在了四吉赫兹左右，之后就再也没怎么提升过，但软件行业根本没收到这个消息，我们还是照旧写代码，仿佛摩尔定律还在为我们的偷懒买单。于是我们做了个交易，我们用性能换来了开发的便利，还自我安慰说这就是进步。

以前网页上的一个按钮只要三行 HTML 就能实现，现在同样的按钮外面包了一层组件库，组件库建在设计系统之上，设计系统又依赖状态管理器，状态管理器又在构建工具之上，构建工具运行在 runtime 之上，runtime 要启动虚拟机，虚拟机跑在浏览器里，而浏览器本身就是个有三千万行代码的操作系统，只是假装成了一个窗口而已。这堆东西根本不是我们精心设计出来的，这是一点点堆出来的，堆了又堆，从来没人审批过这种架构。还有个所有开发团队都不想明说的事实，现在的大部分开发者已经算不上工程师了，他们就是管道工啊，只会把各种管道接在一起，根本不知道管道里流的是什么东西，管道坏了也修不了，要是管道爆了，他们就在旧管道上面再接一根新的，还美其名曰微服务。

我们大部分人都是从这个阶段过来的，现在多数团队也还是这个状态，这不是在骂人，这是招聘体系自然导致的结果。现在招人的标准只看能不能快速上线功能，从来不会问应聘者知不知道 L 一缓存是什么。抽象陷阱的问题不在于抽象本身不好，陷阱在于我们已经失去了看透这些抽象层的能力。这笔账单不会以备忘录的形式出现，它会以基准测试结果的形式摆在你面前，你可以凭着感觉扯皮，但你没法和秒表的结果争辩。一个用 Rust 编写的原生文本编辑器以及一个广受欢迎的基于 Electron 的文本编辑器，两者都在我的电脑上打开同一个一兆字节的日志文件，单次运行冷启动的情况下，后者打开文件的速度慢了四十三倍，内存占用高了二十二倍。这不是因为那款更慢的编辑器背后的工程师水平更差，他们不差，他们中很多人都非常优秀。

问题在于这些优秀的工程师是在一个本身就已经输在起跑线的系统里工作，他们打包的 Chromium 运行时产生的额外开销是上层再巧妙的代码都没法抵消的。另外免得评论区有人跳出来说那套老生常谈的反对意见，说什么要整洁代码，要可维护性。想想上次整个行业把代码风格指南当成宗教信仰的时候，最后是什么下场？那本人都引用的书把简单的数学运算变成了足足六层的间接调用大教堂，在实际工作负载测试下速度慢了整整一个数量级。之后的十年里，资深工程师都在默默推翻这些规则，而初级工程师面试的时候还在被考这些内容。凌驾于常识和实际性能测试之上的规则不是什么原则，只是迷信。当秒表的说服力最终占据上风时，去臃肿化就会到来。看看现在精明的资本都在投什么领域就知道了。要是有一门编程语言简单到你能完全吃透它的所有细节呢？

Zig 就做到了这一点，它编译出的是静态二进制文件，大小只有几兆字节。Bun runtime 正在用 Zig 重写原本属于 Node 的功能模块，因为 Bun 的开发人员已经受够了等待 Node 慢吞吞的执行流程。再来说说 Mojo。过去十。五年里，Python 数据科学站把 C 和 CUDA 藏在三层抽象之下，仅仅导入 NumPy 就要加载差不多五百兆的原生代码，就为了做个点积运算。Modular 之所以诞生，是因为 Modular 的人终于问出了那个显而易见的问题：我们能不能别搞这么多层抽象了？每月一万亿次请求，这是 Cloudflare 的 Pingora 用 Rust 实现的处理能力，这不是什么炒作噱头。

作为基础设施，Discord 已经用 Rust 重写了它的消息已读状态服务，微软也在用 Rust 重写 Windows 内核的部分模块。互联网那些不怎么显眼的基础组件，正在悄悄用一门不带垃圾回收器的语言重构。还有 Go，它正做着最符合 Go 风格的事，一点也不花哨。没有主题演讲，没有宣言，只是默默优化垃圾回收器，默默推出体积更小的二进制文件，默默成了那些曾经首选 JVM，现在觉得用 JVM 有点尴尬的开发者的稳妥选择。这些技术有什么共同点？它们不是 React 语境下的那种现代，它们是工程意义上的现代。设计他们的人看清了抽象陷阱，标签页开销、 runtime 开销、依赖开销，然后得出结论，层数太多本身就是问题。这是底层思维的回归，不是出于怀旧，而是出于成本考量。

云服务账单是真金白银，冷启动延迟是切实的体验问题，笔记本的电池续航是用户的真实需求，用户注意到你的应用占了四吉字节内存也是真实存在的不满。去剥掉那些多余的层吧，如果你说不清楚你用的框架在下层到底做了什么，那你就没有掌控你的技术栈，是你的技术栈在掌控你。要是系统凌晨三点出故障，待命排查的不会是你用的那个框架，是你。过去二十年，行业的策略很简单，堆更多硬件就行。这套策略如今已经走到了尽头，不是因为硬件停止了进步，准确来说也不是，只是软件行业悄悄压住了整个技术栈的那个维度，不再提升了。也就是单线程性能会永远免费提升的假设，它不会永远增长，而且从来都不是免费的。软件的未来不是加更多的库，而是把那些我们从一开始就不需要的库删掉。去臃肿不是什么潮流，而是一次行业修正。

现在还不开始做修正的团队，未来五年都得给首席财务官解释，为什么他们的产品打开个设置面板都要十六吉字节内存。如果你想知道这笔账单最先出现在哪里，就是你设备上最常见，你今天肯定已经打开过又忘了的那个地方。
