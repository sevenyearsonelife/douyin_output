Linux 并非操作系统，而是一个内核。我记不清在网上看过这句话多少次，但那些总复述它的人却鲜少愿意详加解释。本期我们将沿着进程树回溯至首个进程，精确厘清这条分界线。答案竟藏在用户进程中，这点或许会让许多人感到意外。首要任务是理解进程的创建机制。我做过专题视频，这里简要概括下要点。Windows 系统中的进程可通过系统调用请求创建新进程，系统会直接执行。而 Linux 类 Unix 系统要求进程先申请自我克隆，克隆产生的进程再请求替换自身程序。两种系统管理进程创建的方式存在哲学层面的差异，但核心理念始终一致，用户进程皆由其他用户进程创建。为便于理解，本视频将采用 Unix Linux 术语进行讲解。请思考一下，如果所有用户进程都由其他用户进程创建，那就意味着每个进程都有创建它的父进程。

但由于这些父进程本身也是用户进程，它们必然也被其他用户进程创建，以此类推。这意味着如果我们向上追溯，最终会发现一个作为所有用户进程始祖的单一进程。在 Linux 系统中，你实际上可以通过运行这条命令来可视化这棵树状结构。正如这里所示，树状结构根部确实存在一个其他所有进程的始祖进程。但这个根进程引出了一个疑问，它是由谁创建的？它不可能是由其他进程创建的，否则就不会是树状结构的根。信不信由你，答案就在这里。因为在某种意义上，该进程之前发生的所有事情都被视为内核的一部分。既然如此，我们就来定义何为内核。计算机系统的一端是硬件设备，另一端则是以运行多个应用软件为目的的用户。处理硬件实际上非常繁琐且存在风险，为防止应用程序因漏洞或劣质代码导致故障，在用户应用与硬件之间存在非常复杂的中间层。

这一层最底部的组件，也就是直接与硬件交互的部分，我们称之为内核。这种设计的核心思想是，每当用户程序需要操作硬件时，内核都代表它来执行硬件交互。用户进程仍可能试图自行操作，因此需要额外的保护机制。为此，CPU 被设计为两种运行模式，受限模式与特权模式。当 CPU 处于特权模式时，可执行指令集中的所有指令，包括配置硬件、通过页表管理内存、控制中断以及与 GPU、网卡、存储设备等输入输出外设通信。硬件设备在受限模式下，CPU 仅能执行安全指令子集，无法直接访问硬件或关键系统资源。该模式下处理器可执行计算、比较、循环等常规程序逻辑，但无法运行特权指令。由于特权模式能完全掌控处理器和系统资源，运行于此模式的软件决定着受限模式代码的权限范围。如你所料，所有用户程序都在受限模式下运行，而内核则处于特权模式。

因此我们对应使用两个术语，内核空间与用户空间。当用户程序需要访问硬件，例如屏幕显示文字或通过网络发送消息的时，只能通过系统调用请求内核代其执行。现代系统正是通过这种方式确保普通用户程序无法直接访问硬件，既保障正常运行又维护系统安全。不过该隔离层并非单一组件，内核整体运行在特权模式下，但其。内部存在一系列子系统，各自管理特定资源或提供特定服务。没有内核，用户应用程序就无法存在，因为它们需要内核来完成受限模式下无法执行的操作。系统调用接口是内核最接近用户程序的部分。因此，当我们启动计算机时，在从用户角度执行任何有效操作前，必须通过引导启动过程将内核可执行代码加载到内存中。当所有关键组件加载就绪后，内核会创建唯一一个用户进程，这就是 init 进程。

在 Unix/Linux 系统中，PID 为一的 init 进程是唯一不由其他用户进程创建的用户进程。在内核代码深处，存在一段硬编码历程，它会按以下优先级顺序在文件系统中寻找名为 init 的可执行文件。查看 Linux 内核源码中的 init/main.c 文件，可见名为 kernel_init 的函数会初始化大量资源，最终在启动过程中尝试从指定路径运行 init 程序。该函数会调用 run_init_process 函数，而后者内部会调用 exec。注意，这并非用户进程使用的传统 exec 系统调用。由于这段代码本身就在内核模式下运行，无需系统调用，故使用名为 kernel_exec 的变体直接执行新进程加载历程。还需注意，如果所有路径都找不到可执行文件，内核将在启动过程中触发 panic。

此刻您可能疑惑，这些内容对本视频有何重要性？因为内核开发者对用户空间软件的关注仅止于此。开发者直接将启动首个用户进程的历程硬编码在内核中，但对该进程后续的具体行为毫不关心。实际上，Linux 内核源码中根本找不到这个 init 程序，它不属于内核组成部分。我们即将揭晓答案，但在继续之前，请暂停视频观察这个图表并思考，当前架构中缺失了哪些用户应用依赖的操作系统服务？用户应用程序依赖的哪些操作系统组件在这里缺失了？我立刻能想到好几个：显示服务器、命令行终端 shell、会话管理器、网络管理器、软件包管理器、用于远程访问的 SSH 服务器。如果系统支持图形界面，那么桌面环境及其附带组件、终端模拟器、文件浏览器、设置管理器、任务管理器也在此列。这些通常都是我们认为是操作系统组成部分的东西，然而它们都不属于内核。

若您对其中某些组件不太熟悉，这里会简要说明并举例。我们主要讨论 Linux 系统，但也会加入 Windows 的对应组件，方便主要使用 Windows 的观众理解。我很清楚很多人此刻的想法，等等，稍等一下。你是说操作系统并非全部运行在内核空间？没错，这正是我想表达的。我们通常所称的操作系统，其实大部分是用户空间进程的集合。我认为理解这点最好的例子就是桌面环境，KDE、GNOME、Cosmic，那些停靠栏、任务栏、窗口平铺系统，以及我们联想到桌面体验的抽象概念，它们都运行在用户模式。桌面环境并非内核的一部分，因此不直接操作硬件。它通过另一个用户空间进程显示服务器与内核交互，后者利用图形相关的系统调用将渲染好的缓冲区内容呈现到屏幕。内核并不理解窗口的概念，也不知道按钮、控件或深色模式是什么。

屏幕上显示的内容是用户空间软件将像素渲染至缓冲区后，请求内核通知 GPU 进行显示的结果。对内核而言，这只是内存访问和硬件操作。因此更准确的定义是：操作系统是由软件组成的集合，其中被称为内核的组件运行在特权模式，其余部分则运行在受限模式。这正是两者的分界线。这里有个微妙但关键的要点：所有这些用户进程并非凭空出现，它们必须由另一个进程创建。这时就轮到 init 进程登场了。在引导启动阶段，当内核完成关键子系统初始化并准备切换到用户空间时，会执行前文提到的硬编码历程来定位并启动 init 进程。这么设计的原因是，仅靠这个单一用户空间进程就足以繁衍出我们之前看到的整个进程树。从此刻开始，操作系统的其余部分并非直接源自内核，而是由构建应用程序所依赖全套服务基础设施的用户空间代码生成。

例如在 Ubuntu 上运行进程树命令时，你会看到根进程启动了诸如网络管理器、作业调度器、日志服务以及大量桌面环境进程，在 Ubuntu 系统中主要指 GNOME。你还会看到显示服务器 Wayland，这里我们甚至能看到 init 进程如何启动 Snap，这个人人都爱吐槽的包管理器。总之，正是这些进程共同塑造了 Ubuntu 的独特体验。这是 Fedora 系统的进程树作为对比。最明显的区别是这套系统没有 GNOME 的踪影，这很合理，因为我运行的是搭载 KDE 桌面环境的版本。换句话说，我们观察到的是这个根进程如何通过启动各类服务和应用程序，最终塑造出你喜爱的 Linux 发行版的独特行为与个性。这也解释了为什么不存在所谓标准版 Linux，Linux 开发者仅提供内核。

讽刺的是，若没有用户空间程序运行其上，这个内核本身完全无法发挥作用。内核需要这些程序才能真正提供功能。如果你曾好奇 Linux 发行版的诞生过程，这就是答案。它们共享相同内核，但基于该内核构建的服务基础设施会因发行版创建者的设计理念而异。事实上，进程树中显示的根进程可能也会有不同名称，因为 init 有多种实现方案，从传统的 sysvinit、OpenRC 或 runit 到更现代复杂的 systemd 应有尽有。如前所述，内核并不关心这个进程的具体运作方式。正因如此，不同项目对 init 进程的行为规范和职责划分形成了不同理念。传统理念其实很简单，只需将选定的 init 实现编译为 init 程序，放置在内核预期的系统二进制目录或其他指定目录即可。

但由于历史沿革和实际需求，现代系统通常会改用其他名称编译可执行文件并存放于其他位置。在预期目录中仅放置名为 init 的文件，这实际上是个符号链接，类似于快捷方式，指向真正的可执行文件。若存疑，不妨进入系统二进制目录查看详细文件列表，你会发现 init 文件其实指向其他位置的某个文件。以 Ubuntu 为例，内核以为自己在启动名为 init 的程序，实际启动的却是 systemd。这种微妙的间接关联完美印证了。核心观点：内核只负责启动首个用户空间进程，该进程的本质及其后续行为完全不属于内核的管辖范畴。不过内核确实赋予了这个进程若干特殊属性。其一是固定获得进程 ID 一，普通程序的进程 ID 本无保证，但首个创建的进程必然获得 ID 一，这也使得它在任务管理器等工具中易于识别。

第二条与其说是特权，不如说是责任，init 进程永远不应终止。原因其实非常简单，内核不喜欢孤儿进程。假设有个程序创建了 Firefox 进程，这里的父子关系非常明确，但如果父进程终止时，其子进程仍在运行会怎样？进程不能拥有已不存在的父进程，因此当进程或进程组成为孤儿时，Linux 内核会将其父进程重新指派给 init 进程。换言之，init 必须常驻运行，因为内核需要它来收养孤儿进程。所以尽管内核并不关心 init 的具体行为，但确实要求它保持存活。即使发送 SIGKILL 信号，信号九也无法终止它。内核坚持该进程永不终止的原则，直接拒绝传递终止信号。正因为永不终止的特性，许多 init 实现还被设计为故障恢复机制。如果关键服务崩溃，比如桌面环境，init 进程可能会自动重启它。
