做一个消息提醒功能，最直接的办法是让前端每秒问一次服务器，这叫轮询，写起来简单，但代价大得惊人。一百个人在线，一分钟就是六千次请求，而其中绝大多数的回答都是三个字，没有新消息。更难受的是消息真的来了，用户平均还要多等半个周期才看见。根子上的问题是 HTTP 只能客户端问，服务端答，服务端有话想说，却没有办法主动开口。于是浏览器给了另一条路，叫 WebSocket，一次握手之后，连接就变成双向的，两边都能随时发消息。这条视频就带你把 WebSocket 从握手到上线一次讲透。

WebSocket 不是凭空冒出来的协议，它借了 HTTP 的壳，客户端先发一个普通的 GET 请求，但多带两个关键头，Upgrade 写 WebSocket，Connection 写 Upgrade，意思是我想把这条连接升级成另一种协议，再带一个随机生成的 Sec-WebSocket-Key，服务端同意的话，回一个 101 Switching Protocols，注意这个状态码，它不是 200，代表协议切换成功。响应里的 Accept 字段是把 Key 加上一个固定字符串再哈希算出来的，这一步只是证明对方真的听得懂 WebSocket，它不是安全措施。握手完成之后，这条 TCP 连接就不再说 HTTP 了。

升级之后，双方交换的东西不再是请求和响应，而是帧，每个帧前面有一个很小的头，最短只要两个字节，第一个字节里最高位是 FIN，标记这是不是最后一帧，第四位是 opcode，说明这一帧装的是什么，一是文本，二是二进制，八是关闭，九和十是心跳。第二个字节的最高位是掩码标志，剩下七位表示长度，长度只有七位，最大也就一百二十五，那更长的怎么办？如果填一百二十六，就再用两个字节表示真正的长度，填一百二十七就再用八个字节，足够表示任何消息。这种变长设计让小消息的额外开销压到了极低。帧头里那个掩码标志，背后有一条很硬的规定，客户端发给服务端的每一帧都必须做掩码，而服务端发给客户端的反而绝对不能做。这个规则看着奇怪，原因和安全有关。掩码用一个四字节的随机值和数据逐字节异或，每一帧都重新随机，所以同样的内容每次发出去都不一样。

它防的不是偷看，异或是可逆的，谁都能还原，它真正防的是中间的代理服务器被骗。如果内容完全可控，攻击者能拼出一段看起来像 HTTP 请求的数据，老代理可能把它当成真请求存进缓存，这叫缓存投毒。现在把一条消息从发出到收到完整走一遍，你调 send 传进去一个字符串，浏览器先把它编码成 UTF-8 的字节，然后加上帧头，FIN 置一，opcode 填一，代表一个完整的文本帧，生成随机掩码，把数据逐字节异或一遍，顺着那条已经建好的 TCP 连接发出去。服务端读到帧头，先取长度，再解掩码，拿到原始字节，解码成字符串，触发你注册的消息回调。如果消息很大，还可以拆成多帧，第一帧带 opcode，后面几帧都填零，只有最后一帧把 FIN 置一，接收方按顺序拼回完整消息。

WebSocket最大的运维问题是连接会在你不知情的时候断掉。手机切到后台，网络从WiFi跳到流量，中间的代理超时回收。麻烦的是这些情况往往不会触发close事件，你的代码以为连接还在，其实消息早就发不出去了。所以要靠心跳主动确认对方还活着。协议内置了ping和pong两种控制帧，一方发ping，另一方必须回pong，这是协议强制的。但浏览器的JS拿不到这两种帧，前端通常要自己定义心跳消息，连续几次收不到回应就判定连接已死，主动关掉重连。重连一定要用指数退避，否则服务端重启时会被所有客户端同时冲垮。想做实时其实有三条常见的路，各有各的位置。第一条是长轮询，服务端把请求挂住，有数据才返回。兼容性最好，但每收一次消息就要重新建一次请求。

第二条是SSE，服务端单向持续推送，它本质就是一个不结束的HTTP响应，浏览器还自带断线重连。缺点是只能服务端推，客户端要发消息还得另开接口。第三条才是WebSocket，双向、开销低，还支持二进制。代价是心跳、重连、健全、集群这些活都得你自己做。选择标准其实很简单，只需要往下推SSE就够了，只有双向频繁交互才值得上WebSocket。单机跑的好好的WebSocket，一上集群就出问题。因为连接是有状态的，用户A的连接只在第一台机器上，现在用户B给A发消息，请求却落到了第二台机器，第二台机器上没有A的连接，这条消息就发不出去。第一个解法是广播，把消息发给所有节点，谁有连接谁发送。通常用Redis的发布订阅来做，简单，但节点一多就浪费。

第二个解法是记录路由，用Redis存下每个用户连在哪个节点，发消息时先查路由，再定向投递到那一个节点。还要注意负载均衡必须开会话保持，或者干脆改成四层转发，以及每个节点都要在连接断开时及时清掉自己那条路由记录。上线前还有几个坑，几乎每个项目都会踩一遍。第一个是健全，浏览器的WebSocket握手不能自定义请求头，所以没法像调接口那样把token放在Authorization里。常见做法有两种，塞进URL查询参数，或者连上之后先发一条认证消息。色URL要留意，token会被写进访问日志。第二个是Nginx反向代理，必须显示转发Upgrade和Connection两个头，漏了这一步握手会直接失败，这是最高频的部署问题。还要把读写超时调大，否则空闲连接会被代理主动切断。

第三个是限制，限制单用户连接数，限制消息大小，再做频率控制。最后别忘了用WSS，也就是跑在TLS上的WebSocket。WebSocket很好用，但有几个场景它并不合适。第一个是只需要服务端单向推送的场景，通知、进度条、日志滚动这些，用SSE更简单也更省心。第二个是消息很稀疏的场景，一小时才来一条消息，却要一直挂着连接和心跳，不划算。第三个是要求可靠投递的场景，WebSocket只保证顺序。据，不保证送达，网络一断消息就没了。想不丢就得自己做确认、序号和补拉，这等于重造一套协议。更省力的做法是让 WebSocket 只负责通知，真正的数据用接口去拉。一句话，它是通道，不是消息队列，别把可靠性压在它身上。到这里，WebSocket 的核心拼图就凑齐了，我们快速串一遍。

握手，一个带 Upgrade 头的 GET，换回一百零一状态码。帧结构，FIN 加 opcode 加变长长度，最短只要两个字节。掩码，客户端必须加，为的是防代理缓存投毒。心跳，用 PING 和 PONG 确认存活，重连要指数退避。显形，单向推送用 SSI，双向交互采用 WebSocket。集群，要么广播，要么记路由，负载均衡记得会话保持。而 WebSocket 最核心的性格是，一次握手，长连接，双向对等。
