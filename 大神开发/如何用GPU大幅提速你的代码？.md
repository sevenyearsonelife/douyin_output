今天我们会通过编写一个密码暴力破解的程序，来了解如何利用 GPU 来大幅提升代码的性能。如果你想知道我们的显卡除了图形渲染之外还能做些什么，或者对 CUDA 和并行计算的各种概念感到一头雾水，那么这期视频我们全部把它们搞明白。在视频的开头，我们先来回顾一下 CPU 和 GPU 的区别。我们知道 CPU 天生是为顺序执行任务而设计的，CPU 通常拥有较少的核心数量，但每个核心都可以快速处理各种复杂的逻辑和控制任务。而 GPU 牺牲了单个核心的复杂度，却换来了成千上万的核心数量和极高的显存带宽，因此非常适合于执行数据密集、高度并行的计算任务，比如图形渲染、物理仿真，还有 AI 模型的训练等等。那么接下来我们就分别用 CPU 和 GPU 去尝试暴力破解一个密码，然后比较一下它们的性能差距有多大。

我们知道在服务器上密码通常不会以明文的形式存储，而是会将它们进行哈希处理。这是因为哈希是一个单向函数，要生成一个哈希值非常容易，但要从哈希值反推密码在计算上是不可行的。即便黑客窃取到了你服务器上保存的哈希值，想要破解它们，基本只能依靠字典攻击或者是暴力破解，去穷举不同的密码组合，直到找到匹配的结果。这过程通常需要花费大量的时间和计算资源。那么如何去写一个暴力破解密码的程序呢？很简单，我们先去遍历所有可能的密码长度。然后对于每一个密码长度去尝试其中所有可能的密码组合。然后再对于每一个密码我们去计算它的哈希值。这里哈希值的计算并不是重点，我们直接调用系统库来帮我们生成一个 SHA256 哈希值。然后我们将它和用户之前输入的哈希值进行比对。一旦发现两者相同，则说明我们找到了密码，于是我们立刻停止搜索。

这是一个典型的基于 CPU 的单线程实现。显而易见，这种方法在密码稍长一点的时候就会慢得可怜。比如在我的电脑上破解一个六位数的密码用了整整一分钟的时间。其实这里对密码的暴力破解刚好是一个可以用并行计算来加速的完美案例。因为对于每一个密码组合，它们哈希值的计算都是完全独立的。我们完全可以把这些任务分配给 GPU 成千上万的计算核心去并行处理，来大幅提升计算的速度。那么接下来我们就尝试把这段代码改写成 GPU 能够执行的 CUDA 版本。CUDA 的源文件以 .cu 结尾，它扩展了 C 和 C++ 语言，因此我们可以用熟悉的语法来编写 GPU 代码。和之前的 CPU 实现一样，首先我们会读取需要破解的哈希值，然后将它复制到 GPU 的显存中。之所以这么做，是因为 CPU 和 GPU 拥有各自独立的内存空间。

如果我们希望 GPU 也能够获取到用户输入的哈希值，我们可以明确的调用 cudaMalloc 先分配一段显存，然后调用 cudaMemcpy 将主内存中的数据拷贝到显存。和之前的 CPU 版本类似，对于每一个可能的密码长度，我们会尝试其中所有可能的密码组合。不过这次我们不会一个个挨个的去尝试，而是通过 GPU 的上万个计算核心去并行处理，也就是这里我们将要调用的 crackSHA256 函数。这里我们会看到 CUDA 中的第一个奇怪的语法，我们马上讲到。我们先来定义这里的 crackSHA256 函数。这里我们用 CUDA 的关键字 global 来告诉编译器这是一个运行在 GPU 上的函数。这类函数还有一个专门的名字叫 kernel 核函数，它和我们操作系统中的 kernel 内核是两个完全不同的概念。

CUDA 中的 kernel 指的是在 GPU 上并行运算的函数代码。在了解了核函数之后，我们再回来看这里的尖括号语法。这里的这两个数字表示在我们调用核函数的时候，需要启动多。多少个线程，并且需要多少个线程块。这里线程的概念相对比较好理解，和 CPU 中的线程类似，线程是 GPU 上最小的可执行单元，并且每个线程由一个 CUDA 核心运行。我们的核函数会同时运行在多个线程上，来达到并行计算的目的。另外 CUDA 总是会将一系列的线程组成一个线程块，然后将他们一起派发到 GPU 上的一个叫做 SM 的核心部件上一起运行。SM 翻译过来叫流式多处理器，名字比较拗口，这里我们直接简称它为流处理器。

需要注意的是，一个线程块只能在一个流处理器上运行，它不能被进一步拆分，但每一个流处理器可以同时运行多个线程块，它们可以执行完全不同的计算任务。至于由哪个流处理器来执行哪个线程块，都是由硬件自己决定的。CUDA 调度器会在后台自动的平衡负载，让所有的流处理器都尽量的被充分的利用。在搞懂了这些概念之后，再回来看这两个参数就很容易理解了。第一个参数代表我们需要启动多少个线程块来并行执行之前定义的核函数，第二个参数代表每一个线程块中的线程个数。如果我们把这两个数字相乘，就可以得到所有线程的总个数，也就是说 GPU 上最多会有这么多个线程同时运行我们的核函数。接着我们就来实现这个 crack_sha256 核函数。

刚刚我们说到 GPU 中的每一个线程都会去执行这一段相同的函数代码，但我们怎么才能让每一个线程去处理不同的密码组合呢？这里我们就要用到标记线程的独一无二的索引值。CUDA 提供了几个内建的变量，比如 blockIdx 代表每个线程块的索引， threadIdx 代表每一个线程在当前线程块中的索引， blockDim 和 threadDim 分别代表线程块和线程的总个数。根据不同的索引值，我们可以决定当前线程应当处理哪一个密码组合，然后我们去计算这个密码的哈希值，然后再把计算得到的哈希值和用户输入的进行比较。如果匹配成功，我们就把结果保存下来，并终止后续的计算。不过需要注意的是，我们这里定义的这两个全局变量都会由 GPU 上的核函数读写，因此我们需要将它们定义在显存中，而不是主内存。

这里我们可以用 device 限定符来表示。另外在这里我们并没有用任何线程的同步机制或者原子操作来保护这两个变量，这是因为我们知道不会有两个线程同时找到密码，因此无需进行线程的同步，同时也避免了不必要的性能开销。在调用完核函数之后，我们需要执行 cudaDeviceSynchronize，它会让 CPU 等待直到 GPU 上的所有任务都执行完毕。这一步非常关键，因为 CUDA 的核函数调用是异步的，也就是说当我们调用它的时候，控制权会立即返回给 CPU，但此时 GPU 可能还没有开始执行任何操作。而通过调用 cudaDeviceSynchronize，我们就能够保证 GPU 此时已经完成了所有的工作，这个时候我们再从显存中读取数据，程序的逻辑才是正确的。

要读取显存中的数据，我们可以调用 cudaMemcpyFromSymbol，它会将显存中的数据拷贝到主内存。然后我们判断是否已经找到了密码，如果是的话，我们就打印出结果，并且退出主循环。最后我们用 CUDA 的编译器来编译代码，然后运行程序。可以看到 CUDA 的版本仅仅用了一点二秒就暴力破解出了密码，速度快了 CPU 版本将近五十倍，这还是没有做任何优化的情况下。如果我们对程序进行性能分析，可以观察到不同 CUDA API 的执行时间分布，其中 cudaDeviceSynchronize 占用了绝大多数的时间，这说明 CPU 主要是在等待 GPU 执行完毕。相比较之下，内存拷贝和启动核函数的开销几乎可以忽略不计。另外可以看到，在 GPU 上执行的计算任务只有我们定义的这个核函数，每次调用时间大概零点二毫秒。

通过这些数据。可以更好的理解程序的行为，找到性能瓶颈，并且有针对性的进行优化。讲到这里，相信大家对 CUDA 已经有一定的了解了。显然 CUDA 并不是唯一的并行计算框架，比如 AMD 有自己的 HIP，它可以兼容 NVIDIA GPU，并且接口设计和 CUDA 很像。另外还有像 OpenCL 这样的开放标准，支持的硬件也最为广泛。对于图形应用，我们甚至可以用 Compute Shader 来完成简单的并行计算任务。虽然这些框架在使用上有所区别，但核心思想都是相通的。真正重要的是如何将一个问题拆解成能够被并行处理的任务，然后编写程序，并发挥出 GPU 硬件的最大潜力。
