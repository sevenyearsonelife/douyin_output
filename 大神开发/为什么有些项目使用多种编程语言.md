今天我们要讲一些底层概念，除非你在系统层面工作，否则可能永远不需要考虑这些。我收到的最频繁的视频建议之一就是解释为什么有些项目在开发中似乎涉及多种编程语言。解释这个问题可能非常简单，也可能非常困难，取决于项目的类型。以 Django 这样的全栈框架为例，Python 用于处理在服务器上运行的后端，而 HTML、CSS 和 JavaScript 用于构建在客户端显示的用户界面。这是一个多语言项目，但在这种情况下，很容易理解生产环境中一切是如何运作的，因为我们本质上是在开发两个独立的进程，它们在运行时使用某种形式的进程间通信进行远程交互。但还有其他类型的项目，其中用不同编程语言编写的组件需要作为单个进程一起运行。那么，这类项目是如何实现的呢？为了简单起见，我们先只考虑那些编译成机器码的编程语言。

一般来说，每种编程语言都有自己专用的编译器，所以我们不能直接拿一个 Rust 文件用 Go 编译器来编译。这就是事情开始变得有趣又有点令人困惑的地方。如果大多数编程语言都有各自独立的编译器、运行时和内存模型，它们怎么可能共存于同一个二进制文件中呢？经常让人困惑的是一个常见的过度简化，即认为编译器只是把源代码直接转换成可执行文件的工具。别误会，编译器确实会生成可执行文件，但那只是一个复杂的多的多步骤过程的最终结果，而这个过程我们通常看不到。为了说明这一点，我们来看一个简单的 C 语言程序。如果你不是 C 语言开发者，别担心，这个程序只是打印一条消息，但打印的消息会根据你运行它的操作系统而变化。在大多数 GNU Linux 系统上，C 语言的首选编译器是 GCC，它过去代表 GNU C 编译器，但现在不再是这样了。

稍后你就会明白为什么。要编译和运行我们的 C 语言程序，我们通常只需调用 GCC 并传递我们想要编译的文件，然后就会生成一个可执行文件。从我们的角度看，这只是两个简单的步骤，一个是编译程序，另一个是运行它。但在底层，编译器做的事情要多得多。在内部，GCC 经历四个主要阶段将 C 语言文件转换成可运行的可执行文件。GCC 值得单独深入讲解，但我在这里快速分解一下。第一步是预处理，这一步通过删除注释、展开宏、解析条件编译以及关键的解析 include 指令来准备源代码。当你使用 include 时，C 语言预处理器会将那一行替换为头文件的内容，以及它包含的所有头文件，实际上在编译开始之前将那些代码插入到我们的文件中。所以输出仍然是 C 源代码，但已经为下一步进行了预处理。接下来是编译，但不是直接编译成机器码。

相反，预处理后的代码被转换成汇编语言，这些是计算机将要执行的指令，但仍然是人类可读的语言。所以这里打破了我们的第一个误解，编译器并不总是将源代码转换成机器码。事实上，许多编译器将源代码转换成中间表示，比如汇编语言，甚至转换成另一种编程语言。第三步涉及汇编器，从技术上讲，它是另一个编译器，但它将上一阶段人类可读的汇编代码转换成机器码，也就是你的 CPU 能理解的零和一，结果被称为目标文件。但问题来了，这个目标文件还不能运行。GCC 仍然需要确定二进制文件中函数将被放置的位置。在我们这个简单的例子中，我们只是向控制台打印文本。但记住，printf 函数的实际实现存在于 C 语言标准库中，所以那个库也需要经历我们刚才描述的相同编译步骤。这就把我们带到了最后一步，链接。

在这个阶段，我们可能有多个目标文件，一些来自我们的代码，其他来自我们在开发过程中包含的外部库。链接器的工作是将所有这些目标文件组合成一个独立的可执行文件。有两种方法可以做到这一点。最简单的方法是从库中获取每个所需函数的机器码，并将其复制到最终的可执行文件中。这被称为静态链接。我们程序需要的所有库函数都直接嵌入到输出文件中。一切都是独立的，因此随时可以运行。但另一个选择是动态链接。想想你系统上有多少程序使用标准库中的 printf 函数。如果每个程序都静态包含该函数的自己的副本，你最终会在磁盘上存储数千个相同的副本。使用动态链接，库被预编译成一种特殊类型的文件，称为动态共享库。在类 Unix 系统上，这些库的文件扩展名是点 so，而在 Windows 上，它们由点 dll 扩展名标识。

这些动态共享库与可执行文件相似，因为它们包含库提供的函数的可执行代码。关键区别在于它们不包含启动执行的入口点。这是合理的，因为库通常没有用于启动程序的 main 函数。当我们的程序使用动态链接编译时，链接器不会将库中的函数直接复制到可执行文件中。相反，它只会插入一个对包含该函数机器指令的库的引用。在运行时，如果程序需要来自该动态库的函数，操作系统会将所需函数加载到程序的地址空间中，这样程序就可以像使用可执行文件的一部分一样使用它。虽然这一开始听起来可能有点奇怪，但实际上非常高效。系统不会在不同程序中存储同一函数的多个副本，而只存储一次库。每个需要它的程序只是引用共享库，并在运行时按需加载。这既节省了磁盘空间，又节省了内存，是一个巨大的优势，尤其是在有大量依赖通用库的程序的系统上。

它也更灵活，因为你可以更新或修补库，而不必重新编译每个使用它的程序。静态链接和动态链接都是一个很深的话题。老实说，值得专门做一期视频。如果你有兴趣了解更多，请在评论中告诉我，我会专门用一整集来解释链接是如何工作的，包括动态库的来龙去脉。现在回到编译步骤。你可能想知道所有这些模块化的意义是什么？如果编译器可以直接从源代码到可执行文件，为什么要把过程分成这么多阶段？嗯，我们通常看不到所有这些中间步骤的原因是像 GCC 这样的编译器默认配置为隐藏它们，它们只向你展示最终结果，即可执行文件。但使用正确的参数，我们可以暴露所有这些阶段。例如，使用 GCC，如果你编译一个程序并添加 save temps 参数，你不仅会得到最终的可执行文件，还会得到所有的中间文件。我们甚至可以在特定阶段停止该过程。

例如，参数会使进程在生成汇编语言后停止。这在教育环境中非常有用。你可能想看看高级 C 语言代码如何转换为汇编语言或机器码。在专业环境中，这也用于检查性能关键代码。你可以查看生成的汇编语言来验证编译器是否生成了高效的指令。更有趣的是，我们可以从管道中的任何阶段开始。我们可以将汇编文件。传递给 GCC，并简单的告诉它进行汇编和链接。这非常重要，因为这意味着我们可以用汇编语言编写部分代码，在不同阶段传递给编译器，然后链接器会负责将它们混合到一个可执行文件中。这已经开始回答我们最初的问题了。我们来看一个例子。假设我们需要编写一个程序来计算零和给定数字之间存在多少个质数，并且我们希望它尽可能快。

我们可以用 C 语言编写整个程序，但假设我们不信任编译器的优化，所以我们决定直接用汇编语言编写繁重的计算函数，然后从 C 语言中调用它。然后我们将两个文件都传递给 GCC，它会编译和汇编 C 语言代码，汇编汇编代码，并将两个目标文件链接成一个可执行文件。就这样，我们刚刚编译了一个多语言项目。这项技术被许多现实系统所使用，比如 Linux 内核、FFmpeg、OpenSSL 以及许多嵌入式项目。它们通常在大部分逻辑中使用 C 语言，但在性能真正重要时会回退到汇编语言。

现在这里有个事实，你们很多人可能已经得出了结论，但我还是要提一下，我们通常所说的 C 语言编译器，比如 GCC，并不只是一个编译器，它实际上是一个工具链，一系列按顺序执行的工具管道，每个阶段都会消耗前一个阶段的输出，而且这些工具中的每一个都是可插拔的。我们可以替换工具链的部分组件，或者在不同的节点输入我们自己的文件。这就是为什么 GCC 不仅支持 C 语言，它还支持 C++、Objective-C、Fortran、Ada、D，甚至 Go，具体取决于它的配置方式。最初 GCC 代表 GNU C 编译器，但随着时间的推移，它演变成了一个支持 C 语言之外许多编程语言的编译器套件。由于这种扩展，GNU C 编译器这个名字变得容易引起误解，因此 GCC 这个缩写被重新定义为 GNU 编译器集合。

我觉得理解这一点非常重要。每当有人随口称它为 GNU C 语言编译器时，可能会无意中强化这样一种想法，即整个系统是一个单一的黑盒，将 C 语言代码转换成可运行文件。但事实是，多年来它已经不仅仅是这样了。好吧，但汇编语言并不适合所有人，而且公平的说，既然汇编语言已经是编译管道的一部分，使用它感觉有点像作弊，那么换成混合使用高级语言怎么样？比如我们不用汇编语言编写函数，而是用 Fortran 实现项目的一部分，会怎么样？嗯，这完全可行，而且实际上比看起来更常见。不过在这种情况下，我们通常需要多个步骤，一个步骤用于编译和汇编 Fortran 文件，另一个步骤用于编译和汇编 C 语言文件，第三个步骤将两个目标文件链接成单个可执行文件。

与已经嵌入 C 语言编译管道中的汇编语言不同，Fortran 有自己的管道，自己的编译器，有时甚至有自己的运行时依赖。而且到现在答案应该已经非常清楚了，我们最初的问题，不同语言如何共存于单个可执行文件中，归根结底取决于链接器。你看，涉及的不同语言甚至不需要来自像 GCC 这样的同一编译器套件。以 Rust 为例，它与 C 语言有完全不同的工具链，不同的编译器，不同的构建系统，以及完全不同的理念。我可以花几个小时讲它编译器背后疯狂的工程设计，但我们关心的是，当需要生成最终二进制文件时，你猜怎么着？Rust 同样依赖链接器。

所以如果我们想从 C 语言调用 Rust 函数，方法是这样的，我们在 Rust 中实现这个函数，我们将 Rust 代码编译成静态库或动态库，我们在 C 语言代码中声明并使用这个函数，然后我们编译 C 语言代码，并将其与 Rust 编译的库链接起来。当然反过来也可以，我们可以。从 Rust 调用 C 语言函数，这完全取决于我们想要实现什么。事实上，从 Rust 调用 C 语言代码比反过来更常见。C 语言更古老，许多成熟的库和系统 API 都是用 C 语言编写的。Rust 开发者经常需要接入现有的生态系统，特别是在图形、密码学或操作系统 API 等领域。在单个项目中混合使用多种编程语言的原因有很多，但另一个想到的原因是性能。在许多项目中，整个系统不需要超级快，只需要某些部分快就行。

所以很多开发者的做法是，为了方便和开发速度，用高级语言编写项目的大部分内容，然后只用 C 语言这样的底层语言实现性能关键的组件。在结束之前，还有一个非常重要的点需要理解。假设我们有两种高级语言，语言 A 和语言 B。仅仅因为它们都有最终的链接阶段，并不自动意味着它们可以被正确的链接到一个可执行文件中。这里有一个非常简单的例子，我们在语言 B 中实现了一个函数，并从语言 A 中调用它。即使两个编译器都为相同的架构生成汇编语言，它们对函数之间如何传递数据的假设可能不同。例如，语言 A 的编译器可能将两个函数参数放在寄存器零和寄存器一中，但语言 B 的编译器可能期望参数在寄存器一和寄存器二中。两者都生成了有效的机器码，但由于它们的调用约定不同，结果在运行时会出现未定义行为。

语言 A 会将参数放在错误的位置，而语言 B 会使用错误的数据执行操作。而且还不止于此，在这个例子中还有另一个问题。计算出结果后，函数将结果写入寄存器一并返回，但语言 A 期望结果在寄存器零中。所以不仅语言 B 计算出了错误的结果，语言 A 甚至根本看不到或使用那个结果。同样的例子，但这次是语言 X 和语言 Y。在这里，两种语言都使用寄存器零和寄存器一来传递和接受参数。但假设语言 X 对所有函数参数都使用引用传递，它将变量的地址放入寄存器中，这与直接将这些变量的值放入寄存器是不一样的。与此同时，语言 Y 按值传递，所以它期望寄存器中是实际的值。这就是为什么在运行时被调用后，它会立即将这些寄存器中的内容相加。

这种不匹配导致语言 Y 将内存地址解释为实际值，将这些地址相加而不是这些地址存储的值，从而导致完全错误的行为，甚至崩溃。因此，即使两个编译器都生成了有效且可执行的汇编语言，除非双方就如何相互通信达成一致，否则最终链接的二进制文件是不一致的。这些低级规则由所谓的应用程序二进制接口，即 ABI 来定义。就像 API 在应用程序层面定义函数一样，ABI 定义了二进制代码的不同组件如何通过硬件相互交互。所以当我们混合两种不同的语言时，它们都能生成目标文件是不够的。它们中至少有一个，或者具体来说，与另一种语言交互的那部分，必须符合另一种语言的 ABI 期望。在我们的语言 X 和语言 Y 的例子中，实现这一点的一种方法是修改语言 Y 来解引用这些值。

这样函数将首先从提供的内存地址获取数据，在执行加法之前将实际的值加载到寄存器中。在这种情况下，语言 Y 被修改为符合语言 X 的 ABI 期望。但我们也可以采取相反的做法，让语言 X 符合语言 Y 的 ABI 预期，只需将参数值直接加载到寄存器中，而不是它们的地址。这样。语言外中的函数在被调用时就可以立即相加这些值。正如我在视频开头提到的，这些都是底层细节，除非我们在系统层面工作，否则通常不需要考虑。好消息是，语言设计者知道这一点。现代编程语言提供了工具、关键字和编译器标志来简化这个过程。在 C 语言中，你可以使用 extern 声明外部函数。在 Rust 中，你需要使用 extern 关键字和 no_underscore_mangling 属性。在 Fortran 中，你可以使用 bind 属性。

在 Go 中，你可以使用特殊的注释块，直接放在 import "C" 这行上方，来包含 C 语言头文件。它甚至允许你在 Go 源文件中直接编写内联的 C 语言代码。每种语言都有自己的做法，但在编译时，这些声明都服务于同一个目的。它们告诉编译器，嘿，这个函数将与用另一种语言编写的代码进行交互，请确保生成的汇编语言遵循预期的 ABI。
