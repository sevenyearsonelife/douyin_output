一个温度传感器，每十秒上报一次，一天就是八千六百多次。用 HTTP 发，一次请求的头部动辄两三百字节，而它要传的数据只有几个字节。头比数据大几十倍，这些流量走的还是按流量计费的蜂窝网络。更要命的是，每次上报都要重新建一次 TCP 连接，握手加 TLS，一趟下来一两秒。这个设备可能靠一节电池撑三年，射频模块每多开一秒都是在烧命。反过来，服务端想给设备下发一条指令，HTTP 根本做不到，因为设备没有公网地址。只能让设备不停的轮询问有没有我的命令，绝大多数时候答案是没有。MQTT 就是为这种场景设计的，一条长连接，极小的报文，双向都能发。它的固定头最小只有两个字节，比 HTTP 省下的不只是一个数量级。这条视频把 MQTT 的机制和那些容易踩坑的地方一次讲清楚。先搞清楚 MQTT 面对的是什么设备。

这类设备在标准里叫受限设备，受限体现在四个方面。第一是算力，一颗几块钱的单片机，主频几十兆赫兹，内存只有几十 KB，跑不动 TLS 的完整实现，也放不下一个 JSON 解析器加一堆字符串。第二是电量，靠电池供电，却要求撑几个月甚至几年。通信里最耗电的不是计算，是射频模块开着的时间，所以要少发，发的短。第三是网络，NB-IoT 和 2G 的带宽只有几十 KBps，丢包率高，延迟经常上秒。而且设备躲在 NAT 后面，没有公网地址，服务端主动连不进来。第四是规模，一个 Broker 可能要同时挂着几十万甚至上百万个连接。这四条约束直接决定了协议长什么样，报文要小，连接要长，通信要双向。你会发现 MQTT 的每一个设计都是在回应这四条里的某一条。MQTT 的第一个核心设计是把请求响应换成了发布订阅。

HTTP 里客户端必须知道服务端的地址，还得等它回话，这是点对点的耦合。MQTT 里所有人只跟中间那个 Broker 说话。设备把数据发给 Broker，这个动作叫发布。想要数据的人告诉 Broker 我关心哪些数据，这个动作叫订阅。Broker 收到一条发布，就转发给所有订阅了它的人。关键点在于发布者完全不知道谁在收，订阅者也不知道是谁发的。这叫空间解耦，加一个新的数据消费方，设备端一行代码都不用改。还有时间解耦，订阅方现在不在线，Broker 可以先存着，等他上线再给。代价也很直接，Broker 成了整个系统的中心，它挂了所有人都断。所以生产环境的 Broker 一定要做集群，EMQX、HiveMQ、VerneMQ 都支持。但要注意，集群不是简单加机器，订阅关系要在节点之间同步，这是有成本的。

发布和订阅能对上，靠的是 Topic，也就是主题。Topic 是一个用斜杠分层的字符串，比如 factory / line 一 / dev 七 / temp。它没有预先定义这一说，你发到哪个 Topic，这个 Topic 就存在了。订阅方可以用两个通配符，加号匹配一层，井号匹配后面所有层。比如 factory / line 一 / + / temp 能收到一号线 上所有设备的温度，而 factory / # 能收到整个工厂的所有消息。注意，井号只能放在最后一层，加号可以放在任意一层。Topic的设计是这一集里最影响长期维护的一件事。层级要从大到小，从固定到可变，区域、产线、设备、指标。一个很常见的错误是把设备ID放在第一层，这样你永远没法按产线订阅。

还有一条铁律，Topic里不要放会变的东西，比如版本号或者时间戳，那会让通配符失效。现在讲 MQTT 里最容易被误解的部分，QoS。MQTT 有三档投递质量，编号是零、一、二。QoS 零是最多一次，发出去就不管了，不确认也不重传。它的开销就是一个包，适合高频的传感器读数，丢一两个无所谓。QoS 一是至少一次，发送方发完等一个 PUBACK，等不到就重发。因为会重发，接收方可能收到重复的消息，所以业务必须能幂等。QoS 二是恰好一次，靠一次四步握手实现，Publish、Pubrec、Pubrel、Pubcomp。现在说那句反直觉的话，QoS 二不是更好，很多场景下它反而更糟。四步握手意味着两个来回，在丢包率高、延迟上秒的弱网里，任何一步丢了都要重来。

你为了不重复，付出的是更长的时延、更多的电量和更高的整体失败概率。而且 QoS 是逐段生效的，发布端到 Broker 一档，Broker 到订阅端是另一档，实际取两者的较小值。实际的选法其实很简单，遥测数据用零，控制指令用一再加业务幂等。真的需要严格一次，应该在业务层用消息 ID 去重，而不是指望协议。接下来两个特性是 MQTT 特别有意思的地方。第一个是保留消息，Retained Message。正常情况下一条消息发出去，只有当时在线的订阅者能收到。那新上线的订阅者怎么办？他得等到下一次上报，才知道设备现在是什么状态。保留消息就是给这个问题准备的，发布时打上 Retain 标志，Broker 会把它单独存下来。之后任何人订阅这个 Topic 的瞬间，立刻就能收到最后那一条。

所以保留消息的正确用法是存状态，比如开关当前是开还是关，最新的温度是多少。不要拿它存事件流，因为每个 Topic 只保留一条，新的会直接覆盖旧的。第二个是遗嘱消息，Last Will and Testament。设备在连接的时候就把遗嘱交给 Broker，如果我不是正常断开的，帮我发这条消息。于是设备断网、掉电、崩溃，Broker 会自动替它广播一条离线通知，这是做设备在线状态最省事的办法。设备掉线是常态，那它掉线期间的消息怎么办？这取决于连接时的一个标志位，早期叫 Clean Session，五点零里改成了 Clean Start 加会话过期时间。如果设为真，每次连接都是全新的会话，之前的订阅关系和没收到的消息全部清空。如果设为假，Broker 会用客户端 ID 认出你，把上次那个会话接着用。

会话里存着两样东西，你的订阅关系和你不在线时到达的消息。所以持久会话的设备重连之后，不用重新订阅，还能收到断线期间攒下的消息。但这里有个必须注意的点，只有 QoS 一和二的消息会被存下来，QoS 零的不会。还有一个坑更隐蔽，客户端 ID 必须稳定而且唯一。如果你拿随机数当客户端 ID，那每次重连都是新会话。持久会话形同虚设。如果两个设备用了同一个客户端 ID，broker 会把前一个踢下线，然后它重连，又把后一个踢下线。这就是那个经典的连接抖动现象，日志上看就是无限重连，排查起来非常费劲。长连接有个天然的麻烦，TCP 断了，两端可能都不知道。尤其是设备测断网，或者被 net 网关静默回收，连接看起来还在，其实早就死了。

MQTT 用 keep alive 解决这个问题，连接的时候客户端告诉 broker 一个秒数，承诺在这个时间内至少发一个包，没有数据就发一个 pingreq，broker 回一个 pingresp。如果 broker 在一点五倍的 keep alive 时间里什么都没收到，就判定这个客户端死了。判定死了之后，broker 会关掉连接，并且触发那条遗嘱消息。keep alive 设多少是个取舍，设短了检测快，但心跳包本身要耗电耗流量。设长了省电，但一个设备掉线可能十几分钟都发现不了。还有一个现实约束，运营商的 net 通常几分钟就回收空闲连接，keep alive 必须比它短。电池设备一般给到几百秒，长供电的设备可以给到六十秒左右。很多人会问，发布订阅 Kafka 也是，那为什么不直接用 Kafka？

因为这两个东西解决的根本不是同一个问题。Kafka 的核心是一个持久化的日志，消息按 offset 顺序存在磁盘上，可以反复回放。MQTT 的核心是一个消息路由器，把消息转发出去，它的任务就结束了。从连接数看，Kafka 面对的是几十上百个客户端，MQTT 面对的是几十万个。从客户端看，Kafka 的客户端库有几兆，MQTT 的客户端能塞进几十 KB 的固件里。从主题看，Kafka 的 topic 是要预先创建的重资源，几千个就得开始小心。而 MQTT 的 topic 是随手一发就有的轻量字符串，几百万个也没问题。从消费模型看，Kafka 是拉，消费者自己控制进度，MQTT 是推，来了就给你。所以正确的架构通常是两个都用，设备到 broker 走 MQTT，broker 再把数据桥接进 Kafka。

前面负责海量连接和弱网，后面负责持久化、回放和流式计算，各干个擅长的事。最后说安全，物联网的安全事故大部分都出在这一层。第一层是传输加密，MQTT 本身不加密，必须跑在 TLS 上，端口从一千八百八十三换成八千八百八十三。受限设备跑 TLS 确实吃力，可以选 ECC 证书，它比 RSA 短得多，握手也更快。第二层是身份认证，最简单的是用户名密码，但一批设备烧同一个密码，等于没有认证。一台设备被拆开读出固件，整个产品线的设备就都暴露了。靠谱的做法是一机一密，每台设备出厂时烧入独立的凭据。更强的是双向 TLS，每台设备一张客户端证书，broker 验设备，设备也验 broker。第三层是权限控制，认证只解决了你是谁，还要限制你能干什么。

必须按 topic 做 ACL，这台设备只能往自己那个 topic 发，只能订阅自己的命令 topic。没有这条，一台被攻破的设备可以直接订阅井号，把全工厂的数据都拖走。还有一条容易忘，客户端 ID 要和证书绑定校验，否则别人可以拿自己的合法证书冒用你的设备 ID 上线。
