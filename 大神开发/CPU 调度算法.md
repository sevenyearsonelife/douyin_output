内存中通常有很多个进程，而只有个数非常少的 CPU，比如这里只有一个，那么每次 CPU 需要决定下一个运行的进程，这个选择的工作就叫做 CPU 的调度程序。当然如果一个进程里有多个线程的话，内核管理的线程就以线程为基本单位，而不是进程了。我们这里就假定进程里只有一个线程，所以就以进程为基本单位。那么首先进程通常有两种，一种是长时间占用 CPU 进行计算，称为计算密集型，还有一种 CPU 计算时间短，但是访问外接设备如磁盘的时间长次数多，称为 I/O 密集型，这里的 I/O 是 input 输入，output 输出的简写。而实际随着晶片的计算速度越来越快，磁盘的读写速度相对较慢，所以 I/O 密集型进程数量越来越多，现在更加考虑优化 I/O 密集型进程，比如 Node.js 的出现就是应对这类场景。

因此不同的场景需要不同的调度策略，我们大致可以把具体环境分成三类，第一是批处理，比如银行利息计算，保险公司需要索赔处理，商场需要存货清单的处理等。针对这类最简单的调度方式就是先来先服务，比如这里进程一先运行，直到它阻塞，进程二接着运行，等到进程一就绪后就排到末尾。但是这种方式显然是有问题的，假如进程二是计算密集型，而进程三是 I/O 密集型，那么若 CPU 先服务进程三的话，它会很快让出来去做 I/O 处理，而现在进程二却一直占着 CPU，进程三就一直等着，这样整体效率就比较低了。那有了前面的教训，第二种算法就是最短作业优先，也就是谁的计算时间短谁先来。比如我们能够预知每个进程占用 CPU 的时间，那么这样的话 I/O 密集型进程就会在前面，而计算密集型在后面。

那如果 CPU 已经在运行计算密集型进程七分钟了，还剩下一分钟，现在有 I/O 密集型进程陆续到来，虽然比计算密集型进程的总时间要短，但是不是比较剩余的时间更加合理吗？这样算法就更新为最短剩余时间优先。我们来讲第二类交互式，当用户需要与电脑交互的时候，电脑通常会有很多个进程，比如当用户在写 email，那进程中有的处理电子邮件的接受，有的处理鼠标信号，有的接受键盘信号，还有的负责图形界面的渲染等等，显然他们需要同时进行，所以 CPU 也只能轮转执行，这成为轮转调度。一次执行一个进程的时间称为一个时间片，时间片不能太短，因为进程切换需要从用户态到内核态进行处理，再回到用户态，大概需要一毫秒，但又不能太长，所以时间片通常在二十毫秒到五十毫秒之间。

这样也还是不够好，因为不同的进程重要性不一样，这里显然和用户交互的进程 B、C、D 更为重要，而后台处理的进程 A 相对次要些，那区别对待的算法就叫优先级调度，根据重要性把进程分成四个优先级，最上面最重要，最下面最次要。那么进程 A 后台处理最次要，进程 B 和进程 C 接受用户的指令重要一些，进程 D 负责画面，而人的眼睛很灵敏，所以最重要。现在 CPU 总是执行优先级高的，所以执行进程 D，但如果优先级一直这样。的话，剩下的进程只能等进程 D 完成才可以，所以我们还需要时间片轮转。比如现在我们可以让进程 D 先执行一个时间片，然后降低进程 D 的优先级一档，排到优先级三的最后。因为优先级四没有进程了，所以优先级三就是最高优先级了，开始执行进程 B。

进程 B 执行完后就把它降级到等级二，CPU 执行进程 C，然后它也降级，以此类推。那么这里的优先级只是相对的，从优先级一再降级就可以是优先级零，一直下去。最后是第三类环境，实时系统，比如视频流的播放，自动驾驶的系统，准时比正确的运行来得更重要，以后有机会在多媒体技术中会涉及到。
