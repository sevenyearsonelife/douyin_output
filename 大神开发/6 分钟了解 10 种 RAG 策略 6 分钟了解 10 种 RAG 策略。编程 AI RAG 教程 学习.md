再聪明的模型也回答不了关于你个人笔记或者企业内部资料的问题，但如果你懂 RAG 就是另一回事了。RAG 是一套架构，将信息存进数据库，然后等用户提问的时候再从数据库里取出相关的信息。RAG 一直是很流行的一项 AI 技术，但直到今年出现了一种 RAG 已死的说法，理由是一百万的上下文窗口已经是旗舰模型的标配了，所以完全可以将资料都塞进上下文，没必要使用繁琐的 RAG。起来很合理，但从工程的角度来说，成本、延迟和上下文稀释都让这个说法站不住脚。先说成本，在几万字的全文和只挑几百字相关内容，有可能价格能差出几百倍。再说延迟，模型要先读完全部输入才能开始输出，所以输入越长等待的时间就越久。

最大的问题是上下文稀释，模型的注意力是分摊在所有输入上的，所以塞进去的内容越多，真正有用的部分占的注意力就越少，模型也就越容易出错。综合这三个因素，我们还是得继续 RAG。不过 RAG 具体怎么做，每一步其实都有不同的选择。接下来我会带你认识十个流行的 RAG 策略。我们先快速过一下基础的 RAG 流程。RAG 的流程可以分两段，准备阶段和检索阶段。准备阶段负责将资料存进数据库，检索阶段负责从数据库中找出需要的部分。准备阶段具体可以分为三个步骤，chunking 会将资料切成小块，embedding 将小块的文本转成数字向量，然后 indexing 将向量连同原本的文本存进数据库。

检索阶段分为两步，query processing 处理用户的查询语句，让用户的提问更容易匹配到相关的内容，retrieval 从数据库里挑出真正相关的内容。最后模型会参考找出来的内容生成最终的回答返回给用户。接下来我们就看看每个步骤的具体策略。chunking 最传统的做法是直接按固定字数切，但这样可想而知会破坏语义，就像这样两句话被破碎的切割成了三块，破碎的块就算喂给了模型，模型也理解不来。所以为了能让模型能理解在讲什么，我们需要尽可能让每个块的语义完整。一个策略叫做 semantic chunking，语义分块，会计算每个句子的数字向量，数字向量接近表示两个句子的语义接近，它们就可以合成一个块，但如果向量的距离远就拆成两个块，这样做比按固定字数切分要灵活的多，大部分情况下是够用的。

但如果面对的是这样两句虽然向量差的远，但互相关联的话是这种策略就不够用了。可以使用另一个策略叫做 proposition chunking，将资料粗略切成大块后丢给 LLM，让它拆解成一条条原子化的陈述，比如这样一句话就可以产生两条事实陈述。到了 embedding 阶段，我们将使用 embedding 模型来将文本转换成数字向量。现在有许多常见的 embedding 模型，比如 OpenAI 的 text embedding 三，智源的 bge，阿里的千问三 embedding，它们在大多数情况下都表现的很好。但是如果你是特定领域的项目，比如说法律啊、代码、医学，这种通用的 embedding 模型表现可能会差强人意。

比如法律领域的定金和定金意思完全不一样，但在通用模型的转换中两个词可能会很接近，这时就可以选择所在领域的 embedding 模型。在 indexing 阶段，将向量和文本存入数据库，数据库的选择上，小项目可以使用 SQLite 配上 SQLite VEC 插件，中大型项目可以考虑使用 PostgreS 搭配 pgvector 插件。通常除了向量和文本，还会需要一些结构化字段来存放 metadata，表明内容的日期呀、类型、来源等信息，搜索的时候可以根据这些 metadata 进行过滤，将块存到数据库里。最大的风险是丢失块之间的关系，比如一份合同里的第十二条引用了第五条，但数据库丢失了这个信息。对于这种关系很重要的情况，就可以考虑使用 graph RAG。

Graph RAG 会把每个块里的实体和实体的关系抽取出来，形成一张图，节点是实体，边是关系，像第十二条引用第五条这种关系就会。有两个节点和一条边，检索时先定位命中的节点，再顺着边将关联的节点一起找出来。听起来很棒，但也是有代价的。成本上需要让 LLM 通读资料去抽取实体和关系，这一步将耗费大量时间和金钱，准确率也很难说。而且一旦文档更新，数据库不只需要维护更新的部分，而是整张图都得重新梳理。所以 Graph RAG 是一个收益和风险都很显著的方案，需要谨慎考虑。Query Processing 阶段需要处理用户问题，让提问能够匹配到对应的块。一个方案是 Query Transformation，利用 LLM 对用户问题做重写，改写的更具体、更泛化或者拆成几个子问题。

或者是 HyDE，先让模型根据问题生成一篇假设答案文档，再拿这篇文档去做向量检索，因为答案文档在语义上比问题本身更接近正式文档，召回的质量更高。但风险在于如果问题问的是模型本来就不熟悉的冷门内容，那假设文档本身可能就是错的，检索方向反而会被带偏。这两种方案都要用到 LLM，如果你的项目对延迟敏感，也可以完全不对用户的输入做处理。Retrieval 阶段会拿着 Query 去数据库里搜索需要的块。最简单的做法当然是直接用 Query 的 embedding 去比对数据库里现有的 embedding，但是因为 embedding 指标是语义，无法匹配关键词，像一型糖尿病和二型糖尿病这种具体病名会在检索时无法区分。这时我们就会使用 Hybrid Search，除了用向量做语义检索，还使用关键词检索来精确匹配关键词。

不管是向量检索还是 Hybrid Search，都是把 Query 和每个 Chunk 独立打分。我们还要用 Re-Rank 模型把 Query 和候选的 Chunk 放在一起重新排序，找出最相关的块。因为 Re-Rank 的成本比较高，所以我们通常是在初筛之后才使用。到这里我们就介绍完了每个步骤的问题和解决方案。你可能会有种感觉就是我们一直在对一个很简单的架构打补丁，看起来并不是很聪明。确实如此。召回这个事情就算交给人类来做也不是一次性的工作，而是更像一个循环，探索一次看看信息够不够，不够就继续探索。

这就是 Agentic RAG 的思路，用 Loop 去代替 Pipeline，Agent 自己判断信息够不够，要怎么搜索，给 Agent 一些 Tool，比如说 Semantic Search、Batch Tool，Agent 使用这些 Tool 多轮查找信息，直到召回的信息已经足够回答问题，就整理好信息交给回答问题的 LLM。这是一个范式的改变，优势是很明显的，质量高，工程难度也更低，但缺点也是很明显的。LLM 的深度参与让成本和延迟都大幅增加，对一些简单问题来说太浪费了。因此现在又出现一个思路叫做 Adaptive Routine，先用一个轻量分类器判断问题难度，简单的问题直接走 Pipeline，复杂问题才升级到 Agentic RAG。
