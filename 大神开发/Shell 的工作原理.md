终端这个词其实有点历史偶然性。它指的是人们过去用来连接大型机的物理硬件终端。显然我们现在不再使用那些设备了，但终端这个名称保留了下来。现代终端只是模拟那些古老设备行为的应用程序。终端模拟器处理视觉元素，如字体、颜色和滚动，但它实际上并不解释你的任何命令。这项工作属于一个在终端内部运行的独立程序，叫做 shell。Shell 这个名字源于它作为操作系统最外层保护层的角色。它位于内核之上，内核是实际管理你的硬件、运行进程和文件的核心。Shell 接受你的文本作为输入，并将其翻译成内核能理解的清晰请求。这样内核就永远不必接受原始的人类文本作为输入，只有 shell 需要。在我们继续之前，可能有必要明确定义我所说的文件、程序和进程，以避免任何潜在的混淆。文件是存储在磁盘上的有组织的数据。

它可以是文本、图像、源代码，任何东西。很多人认为不同文件类型之间有什么特别之处。也许他们认为 jpeg 文件和 png 文件有根本性的不同。但实际上所有文件都只是字节，任何两种文件格式之间的区别仅在于这些字节的排列方式，并且总是由使用文件的应用程序来决定如何解释它。程序也是一个文件，只是它的字节恰好是计算机可以执行的指令。就我们的目的而言，术语程序和可执行文件是同义的。尽管有时你会听到程序指的是尚未编译的源代码文件。最后，进程是程序实际运行时产生的东西。磁盘上的程序文件本身除了静静地待在那里，什么也不做。进程是那个程序文件被加载到内存中并正在积极执行，拥有自己的内存分配以及在操作系统运行事务列表中的自己的状态。

正如我们所说，shell 是一个程序，这意味着在磁盘的某个地方有一个可执行文件，其中包含了定义 shell 行为的所有指令。我们马上就会发现这个文件的确切位置，并且像任何其他程序一样，shell 作为一个进程运行。当人们提到 shell 时，他们通常指的是这个进程。Shell 进程有自己的 ID、自己的内存以及生成子进程的能力。这个细节在我们开始实际运行命令时会变得更加重要。Shell 有几种不同的类型，这实际上意味着有多个不同的程序都扮演着 shell 的角色。最常见的两种是 bash，它是大多数 Linux 系统的默认 shell，以及 z shell，它是 macOS 的默认 shell。在这个层面上，任何两种大型 shell 之间的差异大多是不可见的。这意味着这里讨论的概念应该适用于所有 shell。

你可以用一个命令来查看你的系统运行的是哪个 shell。echo $SHELL 对我来说，这会返回 /bin/bash，这是实际 shell 程序在磁盘上的位置。我们将来会详细探讨文件路径，但现在你只需要知道这种字符串代表磁盘上的一个唯一位置。在这个例子中，它是 shell 程序文件实际所在的位置。这里确实有三样东西需要拆解，它们是命令 echo、美元符号和单词 shell。那么我们先从 echo 开始，echo 是一个命令，它只是将其参数打印回屏幕上。例如我们可以这样 echo 出几个词，echo 一二三会简单的将一二三打印到屏幕上。我们也可以像这样 echo 字符串，echo 是一个有用的命令，同时也是一个非常简单的命令，它真的没有更多内容了。

那么这就引出了一个问题，如果 echo $SHELL 打印出了 /bin/bash，那么 $SHELL 是如何变成 /bin/bash 的呢？要理解这一点，我们需要谈谈环境变量。环境变量是 shell 存储在其进程内存中的一个。文本变量。请注意，它是一个文本变量，而不是数字、数组或其他任何东西。在使用 shell 时，这个事实会反复出现。在内部，shell 维护着一个从变量名到值的映射，称为环境。而 shell 这个名字就是这个映射中的一个条目。我们可以使用一个叫做 printenv 的命令来检查这个映射。printenv 代表 print environment，它会以键值对格式打印整个映射，就像这样。完全不用担心要记住这里的每一个条目。

环境变量可能非常多，而且在实践中，它们中的大多数是由操作系统或你的 shell 配置设置的。因此，具体内容在不同系统之间往往差异很大。在这里只需注意这个映射中的 shell 条目。我们也可以直接用变量名运行 printenv 来查看它的值。正如预期，这会返回与之前相同的 bin/sh，尽管上次我们是用美元符号来获取它的。美元符号被称为展开运算符，它只是指示 shell 用变量的值替换变量名。因此，在 echo 被调用之前，美元 shell 就通过内部映射被替换成了 bin/sh。我们也可以很容易地创建自己的变量，语法就是 name 等于 value。同样，我们可以使用展开运算符来访问我们赋的值。注意等号两边没有空格，这是因为 shell 使用空白字符来分隔命令和参数，所以例如这样写就是无效的。

我们也可以使用 printenv 来检查我们的新变量。然而，这似乎没有返回任何内容。那么为什么呢？shell 和 name 之间的区别是什么，导致 printenv shell 能打印出 shell 变量的值，而 printenv name 似乎什么也没打印？嗯，事实证明，我之前说 printenv 会打印整个环境时，我撒了谎。它实际上只打印整个环境映射的一个子集。但这并不是 printenv 的错，我的意思是这样的。当 shell 维护其内部变量映射时，它还会将每个条目标记为已导出或未导出。区别在于已导出的变量会被导出到子进程。当你输入一个程序的名称时，shell 进程会生成一个新进程来运行该程序，而这个新进程被称为子进程，因为它是由父进程诞生的。已导出的变量是那些从 shell 传递给子进程的变量。

这就是为什么 printenv name 没有输出，因为运行 printenv 程序的进程根本不知道 name 是什么，甚至不知道它的存在。如果我们用一些无意义的变量名运行 printenv，也会得到同样的结果。通常我们将已导出的变量称为环境变量，将未导出的变量称为 shell 变量。我们可以使用 export 关键字将一个 shell 变量提升为环境变量，例如 export name。现在当然因为 name 被导出了，它将被传递给 printenv 的进程。所有这些都引出了一个值得思考的问题，为什么有人会希望一个 shell 变量不被导出？在回答这个问题之前，让我们先喘口气，把我们目前构建的所有内容整合起来，因为我很清楚这些内容可能会很快堆积起来。

我们从终端应用程序开始，发现真正的工作发生在它内部的一个叫做 shell 的程序中。shell 是一个程序，这意味着它是一个磁盘上充满指令的文件。当它运行时，它就变成了一个进程，在操作系统上有自己的内存和身份。shell 的基本工作是充当操作系统的基于文本的接口，这是它如此强大的一个重要原因。它的工作原理是读取你输入的文本，并将其解析为命令、参数和变量。这些变量存储在 shell 进程的内存中，存储在一个我们称之为环境的映射里。正是这个映射让我们理解了我们的第一个命令，echo 美元 shell。我们发现 echo 本身并没有做任何聪明的事，它只是打印出。传递给它的参数。真正的工作发生在前一步，当 shell 看到美元符号，将单词 shell 视为一个变量，在映射中查找它的值，然后才将结果返回给 echo。

我们还看到，我们可以定义自己的变量，因为 shell 不仅仅是一个接口，它本身也是一种脚本语言。这就是我们遇到有趣事情的地方。我们的新变量与 echo 配合的很好，但在 printem 中却显示为空。原因在于 printem 根本不是在 shell 内部运行，而是在 shell 的一个子进程中运行。而子进程只接收 shell 明确给予它们的变量。由于我们从未导出 name，它只保留在 shell 本地，printem 无法看到它。这正好把我们带回到我们之前暂停的问题。为什么我们一开始会希望一个 shell 变量不被导出呢？答案取决于你如何理解环境到底是什么。我们知道它是一个映射，我们知道它存储文本变量，我们知道它属于 shell 进程，但它不是某种共享的全局状态。它确实只属于创建它的那个 shell 进程。

当 shell 生成一个子进程时，它会将其导出变量的快照传递给该子进程。子进程中的更改不会向上传播，而父进程在生成子进程后的更改也不会向下传播。仔细想想，这意味着有些变量根本不应该被导出。以这个名为 PPID 的变量为例，PPID 存储当前进程的父进程 ID。你可以想象，如果子进程从 shell 继承了 PPID，它就会把 shell 的父进程 ID 当做自己的父进程 ID，这从子进程的角度来看是完全错误的。正因如此，我倾向于认为环境变量这个术语有点用词不当。从根本上说，shell 的环境并非子进程生活其中的空间，而更像是它出生时被递送的一份快照。如果 shell 生成两个子进程，或者说是两个兄弟进程，每个都会得到自己独立的副本，兄弟进程之间无法看到对方的变量。

一旦它们运行起来，它们也无法看到 shell 中发生的更改。每个进程只是带着自己私有的快照继续前进。说到这里，敏锐的观众可能已经满脑子疑问了。shell 本身有父进程吗？如果有，shell 的环境又是从哪里来的？当子进程自己又生成子进程时会发生什么？环境会一直沿着链条传递下去吗？子进程本身也有导出的概念吗？这些都是很好的问题，它们触及了更深层的东西。整个父进程和子进程的故事并非始于 shell，也不一定终于 printem。我们将来会探讨所有这些。现在我真的很想巩固环境作为快照，环境变量仅仅是文本这个概念。最好的方法是直接接触环境，编写我们自己的程序来访问并打印它。我们自己的 printem 的版本，如果你愿意这么叫的话。main 函数是 C 程序的入口点。

正如你可能已经知道的，它可以接受两个参数，通常称为 argc 和 argv。但较少人知道的是，在大多数系统上，main 可以接受第三个参数，称为 env 及环境指针。这个参数持有 shell 的环境，它以一个以空字符结尾的字符串数组形式到达，每个字符串都是一个单独的键等于值条目。这意味着我们可以遍历数组并逐个打印出来。为了让程序有点我们自己的特色，让我们用金色打印每个条目。编译并运行后，你可以看到它产生的输出与真正的 printem 程序基本相同，只是颜色不同。值得一提的是，这只是从 C 程序访问环境的一种方式，甚至不是最标准的方式，但是它可能是最具说明性的。毕竟令我懊恼的是，这并不是一个 C 编程视频。这个新程序给我们带来了一个问题。

我们有一个新造的 printem 程序，它用金色打印环境，而系统有一个名为 printem 的程序，它用白色打印。那么当我只输入 printem 时，哪个会运行？如我们所见，是系统的那个 printem。那么让我们来弄清楚原因。有一个名为 which 的命令，它接受另一个命令的名称，并返回 shell 找到相应程序文件的确切位置。运行 which printem 能精确显示 shell 会调用哪个名为 printem 的程序。它对其他程序也同样有效。例如，我们可以轻松定位 csh。或者如果你有点想递归，我们甚至可以定位 which 本身。但这只告诉我们 shell 在哪里找到了每个程序，而不是它如何知道去哪里找。那么 shell 是如何将像 printem 这样的程序裸名转换成路径及磁盘上的实际位置的呢？

在我展示之前，我想请你思考一下，如果你是 shell 的设计者，你会如何解决这个问题？一种可能的尝试是使用类似 shell 变量的东西，将每个命令名映射到一个路径。例如，如果我们把 printem 设置为这个路径，那么我们只需引用那个 shell 变量就能调用它。但这并不好。首先，我被允许这样做这个事实本身就说明这不是 shell 实际实现的方式。除此之外，在这种模型下，每个命令前面现在都需要一个美元符号，而且 shell 会为我们想要识别的每一个程序都单独只有一个变量。另一个想法是让 shell 每次运行命令时都从上到下搜索整个机器，寻找名称匹配的程序。但这当然慢得令人发指，而且它没有说明当两个程序同名时该怎么办，更不用说如果有一个同名但甚至不可执行的文件该怎么办了。

我们可以通过选择一个单一目录，并声明所有程序都必须放在那里来解决这两个问题。虽然这更接近真正的解决方案，但它在某些方面是僵化的，会导致真正的操作系统层面的麻烦。这种麻烦我们稍后在正确探索文件系统时会更多的遇到，所以这也不是答案。Shell 实际所做的是这些方法的一种混合。它维护一个需要搜索的目录的简短列表，称为 path，并将这个列表作为一个环境变量暴露出来，这样你就能修改它。每当 shell 需要定位一个程序时，它会按顺序逐一检查 path 上的目录，并在找到第一个匹配项时停止。那么让我们来看看这个 path。注意它是一个用冒号分隔的单一字符串，而不是数组或列表。再次强调，这是因为所有环境变量都只是文本。仔细看，我们可以看到 usr/bin 在 path 上，但我们当前目录不在。

这就是为什么刚才系统的 printem 赢过了我们的。但是假设我们真的想用金色打印环境变量，由于 shell 从左到右读取 path，我们可以通过将当前目录放在 path 的最前面来劫持系统的 printem。我们可以这样做。让我们逐段读这行命令。点号是当前目录的简写，冒号将其与后面的内容分隔开。当然美元 path 会展开为 path 的当前值，所以我们真正说的是取当前目录，然后是 path 上已有的所有内容，并按这个顺序将它们全部重新赋值给 path。这是你在处理包管理和 shell 配置时会经常看到的模式。当前目录现在排在第一位，所以 shell 会先于其他任何地方检查它。果然 which printem 现在指向了我们的当前目录。运行 printem 给了我们金色的输出。事实证明这恰恰。

就是为什么你的当前目录默认不在 `PATH` 上。省略它是一个刻意的安全决定。如果当前目录默认在 `PATH` 上，那么任何恰好位于你所在随机文件夹中的与你信任的程序同名的杂散程序，都可以在你毫不知情的情况下代替它运行。最后，为了科学，让我们看看如果完全清除 `PATH` 变量会发生什么。那么如果我们现在运行 `which zsh` 会发生什么呢？我们肯定会得到一个简洁的小错误，告诉我们找不到 `zsh` 程序，对吧？嗯，如果 `shell` 能先找到 `which` 的话，我们确实会得到这样的错误。`shell` 本身连 `which` 都找不到，更别说用它来搜索其他程序了。值得注意的是，在某些系统上，`which` 实际上是 `shell` 的内置命令，而不是一个独立的程序。

在这些系统上，你会发现 `which` 在这里仍然有效，因为 `shell` 根本不需要去搜索它。无论如何，我们总是可以通过路径直接调用程序，像这样。现在 `which` 运行正确了，但由于 `PATH` 是空的，它无法搜索到 `zsh`。这个练习的全部意义在于证明 `PATH` 不仅仅是 `which` 找到你程序的方式，它也是 `shell` 找到 `which` 的方式，进而也是 `shell` 找到你程序的方式。所以，如果你遇到任何命令未找到的错误，或者你期望运行某个程序，但实际上运行了另一个程序，`PATH` 通常是一个很好的首选检查点。
