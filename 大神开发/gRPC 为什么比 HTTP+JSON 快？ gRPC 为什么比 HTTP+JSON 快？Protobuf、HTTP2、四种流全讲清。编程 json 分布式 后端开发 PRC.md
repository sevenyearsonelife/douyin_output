把一个单体应用拆成了十几个微服务，第一个问题就来了，它们之间怎么通信？最常见的做法是 HTTP 加 JSON，简单通用，谁都会写。但服务一多，问题就慢慢浮出来了。JSON 是文本，字段名要在每条消息里重复一遍，网络上跑的全是冗余。接口靠文档约定，你写 user id，对方写 user 下划线 id，编译期发现不了。每接一个新服务，又要手写一遍请求封装和响应解析。于是 Google 把内部用了十几年的 RPC 框架开源出来，就是 gRPC。它用 Protocol Buffers 定契约，用 HTTP/2 传数据，主打高性能和强类型。这条视频就带你把 gRPC 的核心一次性搞懂。先说清楚 RPC 这三个字母，意思是远程过程调用。平时你在代码里写 get user 一，函数就在同一个进程里，调完立刻返回。

现在这个函数搬到了另一台机器上，你就得自己拼 URL，发请求，解析响应。RPC 想做的事，就是把这堆网络细节全部藏起来，让你还是写 get user 一，感觉就像在调一个本地函数。秘密在于中间多了一层代理对象，叫 stub，也叫桩。你调 stub，它负责把参数打包发出去，等回复，再拆包还给你。服务端有一份对应的骨架代码，收到请求后调用你真正的实现。gRPC 就是这样一套框架，契约用 Protobuf，传输走 HTTP/2。用 gRPC 的第一步不是写代码，而是写一个 proto 文件。它是接口描述语言，专门用来定义数据长什么样，有哪些方法。message 定义一个数据结构，比如 user 有 id 和 name 两个字段。注意每个字段后面的等号和数字，那不是默认值，是字段编号。

编号才是二进制里的真正标识，字段名只存在于源码里，所以改字段名不影响兼容，但编号一旦用过，就绝对不能改，不能复用。service 定义服务，里面每个 RPC 就是一个能被远程调用的方法。每个方法都写死了，入参是哪个消息，返回是哪个消息。编码的时候，Protobuf 只写编号和值，省掉了所有字段名。同样一条数据，通常比 JSON 小三到十倍，解析也快得多。proto 写好之后，用 protoc 这个编译器来生成代码。它本身只负责解析，具体生成哪种语言，交给插件决定。装 Go 插件就生成 Go，装 Java 插件就生成 Java，Python、C++ 都有。生成的东西分两部分，客户端用的 stub 和服务端要实现的接口。客户端拿到 stub 直接调方法就行，网络的事它全包了。

服务端只要实现那个接口，把业务逻辑填进去。好处是两边类型完全对齐，字段拼错在编译期就会报错。团队协作也变了，不再互相传文档，而是传 proto 文件。接口一改，双方重新生成一遍，谁没跟上，编译直接过不去。现在把一次调用从头到尾走一遍。客户端先创建一个 channel，它代表到服务端的一条长连接。channel 是可以反复复用的，不需要每次调用都重新建连接。有了 channel 就能创建 stub，然后像调本地方法一样发起调用。stub 先把请求对象用 Protobuf 序列化成二进制，再包装成 HTTP/2。数据帧，顺着已有的连接发出去。服务端收到帧，反序列化成对象，路由到你实现的那个方法。方法执行完返回结果，同样序列化，封帧，原路回传。客户端再反序列化，你拿到的就是一个普通对象，全程感觉不到网络。

gRPC快，很大一部分要归功于它选了 HTTP/2。先看 HTTP/1.1 的老问题，一条连接同一时间只能处理一个请求，前一个响应没回来，后面的就得排队，这叫队头阻塞。浏览器只能靠多开几条连接来缓解，服务端的压力就上去了。HTTP/2 把数据切成二进制帧，每个帧都带着所属流的编号，于是多个请求可以同时跑在一条 TCP 连接上，交错传输，互不阻塞。这就是多路复用，也是 gRPC 能扛高并发的基础。头部还会用 pack 压缩，重复的头信息不用一遍遍地发，再加上长连接复用，省掉了大量的握手开销。很多人以为 gRPC 就是发个请求收个响应，其实它有四种模式。第一种是一元调用，一个请求对一个响应，最常见，跟普通函数一样。

第二种是服务端流，客户端只发一次，服务端连续返回很多条，适合分块下载大文件，拉取历史消息，订阅一段时间的数据。第三种是客户端流，客户端连续发很多条，服务端最后返回一个结果，适合分片上传文件，批量上报买点，最后回一个汇总。第四种是双向流，两边都可以随时发，互相不用等。聊天、实时推送、语音识别这类场景用的就是它。写法上很简单，只要在 proto 里给参数或返回值加上 stream 关键字。这四种都跑在同一条 HTTP/2 连接上，这是 REST 很难做到的。除了业务参数，一次调用往往还要带一些附加信息。gRPC 把它叫 metadata，本质是键值对，作用类似 HTTP 的请求头。认证用的 token，链路追踪的 trace id，通常就放在这里。接下来是特别重要的一个概念，deadline，截止时间。

注意它不是超时时长，而是一个明确的时间点，到几点几分必须返回。好处是这个时间点能一路往下游传，整条链路共用同一个终点。到点还没完成，整条链路一起放弃，不会有服务在那傻等。最后是错误处理，gRPC 用的不是 HTTP 状态码，而是自己的一套。常见的有 not_found 找不到，permission_denied 没权限，还有 deadline_exceeded 超时和 unavailable 不可用，后者通常可以重试。认证、日志、监控这些事，不该在每个业务方法里都写一遍。gRPC 给的答案是拦截器，作用相当于中间件。它包在真正的调用外面，请求进来先过一道，响应出去再过一道。客户端和服务端都能装，一元调用和流式调用各有对应的接口。典型用法是服务端拦截器统一校验 token，不合法就直接拒绝。

再加一个拦截器打访问日志，记录方法名、耗时和状态码。链路追踪也是这么做的，从 metadata 里取出 trace id 继续往下传。传输安全方面，gRPC 内置 TLS，创建 channel 时指定凭证就行。它还默认做客户端负载均衡，配合重试策略，比走网关少一跳。gRPC 很好，但它不是万能的，有几个场景要特别注意。第一个是浏览器，前端的 JS 碰不到底层 HTTP 两帧，发不了原生 gRPC。解决办法是 gRPC Web，前端用它，中间放一个代理做协议转换。第二个是对外开放的 API，第三方开发者更习惯 REST 和 JSON。让别人先装 protoc，再生成代码才能调用，接入成本太高了。第三个是调试，二进制在抓包工具里是一团乱码，不像 JSON 一眼能读。

好在有 grpcurl，只要服务端开启反射，就能像 curl 一样直接调。如果既想要内部高性能，又想对外提供 REST，可以用 gRPC Gateway。它根据 proto 自动生成一层 HTTP 转换，一套定义，两种协议。一句话，内部服务之间用 gRPC，对外和对浏览器用 REST，这是最常见的组合。
