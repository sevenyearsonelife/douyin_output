如果我们把一个 PDF 文件的二进制内容当作机器指令塞进一个可执行文件，然后运行它，会发生什么？CPU 会执行它们吗？它会报错吗？还是说它又会干脆……剧透一下，会发生很糟糕的事，本期视频就会讲到。在计算机里，同一份二进制数据可以有多种不同的解读方式。完全相同的一串比特，可以被解读为八位整数、字符、十六位整数、浮点数、三十二位整数、图像中像素的颜色信息，又或者为什么不呢？中央处理器的指令。计算机上的每一项任务、每一份数据，无论多么微不足道或复杂，最终都表示为一和零的序列。所以我们自然会好奇，如果把任意一个文件当作程序来执行会发生什么？几周前我们讲过，当 CPU 收到一条它不认识的指令时会发生什么，所以你可能会觉得我在重复之前的内容。

不过本期视频真正要讲的并不是 CPU，而是文件扩展名以及它们在现代软件中为什么能出人意料地令人困惑。这里有一个名为 cat.png 的图片文件，我要把它的文件扩展名改成 .exe。一改完，我们就能立刻看到 Windows 文件资源管理器把它的图标换成了通用的可执行文件图标。但如果我试着运行它，就会弹出一条错误提示。有一点可能不那么明显，它运行不了并不是因为 CPU 拒绝了那些二进制指令。事实上，文件里的那些一和零根本就没有作为指令到达 CPU。但这是为什么呢？如果我们改用终端做同样的事，就能更清楚地看出到底发生了什么。这和文件格式有关。你看，人们很容易以为可执行文件里只有给 CPU 的机器指令，但它们包含的东西其实远远不止这些。一个可执行文件被划分成几个节区，而运行程序所需的可执行代码和数据只是其中的一部分。

这些额外的信息都是必须的，因为当我们把一个程序交给操作系统时，内核需要知道的远不只是该执行哪些指令。程序的入口点在哪里？程序是否依赖外部的动态链接库？它是否依赖某种运行时环境？需要预留多少初始内存？程序的不同部分应该被加载到内存的什么位置？这类信息并不包含在机器指令本身里，所以编译器和链接器把它作为额外的元数据和结构信息一起放进可执行文件。程序真正使用的可执行代码和初始数据最终只占文件的一部分。所以把随便一个文件的扩展名改成 .exe 之所以不行，是因为操作系统期待可执行文件内部有一个非常特定的结构。但如果我们给它的东西本来就不是按可执行文件生成的，那么它试图解读的很多信息就完全说不通。这就是为什么那些一和零从来不会以指令的形式到达 CPU。操作系统不允许这样做，不是因为它不想，而是因为它看不懂这个文件的结构。

而且这不仅仅适用于可执行文件，对各种文件格式来说都是如此。想一想图像，构成那张图片的像素颜色最终被编码成一和零的序列。但仅有这些颜色并不足以完整描述这张图像。比如只靠像素颜色信息，我们无法知道这些像素在屏幕上该如何排列。图像是这样的吗？还是这样的？同样数量的像素可以有很多种排列方式。被设计用来打开这张图片的软件还需要知道它的尺寸和色彩深度，需要知道图像数据是否经过压缩，如果压缩了，又该用哪种算法来解压。大多数现代文件格式都包含这类附加信息，而文件扩展名仅仅是文件名的一部分。扩展名告诉操作系统、应用程序和用户这个文件里应该装着什么。这在选择图标、决定用哪个程序打开文件，或者在文件选择器里筛选文。文件时都非常方便，但文件扩展名并不可靠，因为它可以在完全不改变文件内容的情况下被改掉。

我们可以把 photo.jpg 重命名为 photo.pdf，操作系统可能会立刻更新它的图标，但这并不意味着文件里的字节会神奇地重新排列去满足 PDF 阅读软件期待的结构。说到魔法这回事，我们接下来要讲的就是魔术字节，没错，这确实是一个计算机科学概念。这里有一个小程序，它会打印某个目录的内容以及每个文件开头的前几个字节，它还会按文件扩展名对内容进行分组。可以看到这个目录里有很多不同类型的文件，现在如果你看看它们开头的几个字节，会发现一件非常有意思的事，你能看出来吗？看不出来，那我来帮你把这些开头的字节当作字符来解读并按字符打印出来。现在明显多了，对吧？格式相同的不同文件往往以相同的字节序列开头，这就是所谓的魔术字节，也常被称作文件签名或魔术。

很多文件格式都采用这种约定，在文件开头附近放一段可识别的字节序列，这让软件可以检查那些字节，判断自己真正面对的是哪种文件，而不是盲目相信文件扩展名，它们本质上就像藏在文件内部的一个身份标签。如果你足够细心，可能已经注意到并不是所有文件格式都遵循这个约定，基于文本的文件通常是例外。比如这里可以看到 txt 文件或 c 文件并没有强制的开头字节序列，它们直接从自身包含的文本开始。大多数文本文件之所以是魔术字节约定的例外，是因为它们的内容本来就要作为纯文本被直接阅读和编辑。一旦加上强制的标识字节，这些字节就会变成文本的一部分，除非每个使用该格式的程序都被专门设计成忽略它们。不过与大多数纯文本格式不同，几乎所有结构化的二进制文件格式都包含某种可识别的签名或结构，供软件用来识别它们。

一个重要细节是魔术字节不一定位于第零个字节，比如在 mp4 文件里，前四个字节是 mp4 盒子的大小，而 ftyp 从偏移量四开始。同样，wav 和 avi 都以 riff 开头，所以我们需要检查偏移量八处的字节才能区分它们。另一个有趣的事实是微软 office 文件通常以 504b 开头，也就是 pk 这两个字符的十六进制序列，而这正是压缩 zip 文件使用的同一组魔术字节。有些喜欢逐帧暂停找错的狠人可能早就发现这一点了。这是因为现代的微软 office 文档实际上就是装着 xml 文件的 zip 容器。如果你不相信我，就去找一个 office 文件，把文件扩展名改成 zip，解压之后你会得到一个装满 xml 文件的文件夹。

在我们最开始的例子里，把图片或 pdf 文件改成 exe 之后，操作系统并不需要盲目的解读整个文件，一旦它开始检查结构，发现这不匹配任何有效的可执行格式签名，就可以直接拒绝这个文件，根本不会把它的内容当作程序指令交给 cpu。顺便说一句，windows 通常使用可移植可执行格式，而 linux 通常使用 elf 格式，也就是可执行与可链接格式。当同一个扩展名被用于完全不同的文件格式时，魔术字节也很有用。比如拿到一个 ts 扩展名的文件，开发者多半会立刻认为这是 typescript 文件，但 ts 也可以代表 mpeg 传输流，这是一种常用于电视广播、蓝光相关工作流和视频流的容器格式。如果我们用 vlc 打开一个实际装着 typescript 代码而不是视频。

数据的 .ts 文件，播放器不必仅仅因为扩展名就盲目认定那些字节代表视频。它可以检查文件内容，很快发现这些内容与有效媒体文件应有的结构并不匹配。如果传入的是真正的传输流文件，它就能成功打开。另一个很典型的例子，尤其是在过去，就是 .scr 扩展名。你还记得吗？电脑闲置太久就会自动开始显示屏保，那些屏保其实未必是正在播放的视频，它们实际上可能是程序在后台进行计算，并直接在屏幕上绘制图形。它们就是实实在在的可执行程序，但为了与普通应用程序区分开，Windows 使用了 .scr 这个扩展名。其实我在制作这期视频时才发现，即使在 Windows 十一里进入 system 三十二目录，你依然能找到一些这样的屏保程序。像运行其他可执行文件那样运行它，它就会像当年那样启动起来。

我不是 Windows 专家，不过我猜屏保之所以被做成真正的程序，而不是简单播放一段视频，原因之一是这样它们既能高效运行，又能一直监听鼠标和键盘输入，用户一有操作就能立刻停止。不管怎样，有意思的地方来了，AutoCAD 也用 .scr 扩展名来表示脚本文件。结果是，如果你在 Windows 上安装了 AutoCAD，由于注册表里保存的文件关联，文件资源管理器会立刻开始把那些屏保可执行文件当成 AutoCAD 脚本文件来显示。顺便说一句，它们都是 Windows 自带的。而这才是这里真正关键的区别。文件内部的魔术字节和其他信息主要对软件有用。当我们让某个程序打开文件时，这个程序可以检查文件内容，确认它确实符合预期的格式。而文件扩展名主要对用户和操作系统有用，它让用户可以快速判断一个文件里大概装着什么内容。

在图形界面环境里，它还能帮助文件管理器选择图标，用视觉方式传达这一信息。当我们打开文件时，扩展名可以帮助操作系统决定默认用哪个程序打开这一类文件。不过我得说，这并非铁律。现代版本的 Linux 和 macOS 显然并不完全信任文件扩展名，就像这里看到的这样。我做这期视频的主要原因是最近有人问我怎么创建自己的文件扩展名。显然有些人以为某些扩展名在某种程度上是大软件公司专属的，但正如我们刚才了解到的，文件扩展名只是文件名的一部分，所以你完全可以随心所欲用任何你喜欢的扩展名，只要确保定义了可识别的文件结构，最好包含你自己的魔术字节，并尽量避免选择可能与现有文件格式混淆的签名。这样一来，如果你的软件被要求打开一个错误的文件，它可以先再核对一次签名，然后报错，而不是盲目认定文件有效去解析或修改它，最后可能损坏文件内容。

但现在让我们回到最初的问题。如果我们设法把某个随机文件的二进制内容塞进一个完全有效的可执行文件的代码节区里，会怎么样？如果 CPU 真的把这些字节当作指令收到会发生什么？当 CPU 逐个走过原文件内容里的这些字节时，它会尝试把它们解码成指令，但这些指令本质上是随机的，因为它们不是编译器精心生成的，所以可能对应到任何东西。取决于指令集架构，有些字节序列会解码成完全有效的指令，而另一些则不对应 CPU 能识别的任何指令。而且既然这些指令实际上是随机的，那么即便是有效的那些，也可能是指令集里的特权指令，也就是普通用户态程序不允许执行的操作。所以如果我们设法强行让处理器运行这个程序，那么 CPU 每次尝试执行一条指令时，都可能发生三种情况之一。如果它是一条有效的普通指令，就会直接执行它。

如果它是一条特权指令，CPU 能成功解码，但从非特权进程去执行它，会触发保护异常。而如果这个字节序列不对应有效指令，CPU 解码器会把它判定为无效，并抛出非法指令异常。更麻烦的是，即使是第一种情况，也可能发生异常。想象一下，指令本身完全有效，但它试图访问的内存并不属于这个进程。这种情况下，即使指令本身没有任何问题，CPU 也会抛出内存访问异常。所以从概率上讲，当我们面对的基本上是随机指令时，很多完全有效的指令也有引发异常的潜力，这取决于它们做什么，以及恰好用到哪些操作数。而当 CPU 抛出异常时，它会把控制权交给操作系统，操作系统随后处理这个异常，通常是发送一个信号，而这很可能会立即终止程序。我知道你们中有些人可能期待更刺激的结果，但现代系统就是这么复杂又安全，事实就是如此。

幸运的是，我们可以想象这样一个世界，每一种可能的比特序列都对应某条有效指令。为此，我做了这个非常小的模拟器，是为之后某一期节目准备的。它用来显示 CPU 的状态，中间的内存内容，以及右边的视频输出。内存的内容用白色和黑色像素来表示，分别代表一和零。为它编写的正常程序看起来是这样的，它条理清晰，经过精心设计，会遵守内存中划定的边界。不过，如果我拿一个图片文件，把里面所有的一和零都当作指令来解读，就会变成这样。可以看到，它开始正常运行，我们甚至能看到它开始往栈里写东西，但仅仅几秒之后，栈就溢出了，程序开始往帧缓冲区里写数据，这就是屏幕上开始出现那些线条的原因。所以一开始它看起来几乎像是在做有条理的事，但如果我们让它继续运行，就会发现它最终开始覆盖自身，而一个正常守规矩的程序绝不会故意这么做。

在底层，指令有点像字母表里的字母，字母本身传达不了任何有用的信息，要传达有意义的内容，我们必须按照特定的结构仔细排列它们。如果只是随机摆放字母，我们得到的多半是一堆无意义的乱码，而这正是这里正在发生的事。当我们把图片、文本文件或 PDF 文件的字节拿来，强行让计算机把它们解读为机器指令时，即使这些字节序列碰巧每一条都对应有效指令，这些指令也不是有意排列成一个有用的程序的。从 CPU 的角度看，它们本质上是随机的，由此产生的行为完全无法预测，这个程序做不了任何有用的事，还会违反正常程序都会遵守的各种假设和边界。CPU 确实在成功执行指令，只不过这些指令从来就不是为了成为程序而存在的。
