C 加加二十中新引入了一个比较运算符，叫做三路比较运算符。不同于其他比较运算符返回一个布尔值，三路比较运算符返回一个包含三种可能结果的值：大于、小于、等于。将三路比较运算符的结果再次与零比较，便可得到我们熟悉的布尔类型，从而对接逻辑语句。不过这么看上去，这个三路比较运算符多少带点南辕北辙、脱裤放屁之美。这是因为这并不是它的常规用法。对于一个自定义的类或者结构体，若想让对象支持比较运算，需要重载并完整实现全部的六个比较运算符。这六个运算符一个不能落，写起来既繁琐又枯燥，并且很容易犯错，导致逻辑不一致，进而导致 bug。而有了三路比较运算符，一切都简单多了。我们只需要定义这一个运算符，编译器便会自动的为我们生成其他那些繁杂的比较运算符。

另外，由于是编译器自动生成的，比起手写，它可能会有额外的优化，进而让比较运算运行的更高效。不过最重要的还是简洁和一致性这两点。运行这段代码，你会发现输出结果合情合理，这证明编译器已经替我们实现了必要的比较运算。对于这种简单的类型，默认比较会按照成员逐个进行比较。三路比较运算符的比较结果类型定义在头文件 compare 中。根据我们比较的对象类型不同，返回的可能是三种标准类型之一。但是有一个要点要注意，手动定义三路运算符时，编译器不会实现相等运算。只有你在使用默认生成的三路运算符时，如果类中没有自定义的相等运算，那么编译器才会隐式生成相等运算。总之，三路运算符就是这么简单，讲完。注意力惊人的同学想必已经发现了，视频的进度条还没过一半。是的，我们的故事还远没有结束。三路比较运算符仅仅是一个语法糖吗？

背后有没有什么数学含义？它的结果为什么需要区分三种不同的类型？任何类型都可以定义比较运算吗？请注意，这期并不是短的 C 加加，而是程序那些事。我们今天的主题是比较。在 C 加加二十出现三路运算符之前，许多的语言以及编程习惯早就有了三路比较的概念。比如 JavaScript 语言在为列表排序时传入的比较函数，通常是带比较字段的两数之差，这其实就是三路比较运算。不止 JS，C 也都是类似的思路来实现三路比较运算。实际上，使用减法比较数据的大小不仅是高级语言的习惯，也正是计算机执行比较运算的实际实现方式。大家小学二年级都学过，叉八六架构中用于比较运算的指令是 CMP 指令，而这个指令其实就是一个特殊的减法命令。它在执行了减法运算后，并不会存储计算的差值，而是仅仅根据结果设置 CPU 的标志位。

其中关键的标志位有两个，零标志位和符号标志位。根据这两个标志位的结果，可以判断比较的结果。所以从硬件角度来讲，比较几乎就是相减然后看结果。由此可以得出一个有趣的结论，比较运算的第一步也是最核心的一步，其实就是减法。通过减法得到一个差值，我们就能进一步衍生出各种判断。差值为负则意味着小于，差值为零则意味着等于，差值为正则意味着大于。之后通过非运算便可以得到剩下的三种比较运算。在机器的世界里，这是判断大小的直接手段。换句话说，减法提供了一个度量两个值差异的有效方法。但是光靠减法定义比较运算就万无一失了吗？答案是否定的。若想搞明白减法的局限性，需要先重新认识一下。比较运算。在数学中，比较两个东西的大小涉及到所谓的序关系。所谓序关系，通俗点讲就是将一组元素排个顺序。

既然可以排序，那就存在着排序的前后关系，因此便会存在大于、小于以及等于这三种关系，这便是我们熟悉的三态比较模型。任何数值类型均可以在我们这个比较模型中进行比较，这是三态模型的开始，接下来我们需要将它发扬光大。要知道并不是所有的类型和数据都是数值类型，那么对于任何类型能否通过定义一个特定的比较规则，使它的取值集合成为一个有序集合吗？当然答案大家都已经知道了，肯定是可以的。比如我们可以定义一个可比较的 set 类型，规定两个集合 A、B 之间，若满足 A 包含 B，则 A 大于 B，若 B 包含 A，则 A 小于 B，若 A、B 包含同样的元素，那么 A 就是等于 B。这就是根据集合的包含关系来定义这个自定义类型的序关系。将这个 set 类型全部的可能取值作为一个集合 S，这个集合有序吗？

先解释一下什么是有序，数学上如果一个集合具有这么三个特点，那这个集合就是有序的。对于任意一个来自集合 S 的元素 a，如果满足 a 小于等于它自己，那么这个集合就满足自反性。对于任意两个来自集合 S 的元素 a、b，如果已知 a 小于等于 b 且 b 小于等于 a，可推出 a 和 b 相等成立，则这个集合满足反对称性。对于任意三个来自集合 S 的元素 a、b、c，如果已知 a 小于等于 b 且 b 小于等于 c，可推出 a 小于等于 c 成立，则这个集合满足传递性。注意到我们前面定义的集合 S 确实符合这三个特性，因此是有序的。证明很简单，就留给大家自己练练手，如果不会的可以问这些家伙。这样的序关系我们称为部分序关系，或者说偏序关系。

偏序指的是集合中并非任意两个元素均可比较，比如我们刚才构建的集合 S 中，就可以注意到一二构成的集合和二三构成的集合就是不可比的，它们既不是大于也不是小于，更不是相等关系。大家熟悉的浮点类型便是典型的偏序关系，而 IEEE 规定的浮点格式中就有一个超脱城市之外不在五行之中的取值，它与其他的任何取值都是不可比的，用 NaN 与其他浮点值做比较运算得到的始终是 false。因此在 C++ 中，部分序关系的比较结果有四个，除了大于、小于、等价之外，还有一个 unordered 代表无序或者说不可比较。相对的，如果某个有序集合满足任取其中的两个元素均是可比较的，即满足可比性，则这个集合被称为全序集，其中元素间的关系是全序关系。自然数集、实数集都是全序集。除了全序和偏序关系，数学中还定义有强序关系和弱序关系。

不过在 C++ 中强序和弱序和数学中的定义略有区别，C++ 中的强序和弱序都是在全序的基础上扩展出来的。如果一个全序类型的全部的可能取值，除了它自己之外不和其他任何值相等，那么就为强序，否则是弱序。比如整数就是强序的，如果两个整数相等，那么它们的值一定是相同的。而字符串根据比较的方式可以是弱序的，如果比较时忽略大小写，那么 black 和 Black 就是相等的，尽管它们的值并不相同，其中一个还可能是个人名。因此弱序关系中的结果中相等对应的是等价而不是 equal 相等。简单小结一下，我们有三态比较模型，小于、等于、等价、大于，这是基本的三种结果。而在偏序中需要考虑到第四种结果无序。强序是最严格的信息量最大的关系，弱序其次，偏序则最为宽松。在编程语言的比较运算设计中，理想的模型应该都能涵盖这些情况。

理解了三态模型再回头看减法比较，就会发现潜在的问题了。首先在语义上，减法并不能完美的表达比较关系。减法计算的是两个值之间的差值，直观的含义是两个值之间的距离。这本身要求了参与运算的类型是可度量的，也就是数值类型或者是可以转换为数值的类型。对于整数浮点这样的数值，差值确实有意义。但是对于无法量化的对象，比如字符串、对象实体，减法根本无从定义。所以减法天然就有类型的限制，它只能用于数值或者定义了减法操作的类型，不能直接用于更一般的比较。另外，差值强调的是距离而非单纯的大小关系。我们用 a 减 b 来判断大小是一种巧用，但在代码的可读性上，这未必是最清晰的表达。如果一个函数返回 x 减 y，读代码的人可能需要反应一下，哦，这是用差值的正负来判断 x 和 y 的大小。它并没有直接说出谁大谁小。

相比之下，一个专门的比较函数或者像三路比较运算符这样，直接返回一个表示大小关系的对象，可读性就强多了。它明确告诉你这是在比较，并不是在算差。不过更大的问题在于减法无法表示不可比较的情况。正如上一章讨论的偏序关系，有些东西是无法直接比较的。这个时候如果我们用差值来表示比较的结果，就会陷入两难。要么硬着头皮返回一个数字表示无序，可是返回什么呢？零表示相等，但这里并不是相等关系。正负也不对，因为我们并没有大小之分。或许你会想到抛出一个异常或者返回特殊类型来表示不可比，但是这些都偏离了减法的范畴。减法本身并没有一个无序的标志。比较两个集合的子集关系，如果不考虑不可比的情形，用减法毫无意义，集合是没办法相减得出一个数字的嘛。

再比如比较浮点数的时候碰到我们之前说过的 NaN，a 减 b 本身得到的还是 NaN，还是没法直接用来判断，更不用说它本身和别的值不可比，减法根本就无法传达这一点。其次在类型的层面，减法比较对返回值类型也有限制。减法的结果类型由参与运算的类型决定，一般就是数值类型或者提升后的类型。这意味着如果我们的比较对象的范围很大，一个是差值可能会溢出，例如两个很大的整数，单靠相减也许会超出类型可表示的范围。其次对于一些用户自定义的类型，即使它们可以定义减法操作，返回的类型也未必是可以用来判断正负的类型。还有有些类型根本就不适合添加减法，比如字符串。用减法实现比较在很多情况下是可行的，但它在语义和适用范围上都有局限。减法强调的是数值的差距，要求类型是可计算差值的类型，因而不适合非数值类型的比较。

并且它无法表达不可比较这种数学上可能存在的关系。相比之下，三态比较直接处理序关系，天然的可以区分不同的序关系模型，返回结果也比较清晰，这就为更复杂的比较需求提供了基础。还记得此前我们已经多次提到了，如果我们手动定义了三路比较运算符，编译器是不会替我们隐式生成相等运算的。这并非偷懒或者 bug，而是刻意为之的设计。原因在于三态比较模型中的相等和相等运算符的相等其实并不是同一个概念。我们先明确两种等的含义。当三路运算符返回的结果表示等于时，指的是在序关系下的等价。而相等运算符更多的表示两个值是完全等同的，这是一种更强的判定，通常会直接设为同一个值或者同一个实体。举一个具体的例子，想象一个 Person 类，有姓名和年龄两个成员。

如果我们定义一个三路比较运算符来比较 Person，但我们只比较年龄，忽略姓名，那么两个年龄相同的人，都会被判断为等价，因为年龄相同，排序中的谁前谁后根本无所谓。然而这并不意味着两个人在实际意义上是相等的，他们的姓名完全不同，显然不可能是同一个人。也就是说 Person 一和 Person 二返回等价，只能说明在排序意义上无法区分它们，但我们不希望两个连名字性别都不同的人被认为是同一个人。也就是说三路比较运算符判断的等价并不是真正的相等。C++之所以不在你自定义三路比较运算符时自动生成相等，正是因为编译器不敢擅自假设等价即是相等，除非你通过显示声明使用默认的相等运算符，来明确告诉编译器在该类型中此假设成立，否则它会选择保守一些，哪怕多写几行代码，也要避免任何可能的错误。

但是如果使用了默认的三路比较运算符，那等于说所有的成员都参与比较，而对于所有成员都相等的情况，那几乎可以肯定说这就是对象意义上的相等了，编译器便认为等价即相等的假设成立，所以放心的提供了相等运算的实现。而使用自定义的三路比较运算时，因为你的三路比较运算也许并没有涵盖对象的全部信息，自然不应该假设等价即相等。总而言之，三路比较运算符关注的是排序关系，而相等运算符关注的是值本身的相等，两者在大多数简单的情况下可以重合，但在更加复杂的情况下未必一致。C++的设计选择了尊重程序员的意图，不轻易的把一种关系替代为另一种，除非显示的声明就按默认的来。这也体现出 C++ 的一贯作风，显示优于隐式，该说清的东西一定要让程序员说清楚。

通过三路比较运算符的这个例子，我们可以窥见 C++ 设计中的一些思路，不要做任何程序员没有明确表达意图的假设，也就是显示优于隐式。C++ 倾向于让程序员亲自决定程序的行为，而不是语言替你猜测。就像我们刚才讨论的几个点，编译器不会因为你定义了三路比较运算符，就自动假设相等怎么实现，除非你显示声明了使用默认的实现。这种理念贯穿于 C++ 的方方面面，比如 C++ 有各种引用类型，需要你在合适的场景选择使用。又比如 auto 关键字不支持推导引用，必须显示添加引用标识符。再比如 Lambda 表达式，你必须显示的指出捕获列表，并告诉编译器是按引用捕获还是按值捕获，它不会像某些语言默认把周围的变量通通捕获。再比如构造函数要不要做隐式转换，也是容许在构造函数上加上对应的关键字，来防止编译器擅自进行类型转换。

这些设计无一不体现出 C++ 对程序员的信任和对明确意图的推崇。C++ 提供了丰富的语法，让你可以精细的控制程序的每一个细节，从内存管理到运算符重载，几乎每一件事情都有显示的机制来供你选择使用或者不使用。当然这意味着 C++ 的学习路线非常陡峭，因为你需要掌握和考虑的细节非常多。但在另一方面，它给了你巨大的灵活性和性能潜力，只要你愿意承担相应的责任。这就是 C++ 的风格，将这个数字世界的一切都交给你，在这里你就是上帝。好了，这就是这期视频的全部内容了，我是新 UP 主鬼明，感谢你能看到这里，我们下期再见。嗯。
