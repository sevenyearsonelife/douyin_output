本期视频我们将揭秘 CPU 执行函数调用的底层机制。听起来简单，但对仅能顺序执行指令的机器而言，这实则是个惊人的难题。从硬件层面看，执行代码调用其他代码并无特别之处。但在软件层面情况则截然不同。编译器负责生成有效的机器代码，其中包含 CPU 执行函数所需的逻辑，使这一切成为可能。正如我多次强调的，最终处理器执行的机器指令正是由编译器生成。它会将您编写的所有代码行转换为计算机电路能够理解的内容，一个精确的指令序列。出于教学目的，我们将使用汇编语言进行解释，因为原始机器码对人类基本不可读，而汇编语言只是可执行文件中零和一的文本表现形式。编译器实现函数调用有两种基本方式：函数内联和函数外联。较为简单的函数内联，其原理是复制函数体，解析每次调用的变量，并在每次调用时将代码直接插入调用处。

从高层次视角看，这就像编译器生成的代码完全没有使用函数进行模块化，而是将所有指令写成单一作用域下的长序列。由于所有指令最终按顺序排列，CPU 只需连续执行指令即可运行程序。信不信由你，即便我们尝试模块化代码，编译器仍会尽可能使用函数内联。但要理解原因，我们需要看第二种实现方式：函数外联。在函数外联中，编译器仅生成一次函数代码，将其存放在与调用代码不同的内存区域。当函数被调用时，CPU 会跳转至该代码段。函数执行完毕后，会返回到调用方的原始位置。当然，这并非魔法般的自动实现。编译器必须发出额外指令，告诉 CPU 不要继续执行下条指令，而是跳转到函数代码，并设法返回到函数被调用的位置。许多人认为这种方式调用函数需要两条特殊指令 call 和 ret，但这并不完全正确。

这些指令本质上是快捷方式，将我们通过常规指令就能构建的过程自动化了。因此在视频接下来的部分，我们将探索如何不用专用指令实现这个功能。仔细想想，我们真正需要的只是跳转指令。对不了解的人解释，跳转指令会让 CPU 不再执行内存中的下一条指令，而是跳转到指定地址继续执行。大多数情况下，CPU 会顺序执行内存中相邻的指令，但有时我们需要明确告诉它去执行其他位置的代码。在汇编语言中，指令的内存地址通常用标签表示，这些标签最终会被解析成可执行文件中的实际内存地址，这样 CPU 就能准确知道跳转目标。跳转指令本身与函数并无必然联系，它们之所以存在，是因为从根本层面来说，它们对控制程序流程至关重要。正如我们在前一集中探讨的，这能让 CPU 实现循环和条件逻辑。为了便于理解，我们现在从既不接收参数也不返回值的函数开始讲解。

请记住，当主程序调用函数时，函数外联要求 CPU 跳转至该函数的可执行代码处。因此最简单的实现方式如下：当程序需要调用外联。函数时，会使用无条件跳转指令将执行流程转移到该函数的起始地址。CPU仅需如此即可开始运行另一段代码。接下来的问题是，当函数执行完毕后，CPU如何知道该返回到何处？有人可能会想，只需在返回点定义另一个标签，并在函数末尾添加一条跳转指令，跳回到函数调用后的指令即可。如果我们解析地址并将程序加载到内存中，似乎这个方案是可行的。主函数跳转到 doSomething 函数的代码，待该函数执行完毕后，又跳转回主函数。但这在普遍情况下并不适用，因为函数可能会被程序中的多个位置调用。如果硬编码单一的返回地址，函数将始终返回到同一位置。这意味着它可以从任何位置被调用，但只能返回到一个固定位置。

为了解决这个问题，我们可以让返回地址变成动态的。一种思路是定义一个名为 returnAddress 的变量。当主程序要调用函数时，会先将应返回的地址写入此变量，再跳转到目标函数。在函数内部，它并非跳转回一个固定地址，而是从内存中读取返回地址并跳转到该位置。这样，函数总能返回到正确的位置。下面通过直观动画展示程序执行流程。当我们将返回地址设为动态时，会发生以下情况。程序首先在主函数中开始执行。当执行到第一个函数调用时，它会存储返回地址并跳转至目标函数。随后该函数开始执行。函数执行结束时，会取出需要返回的地址。获取该地址后直接跳转返回。主函数继续执行，直到需要进行第二次函数调用。在跳转到函数代码前，程序再次更新了返回地址。函数执行完毕后，会取出返回地址并通过跳转指令返回到正确位置。这个逻辑很合理，对吧？

但这种方法依然不够完善。试想主程序调用某个函数后，该函数又调用了另一个函数的情形。主程序将返回地址写入变量后，跳转至第一个函数。当这个函数调用第二个函数时，又会复写同一个变量中的返回地址再次跳转。导致内层函数虽能正确返回。但外层函数的返回地址已丢失，程序不仅无法返回主程序，还会跳转到错误位置，从而导致运行出错。在这种情况下，程序甚至可能永远重复执行相同的指令。为每次函数调用创建独立变量存储返回地址看似可行，但优秀程序员明白动态问题需要动态解法。我们需要更灵活的解决方案。我们需要一个数据结构，而根据问题本质，这个数据结构正是栈。这种结构将元素层层堆叠，总是优先移除最新添加的元素。核心思路如下：每次调。调用函数时，程序会在跳转至函数代码前，将返回地址压入栈中。函数完成时，只需弹出栈顶值作为返回地址即可。

接下来的问题是如何用汇编语言实现栈。其实也没那么难。首先，我们需要为栈选择一块内存区域。为简化起见，假设栈从内存地址九千九百九十九开始，并朝低地址方向向下增长。为了实现压栈和弹栈操作，需要追踪栈顶位置。为此我们引入栈指针变量，该变量存储着栈顶元素的地址。压栈操作时，读取栈指针值，将其递减指向下一个空闲位置，存储新值后更新栈指针指向新栈顶元素。弹栈操作时，获取栈指针值，然后读取该指针指向的内存内容。最后递增栈指针并更新内存中的值，使其重新指向下方元素。这类数据结构操作通常会被实现为可复用的例程，存储在内存其他位置，需要实在跳转执行。但这里不能这么做，因为跳转至辅助例程的机制正是我们试图构建的核心功能。

因此现阶段我们只能内联堆栈逻辑本身，在每次函数调用时注入将返回地址压入堆栈的代码，在每次函数返回时注入从堆栈弹出地址的代码。以下动画演示该机制的工作原理。程序开始执行，当需要跳转至函数时，程序会先将该次调用的返回地址压入堆栈，再执行跳转。若该函数又调用其他函数，则会重复相同操作，将本次调用的返回地址压栈后，跳转至内部函数执行。当内部函数执行完毕时，它会从堆栈中弹出最近压入的地址，并通过跳转指令精准返回到当初被调用的位置。随后外部函数继续执行，当它最终需要返回主函数时，由于堆栈已恢复到内部调用前的状态，外部函数的返回地址又会成为栈顶元素。因此 CPU 只需弹出堆栈并跳转到获取的地址。通过这种方式，函数能可靠的返回到正确位置，而不会覆盖先前外部调用的返回地址。

这就是仅通过跳转和堆栈实现函数外联的方式，无需专用处理器指令。值得注意的是，整个堆栈机制对高级代码是完全透明的，源代码中根本找不到任何与堆栈相关的内容。在幕后，编译器必须注入所有这些额外逻辑才能实现函数外联。这里我们就能看出函数内联的优势之一，由于无需在每个调用点注入额外指令，且执行过程也无需跳转到程序其他位置，总体上执行的指令更少，从而提升性能。但栈结构对程序执行至关重要，至少在我们常规编程方式中是如此。提前剧透下，函数内联并非总是最优解，甚至有时根本无法实现。因此早在一九七零年代，CPU 就开始配备专门优化栈管理的硬件。CPU 没有将栈顶元素地址存储在普通内存变量中，而是提供了名为栈指针的专用寄存器。栈本身仍存在于内存中，但由于指针保留在处理器内部，访问速度极快，因为可以避。免两次内存操作。

将栈指针存入专用寄存器后，CPU 还能提供操作栈的专用指令 push 和 pop。Push 指令能将数值存入栈并更新栈指针，整个过程只需一条指令。Pop 指令可从栈中取出数值并更新栈指针，同样只需一条指令。因此，之前编写的所有样板代码现在都能简化为类似这样。可能有人从视频开始就在疑惑 call 和 ret 指令，现在终于要揭晓答案了。这些指令本质上只是基于栈操作的快捷方式。Call 指令会让 CPU 将返回地址压入栈，然后跳转到目标函数。Ret 指令则让 CPU 弹出栈顶地址并跳转到该地址。因此，跳转到函数并返回到调用者的整个过程最终可以简化为类似这样。在我看来，这绝对比手动处理栈要更易读。这不仅使程序更易读，而且更高效，因为 CPU 需要获取和执行的指令更少，就能达到相同的结果。

关于函数参数和返回值，编译器还需要注入额外的代码来处理这些情况。调用函数时，在跳转到其代码之前，需要额外的指令将参数放置在卡莉可以访问的位置。有两种基本方法可以做到这一点。一种方法是通过通用寄存器传递参数。使用这种方法时，函数会被编写为直接从特定寄存器读取其参数。一旦函数开始运行，它可以直接使用 CPU 寄存器中的值。返回值也可以通过寄存器来完成。在跳转返回前，卡莉架构会将结果留在指定寄存器中，由调用者从该寄存器读取返回值。另一种传递参数和返回值的方式是通过内存。在跳转至函数前，调用者将参数写入特定内存位置，而卡莉架构在需要访问参数时从这些位置加载数据。返回值同样可被写入内存供调用者获取。第二种方法通常更灵活，因为参数可能是寄存器无法容纳的复杂数据，或因函数所需参数超出系统中通用寄存器的数量上限。

这属于平台调用约定的一部分，由应用二进制接口定义。需再次强调，相比函数内联，这些用于参数传递的额外指令会影响性能。即使不涉及参数或返回值，跳转至函数和返回所需的额外指令也会产生可测量的性能开销。根据目前讨论的内容，似乎函数内联始终是最佳选择，但事实并非如此。假设我们有一个非常大的函数，若该函数在程序中被调用数百次，在每处都进行内联可能导致可执行文件体积暴增。此时函数外联更为合适，因为函数代码只需生成一次，程序通过跳转调用，最终生成更小的二进制文件。反之，若函数体量小且调用频繁，外联可能并非理想之选。处理调用与返回的额外指令最终可能增加而非减少代码量，与预期效果背道而驰。这正是该话题的魅力所在，决策需视具体情况而定。不能简单的认为某种方法就一定比另一种更好。在某些情况下，最终还是要取决于每个函数的具体用途。

例如在现代系统中，缓存对这类决策有着重大影响。假设某个函数仅在循环内部的一个位置被调用。若采用函数外联，其代码很可能尚未加载到 CPU 缓存中。程序执行到该函数时会发生缓存未命中，CPU 不得不等待指令缓存填充完成。函数返回时可能再次出现同样情况。此时函数内联就能发挥作用，内联后的代码很可能与调用者共享缓存空间，既降低缓存未命中几率，又能提升性能。这个案例最有趣的地方在于，尽管两种版本在技术上是相同的程序，缓存机制却彻底改变了执行效果。但这并不意味着为了缓存优化就必须永远采用函数内联。以一个处理罕见错误的函数为例，从统计数据来看，它几乎从不执行。若通过函数外联将该代码移至他处，高频执行代码就更可能完整载入缓存，从而提升整体性能。缓存行为本身值得单独制作视频讲解，此处不再深入探讨。

可以肯定的是，若想精准控制函数内联或外联，系统级编程语言通常提供影响编译器决策的方式。例如在 C 语言中，可以在函数定义时使用 inline 关键字。而在 Rust 中，可用 inline 属性提示编译器执行内联，覆盖其常规启发式规则。最后还存在一种函数内联根本不可行的情况，递归调用。当函数自调用且编译时无法确定递归层数时，内联操作就无法实现。这种情况下，函数外联就必不可少。有趣的是，要实现递归功能，编译器不仅要确保函数如视频所述正确跳转和返回，还需生成代码防止每次递归调用覆盖前次调用的变量。本例中程序会偏离预期行为，因为传递变量使用的内存地址是硬编码的。每次函数递归调用时，它在尝试向下一级传递参数的同时，会覆盖自身的参数。
