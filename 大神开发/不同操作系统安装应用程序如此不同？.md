通于 Windows 几乎什么都要安装程序，大多数 macOS 应用只需要把图标拖进文件夹就能安装，而显然这让一些人抓狂。当然，X 平台上的大多数言论都是博取关注，但我仍然觉得做一期视频讲讲在 macOS 上安装应用时实际发生了什么，并解释其他平台上的工作原理会很有意思。要弄清楚 macOS 里是怎么回事，我们打开终端，进入应用程序目录。如果列出这个文件夹的内容，我们会看到一堆看起来像是文件的东西。现在如果我们打开 Finder 进入同一个目录，应该看到同样的东西，对吧？我知道有些人在想什么，废话，你做的完全是同一件事，只不过换了一种用户界面，当然会看到同样的东西。嗯，不完全一样。我们挑一个项目，比如 Firefox，在 Finder 中，如果我们双击 Firefox，应用就会启动。

所以乍一看，这些东西似乎都是可执行文件。所以从技术上讲，要想在终端里做同样的事，我们只需要告诉 shell 去执行这个文件。但如果我们真的去试，啪，就报错了。但这是为什么呢？一开始你可能会觉得答案就在眼前，这个文件没有执行权限。但如果我们检查一下权限，会发现它其实是有执行权限的。所以这到底是怎么回事？其实答案就在我们眼前，看到这个首字母了吗？它告诉我们文件类型，而 d 代表目录。如果我们仔细看一下应用程序文件夹的内容，就会发现这些其实都是目录，很多人也直接叫它们文件夹。事实上，如果我们运行 tree 命令，就能看到它们里面的内容，然后对其中一个运行 change directory 命令，你会发现它真的能进去。

所以 Finder 其实是在跟我们玩把戏，我们在图形用户界面里看到的这些东西根本就不是可执行文件，它们其实是文件夹，事情一下子就变得奇怪了，是吧？很多人认为 macOS 中的点 app 扩展名等同于 Windows 中的点 exe 扩展名，但正如我们刚刚看到的，事实并非如此。在类 Unix 系统中，启动一个程序通常涉及两个重要的系统调用，系统调用 fork 通过复制父进程来创建一个新的子进程，然后系统调用 exec 用一个新的可执行程序替换掉那个子进程。这个应用无法从终端启动的原因是点 app 路径指向的不是一个可执行文件，它指向的是一个目录。当我们输入类似这样的命令时，shell 最终会请求内核执行那个路径，过程大致是这样的。但是内核无法把那个路径当做程序来执行，因为它不是一个可执行文件，它是一个目录。

目录也可以有执行权限，但对目录来说，这个权限的含义和普通文件是不同的。对于普通文件，执行权限意味着这个文件可以作为程序来运行，但对于目录，执行权限表示允许你进入这个目录并访问里面的内容。所以这个错误信息并不是在说火狐被阻止了，因为你没有管理员权限，它更像是在说这个路径无法按照你请求的方式被执行。我们告诉内核运行位于 Firefox 点 app 的那个东西，但位于那里的东西是一个文件夹，而不是真正的二进制文件。那么为什么这个应用在 Finder 中就能启动呢？这是因为当我们编写代码。并编译它时，会生成一个可执行文件。这个可执行文件就是我们通常所说的程序。对于基于终端的应用来说，通常只需要那个文件就够了，因为终端环境主要是基于文本的。但在图形用户界面中，同一个可执行文件看起来会是这个样子。

从技术上讲，我们可以把所有程序的可执行文件都放在同一个目录里，但它们的外观基本上都一样。唯一能区分每个程序的方法就是看它的文件名，而这完全违背了图形用户界面的核心理念，应用程序应该像是独特、可辨别的对象。这时候应用包就派上用场了。对于桌面应用，我们通常不会只分发一个单独的可执行文件，至少需要随可执行文件一起附带一个图标包，这样操作系统才能显示一个图标，让这个应用看起来独一无二。而实际的应用通常还需要几十个额外的文件，不仅仅是可执行文件和图标、动态库、默认配置文件、插件、框架、本地化文件、资源文件以及应用可能需要的许多其他资源。所有这些都是应用包的一部分。问题是，如果我们只是简单的把可执行文件、图标、库和配置文件放在一起，它们在文件管理器里就会一个一个单独显示出来。

当然，这就引出了一个重要的问题：操作系统是怎么知道该为每个具体的应用显示哪个特定的图标呢？嗯，其实这完全取决于操作系统。这里请注意我的措辞，我说的是操作系统，而不是内核。已安装的应用程序如何以图形方式呈现给用户，主要取决于桌面环境、文件管理器以及其他用户空间服务。而且正如我们在上一集所学的，这些都是用户程序。所以内核并不决定某个内容应该显示为普通文件夹、应用程序图标还是其他类型的图形对象。内核提供对文件系统的访问，图形环境决定如何将该文件系统呈现给用户。所以继续之前，我们需要回答的问题是，操作系统是否识别应用包？答案就像我们这里介绍的几乎所有内容一样，非常有趣。我们先从 macOS 说起。macOS 确实被设计为能够识别应用包，但如果我们作为开发者希望自己的包被正确识别，就需要遵循一定的约定。

第一个约定就是点 app 扩展名。Finder 作为一个用户空间程序，会不断向内核请求我们所浏览的目录的内容。文件系统里实际上还是和我们在终端里看到的东西一样，但 Finder 并不需要以完全相同的方式去展示它们。macOS 中的点 app 扩展名会告诉 Finder 这个目录应该被当做应用包来处理，所以 Finder 不会把它显示成一个普通文件夹，而是显示成一个独立的应用，并且会使用包内某个位置存储的图标。如果用户点开这个应用包，Finder 并不会显示它的内容，相反它会运行应用包里面包含的那个可执行文件。如果你不信，可以试试这个，去文件系统的任何地方，我就在桌面上操作吧。新建一个名字以点 app 结尾的文件夹，macOS 会询问你是否确定，你可以点是。

马上你就会发现 macOS 显示的并不是一个普通文件夹，而是一个应用图标。因为里面还没有放什么有用的东西，所以它会用一个默认图标。如果你双击它，会看到这样一条提示信息，这是因为里面啥都没有。现在在 Finder 中打开应用程序。去文件夹。随便选一个应用，右键点击它，然后选择显示包内容。这会让 Finder 显示这个应用包的内容，而不是启动它。现在把那个应用里的 Contents 文件夹复制下来，粘贴到你刚才创建的假点 app 文件夹里。等一会儿，macOS 最终就会把这个文件夹当做一个应用来显示。如果你双击它，这个应用真的会启动，因为这个应用包里现在包含了 macOS 所期望的内部结构。一个典型的 macOS 应用包有特定的内部结构。

在这个应用包里面通常会有一个 Contents 文件夹，在那个文件夹里面还有几个其他的目录和文件。MacOS 文件夹里面存放着应用真正需要的可执行文件。Resources 文件夹里则包含资源文件，比如图标、图片、本地化文件以及其他应用会用到的文件。Frameworks 文件夹里包含应用所依赖的库和框架。有些应用可能还会包含用于存放插件、辅助工具或其他组件的文件夹。但应用包里最重要的文件是这个 Info.plist。这个文件告诉 macOS 一些重要信息，比如应用的名称是什么，真正的可执行文件在哪里，Finder 应该显示哪个图标，应用能打开哪些文件类型，它需要哪些权限或功能，以及它的版本号是多少。换句话说，在 macOS 中，应用包内的 Info.plist 文件会告诉操作系统许多关于该应用程序需要了解的信息。

每当 Finder 发现一个以点 app 结尾的目录时，它就知道应该把这个目录当做一个应用包来处理，并查看其内部，以确定如何显示和启动该应用。所以当我们通过将应用拖入应用程序文件夹来安装它时，我们拖动的不仅仅是一个图标，我们拖动的是一个完整的应用包，一个装满资源的目录，这些资源是应用程序和操作系统为了在桌面环境中让该应用正常显示和运行所必需的。而这是一个非常重要的点。这种抽象之所以成为可能，是因为 Finder 和桌面本身并不是内核，它们是用户空间的程序。它们仍然是操作系统体验的一部分，但它们的工作是将许多底层的复杂性对用户进行抽象化。一个 Unix 终端并不会自动理解一个点 app 目录是一个应用包。

如果我们想从 macOS 的终端打开一个点 app 的应用，我们需要使用 open 命令，并将该应用包作为参数传递过去。这个命令并不会直接执行点 app 这个目录，而是只是终端像 Finder 那样打开这个应用包，通过访问包内的 Info.plist 文件，确定真正的可执行文件，然后告诉内核去运行那个文件。我想这回答了本视频的主要问题，但很自然你现在可能会想，那 Windows 呢？大家都知道，在 Windows 上安装应用通常需要运行一个安装程序。Windows 也有专门的目录来存放应用文件，大多数现代应用放在 Program Files，而较老的三十二位应用如果运行在六十四位 Windows 上，则放在 Program Files (x86)。那么为什么不能像把应用包拖进应用程序文件夹那么简单呢？

如果我们同时从终端和 Windows 资源管理器打开这个目录，就能发现一些重要的事情。两者都将这些应用显示为文件夹，所以我们首先可以得出结论，Windows 不像 macOS 那样设计来识别应用包。Windows 不会看到一个应用文件夹就说这是个应用包，所以我要把它显示为一个应用图标。再解释为。什么安装程序在 Windows 上如此常见之前，我们先来探索其中一个应用文件夹。我们以 Firefox 为例。正如我们之前解释的，一个应用通常不仅仅是作为一个可执行文件发布的，它还需要动态链接库、配置文件、资源文件、插件以及其他资源，这些在这里都能清楚的看到。那么，如果你是那种注重细节的人，你可能会注意到这里有个有趣的地方。你注意到了吗？如果没有，让我在终端列出这个文件夹的内容来帮你一下。还是没发现？

这里的这个文件是一个可执行文件，但 Windows 资源管理器却为它显示了一个专门的图标，而这就是关键区别之一。在 macOS 中，Finder 会根据应用包的内部结构以及 Info.plist 中存储的信息来显示整个 .app 包对应的图标。而在 Windows 中，可执行文件本身就可以包含图标、版本信息以及其他元数据这类资源。所以当资源管理器找到一个 .exe 文件时，它可以直接显示该可执行文件中嵌入的图标。你可以自己测试一下，只要把这个文件复制到别的地方就行了。无论你创建多少个副本，或者把它们粘贴到哪里，Windows 都会一直显示同样的图标，因为这个图标是跟着可执行文件走的。但是可执行文件并没有包含 Windows 需要了解的关于该程序的所有信息。比如说，这个应用程序能打开哪些类型的文件？

它是否应该是某些文件类型的默认程序？它应该如何在开始菜单中显示？或者它应该如何被卸载？Windows 中很多系统级的应用程序配置都存储在一个叫做 Windows 注册表的东西里，它基本上是一个由操作系统和应用程序共同使用的集中式数据库。这个数据库帮助 Windows 记录已安装的应用程序、卸载信息、文件关联、默认程序、上下文菜单项、应用程序路径以及许多其他的系统集成信息。而这带来了一个非常重要的影响，Windows 并不会像 macOS 那样通过扫描一个文件夹并从一个名为 Info.plist 的文件中推断出所有需要的信息。相反，Windows 希望所有这些信息都存放在注册表中。这意味着在 Windows 将一个应用程序完全识别为已安装的程序之前，必须有某种机制用这些新信息来更新系统。

这就是 Windows 应用程序通常使用安装程序的主要原因之一。安装程序会在 Program Files 中为应用程序创建一个新文件夹，并将捆绑文件复制到那里，但它还会将应用程序与系统的其余部分集成，更新注册表，并创建快捷方式以便在桌面上显示该应用。所以如果你正在使用 Windows，下次安装应用时，你大概不会错过安装过程中那个更新组件注册的步骤。这就是 macOS 和 Windows 在安装过程上的不同之处。在 Windows 上，安装程序不仅需要将应用程序放在磁盘的某个位置，还需要将该应用程序与操作系统的其余部分连接起来。对于 Linux 用户，我有个坏消息，你们喜欢的那句话在这种情况下就变得非常烦人了。

如果 Linux 只是一个内核，那么不同的 Linux 发行版就是将这个内核与大量不同的用户空间程序组合而成，这些程序都是根据不同的目标和理念挑选出来的。从技术角度。讲，它们共享同一个内核，但它们是不同的操作系统。请记住，内核并不真正关心已安装的应用程序，这个概念主要属于桌面环境、文件管理器和其他用户空间组件。那么，如果不同的发行版基于不同的理念，使用不同的桌面环境构建，我们又怎么能指望它们在这方面兼容呢？令人惊讶的是，它们是兼容的，大部分情况如此。大多数 Linux 桌面环境遵循一种共同的约定，叫做 XDG 桌面入口规范，它最初来自 freedesktop.org，这是一个协作项目，旨在创建开放的规范和软件，以提高 Linux 桌面环境之间的互操作性。

然而，在 Linux 上真正的噩梦不是桌面入口，而是分发方式。有不同的包管理器，不同的包格式，以及成千上万种打包应用程序的方法。每个发行版的维护者似乎都有自己的首选方案。在这里解释所有这些会让这个视频延长二十分钟，所以我们会在未来的节目中讨论这个问题。现在我只想分享一下我在 Windows 和 macOS 之间更倾向于哪种方法。你可能会惊讶的发现，我最喜欢的是 Windows 的做法。明确的说，我并不讨厌 macOS 的做法。正如我之前所说，一旦你理解了当你把那个图标拖进应用程序文件夹时实际发生了什么，这多少就说得通了。但恰恰就是在这里出现了第一个问题，也就是应用程序文件夹。在 Windows 上，安装程序通常会显示应用程序文件将被写入的位置，如果你不喜欢那个位置，通常可以自由选择另一个。

这是可行的，因为安装程序可以简单的将你选择的任何位置提交给注册表，而 Windows 仍然会知道应用程序在哪里。而在 macOS 上，通常不是这样的运作方式，你其实没法选择其他位置。据我所知，macOS 只在这些目录中寻找应用包。遗憾的是，我无法给出 macOS 为何只使用这些特定位置的明确答案。讽刺的是，尽管 macOS 的内核是开源的，但作为完整操作系统的 macOS 却不是。但我最好的猜测是，这样做主要是为了便于发现，为了避免像不停扫描整个磁盘来寻找应用包，并在启动台显示它们这样的问题，macOS 期望应用存放在几个特定的位置，这样系统只需扫描那些已知的目录，而不用到处搜索。总之，macOS 用户常认为安装应用直观又简单，只需拖拽就可以了。对于很多应用来说确实如此。

但接着我们遇到了另一个问题，有些应用不是单独分发的，它们是作为套件的一部分分发的，比如微软 Office 或 Adobe 应用。在这些情况下，或者当应用需要下载安装系统范围的动态库或其他应存放在包外的共享组件时，你通常终究还是得运行安装器，否则你就得手动把多个应用包和支持文件拖到不同的位置，这太荒唐了。所以呢，我觉得这充分证明了，有时候安装程序和卸载程序就是避不开的。
