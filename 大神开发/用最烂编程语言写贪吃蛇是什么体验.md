你还有一个光标初始时指向第一个数字。你可以使用这两条指令来向右或向左移动光标。你可以使用加号和减号对当前选中的数字进行加一或减一操作。逗号用于每次读取一个用户输入符号，点号用于输出一个符号。最后方括号表示循环，任何代码都会重复执行直到选中的值变为零。没错，这就是全部了。恭喜，你已经成功学会了一整门编程语言。好的，我们已经了解了这些基础组件，但怎么用它们来做游戏呢？要做到这一点，我们首先需要一个屏幕。我写了一个程序，能将前二百五十六个单元格可视化为像素。这意味着，例如，如果我们增加第一个单元格的值，第一个像素就会变亮。如果我们对前面几个单元格做同样的操作，就能点亮不同的像素。这样一点点地，我们就能开始构建一整幅图像了。从技术上讲，屏幕不一定非得是十六乘十六的，但这种尺寸确实能让游戏开发变得更简单。

BF 使用八位数值，这意味着你能得到的最大数字是二百五十五，超过这个数值就会回滚到零。同样，从零减去一也会变成二百五十五。一个十六乘十六像素的屏幕正好有二百五十六个像素，这意味着我们可以只用一个单元格来存储玩家位置之类的信息。而根据这个位置实际绘制玩家，就开始变得有意思了。假设我们把位置存储在第二百五十六个单元格，就在像素缓冲区的外面。要在指定位置绘制玩家，我们需要一种方法将这个数字转换成一系列光标移动指令。直接硬编码这些肯定不行，因为那样你就得修改代码才能移动玩家。我对此的解决方案是使用一种我称之为滑翔器的东西。它是一个循环，里面只有一条箭头指令，其作用是让光标持续朝一个方向移动，直到遇到零为止，这时循环就会停止。

这实际上重新定义了问题，因为现在我们只需要用正值填充一些连续的单元格区域，这比直接跳转要可行得多。我这里用的代码会先递减位置计数器，然后滑入像素缓冲区，增加链条末端的一个值，再滑回来。如此反复操作就能得到一连串的一一直延伸到玩家应该在的位置。现在如果你再用一组滑翔器，就能到达这条链条的末端，在那里画一个纯白色像素，然后滑回来，同时沿途清理掉这些临时数据。是啊，这可不是游戏编程通常的样子。到这里你可能会说，这有什么大不了的？我们很久以前就已经在绘制像素了。但最酷的是我们现在可以把所有绘图代码放在单独的循环里，每次循环运行时改变位置，这样像素就开始移动了。现在还不完全是贪吃蛇，但我们正在接近目标。我们现在需要的是一种控制玩家的方法。我之前提到过。

逗号运算符可以读取用户输入的符号，但在我的引擎中，我对它做了些微调，让它能返回控制器输入的位掩码。简单说，当我使用逗号时，会得到一个数字，这个数字对应某个按钮或多个按钮的组合。需要说明的是，我没有添加任何新功能，这一切在原生 BF 语言中仍然可以实现。实际上，我只是把这些输入重新映射，让游戏操作更直观而已。所以有了这个和一大堆 BF 代码，我终于可以开始在屏幕上移动像素了。至于这算不算游戏，就得看你有多容易满足了。或许让这一切以及游戏其他部分成为可能的基本概念，就是条件语句。在大多数编程语言中，这些都是类似 x 是否等于五这样的表达式，或者 a 是否小于 b。但哦，不不，哦不行，这可是 BF 语言，我们可没这么高级的功能。我们只有几个自增和循环指令。不过我们并没有因此退缩，还是让它实现了功能。

仔细想想，BF 语言的循环有点像一个条件判断，问的是这个数字是否不等于零。如果是，它就会执行并重复循环内的代码。如果不是，它就会向前跳转并跳过这个循环。乍一看这似乎是条死胡同，但你接着看，如果我们在循环前加上几次减法，现在就能开始判断类似这个数字是否不等于三这样的问题了。因为这基本上就相当于把数字三移到等式的另一边。我们还可以嵌套循环来判断类似这个数字是不是不等于三或四这样的问题。虽然看起来我们只能判断不等于的情况，但其实也有办法解决这个限制。你看，我们有一个总能运行的循环，它有一个专用的标志位，数字会被设为非零值。不管它前面是什么数字，这个循环总能通过，因为它实际上检查的是另一个完全不同的数字。但记住，我们有能力排除任何数字，所以我们可以在这个循环前面再加一个循环，用来检查光标指向的数字是否不等于三。

如果是的话，它会翻转那个标志位，这样对于任何不等于三的数字，第二个循环就会被跳过。一下子理解这么多可能有点困难，但本质上这意味着我们可以开始把一些基本条件组合起来，比如左键方向键是否被按下，如果是的话就改变玩家的位置。但说实话，没有目标的话，这根本算不上游戏。那我们试着再加一个稍微暗一点的像素吧。在贪吃蛇里，这就是苹果，但这有点蠢，因为蛇其实不吃苹果。所以咱们私下说这个游戏的主角其实是一只非常饥饿的毛毛虫。不管怎样，如果我们直接复制玩家渲染代码，一开始似乎是能行的，直到你走到它的右边。这是因为我们在屏幕上滑动的方式导致的。在这种情况下，玩家会先被绘制出来，然后苹果的渲染程序必须划过它才能在之后被绘制。但苹果无法真正区分自己放置的标记和已经存在的像素，所以玩家实际上会把苹果向左偏移一个单元格。

我不知道有没有好的解决办法，至少我还没想出来，而且就算我想出来了，我也不会回来更新我的渲染流程。重构一个用 BF 写的程序可不是件小事。我的解决办法挺蠢的，但确实管用。我只需检查玩家坐标是否小于苹果坐标，如果是就减一。这种方法之所以烂，是因为你现在每添加一个新像素都得这么做，这让代码越来越难搞。抱歉，失陪一下，差点就被搞心态了。最后我们需要一种方法，在苹果被吃掉后随机生成它的位置。BF 本身没有任何随机化函数，但就像许多经典的 NES 游戏一样，我们可以通过使用每帧递增的计时器来模拟随机性。我的引擎以六十 fps 运行这个游戏，而且每次捡苹果时要预测计时器的精确值会相当困难，所以这基本上就是随机的了。说到帧率，在六十 fps 下玩家移动速度太快，操作起来。其实挺难的。

我之前没提过，不过我重新利用了通常用于打印单个字符的点运算符，让它转而向运行时发出帧缓冲区已准备好绘制的信号。我们可以通过连续绘制多个相同的帧来减慢游戏速度，但这会让移动操作的响应感大打折扣。所以我会在每帧将一个计数器递增三十二次，只有当计数器归零，也就是每八帧一次时才更新玩家的位置。这样一来，我仍然可以在每一帧读取玩家输入，但处理输入的频率会慢很多。好了，我们已经做出了一个相当不错的吃豆游戏，但这还不是贪吃蛇。尾巴在哪儿呢？是啊，不，就，就是尾巴在哪儿呢？其实绘制一节尾巴和绘制一个落后一帧的玩家差不多。把尾巴弄长才是麻烦事儿，我其实拖延了超久，结果反而先实现了八位色彩。这其实没那么难。我没有将每个像素绘制为亮度值，而是把帧缓冲区中的数字当作 RGB 三三八颜色值来处理。这基本上意味着特定的数字对应特定的颜色。

所以要让玩家显示绿色，苹果显示红色，我只需要在绘制像素时使用那些特定的数字就行。要改变背景颜色，我只需给帧缓冲区中的每个像素都加上某个数字就行。这确实也会搞乱现有像素的颜色，但这是可以弥补的。好了，不说这个了。我们确实需要一条尾巴。有两种实现方法。我们要么写一个绘制单个尾巴像素的模板，然后大量复制粘贴，要么想办法实现一个数组。而且不管我选哪种方案，由于我的渲染流程很烂，每个尾巴段都必须考虑其他所有尾巴段的位置才能正确排序。这里所谓的优雅解决方案，如果这也能算的话，就是使用某种数组结构。记住，我们无法直接让 BF 获取第 N 个尾巴段。我们之前在帧缓冲区上解决过类似的问题，但那是针对向空白画布写入内容的情况，这次情况正好相反。一种方法是预留所需内存的两倍空间，并将坐标填充到后半部分。

要从特定索引获取元素，可以将整个数组向后移动该索引的量，然后定位到第一个坐标原来的位置。现在那里就保存着你想要的数组元素，这本该是一种更优雅、更巧妙、更动态的方法，但我的代码并没有这么做。我只是写了一些 JavaScript 代码，它会获取绘制单个尾巴段的模板，然后复制粘贴十六次。这是种又蠢又臭的方法，但它确实有个好处，速度快得多。尤其是如果不用这种方法，你就得把整个数组移来移去无数次，才能交叉比较所有尾巴像素的坐标。这一点可能真的很重要，因为即便是用这种方法，简单的方法，我的毛毛虫在吃了太多苹果后也开始变得不太对劲了。解决这个问题的办法就是优化解释器。例如不必逐条执行单个加号指令，你可以提前统计它们的数量，然后存储要添加的确切数值。同样不必一步步执行整个循环来寻找开头或结尾，我们可以提前计算括号之间的距离。

这实际上就是现实世界中一些基本压缩系统的工作原理。只需做这样几处改动，即使尾巴完全展开，也不会再有任何卡顿了。你甚至可以通过将这种二进制格式转换为 C 代码，然后将其编译成能在处理器上原生运行的实际机器码来进一步优化性能。但我觉得我们的游戏不需要做到那一步。在整个项目中，实现咬到尾巴的游戏结束状态可能是最简单的部分了。你要做的就是创建一个无限循环，一遍又一遍地绘制相同的帧。现在我很想说我们终于完成游戏了，但接下来是最可怕的部分，调试 BF 代码。存在不少图形错误，游戏玩法上的错误就更多了。举个例子，如果你斜向移动，就会开始跳过像素点，运气好的话基本能让你穿过自己的尾巴。我通过将斜向移动改为分步移动修复了最后这个问题。简单来说，我设置了一个值，每次处理移动时它就在零和非零之间切换。

这样一来，斜向移动时就不会同时修改两个坐标，而是根据这个标志选择一个方向进行移动。这样看起来也更符合预期效果。因为我也不能让尾巴无限变长，所以你可以利用屏幕边角的环绕效果来做到这一点。这有点像无限刷分的漏洞。为了解决这个问题，我添加了这个蓝色像素，碰到它就会死亡。你可以把它当成一种毒苹果。等一下。没错，我确实也在运行时添加了声音效果。运行点运算符时选择的地址通常用于指定要打印的字符，但在这里它指定了在该帧剩余时间内要播放的 MIDI 音符。在我的游戏中，我为拾取苹果添加了基本的 B 声音效，并为玩家死亡添加了三音符序列。我觉得这已经是能做到的最好程度了。
