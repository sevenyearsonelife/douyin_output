看完这期视频，你将彻底掌握 TCP 协议，不管是网络故障排查还是面试提问，都能从容应对，游刃有余。今天干货有点长，可以先收藏。在正式开始前，我们先明确一个基础问题：TCP 在计算机网络模型中的位置。在 OSI 七层模型里，它位于第四层，传输层。TCP 又叫传输控制协议，它的功能很简单，在不可靠的 IP 网络层之上，搭建起一个可靠、面向连接的传输通道。大家一定要记住这三个核心关键词，缺一不可。第一，面向连接，通信前必须先建立起专属的逻辑通路，就像打电话前要先拨号接通一样。第二，可靠传输，全程保证数据不丢失、不混乱、无错误，稳稳送到目的地。第三，字节流，TCP 不会区分数据的具体结构，只会把所有数据看作一连串无差别的字节流来处理。要理解 TCP 协议，首先得搞懂它的数据包长什么样。

一个完整的 TCP 报文段由头部和数据两部分组成，其中头部通常是二十个字节，里面封装了 TCP 工作所需的所有控制信息。其中重要的一些信息有：首先，源端口和目的端口各占两个字节。大家可以这样理解，IP 地址解决了数据发给哪台电脑的问题，而端口号则解决了数据发给电脑上哪个应用进程的问题，二者配合才能精准投递。其次，序列号占四个字节。TCP 是字节流传输，每一个字节都会分配唯一编号，序列号就是本报文段所发数据的第一个字节的序号，核心作用是解决网络包乱序的问题。第三，确认号又叫 ACK 号，同样占四个字节，它表示我期望收到你下一个报文段的第一个数据字节的序号。如果确认号是 N，就意味着前 N 一个字节我已经全部收到，下次请发序列号为 N 的数据，这也是 TCP 实现可靠传输的核心关键。

第四，标志位 flags，这里有几个关键比特位，直接决定 TCP 的工作状态，感兴趣的可以详细看看。最后，窗口大小，它的作用是告知对方我的接收缓冲区还能容纳多少字节的数据，是 TCP 实现流量控制的基础，避免接收方因缓冲区满而丢失数据。理解了 TCP 协议报文头部的五个核心字段，你就能轻松看懂 TCP 网络抓包，真正掌握 TCP 的交互语言。搞懂了报文格式，接下来我们看 TCP 连接的建立过程，也就是大家常听的三次握手。很多人以为这只是简单的打招呼，其实不然，它的本质是通信双方互相交换确认各自初始序列号，为后续可靠传输打下基础。三次握手的具体过程很清晰，大家记好这三步。

第一步，客户端发送 SYN 报文，客户端随机生成一个初始序列号 X，填入 TCP 头部的序列号字段，同时将报文头的 SYN 标志位置为一，此时客户端进入 SYN 下划线 sent 状态，等待服务端响应。第二步，服务端发送 SYN 加 ACK 报文，服务端收到客户端的 SYN 报文后，会随机生成自己的初始序列号 Y，然后构造一个包含 SYN 和 ACK 两个标志位的报文，SYN 位置一，ACK 位置一，序列号字段填入 Y，确认号字段填入 X 加一，意思是我已经收到你的序列号 X，下次请发 X 加一，此时服务端进入 SYN-RCVD 状态。

第三步，客户端发送 ACK 报文，客户端收到服务端的响应后，会先检查确认号是否为 X 加一，确认无误后，再次发送确认报文，将 ACK 位置为一，序列号设为 X 加一，确认号设为 Y 加一，意思是我也收到你的序列号 Y，下次请发 Y 加一。到这里，三次握手就完成了，TCP 连接正式进入 established 已建立状态，双方可以开始传输数据了。这里有一道经典面试。题大家一定要掌握，为什么 TCP 连接建立必须是三次握手？核心原因是只有经过三次握手，才能双向验证双方的发送能力和接收能力，同时确保双方的初始序列号都被对方确认。我们可以做个假设，如果只有两次握手，客户端发送 SYN 报文，服务端回复 SYN+ACK 报文，此时客户端会认为我能发也能收，但服务端只知道我能收，却不确定客户端是否收到了自己的响应。

一旦服务端的 SYN+ACK 报文丢失，服务端就无法确认客户端是否具备接收能力，后续传输就会出问题，所以两次握手行不通。而四次握手又完全多余，因为三次握手已经能让双方的状态达成一致，多一次交互只会浪费时间和资源。数据传输完成后，就到了 TCP 连接的关闭环节，也就是四次挥手。很多人会疑惑，为什么建立连接是三次，关闭连接却要四次？核心原因是 TCP 是全双工通信，客户端说我不发数据了，只代表客户端到服务端的发送通道关闭，而服务端可能还有未发送完的数据需要继续传输。四次挥手的具体过程我们一步步拆解。第一步，客户端发送 FIN 报文，序列号为 U，此时客户端进入 FIN-WAIT-1 状态，相当于告诉服务端我没有数据要发了，申请关闭我的发送通道。

第二步，服务端回复 ACK 报文，确认号设为 U+1，此时服务端进入 CLOSE-WAIT 状态。这里要注意，此时 TCP 连接处于半关闭状态，客户端不能再发送数据，但还能接收服务端发来的数据，服务端则可以继续发送未完成的数据。第三步，服务端发送 FIN 报文，等服务端把所有数据都发送完毕后，就会发送 FIN 报文，序列号为 W，此时服务端进入 LAST-ACK 状态，告知客户端我也没有数据要发了，准备关闭连接。第四步，客户端回复 ACK 报文，确认号设为 W+1，此时客户端进入 TIME-WAIT 状态，服务端收到这个 ACK 报文后，就会彻底关闭连接。

这里有个重点知识点，TIME-WAIT 状态也常被称为 2MSL 状态，其中 MSL 是 Maximum Segment Lifetime 的缩写，也就是最大段生存期，指的是任何一个 TCP 报文段在网络中被丢弃前所能存在的最长时间。当 TCP 执行主动关闭，发送完最终的 ACK 报文后，连接必须进入 TIME-WAIT 状态，并持续两倍于 MSL 的时间才能彻底释放资源。又一个高频面试题来了，为什么客户端发完最后一个 ACK 后不能直接关闭，还要进入 TIME-WAIT 状态等待两倍 MSL？核心有两个原因，大家记牢。原因一，保证最后一个 ACK 报文能可靠到达服务端。客户端发送的最后一个 ACK 报文有可能在网络中丢失、损坏或超时，这会导致服务端重新发送 FIN 报文。

如果客户端发送 ACK 后立刻释放资源，就无法处理服务端重传的 FIN 报文，导致服务端一直卡在 LAST-ACK 状态，无法正常关闭连接。原因二，防止旧连接的残留报文干扰新连接。四次挥手完成后，虽然理论上连接已经断开，但网络中可能还残留着上一次连接的报文。如果客户端立即释放资源，又用同一个四元组源 IP 加源端口加目的 IP 加目的端口建立新的 TCP 连接，那些残留的旧报文就可能被当做新连接的数据处理，从而引发不可预估的错误。而等待两倍 MSL 的时间，能确保网络中所有残留的旧报文都被丢弃，避免干扰。好了，今天的内容就总结到这里，我们主要讲解了 TCP 报文的格式，头部五个核心字段的作用，以及 TCP 如何通过三次握手建立连接，四次挥手关闭连接，完整梳理了 TCP 连接的整个生命周期。
