如何设计一个百万级消息推送功能？很多人第一反应可能是，不就是循环调推送接口吗？一万个用户就循环一万次，一百万个就循环一百万次。逻辑上没错，但真这么干，系统活不过三分钟。为什么？因为同步循环调用请求会超时，内存会爆，下游服务会被你打挂。百万级推送的核心难点就三个：怎么维持百万条长连接，怎么把消息快速分发出去，怎么保证不丢不重。先看连接层，传统 H T T P 请求响应完就断开，服务器没法主动找客户端，所以推送通常用长连接，比如 Web Socket 或者基于 T C P 的自定义协议。一台服务器能维持多少连接？这取决于内存和文件描述符。每个连接在内核里占一个 socket，在应用层占一块会话内存。

假设每个连接消耗几十 K B，一台八 G 内存的机器大概能撑十万左右，所以百万连接至少需要十几台接入机，并且要用网关层做负载均衡，把连接分散开。这里的关键是接入机要无状态，会话信息不能只存在本地，否则某台机器挂了，上面的连接全断，用户就得重连。连接建立之后，用户和接入机的映射关系得存起来，通常用一个中心化的路由表，比如 Redis 或者专门的服务，记录用户 I D 对应哪台接入机。当业务系统要推消息时，先查路由表，找到用户所在的接入机，再把消息转发过去。如果用户量很大，路由表本身也会成为瓶颈，所以一般会按用户 I D 分片，每片独立查询。接下来是消息分发，如果一条消息要发给一百万个人，业务系统不可能逐个查路由再逐个发。常见做法是引入消息队列，比如 Kafka。

业务系统把消息扔进一个主题，多个推送工作节点从队列里消费，每个节点负责一部分用户，这样就把串行的百万次发送变成了并行的多节点处理。队列还起到削峰作用，比如突发新闻推送，瞬间百万条消息涌入，队列先缓冲，工作节点按自己能力慢慢消费，不至于把接入机打垮。但这里有个问题，一条消息要发给百万用户，是每个用户一条队列消息，还是一条消息广播给所有工作节点？前者叫扇出，消息量大但逻辑简单；后者叫广播，队列压力小但每个节点都要处理全量用户。实际中常结合，按用户分片，每个分片一条消息，工作节点只处理自己分片的用户。再往下是投递可靠性，消息进了队列不代表一定送到，网络可能断，客户端可能不在线，所以要有确认机制。接入机把消息发给客户端后，客户端回一个 A C K，接入机收到 A C K 才认为投递成功，如果没收到就重试或者存离线消息。

离线消息通常存数据库或对象存储，等用户下次上线再拉取。这里要小心重复投递，所以消息要带唯一 I D，客户端做去重。还有一个容易被忽略的点，心跳和连接保活。长连接如果长时间没数据，中间的网络设备可能把它断掉，所以客户端要定期发心跳包，服务器也要检测心跳，超时就清理连接，释放资源。百万连接下，心跳包本身也是流量，得控制频率，比如三十秒一次。最后是水平扩展，当用户从一百万涨到五百万，系统能不能线性扩容？关键在于每一层都要能加机器，接入机加机器，路由表分片扩容，队列加分区，工作节点加消费者，只要没有单点，扩容就是加资源的事。

总结一下，百万级推送不是靠一台超级服务器，而是靠分层，接入层管连接，路由层管寻址，队列层管削峰和解耦，工作层管并行分发，存储层管离线消息，每一层都无状态可扩展，再配合确认和去重机制，才能做到既快又不丢。理解了这个框架，你就能根据自己业务的在线量、实时性要求和可靠性要求去选择合适的技术组合。
