MySQL 同步到 Elasticsearch 的方案应该如何选择？这期内容会讲清四种主流方案：双写、异步消息、Binlog 订阅以及开源同步工具。它们不是四种并列的选项，而是对应四种完全不同的取舍。先说第一种，应用层双写。意思是业务代码里同时写 MySQL 和 Elasticsearch。常见的写法是先在业务服务里完成数据库写入，再调用 Elasticsearch 的索引接口更新文档。这个方案最大的优点是直接好理解，也不需要引入额外中间件。但它的缺点非常明显，两次写不在同一个事务里，一旦 Elasticsearch 写入失败，而 MySQL 已经提交，两边就不一致了。更麻烦的是代码里到处散落着同步逻辑，字段一改所有写入点都要跟着改。

所以双写通常只适合数据量小、变更少、对一致性要求不高的早期项目，或者作为临时过渡方案。第二种是异步消息解耦。业务代码只负责写 MySQL，同时发一条消息到消息队列，比如 Kafka 或 Rocket M Q，由独立的消费服务负责更新 Elasticsearch。这个方案把同步职责从业务服务里拆了出来，业务代码干净很多，而且消息队列天然支持削峰和重试。但它依然有一个根本问题，写库和发消息同样不在一个事务里，如果数据库提交成功但消息没发出去，数据就丢了。要缓解这个问题可以用事务消息或本地消息表，让发消息和业务写库绑定在同一事务里，代价是复杂度上升。异步消息适合对实时性要求高、写入量偏大，并且团队已经具备消息队列运维能力的场景。第三种是订阅 Binlog。

Binlog 是 MySQL 用来记录所有数据变更的二进制日志，任何一次插入、更新、删除都会按顺序写进去。订阅 Binlog 的思路是不让业务代码参与同步，而是用一个组件把自己伪装成 MySQL 的从库，持续接收 Binlog，解析出变更事件，再转换成 Elasticsearch 的写入请求。这个方案最大的优势是业务零侵入，代码完全不用改，而且因为 Binlog 本身就记录了提交后的变更，天然避免了库写成功但消息没发出去的那类不一致。不过它也不是没有代价，需要解析 Binlog，处理表结构映射，应对大事务和 D D L 变更，运维复杂度明显更高。这个方案适合中大型系统，尤其是业务代码多、改造成本高，又需要较高一致性的情况。第四种是直接使用成熟的开源同步工具，最常见的是 Canal 和 Debezium。

Canal 是阿里开源的项目，专门模拟 MySQL 从库订阅 Binlog，再通过配置把变更推到 Elasticsearch，国内使用非常广泛。Debezium 则基于 Kafka Connect 把数据库变更捕获成标准事件流，适合已经深度使用 Kafka 的团队。用现成工具的好处是不用从零实现 Binlog 解析，社区踩过的坑大多已经修掉。但要注意这些工具并不是开箱即用，表结构映射、字段类型转换、嵌套文档构建、失败补偿这些仍然需要配置和二次开发，它们本质上是对第三种方案的工程化封装。怎么选？关键看三个条件：业务代码能不能改，团队能承受多高的运维复杂度，以及允许的最大延迟和一致性偏差是多少。如果只是小项目，双写最快；如果追求业务解耦又能接受消息中间件，异步消息合适；

如果业务代码动不了，又希望同步尽量可靠，Binlog 订阅或 Canal、Debezium 是更稳妥的方向。现实里很多团队会先双写起步，等数据量和一致性要求上来以后，再迁移到 Binlog 方案。
