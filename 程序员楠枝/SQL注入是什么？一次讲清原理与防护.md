什么是 SQL 注入？简单说，它是一种利用网站数据库查询漏洞来执行攻击者意图的技术。攻击者把恶意的 SQL 代码混进正常输入里，如果网站没有严格检查这些输入，数据库就可能把恶意代码当成命令执行，这会导致数据泄露、账号被盗，甚至整个数据库被删掉。今天我们要讲清楚三件事：SQL 注入到底是怎么发生的，常见的攻击方式有哪些，以及开发者和普通用户分别该怎么防。先理解正常查询是怎么工作的。假设一个登录页面，用户输入用户名和密码，网站后台会拼出一条查询语句，意思是去数据库里找一条记录，用户名和密码都匹配才算登录成功。正常情况下，用户输入什么查询就按字面意思去匹配。问题就出在拼接方式上。如果后台直接把用户输入的内容塞进 S Q L 语句，没有做任何过滤，那么输入的内容就可能改变整条语句的结构。最经典的例子是登录绕过。

攻击者在密码框里输入一串特殊内容，比如一个单引号加上或者一等于一。单引号在 SQL 里用来标记字符串的边界，攻击者输入的单引号会提前闭合原本的字符串，后面再跟上一段永远为真的条件。整条查询就变成了去找一条记录，用户名是某个值，密码是空或者一等于一。因为一等于一永远成立，数据库就会返回第一条匹配的用户记录，攻击者不需要知道真实密码就能登录进去。还有一种更危险的情况，攻击者利用分号一次执行多条语句。分号在 SQL 里表示一条语句结束，可以接着写第二条。如果数据库允许一次执行多条命令，攻击者可能在登录请求后面追加一条删除表的命令，一旦执行，整个用户表可能被清空。这类攻击之所以严重，是因为它不只是绕过验证，而是直接操作数据库本身。联合查询注入是另一种常见手法。

攻击者利用联合查询把两张表的结果拼在一起，从而读取本不该看到的数据。比如一个新闻页面本来只查文章标题，攻击者修改参数，让查询额外返回用户名和密码。如果网站把查询结果直接显示在页面上，攻击者就能从页面内容里读出敏感信息。即使页面不直接显示，攻击者还可以用盲注的方式，通过观察页面响应时间或返回内容是否有差异，一个字符一个字符地猜出数据。SQL 注入的根本原因是程序把数据和代码混在了一起。用户输入本应只被当做数据，但因为没有正确分隔，数据库把它当成了代码的一部分。这就好比你在表格里填名字，结果填的内容里包含一句命令，而处理表格的系统居然执行了那句命令。防止 SQL 注入的关键就是让数据永远是数据。对开发者来说，最有效的办法是使用参数化查询，也叫预编译语句。

它的思路是先确定 SQL 语句的结构，把用户输入的位置留成占位符，再把输入作为参数单独传进去。数据库明确知道参数只是数据，不会把它当代码解析。无论用户输入什么奇怪字符，都不会改变语句结构。这是目前公认最可靠的防护方式。另一个重要原则是最小权限，数据库账号不应该拥有超出业务需要的权限。比如一个只负责查询的页面，不应该使用能删表的管理员账号连接数据库。即使某个查询点被注入，攻击者能做的事也会被限制在账号权限范围内。同时，对输入做白名单校验也有帮助，比如数字参数就只允许数字，但这只能作为辅助手段，不能替代参数化查询。对普通用户来说，虽然无法直接修复网站漏洞，但可以降低自己的风险。第一，不要在不确定安全性的网站上提交真实密码，尤其是重要账号的密码。

第二，不同网站尽量使用不同密码，这样即使一个网站被拖库，其他账号也不受影响。第三，开启多因素认证，即使密码泄露，攻击者也很难直接登录。第四，定期检查账号是否有异常登录记录。判断一个网站是否可能存在问题，可以看一些信号，比如输入单引号后。页面报错或行为异常，可能说明输入被直接拼接进了查询。但这不是绝对的，现代网站即使没有漏洞，也可能因为其他原因报错。普通用户不需要主动测试，更重要的是保持警惕，不要因为网站看起来正常就放松对密码的管理。总结一下，SQL 注入是一种利用输入处理缺陷操纵数据库查询的攻击方式，它的核心问题是数据和代码没有分离。常见形式包括登录绕过、多语句执行、联合查询和盲注。对开发者，参数化查询是第一道也是最重要的防线，最小权限和白名单校验是补充。对普通用户，密码隔离和多因素认证是有效的自我保护。

理解了 SQL 注入的原理，你就会明白很多数据泄露事件并不是因为密码太简单，而是因为系统在最基础的输入处理上出了问题。
