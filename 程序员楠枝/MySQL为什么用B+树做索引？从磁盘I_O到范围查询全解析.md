为什么 MySQL 选择使用 B+树作为索引结构？先理解索引要面对的现实：MySQL 的数据是存在磁盘上的，磁盘读写比内存慢几个数量级，一次磁盘 I/O 大概要花几毫秒，而内存访问是纳秒级，所以索引设计的第一目标不是算法上更快，而是尽量减少磁盘 I/O 次数。磁盘读数据不是按字节读，而是按页读，InnoDB 里一页默认十六 K B，也就是说哪怕你只查一行，磁盘也会把包含它的整页数据读进来。所以索引结构必须配合页这个单位来设计。那为什么不用哈希表？

哈希表查找单个等值记录确实快，时间复杂度是 O1，但 MySQL 索引要支持的查询远不止等值查询，范围查询如 age 大于二十小于三十，排序如 order by price，前缀匹配如 name like 张百分号，哈希表全都无能为力，因为哈希值不保持顺序，所以哈希索引在 MySQL 里只作为内存引擎的辅助结构，不能作为主要的通用索引。为什么不用普通二叉搜索树？二叉搜索树每个节点最多两个子节点，数据多了树就很高，比如一百万条数据，平衡二叉树高度大约是二十左右，每个节点一次磁盘 I/O，查找一条记录要读二十次磁盘，太慢，而且二叉树节点只存一个键和两个指针，磁盘页利用率极低。真正要解决的是让每个磁盘页装更多节点，让树更矮。那为什么不是 B 树而是 B+树？

B 树已经是多路平衡查找树，每个节点可以存多个键和多个子指针，树高大幅降低，但 B+树在 B 树上做了两个关键改进。第一，B+树所有数据都放在叶子节点，非叶子节点只存键和指针，不存数据，非叶子节点能存放的键数量就大大增加。以一页十六 K B 为例，如果每个键加指针占二十字节左右，一个非叶子节点大概能存八百个键。假设一棵三层 B+树，第一层有八百个键，第二层每个节点再分八百个孩子，那第三层就能覆盖大约六十四万个叶子节点，每页能存若干条记录，所以两三层 B+树就能支撑上亿条记录的索引，查找任何一条记录，磁盘 I/O 次数基本就是树的层数，通常不超过三到四次。第二，B+树的叶子节点之间用链表串联起来，而且通常是双向链表，这让范围查询和排序变得极其高效。

比如查 age 在二十到三十之间的所有用户，只要先找到第一个符合条件的记录，然后顺着叶子节点的链表向后扫就行，不需要回到上层节点重新遍历，而 B 树的叶子节点之间没有这样的链接，范围查询必须在中序遍历中反复上下跳转，每次跳转都可能触发磁盘 I/O，性能就差很多。另外，B+树所有数据都在叶子节点，查询任意一条记录都要走到叶子节点，所以查询性能非常稳定，而 B 树中有些数据在非叶子节点，查到的路径可能短一些，性能会有波动。对于数据库这种需要稳定响应时间的系统，B+树的这个特性也很有价值。还有一个容易被忽略的细节是空间局部性，B+树的叶子节点按顺序排列，叶子页之间物理上往往也相邻，或者通过链表逻辑上连续，当执行范围查询时，顺序读取相邻页比随机读取快得多，因为磁盘顺序读不需要频繁移动磁头，固态硬盘也能利用预读机制。

所以 B+树不仅在逻辑上适合范围查询，在物理存储上也适合顺序扫描。那 MySQL 的 InnoDB 引擎具体是怎么用 B 树的？一张 InnoDB 表的主键索引就是一棵 B+树，它的叶子节点直接存放整行数据，所以你通过主键查询时，从根节点开始，经过两三次磁盘 I/O，就能在叶子节点拿到完整数据，这个索引也叫聚簇索引。而其他普通索引，比如你在 user name 字段上建的索引，它的叶子节点存的是主键值，不存整行数据，这叫二级索引。如果用 user name 查询。先走二级索引的 B 加树找到主键，再回主键索引的 B 加树查一次，整个过程叫回表。但也有些查询要的字段刚好都在二级索引里，那就不用回表，这叫覆盖索引。理解了 B 加树的结构，就能自然理解 MySQL 这些常见优化手段的逻辑。

B 加树还有一个重要能力是适应数据插入和删除。B 加树是平衡树，插入时如果节点满了就分裂，删除时如果节点太稀疏就合并，始终保证树高稳定。这个过程会带来一些写入开销，但对于以查询为主的业务，这个代价完全值得。而且 InnoDB 对分裂和合并做了很多优化，比如页分裂会尽量保留顺序，减少碎片。最后做个总结，MySQL 选择 B 加树，本质上是在磁盘 I O 受限、要支持范围查询和排序、又要保持性能稳定的多重约束下做出的最优解。哈希表只能等值查询，二叉树太高，B 树虽然矮但范围查询和顺序访问不如 B 加树。B 加树用非叶子节点只存索引，叶子节点存数据加链表连接的方式，把树高压到两三层，让范围查询可以顺序扫描，让每次查询的 I O 次数可控。

所以从磁盘页、查询稳定性、范围扫描三个方面看，B 加树都更贴合数据库引擎的真实需求。理解这一点，你就明白了为什么 MySQL 索引不是随便选一种树，而是经过充分权衡后的必然选择。
