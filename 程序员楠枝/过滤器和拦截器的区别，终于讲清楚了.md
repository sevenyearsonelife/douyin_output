过滤器和拦截器的区别是什么？我们先说清楚它们各自是什么。过滤器，英文叫 Filter，是 Java Web 里最外层的一道关卡，它工作在 Servlet 容器这一层，也就是说请求还没真正进到你的业务代码里，过滤器就已经可以动手了。你可以把它理解成小区门口的门卫，任何人进小区之前，门卫都可以先看一眼，登记一下，甚至直接拦下来。过滤器能拿到的信息，主要是最原始的请求和响应对象，比如网址、请求头、参数这些。拦截器，英文叫 Interceptor，工作在框架层，在 Spring 这个体系里，它比过滤器更靠里一层，请求已经通过了门卫，进了小区，走到了某一栋楼的单元门口，这时候拦截器才出现。拦截器能拿到的信息比过滤器更多，它已经能看到你的控制器方法是哪一个，甚至能在方法执行之前和之后分别做一些事情。

所以第一个关键区别就出来了，它们工作的层级不同，过滤器在 Servlet 容器层，拦截器在 Spring 框架层，这个层级差异直接决定了第二个区别，它们能做的事情范围不同。过滤器因为更靠外，它接触不到 Spring 容器里的很多细节，比如它不知道请求最终会交给哪个方法处理，也没办法直接拿到方法参数上的注解。而拦截器可以，它能拿到处理器对象，能知道方法签名，能在方法执行前后插入逻辑。第三个区别是它们的触发范围，过滤器是基于路径匹配的，你配置一个斜杠星号，所有匹配这个路径的请求都会经过它，不管是静态资源还是动态接口。拦截器则更精细，它可以在配置时排除某些路径，也可以针对具体的处理器做判断。而且拦截器天然支持更丰富的生命周期，它有三个关键节点，方法执行前、方法执行后、整个请求完成后。

过滤器虽然也有类似的前后逻辑，但它的颗粒度没有拦截器这么细。这里需要补充一个条件，过滤器并不是只能用在 Java Web 里，很多语言和框架都有类似过滤器的机制，比如中间件。但在中文技术语境里，当大家把过滤器和拦截器放在一起比较时，绝大多数情况都是在讨论 Java 的 Servlet Filter 和 Spring HandlerInterceptor。所以今天讲的结论主要建立在这个具体语境下。那为什么有了过滤器还要拦截器？因为它们解决的问题不一样，过滤器更适合处理横切在最外层的通用问题，比如字符编码、跨域设置、简单的权限校验、请求日志，这些事情和业务无关，越早处理越好。

拦截器则更适合处理与业务有一定关联的逻辑，比如登录态校验、权限判断、接口耗时统计、操作日志记录，这些逻辑需要知道请求具体要执行哪个方法，过滤器做不到。我们用一个具体场景来感受一下，假设用户要访问一个需要登录的接口，请求先到过滤器，过滤器做第一层检查，比如看看请求里有没有携带合法的令牌格式，如果没有，直接在最外层拒绝，根本不会让它进到框架里。如果格式没问题，请求继续走，进入拦截器。拦截器这时候可以去查缓存或者数据库确认，这个令牌对应的用户是不是真的存在，有没有被拉黑，有没有权限访问这个具体接口。如果权限不够，拦截器可以拒绝，并且返回一个更具体的错误信息。如果都通过了，请求才会真正进入控制器方法。这个流程里，过滤器做的是粗筛，拦截器做的是精查，粗筛追求快，精查追求准。

如果把所有逻辑都堆在过滤器里，过滤器会变得很重，而且它拿不到框架里的细节。如果都放在拦截器里，一些最基础的安全检查又做得太晚，所以实际项目里它们经常配合使用。最后还要提一下 A O P 切面，因为很多人会把这三者混在一起。A O P 是面向切面编程，它的工作层级比拦截器还要深，已经进入了 Spring 的 Bean 内部。拦截器主要拦截的是控制器方法，而 A O P 可以拦截任意一个 Spring Bean 的方法，包括服务层的方法。所以从能力范围来看，过滤器最窄，拦截器居中，A O P 最灵活，但从使用成本来看，过滤器最简单，拦截器次之，A O P 需要理解切点表。表达式和通知类型，学习成本最高。总结一下，过滤器和拦截器的区别，本质上就是工作层级、信息获取能力和适用场景的区别。

过滤器守在 Servlet 容器层，适合做最外层的通用处理；拦截器工作在 Spring 框架层，适合做与控制器方法相关的业务逻辑。理解了这个层级关系，你就能在合适的场景里选择正确的工具，而不是凭感觉随便挑一个。
