直播间点赞的后端设计，本质上是一场对高并发写入的驯服。很多人以为点赞就是数据库里加一个数字，但真实场景下，一个头部直播间每秒收到的点赞请求可以到几十万次。如果每次都去更新数据库，数据库瞬间就会被打垮。所以整个设计核心就一句话，把高频的计数操作从数据库里剥离出来，用内存扛流量，用异步做持久化。这篇我会从接口设计、Redis 计数、消息队列落库、防刷限流，到前端推送，一步步说清楚这套系统是怎么搭出来的。先说业务特点。直播点赞跟普通评论、下单不一样，它有很明显的特殊性，写多读极少，数据量巨大但内容极简。一个观众可能在一场直播里点几千次赞，服务端只需要记录一个总数，不需要存储每一次点赞的用户和时间。同时，用户对点赞数的准确性要求并不苛刻，看到一百万还是一百万零二十三，没有任何感知。

这个特性非常重要，它意味着我们可以暂时牺牲强一致性，换更高的吞吐和更低的延迟，只要最终别把数字写错，短时间少记一两次完全能接受。接下来是接口设计。点赞接口要尽量轻，不能像下单那样包一堆字段，通常只要一个直播间的 I D，用户身份从登录态的 token 里取。比如发一个 POST 请求到 /live/like，后端校验直播间存在，校验用户是真实登录的，然后执行加一操作，返回状态码。这里不需要把点赞后的总数放在每个接口的响应里，因为高并发请求返回太多数据只会增加网络消耗，观众看到的数字通常由另外的推送或者轮询机制来更新。同时，单独一个赞事件本身不需要幂等，因为它就是一个计数器加一操作，多点一次就是多一下，不像支付请求必须防重复。存储层的选择是这个设计的核心，直接更新数据库行是绝对不行的。

比如一行记录存直播间的总点赞数，每个请求都执行 update live_room_set like_count 等于 like_count 加一 where id 等于，所有点赞都会锁到这一行上，数据库的行锁和磁盘 I O 会迅速让吞吐量掉到每秒几千次，再强的机器也扛不住。所以业界普遍用 Redis 这种内存数据库，用 Redis 的 incr 命令，对 live:like:roomid 这个 key 直接加一，每次操作在微秒级完成，单机每秒能处理十几万次。Redis 本身是单线程执行命令，天然没有并发竞争问题，也不容易出现超卖那种数据错乱。如果你的直播间数量不多，热点集中在少数几个 key 上，这一个方案已经能解决绝大多数问题。

但 Redis 是内存存储，数据有丢失风险，机器宕机、断电、主从切换都可能导致最后几秒的点赞数没了，所以不能把所有鸡蛋放一个篮子里，需要开启 Redis 的持久化，比如 AOF 策略，每秒刷新一次磁盘，最多丢一秒数据。但这还不够，因为 Redis 里存的是实时热数据，最终还需要落到 MySQL 这类关系型数据库里做归档和后续查询。落库不能一条一条写，要采用异步和批量，常见做法是把每一次点赞事件作为一个消息发给 Kafka，或者更轻量的方式直接让定时任务去扫描 Redis 里的计数。比如每五秒取一次增量排序，合并后写入数据库，批量写入能在极大程度上降低数据库压力。比如一个百万赞直播间，每天二十四小时，数据库里只需要更新几千次就能把所有计数同步完。

同步的过程中还要考虑消息丢失和重复问题，如果用消息队列，消费者把一千条点赞消息聚合成一条 update 语句，更新数据库的总数。但如果消费者挂了或者一条消息被重复消费，可能会导致多计数，所以比较聪明的设计是数据库里不直接存 like_count 这个最终值，而是存一张按时间分片的统计表，比如 live_room_like。划线抗存每分钟的增量，消费者按分钟密等合并，即使重复消费，只要拿到了时间窗口和直播间 I D，再做一次去重，就不会有多计的问题。这个设计虽然比直接更新一行复杂，但它把崩溃后恢复的正确性大大提高了。再来看高并发下的热点问题，一个超头部直播间，所有用户都在点赞同一个 key，Redis 即使能支撑，也可能会出现网络带宽的瓶颈。

一个常见优化是让客户端批量上报，不要每一次点赞都发一个 H T T P 请求，而是让客户端在本地攒一攒，比如一秒钟内点了二十次赞，打包成一个请求，后端收到后直接给这个直播间的技术加二十，这样可以把后端请求量降低几十倍，而观众几乎感知不到延迟。另一种方案是在引入 Redis 集群时，对这个直播间的 key 做一致性哈希，让流量分散到多个节点，但一个 key 只能落在同一个节点。所以批处理才是真正有效的解法，这样处理还有一个额外好处，点赞服务不需要频繁修改数据库，对下游的压力也会小很多。防刷和限流也必不可少，如果不设置限制，恶意用户可以用脚本一秒点一万次，把整个直播间技术刷上天。基础做法是对单个用户做频率控制，比如每个用户每分钟最多允许点六百次，超过就直接拒绝。

这个计数器也可以放在 Redis 里，用滑动窗口或者固定窗口实现。更细一点可以加上设备号、I P、用户等级等维度，在接入层做令牌桶限流，直播间的整体点赞速率也可以做保护。比如设置每台机器每秒最多处理多少点赞事件，超过了就降级，直接返回成功，但不再累加。这里要注意点赞功能天生适合牺牲数据精确性来保系统稳定，所以在压力极大的时候做降级是完全可以接受的。最后是用户端的数字展示，前端不可能从 Redis 里直接读，也不能每次都去查数据库，通常使用 Web Socket 长连接，服务端每隔几秒推送一次当前的总数。这里的推送频率也没必要固定，热门直播间可以一秒推一次，普通直播间十秒一次。如果直接每点赞一次就全直播间接广播，那相当于把点赞流量的成本又放大了一遍。

所以点赞服务在 Redis 里加完数后，只负责触发一次定时任务，由推送服务读取最新的计数，批量广播给当前直播间的在线用户，这样整条链路才是闭环。到这里我们可以给整套设计画一张图，客户端批量上报点赞进入接入层网关做健全和限流，然后点赞服务更新 Redis 计数，异步从 Redis 里抽取增量写入 Kafka，由消费者批量合并到 My Circle，同时推送服务定时从 Redis 取最新数值，通过 Web Socket 广播给直播间内用户。R D B 和 A O F 双持久化保证 Redis 数据不容易丢，My Circle 里保存最终归档数据用于回放和结算。当然这套方案并不适用于所有场景，如果你的直播间日均点赞只有几千次，直接用数据库更新反而更简单可靠。

真正值得引入 Redis 和消息队列的，是那些高热门活动或者头部主播的直播间。所以设计直播间点赞，与其说是追求一个完美方案，不如说是在理解业务一致性要求的基础上做取舍，接受秒级延迟，换取十倍以上的吞吐量，接受少量数据丢失，换取服务不崩溃。把这一点想清楚，你也就掌握了高并发后端设计的精髓。
