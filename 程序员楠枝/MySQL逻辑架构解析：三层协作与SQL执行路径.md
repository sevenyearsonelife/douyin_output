MySQL 的逻辑架构通常从上到下分成三层，最上面是客户端连接层，中间是核心服务层，最下面是存储引擎层。这个分层最重要的意义在于，核心服务层不负责数据在磁盘上的具体存放，存储引擎层也不关心 SQL 语法怎么解析。两层之间通过统一的接口协作，所以 MySQL 才能支持多种存储引擎，比如 InnoDB 和 MyISAM。先看第一层，连接管理。每当你用客户端连接 MySQL，服务端会从线程池里分配一个线程专门服务你。这个线程负责认证你的身份，校验用户名密码和来源主机，之后你发的每一条 SQL 都由它接着处理。这里有一个容易忽略的点，连接本身是有状态的，事务、临时表、会话变量都绑定在这个连接上，如果连接断了，这些状态也就没了。第二层是核心服务层，这是逻辑架构里最复杂的一层。

一条 SQL 进来，先经过查询缓存，MySQL 会把查询语句本身和它对应的结果集存下来，如果完全相同的 SQL 再次进来，就直接返回缓存结果，省去后面所有步骤。但查询缓存有一个很严格的条件，只要底层表发生过任何数据变更，这张表相关的所有缓存都会失效。在写入频繁的场景下，维护缓存反而成了负担，所以 MySQL 八点零已经把这个功能整个移除了。查询缓存之后，SQL 进入解析器，解析器先做词法分析，把语句拆成一个一个有意义的词，再做语法分析，检查这些词组成的结构是否符合 SQL 语法规则，并生成一棵解析树。如果语法错了，比如少一个逗号或者关键字拼错，就是在这个阶段被拦下来的。但解析器只负责判断语句长得对不对，不负责判断你查的表到底存不存在。

接着是预处理器，它拿着解析树去系统表里核对列名和表名是否真实存在，也会做一些权限检查。如果表名写错了，或者没有某张表的访问权限，通常在这一步就会报错。通过预处理器之后，解析树就升级成了更完整的查询树。然后进入查询优化器，这一步是整个核心服务层里对性能影响最大的环节。优化器的任务不是照着你的 SQL 原样执行，而是想办法找出一种它认为成本最低的执行方案。比如你写了一条多表关联查询，优化器会决定先查哪张表，用哪个索引，表之间用什么连接顺序。它依据的是统计信息，比如每张表大概有多少行，索引的区分度怎么样，所以同一个查询，数据量变化之后，执行计划可能完全不同。优化器输出执行计划之后，执行器开始真正干活。执行器先做权限复核，然后根据执行计划调用存储引擎的接口。

这里有一个关键角色叫 handler 接口，执行器不直接碰磁盘文件，它通过这个接口向存储引擎要数据，比如帮我读这一行的下一行。存储引擎负责从内存或磁盘里把数据取出来，再交回给执行器。执行器拿到数据后做过滤、排序、聚合等操作，最后把结果集返回给客户端。第三层就是存储引擎层，存储引擎管理数据在磁盘上的物理存储结构、索引组织方式、事务和锁机制。InnoDB 是目前默认的引擎，支持事务和行级锁，数据按主键聚簇存放。MyISAM 更简单，不支持事务表级锁，适合读多写少的旧场景。因为核心服务层通过统一接口和引擎通信，所以更换引擎不需要重写 SQL，但会直接影响并发能力和数据安全性。现在我们把整条链路串一遍，假设你执行一条查询，从用户表里查出某个城市的所有活跃用户，并按注册时间排序。

这条 SQL 先到连接层，线程确认你有权限，然后进入服务层，解析器检查语法，预处理器确认表和列存在，优化器根据统计信息决定是否走城市字段的索引，再决定排序要不要用索引顺序。执行器按计划调用 InnoDB 接口取数据，InnoDB 从缓冲池或磁盘里读取行记录，返回给执行器完成排序和过滤，最后结果回到你的客户端。理解这个逻辑架构最大的好处是你能准确定位问题。语法错误发生在解析层，表不存在发生在预处理层，执行慢通常要看优化器选的执行计划和存储引擎的读取效率。所谓 SQL 优化，本质上就是在优化器给出的各种可能路径里找到成本更低的那一条。
