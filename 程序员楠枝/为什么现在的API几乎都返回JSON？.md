为什么现在的接口几乎都返回 JSON？要回答这个问题，我们得先明白接口返回的数据格式本质上是程序之间对话用的信封，信封上写清楚数据怎么拆、怎么读，接收方才能不费力地处理。而在今天，这个信封几乎统一成了 JSON。JSON 的全称是 JavaScript Object Notation，直译过来就是 JavaScript 对象表示法。它最初是从 JavaScript 语言里借用了一种写数据的习惯，但后来发展成了一个完全独立的文本格式。它只靠两种结构表达信息，一种是用花括号包起来的键值对，另一种是用方括号包起来的值列表。键值对负责描述一个东西有哪些属性，列表负责表达一组同类的东西。就这两样，已经足够覆盖绝大多数程序需要交换的数据。那为什么是 JSON 赢下来，而不是更早的 XML 或者其他格式？

关键要看接口的使用场景发生了什么变化。早期接口主要服务于服务器和服务器之间的正式通信，XML 的标签结构很严谨，适合那种像公文一样需要层层校验的数据。但后来接口的主要消费者变成了浏览器和手机应用，这些客户端需要的是轻、快、读起来直接的东西。JSON 天生就是 JavaScript 能直接识别的结构，浏览器拿到之后几乎不用做转换，这在 Web 应用爆发的年代是巨大的优势。更实际的原因是 JSON 足够简单，一个字段名、一个冒号、一个值，没有额外的标签包裹，没有复杂的属性定义。同样的数据用 XML 表达，每一个字段都要写开始标签和结束标签，文件体积会明显变大。体积大意味着网络传输更慢，在移动网络下尤其明显。而 JSON 的紧凑性让它天然适合高频、小包、要求低延迟的接口调用。

还有一点常常被忽略，就是 JSON 对类型的表达更直接。数字就是数字，布尔值就是 true 和 false，空值就是 null，程序拿到之后不需要再根据文本内容去猜测这到底是字符串还是数字。XML 本身不区分这些，所有内容默认都是文本，要靠额外的约定或模式文件来补上类型信息。对于写接口的人来说，JSON 省掉了一层解释成本，对于用接口的人来说，也少了一类出错的可能。当然 JSON 也不是没有缺点，它不支持注释，意味着没法在数据里直接写说明。它对日期的处理很模糊，通常只能把时间表示成字符串。它也没有内建的二进制支持，传文件时还得先编码成文本。但这些不足在实际工程里都能用约定来绕开。相比之下，它的简单和通用带来的好处远远超过了这些麻烦。从生态角度看，JSON 的胜利也是路径依赖的结果。

几乎所有主流编程语言都内置了 JSON 的解析和生成工具，不需要额外安装库。前端 JavaScript 的原生支持，后端 Java、Python、Go、PHP 全都提供现成的转换函数。一个格式如果让每一种语言都能低成本地读写，它就会迅速变成默认选项。开发者不需要为选格式开会，默认就是 JSON，这本身又进一步巩固了它的地位。还有一个容易被忽视的推动力来自数据库。很多现代数据库，尤其是文档型数据库，底层存储结构就采用了类似 JSON 的形式。应用从数据库读出数据，几乎可以直接变成接口返回的内容，中间不需要复杂的映射转换。这种从存储到传输再到前端消费的一致性，让整个开发链路变得非常顺。以前那种数据库一张表，中间一层对象，输出再转成 XML 的多重转换，在今天的小团队里几乎没人愿意再做了。

所以今天的接口几乎都返回 JSON，并不是因为某个标准组织强制规定，而是因为它在轻量、易读、跨语言、类型明确这几个维度上恰好击中了现代应用开发最核心的需求。它从浏览器的便利格式，逐渐变成了整个互联网数据交换的通用语言。当然这不意味着所有场景都该用 JSON，在需要严格校验、复杂命名空间或二进制传输的领域，其他格式仍然存在。理解 JSON 的优势。也要理解它的边界，才能真正用好它。
