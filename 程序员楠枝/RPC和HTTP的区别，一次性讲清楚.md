什么是 R P C？什么是 H T T P？它们到底有什么区别？先说 H T T P，H T T P 是一种应用层协议，全称是超文本传输协议。它最早是为了在浏览器和服务器之间传输网页而设计的，核心模型是请求到资源，客户端发一个请求，服务器返回一个响应，请求里通常包含方法、路径、请求头和请求体。比如你要获取用户列表，就发一个 get 请求到某个路径，服务器返回 json 或者 html。H T T P 本身并不关心你传输的是网页、图片还是接口数据，它只定义了一套通用的报文格式和状态码规则。现在大多数互联网对外接口都走 H T T P，因为它足够通用，任何语言、任何平台都能解析。而 R P C 的全称是远程过程调用，它的核心目标不是传输资源，而是让你调用远程机器上的函数时，看起来像调用本地函数一样。

比如你本地写了一个 get user 函数，在 R P C 框架里，你直接写 get user by id，框架会帮你把这个调用打包成网络消息发给服务端，服务端执行完再把结果返回给你。整个过程里，你不需要手动拼 U R L、拼请求体、解析响应状态码，R P C 把网络通信的细节藏在了函数调用后面。所以从目标上看，H T T P 偏向传输协议，它定义的是数据在网络上怎么走，R P C 偏向调用模型，它定义的是程序员怎么写代码来触发远程逻辑。这两者其实不在同一个维度，严格来说，R P C 可以用 H T T P 作为底层传输协议，也可以用 T C P 直连，甚至可以用 H T T P 二。很多 R P C 框架底层就是跑在 H T T P 上的，比如 g R P C 用的是 H T T P 二。

所以 R P C 和 H T T P 有什么区别？这个问题本质上是在拿一个调用模型和一个传输协议做比较。那为什么大家还总把它们放在一起比？因为在实际工程里，它们经常被当成两种不同的服务通信方案。一个团队可以说我们服务之间用 H T T P 接口，也可以说我们服务之间用 R P C，这时候比的其实是两种风格的差异。第一个差异在接口定义方式，H T T P 接口通常以资源为中心，路径和方法组合起来表达操作，比如 post 加一个创建用户的路径。R P C 接口通常以动作为中心，直接暴露函数名和参数，比如 create user，一个更贴近 web 的资源语义，一个更贴近代码的函数语义。

第二个差异在调用体验，H T T P 需要调用方自己处理请求构造、序列化、状态码判断、错误解析这些步骤，R P C 框架会把这些事情自动完成，调用方拿到的要么是返回值，要么是异常。开发效率上，R P C 通常更省事，尤其是服务内部有大量方法调用时。第三个差异在性能，H T T P 一点一是文本协议，头部信息比较大，每次请求都带一堆字段，长连接复用也不够高效。很多 R P C 框架使用二进制序列化和更紧凑的协议格式，传输体积更小，解析更快。这也是为什么高并发服务内部通信更倾向 R P C。不过 H T T P 二和 H T T P 三已经改善了很多，头部压缩、多路复用都补上来了。第四个差异在跨语言和跨团队协作，H T T P 几乎没有任何使用门槛，任何语言都有成熟客户端，调试工具也多。

R P C 虽然也有很多跨语言实现，但不同框架之间的兼容性不如 H T T P 统一，调试和联调成本更高。所以对外暴露给第三方或者前端时，H T T P 几乎是默认选择，对内服务之间，尤其是同一个技术栈内部，R P C 更常见。那什么时候该用哪个？一个比较实用的判断标准是看调用边界。如果这个接口要暴露给外部系统、前端、第三方开发者，或者你不确定未来谁会调用，优先用 H T T P，因为通用性、可调试性和生态成熟度都更好。如果这是内部服务之间的高频调用，双方都由同一团队维护，对性能和开发效率要求高，那 R P C 是更合适的选择。很多大型系统是混合使用的，对外。一层 HTTP 网关，内部服务之间走 RPC。最后总结一下，GTP 是一套通用的网络传输协议，解决的是数据怎么在网络上交换的问题。

RPC 是一种远程调用模型，解决的是怎么让远程函数调用像本地调用一样简单的问题。它们不是二选一的对立关系，RPC 完全可以建立在 HTTP 之上。真正需要你判断的，是你的接口面向内部还是外部，是追求通用性还是追求调用效率和开发体验。把这个边界想清楚，选择就不会纠结。
