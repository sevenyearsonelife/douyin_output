什么是 R P C 框架？说白了就是让一台机器上的程序能像调用本地函数一样去调用另一台机器上的函数。今天这条视频从零开始拆解一个 R P C 框架的核心设计思路，你会搞清楚它到底要解决什么问题，关键模块有哪些，每一步是怎么串起来的，以及哪些地方最容易踩坑。先建立正确的心智模型。一，哎，Top B C 远程过程调用，它的本质是伪装，把网络通信的复杂度包装成一个普通的函数调用。你写代码时调一个方法，传参数，拿返回值，感觉和调用本地方法没区别，但实际上参数被序列化成字节流，通过网络发到另一台服务器，服务器反序列化执行真正的逻辑，再把结果序列化发回来，整个过程调用方完全无感知。那设计一个 R P C 框架，第一步要做什么？不是写代码，而是定协议。

协议就是双方约定好的对话格式，你得明确一条消息里哪些字节代表方法名，哪些代表参数，哪些代表返回值，错误信息怎么放。最常见的做法是分两部分，头部和体部。头部放元信息，比如魔术、版本号、消息类型、请求 I D，体部放真正的业务数据。这里有个关键点就是请求 I D，网络是异步的，你发一个请求可能同时有几百个请求在飞，响应回来时你怎么知道这个响应对应哪个请求？就是靠请求 I D 匹配。这是 R P C 框架和普通 H T T P 调用一个很大的区别，H T T P 是一问一答，R P C 可以多路复用。第二步是序列化，这是 R P C 里性能影响最大的一环。序列化就是把内存里的对象变成字节流，反序列化就是把字节流变回对象。设计时你要做取舍，JSON、 XML 这种文本格式可读性好，但体积大解析慢；

Protobuf、 Thrift 这种二进制格式体积小速度快，但需要定义 I D L，也就是接口描述语言，维护成本高。这里有个容易忽略的坑，跨语言时不同语言对数据类型的表示不一样，比如 Java 的 Big Decimal，C 加加的 long long，序列化协议必须能无损表达这些类型，否则就会出现精度丢失这种诡异问题。第三步是网络通信层，这一步要决定用什么传输协议，绝大多数 R P C 框架都跑在 T C P 之上，因为 T C P 可靠有序，但 T C P 有个问题就是粘包和拆包，发送方可能一次写入了两个完整的请求，接收方读到的数据却混在一起，或者一个请求被拆成了两段到达。所以接收方必须能从字节流里准确切分出一条完整消息，这个就靠第一步协议里的长度字段来实现。

一，先读固定字节的头部，拿到体部长度，再按长度读取体部。这一层还涉及连接管理，是长连接还是短连接，长连接要心跳保活，要处理断线重连，还要考虑连接池的大小。另外，是同步阻塞 I O 还是异步非阻塞 I O，现代 R P C 框架基本都是异步的，底层用 Netty 这类框架配合 Future 或者 Callback 模式，把等待响应的线程解放出来。第四步是服务注册与发现，这是从能跑到能用于生产的分水岭。在分布式环境下，服务提供方有很多台机器，I P 和端口是动态变化的，调用方怎么知道该连谁？这就要引入一个注册中心，服务启动时把自己注册到注册中心，同时上报自己的 I P、端口、权重等信息，服务下线时主动注销。调用方在发起请求前，先从注册中心拉取可用服务列表缓存在本地，这里有个经典问题，注册中心挂了怎么办？

所以设计上一定要有本地缓存兜底，即使注册中心暂时不可用，调用方也能用缓存的列表继续工作。同时还要考虑负载均衡策略，明日是随机轮询，还是根据机器响应时间做加权，这些策略决定流量怎么分配。第五步是动态代理与调用端封装，这一步是 R P C 伪装成本地调用的关键。在客户端，你定义一个接口，R P C 框架通过动态代理为这个接口生成一个实现类，你调用接口方法实际上是调用了代理对象里的。逻辑：代理拿到方法名、参数类型和参数值，把这些信息塞进协议里，交给网络层发送，然后阻塞等待结果。服务端正好反过来，收到请求后，根据方法名找到对应的实现类，用反射去调用真实方法，拿到结果再返回。这里要注意的是，反射调用有性能损耗，所以很多框架会做方法缓存的优化。Mason 第一次查到方法后，把 Method 对象缓存起来，避免反复反射。

最后给你串一遍完整流程：客户端调用接口方法，动态代理拦截，把方法信息打包，序列化成字节流，通过连接池发给服务端。服务端收到字节流反序列化，解析出方法名和参数，从本地注册表里找到实现类，反射调用拿到结果，序列化后返回。客户端收到响应，根据请求 ID 匹配到对应的 Future，把结果喂给调用线程，调用线程被唤醒，拿到返回值。整个链路每一环都环环相扣，六年协议定得不好，解析就慢；序列化选得不好，传输就慢；连接管理不好，延迟就高；注册发现不好，系统就脆弱。
