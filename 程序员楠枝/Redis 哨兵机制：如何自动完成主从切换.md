什么是 Redis 哨兵机制？简单说，它是给 Redis 配的一套自动值班系统，专门解决一个问题：主节点挂了，谁来接管，怎么让业务不中断。Redis 经常被用来做缓存、做计数器、做排行榜，很多系统里它是挡在数据库前面最吃性能的一层。如果只部署一台 Redis，它一旦宕机，所有请求会直接打到后端数据库，数据库很可能被瞬间压垮。所以生产环境通常会把 Redis 搭成主从结构，一台主节点负责写入，多台从节点负责同步数据和分担读请求。但主从结构本身有个致命缺陷，主节点故障时，从节点不会自动升级，系统只会整体进入只读或不可用状态，必须靠人手动介入。哨兵机制就是来解决这个自动故障转移问题的。它由一组独立的哨兵进程组成，这些进程不存业务数据，只做三件事：监控、通知、自动切换。

监控就是持续检查主节点和从节点是否在线，响应是否正常。通知就是发现某个节点出问题时，给管理员发告警或者通知客户端新的主节点地址。自动切换就是当确认主节点真的挂了，哨兵会从从节点里选出一个，提升为新的主节点，并让其他从节点重新跟着新主节点同步。这里有一个关键设计，哨兵不是单台机器，而是一个集群。为什么不能只放一个哨兵？因为单个哨兵自己可能网络抖动，也可能自己挂了。如果只有一个哨兵，它一旦误判主节点失联，就会触发一次错误的切换，把原来的主节点降级，造成数据混乱。所以哨兵集群通常要求至少三个节点，并且需要超过半数投票同意，才能认定主节点真的故障。这个半数机制叫法定人数，它保证了即使个别哨兵误判，也不会轻易触发切换。接下来说说哨兵是怎么判断主节点挂了的。它有两个判断阶段，分别叫主观下线和客观下线。

主观下线就是一个哨兵在指定时间内连续收不到主节点的有效响应，它自己认为主节点可能挂了，但这只是它一个人的判断，不能做数。于是它会去问其他哨兵，你们也联系不上主节点吗？如果超过一定数量的哨兵都确认联系不上，这个状态就升级为客观下线，整个哨兵集群才正式启动故障转移。这个设计避免了单点误判。确认主节点故障后，哨兵要选一个新的主节点，它会遍历所有从节点，先剔除掉那些长期断线、数据太旧或者被管理员标记为不参与选举的节点。剩下合格的从节点里，谁的复制偏移量最大，也就是谁的数据最接近原主节点，谁就优先当选。如果多个从节点数据一样新，就按配置里的优先级排序。这样选出来的新主节点能最大程度减少数据丢失。

新主节点选出来之后，哨兵会向它发送命令，让它从从节点角色切换成主节点，然后哨兵会通知其他从节点，让它们停止同步旧主节点，改为从新主节点复制数据。最后，哨兵会把新主节点的地址告诉客户端，客户端如果接入了哨兵，就会自动更新连接目标，不需要人工改配置。这里需要强调一个重要的边界，哨兵机制不能保证数据零丢失。因为 Redis 的主从复制是异步的，主节点收到写入命令后，不会等从节点确认就返回成功。如果主节点在同步完成前突然宕机，这一小段数据就永久丢了。哨兵能做的是选一个数据最新的从节点来接管，把丢失范围压到最小，但无法完全消除。如果你的业务对数据一致性要求极高，需要配合持久化策略或其他一致性方案一起使用。还有一个常见误区，就是把哨兵和集群模式混为一谈。哨兵解决的是高可用，也就是主节点挂了能自动换人。

集群模式解决的是数据分片，也就是数据量太大时，把数据分散到多个主节点上。两者可以各自独立使用，也可以组合使用，但职责完全不同。总结一下，Redis 哨兵机制是一套独立的监控和自动切换系统，它通过哨兵集群的多数投票来确认主节点是否真的故障，自动从从节点中选出数据最新的一个接管工作。把新地址通知给客户端，它让 Redis 主从结构从手动恢复变成了自动恢复，是生产环境里保障 Redis 高可用的基础组件。
