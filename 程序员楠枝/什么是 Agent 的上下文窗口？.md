什么是 Agent 的上下文窗口？简单说，它就是智能体在处理当前任务时能够同时看见和记住的信息总量。这个窗口里装着的不只是你刚发过去的那句话，还包括系统提示、历史对话、工具返回结果，以及它自己已经写好的思考片段。今天我们要讲清楚三件事：上下文窗口到底由什么组成，为什么它直接决定了 Agent 的表现，以及在实际使用中开发者是怎么应对窗口被塞满这个问题的。先看它是什么。你可以把上下文窗口理解成 Agent 的工作台面，台面大小是固定的，所有跟当前任务有关的材料都得放在上面。对基于大语言模型的 Agent 来说，这个台面通常以 token 为单位计算。Token 不是单词，而是模型处理文本的最小片段。一个汉字可能是一个 token，一个英文单词可能被拆成两三个。

窗口大小从几万到上百万 token 不等，但无论多大，本质都是一个有限的注意力范围。这个窗口里通常装着四类东西。第一类是系统提示，也就是开发者预设的角色规则和工具说明，它从对话开始就常驻窗口，一直占用空间。第二类是历史对话，你和 Agent 一来一回的所有内容。第三类是工具调用记录，比如 Agent 去查了一次数据库或者读了一份文档，返回的内容也会被写进窗口。第四类是推理过程，一些 Agent 会把中间思考步骤也放进去，方便后续决策。这四类内容加起来就是当前窗口的占用情况。为什么这件事重要？因为它直接决定了 Agent 会不会失忆。窗口一旦被占满，最早进入的信息就会被截断或压缩。如果被挤掉的是系统提示里的关键规则，Agent 可能开始不按约束行事。如果被挤掉的是几轮之前的对话，它就可能忘记你最初的要求。

很多用户觉得 Agent 变笨了，其实不是模型能力下降，而是窗口里已经没有足够的信息支撑它做出正确判断。更隐蔽的影响在于任务质量。窗口越接近上限，模型对中间信息的注意力就越分散。一个需要同时比对多个文档的任务，如果材料刚好塞满窗口，模型可能只对开头和结尾的内容印象更深，中间部分被相对忽略。这不是玄学，而是由模型处理长序列时的注意力分布特点决定的。那怎么理解它如何工作？可以看一个简单流程。你给 Agent 一个任务，它先把系统提示、历史消息和你的新指令打包，作为一次调用的输入。模型读取整个窗口，生成下一步动作，比如调用搜索工具。工具返回结果后，这份结果会追加进窗口，形成新的输入，再让模型决定下一步。每一轮循环，窗口都在变长，直到任务完成或者空间耗尽。

这里就带出核心矛盾：Agent 需要记住更多信息才能做好复杂任务，但窗口越长，成本越高，响应越慢，注意力也可能越稀释。所以实际开发中，工程师不是在追求无限大的窗口，而是在管理窗口里到底放什么。常见的应对方式有三种。第一种是滑动窗口，只保留最近若干轮对话，更早的内容直接丢弃。第二种是摘要压缩，用一个额外步骤把历史内容总结成简短要点，用摘要替代原文，省下大量空间。第三种是外部记忆，把完整信息存到向量数据库或文件系统里，需要时再检索相关片段放回窗口。这三种方式常常组合使用，本质都是在有限台面上做信息取舍。还有一点值得注意，上下文窗口和 Agent 的长期记忆不是一回事。窗口是工作记忆，断电即清空；长期记忆依赖外部存储，可以跨会话保留。

一个设计良好的 Agent 往往是用小窗口处理当下，用外部记忆承载过去，再通过检索把过去的相关部分临时调回窗口。理解这个区分能帮你判断一个 Agent 产品宣称的记忆到底是真的长期能力，还是只是这次对话没关窗口。总结一下，上下文窗口是 Agent 处理任务时的工作记忆上限，它装着规则、对话、工具结果和推理痕迹。窗口管理的好坏决定了 Agent 在长任务中是保持连贯还是逐渐跑偏。使用者来说，把重要约束放在前面，及时清理无关历史，必要时主动让Agent总结进度，都是在这个机制下更有效的协作方式。对开发者来说，窗口不是越大越好，而是要在信息完整度、响应成本和注意力质量之间找到平衡。理解了这一点，你就抓住了Agent的工作方式里最基础也最关键的一环。
