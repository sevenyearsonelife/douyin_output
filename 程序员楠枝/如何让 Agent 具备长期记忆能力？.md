想让 agent 真正成为一个能够长期协作的智能助手，光靠大模型本身还不够，还需要解决一个关键问题，记忆。比如你上周交代过的任务，之前确定的业务规则，或者 agent 自己执行任务时积累的经验，到了下一次对话，它还能不能准确地找回来并继续使用？这就是长期记忆要解决的问题。先理解一个关键区别，上下文不等于记忆。大模型本身没有持久状态，它每次推理只能看到你塞进上下文窗口里的内容。所谓短期记忆，就是把最近的对话、工具结果临时放进上下文，窗口一关就消失。而长期记忆是把值得保留的信息写到模型之外的外部存储里，等以后需要时再找回来。所以长期记忆的本质不是让模型记住，而是给 agent 外挂一套可写入、可查询的记忆系统。为什么这件事很重要？因为真实使用中，很多任务跨天、跨会话。

比如一个个人助理 agent，今天你告诉它我对花生过敏，下周你让它推荐餐厅时，它应该自动排除含花生的选项。如果它每次都忘，你就要反复交代，信任感会迅速下降。再比如客服 agent，记住用户上次遇到的问题和已尝试的步骤，能避免用户重复描述。长期记忆解决的核心问题就是让 agent 的行为具备连续性和个性化。那记忆具体存在哪里？常见有三类位置。第一类是本地文件或嵌入式数据库，比如把记忆写成 json 文件或存进 sqlite，适合单机个人场景，简单可控。第二类是专用向量数据库，比如把记忆切成片段，转成向量后存入 chroma、pinecone 或 milvus，适合需要语义检索的大量非结构化记忆。第三类是传统数据库加全文索引，比如 postgresql 配合关键词搜索，适合结构化程度高、需要精确匹配的场景。

实际系统里往往会混合使用，而不是只选一种。存储只是第一步，更难的是检索。因为记忆多了以后，不可能把全部历史都塞进上下文，那样又贵又慢，还会稀释注意力。所以 agent 每次行动前，需要根据当前任务只捞回最相关的记忆。主流检索方案大致有三种。第一种是语义检索，把记忆内容用嵌入模型转成向量，查询时也把当前问题转成向量，然后按相似度排序取前几条。好处是能理解意思相近但用词不同的内容，比如花生过敏和不能吃坚果可能被关联起来。代价是它可能漏掉精确事实，而且需要额外维护向量索引。第二种是关键词检索，直接用词匹配或全文索引，比如搜过敏、餐厅偏好。好处是精确可解释，实现简单。坏处是换一种说法就搜不到，所以很多系统会把语义检索和关键词检索结合，先各自召回一批，再合并排序，这种叫混合检索。

第三种是结构化查询，如果记忆里存的是明确字段，比如用户年龄、会员等级、常用地址，那直接按字段查最快也最准。这类记忆通常不需要猜，而是需要可靠的读写规则，适合用传统数据库管理。除了检索，还要考虑记忆的写入策略。不是每句话都值得记，常见做法是让 agent 在对话结束后做一次记忆提炼，把零散信息整理成稳定的事实或偏好，再决定新增、更新还是合并。比如用户先说我住北京，后来说我搬到上海了，系统应该更新地址，而不是同时保留两条矛盾记忆。这里就涉及冲突处理、时间戳和来源标记。还有一类容易被忽略的是程序性记忆，也就是 agent 从成功或失败任务中总结出的经验。比如某次调用某个 api 时，发现必须加特定参数才能返回完整数据，这个经验可以存成一条下次这样做的记忆。这类记忆往往带条件，需要记录适用场景，否则容易错误套用。

总结一下，让 agent 具备长期记忆不是简单加个数据库，而是三件事的组合：设计合适的存储介质，建立按需检索的机制，以及制定可靠的写入与更新规则。语义检索适合模糊相关，关键词检索适合精确匹配。结构化查询适合稳定事实，真实系统通常混合使用。长期记忆的效果取决于记忆质量和检索精度，而不是存的越多越好。能把这三层做扎实，Agent 才可能真正表现出记得你、懂你、越用越顺手的能力。
