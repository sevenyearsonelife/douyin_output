你是否有过这种经历？逛电商网站，把商品加到购物车，然后不小心关了页面，重新打开发现购物车还是满的。网站怎么能记住是你放进去的？或者是登录了邮箱，关闭浏览器再打开，网站依然知道是你。这一切的背后都靠一个叫 session 的机制在支撑。先从最基础的问题开始，什么是 session？Session 的中文翻译叫会话，它指的就是你和某个网站之间一次完整的交互过程，从打开网站的第一个请求到关闭浏览器或主动退出，这整段时间算一次 session。但 session 如果只定义了一个时间段，服务器面对几十亿用户的同时访问，怎么区分具体是谁呢？答案是服务器需要给每次会话分配一个独一无二的标识符，叫 session ID。

这个 ID 就像一把钥匙，维系在你和服务器之间，服务器只要看到这个 ID，就能知道你是谁，购物车里有啥，以及是否已登录。那么服务器是怎么把 session ID 给到你的？最常用的手段是通过 cookie，比如首次访问一个网站，服务器在响应报文里加一个 set-cookie 头，写着一串类似 session id 等于三 f a b 九二 j 的内容。浏览器收到后存下来，下次再向同一服务器发请求时，自动在请求头里带上这个 cookie，服务器就能根据这个 ID 去内存或数据库里查找，一查你的个人数据就全出来了。

所以说 session 和 cookie 是一对亲密搭档，但必须分清角色，cookie 是客户端存储凭证的机制，session 是服务端存储状态的机制，cookie 负责传递 session ID，session 负责存储你的所有数据。有人可能会想，既然 cookie 也能存东西，比如直接放一个 user 等于张三进去，那为什么还要搞 session？答案很简单，安全。如果把用户信息直接存在 cookie 里，就等于把数据交到了用户手中，用户完全可以在浏览器里修改，变成 user 等于管理员，服务器如果再信这个 cookie，整个系统就崩溃了。但 session 不一样，用户手头拿到的只是那个随机生成的 ID，真实的用户数据全在服务器上，客户端想改，改不了服务器里的内容。

所以 session 的核心价值就是让服务器拥有控制权，确保用户信息不被篡改或伪造。理解了 what 和 why，再来看 how，session 的典型生命周期是怎样的？第一步，启动，首次访问网站时，服务器自动创建一个 session 对象，分配一个几乎不重复的 ID，然后把这个 ID 做成 cookie 发给浏览器。session 对象初始是一个空容器，里面通常包含几个关键字段，唯一 ID、创建时间、最后访问时间以及一个空数据区。

第二步，维持，一旦 session 建立，后续所有请求都会带上那个 cookie，服务器每次请求都去查找对应的 session 对象，如果操作是添加商品到购物车或登录成功，服务器就在 session 里写入对应的数据，改完之后，服务器依然只保存这个 session ID，信息你拿不到也改不了。第三步，销毁，session 不会永远存在，一种是手动退出，服务器主动调用失效方法删除 session 对象，另一种是超时，比如长时间不操作，服务器配置了超时时间，通常是三十分钟，超过这个时间没有请求，服务器就会把 session 当做过期垃圾清理掉。还有一种是服务器重启，内存里的 session 会瞬间全部消失，这就是为什么很多线上系统会把 session 存到共享的 redis 中，防止重启丢数据。

前面提到了 session 和 cookie 的配合，但有没有不用 cookie 也能保持 session 的方法？有，一些系统会采用 URL 重写，比如在网址后面加一个参数 session id 等于三 f a b 九二 j，用户每次点击链接都会把这个 ID 传过去，这种做法在禁用 cookie 的场景下很实用，但缺点也明显，URL 里直接暴露了 session ID，容易被中间人截获。还有一种方式是隐藏表单字段，把 session ID 塞进 html 表单里，提交时带回去，这两种方式都可行，但复杂度更高，且同样存在被截获的风险。接下来聊一个更严肃的话题，session 的安全。session ID 如果被黑客获取，黑客就能冒充你，这个过程叫会话劫持，获取手段主要有哪几种？

第一，XSS 脚本攻击，黑客在评论框或图片链接里注入 JavaScript 代码，执行后偷偷读取你浏览器里的 cookie，再发送到黑客的服务器。第二，网络嗅探，你在公共 wifi 上访问网站，如果不加密，中间人可以截获 HTTP 流量，直接把 session ID。带走。第三，直接暴力猜测。如果服务器生成的 ID 太简单，黑客可以枚举尝试。知道了这些手段，防御办法也不难。强制使用 HTTPS 加密传输，让网络监听失效。给 Cookie 打上 HTTP Only 标记，防止 JavaScript 读取，使 XSS 攻击无法生效。设置 Secure 标志，确保 Cookie 只在 HTTPS 下发送。另外，定期轮换 Session ID，比如登录前后生成新的 ID，旧的就失效，也能显著降低被劫持的风险。

现在可以做个总结了。Session 实际上是互联网上最基础、最普遍的身份保持方式。它通过生成唯一标识并存储在服务器端的用户状态，来达成一件事，让原本无状态的 HTTP 协议变得有记忆。没有 Session，购物车装不了商品，登录也无法跳过重复输入密码。但 Session 不是万能的，它的机制依赖于一个安全传递的 ID，你必须做好 HTTPS、HTTP Only 这些基础防护。最后给你一个实用建议，如果你正在写新项目，对于简单的 Token 式架构，可以考虑用 JWT 代替 Session，但对于复杂、需要频繁访问用户大量数据的功能，Session 依然是更成熟稳定的方案。好了，今天的 Session 就聊到这里，如果你还有其他想让我解释的技术概念，欢迎留。
