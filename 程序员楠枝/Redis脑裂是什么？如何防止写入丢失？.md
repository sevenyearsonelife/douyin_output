什么是 Redis 脑裂？简单说就是在一个本应只有一个主节点的 Redis 高可用集群里，同时出现了两个或多个节点都认为自己是主节点，并且都能接收客户端写入。这种状态一旦发生，数据就可能朝着不同方向分叉，最后在恢复时丢掉其中一部分。这期内容会讲清三件事：脑裂到底是怎么发生的，它为什么危险，以及主流的哨兵和集群方案分别怎么限制它的影响。先看它发生的条件。Redis 高可用通常靠哨兵来监控主从节点，哨兵发现主节点失联，就会发起故障转移，把某个从节点提升为新主节点。问题在于哨兵判断失联靠的是投票，而投票需要时间。如果原来的主节点并没有真的宕机，只是网络抖动、负载过高，或者它和哨兵之间的网络断了，它自己仍然活着，客户端也仍然连着它，它就会继续接收写入。

与此同时哨兵那边已经选出新主节点，于是集群里出现两个主节点，脑裂就形成了。这里要强调一个关键点，脑裂不是 Redis 独有的概念，任何依赖多数派投票来选主的分布式系统都可能遇到。Redis 的特殊之处在于它默认并不要求主节点必须得到大多数从节点的确认才接受写入，这就给脑裂留下了更大的窗口。为什么说它危险？因为两个主节点会各自接受不同的写入，比如原主节点收到键 a 等于一，新主节点收到键 a 等于二。等网络恢复，原主节点会被降级为从节点，并且需要从新主节点同步数据，它自己多出来的那部分写入默认情况下会被直接清掉。也就是说客户端明明收到了写入成功的回复，最后数据却没了。对于订单、库存这类场景，这是不可接受的。那怎么解决？先看哨兵方案。Redis 提供了两个参数专门用来收窄脑裂窗口。

第一个是主节点要求的最小从节点数量，如果可用的从节点少于这个数，主节点就拒绝写入。第二个是主节点要求从节点确认写入的最大延迟，如果从节点在规定时间内没有确认，主节点同样拒绝写入。这两个条件通常配合使用，意思是主节点只有在至少有一个从节点跟得上自己时，才允许客户端写入。这样当原主节点因为网络问题被孤立时，它发现自己联系不上任何从节点，就会主动停止接收写入，从而避免数据分叉。但要注意这两个参数有一个副作用，如果从节点真的全部宕机，主节点也会拒绝写入，整个系统变成只读。所以它们本质上是牺牲一部分可用性来换取数据一致性，配置多严格取决于业务能接受丢多少数据，还是能接受短时间不可写。再看集群方案。Redis Cluster 的脑裂处理思路不完全一样。

集群模式下，每个主节点负责一部分哈希槽，如果一个主节点和集群多数派失联，集群会判定它故障，并把它的槽位迁移给从节点。原主节点如果还活着，它可能会在短时间内继续服务，但集群有节点超时机制，超过一定时间联系不上多数主节点，这个节点就会停止接收写入。因此集群模式下的脑裂窗口通常更短，但仍然存在，特别是在网络分区恰好把集群切成两半，两边主节点数量接近时，行为会更复杂。最后说一个常见误区，有人以为只要用了哨兵或者集群就不会脑裂。实际上这些机制能减少脑裂，但不能在所有网络条件下完全消除。真正稳妥的做法是结合业务要求，明确写入需要多少副本确认，也就是常说的强一致写入。Redis 默认是异步复制，追求的是性能，不是绝对一致。理解这一点比记住任何配置参数都重要。

总结一下，Redis 脑裂是分布式系统在网络分区时选主机制和异步复制共同作用的结果，它的核心危害是已确认的写入可能丢失。哨兵方案通过限制主节点在孤立状态下的写入能力来降低风险，代价是可能牺牲可用性。集群方案用槽位迁移和超时机制缩短脑裂窗口，但同样不提供绝对保证。最终怎么取舍，取决于你的业务到底更怕丢数据，还是更怕停服务。
