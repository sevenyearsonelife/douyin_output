如何设计一个踢人下线系统？先说为什么需要它。因为登录状态本质上是一种信任凭证，而凭证一旦被滥用、被盗用或者不再该被信任，你就得有办法立刻收回它。比如账号共享、异地登录风险、用户违规封禁或者员工离职后权限回收。没有踢人能力，你就只能等凭证自然过期，这个窗口期可能长达几小时甚至几天，风险完全不可控。要理解这个系统怎么做，核心得抓住一个问题：登录状态存在哪里，你就能在哪里踢人。最常见的两种形态，一种是服务端存储的会话，比如 session 或 redis 里的 token，另一种是无状态的 jwt，服务端不存任何会话。这两种形态踢人的手段完全不同。先看服务端会话，用户登录后，服务端在 redis 里存一条记录，键是 token，值是用户 id 和过期时间。

每次请求，服务端拿着 token 去查 redis，查得到就放行，查不到就拒绝。这种情况下，踢人极其简单，删除 redis 里那条记录，甚至不需要真的删，你可以在记录里加一个版本号或状态字段，标记为已失效。这样做的好处是即时生效，下一次请求立刻失败，而且你还能精确控制踢的是哪个设备哪个端。但这里有个细节，很多新手会忽略踢人的力度，你是按用户踢还是按设备踢？如果用户手机和电脑同时登录，你只想踢电脑，那你的会话记录里就必须有设备标识。所以设计时 redis 的键不能只是用户 id，而应该是用户 id 加设备 id 的组合。否则你只能一刀切，把用户所有设备全踢下线，这在真实场景里常常不可接受。再看无状态 jwt 的情况，jwt 本身不存服务端，你没法删它，那怎么踢？

核心思路是引入一个可撤销层，最常见做法是在 redis 里维护一个黑名单，存被踢 token 的 id 或签名，并设置一个和 token 剩余有效期一致的过期时间。每次请求，服务端先验签，再查黑名单，命中就拒绝。这个方案能工作，但代价是每次请求多一次 redis 查询，而且如果 token 有效期很长，黑名单也会存很久。更优雅一点，你可以给 jwt 加一个会话版本号字段，用户登录时 redis 里存当前版本号，jwt 里也带这个版本号。踢人时把 redis 里的版本号加一，请求校验时对比 jwt 里的版本号和 redis 里的当前值，不一致就拒绝。这个方案的好处是黑名单不用存，而且踢人操作是 O 一的。缺点是如果 redis 挂了，所有请求都会失败，因为每次都要查版本号。那真实系统里怎么选？

我的建议是绝大多数业务场景优先用服务端会话，也就是 redis 存 token，它简单可控、即时生效，而且天然支持多设备管理和批量踢人。jwt 适合那种服务端无状态、需要水平扩展且对性能要求极高的场景，但你必须接受踢人需要额外机制这个事实。还有一个关键点，踢人之后客户端怎么感知？你不能指望用户自己发现。标准做法是后端在响应里返回一个统一的未授权状态码，比如四百零一，并带上一个业务码，表示会话被强制终止。前端拦截到这个业务码后，清掉本地登录态，跳转到登录页，并提示账号在其他设备登录或你已被管理员封禁。这个联动必须提前约定好，否则就会出现用户操作到一半，请求莫名失败，但界面毫无反应。最后，别忘了踢人本身也是一个操作，得留下痕迹。谁踢的？什么时候踢的？踢的是哪个用户？哪台设备？踢完对方是否立刻重登？

这些都应该记录到操作日志里。尤其是管理员踢人，一定要有审计，否则一旦误操作，你连回溯的依据都没有。总结一下，踢人下线系统的本质就是让登录凭证从只能等过期变成随时可作废。服务端会话直接删记录，jwt 靠黑名单或版本号机制。设计时重点考虑三件事：踢人的力度要支持按设备，踢人的操作要及时生效，踢完要让客户端能感知并引导用户重新登录。把这三件事想清楚，你的踢人系统就能。在真实场景里站得住脚。
