TCP 粘包，简单说就是接收方在一次读取数据时，一次性拿到了多个本该独立发送的数据包，或者只拿到了一个数据包的一部分。很多刚开始接触网络编程的人都会在这里栽跟头。这篇内容我会讲清楚 TCP 粘包到底是怎么产生的，它和 TCP 的传输机制有什么关系，以及在什么条件下才会真的遇到它。最后我会告诉你最常见的三种解决办法，以及每一种方法各自的适用场景。先明确一个核心事实，TCP 本身没有包的概念，TCP 是面向字节流的协议。什么叫字节流？就是发送方往 TCP 连接里写进去的字节，接收方就像从一根水管里连续接水一样，按顺序读到一连串字节。至于这一串字节从哪儿断开，TCP 根本不管。

你从应用层调用 send 发送了一百个字节，又调用了两次 send 发送了二百个字节，接收方可能一次就读到三百个字节，也可能分三次每次读一百个字节。这三百个字节在你的应用逻辑里明明是三个不同的消息，但在接收方眼里就是一个没有边界的连续字节序列。所以粘包的本质不是 TCP 帮你把多个包粘在一起了，而是 TCP 没有义务帮你维护消息的边界，接收方读取时如果一次读得太多，把好几个消息的内容当成一次数据处理，看起来就像粘包。如果一次读得太少，把一个消息拆成了好几段，那叫做拆包或半包。大家习惯统称粘包，但严格来说粘包和半包是同一个根因的两面。那这个根因到底是什么？主要有两个层面，第一个层面就是刚才说的字节流特性。

应用层发送的数据交给 TCP 后，TCP 会把这些数据放进自己的发送缓冲区，它并不会按照你每次 send 调用次数来保持数据的语义分组，它可能把多次 send 的数据合并到同一个 TCP 段里发出，也可能把一个大的 send 数据拆成多个 TCP 段发出。你能控制的是每次往缓冲区里写入多少数据，但管不了 TCP 底层怎么切分和发送。第二个层面是接收方的读取时机。接收方的应用代码通常是在 socket 可读时去读取数据，但到底能读到多少字节，取决于内核接收缓冲区里已经有多少数据，以及你的 read 或 recv 函数指定了多大的缓冲区。

网络是瞬时的，两次 send 之间可能只隔了几毫秒，第二次 send 的数据在接收方还没开始读取之前就已经到达了，于是接收方一次 read 就把两份数据全读走了，这就在应用层形成了粘包效果。那么完全避免粘包有没有可能？有一种特殊情况是可能的，如果你每次发送数据后都等待接收方做出响应，确认收到了，然后再发送下一条数据，也就是采用严格的一问一答模式，那么每条消息在时间上被清晰隔开，接收方每次读取通常只会读到一条消息。但即便如此，也不能保证必然不会粘，因为 TCP 的 Nagle 算法可能把多个小数据段合并，或者网络延迟导致数据在接收缓冲区里同时存在。所以严格来说，只要应用层有两条以上消息在同一个连接上连续传输，就存在粘包或半包的风险，你必须主动去解决它。怎么解决？常见的办法有三种。

第一种，固定消息长度，你规定每条消息固定是一百个字节，不足的部分用空格或零填充，接收方每次就按一百个字节去截取。这个办法实现最简单，适合消息长度本来就固定或者长度极小的场景，比如一些设备控制协议。但它浪费带宽，而且如果消息长度超过一百个字节就没法处理了。第二种，使用特殊分隔符，每条消息发送时在尾部加一个自定义的结束标志，比如换行符，或者像一些文本协议里用的空行。接收方不断读取数据，检查缓冲区里有没有这个分隔符，一旦找到，就认为分隔符之前的内容是一条完整消息。HTTP 协议早期就是用空行分隔请求头，这个方法灵活，但有个。问题，如果消息内容本身里出现了和分隔符一样的字符，就可能导致错误切分。所以需要设计转义机制，比如把内容里的分隔符转义成别的字符，这样实现起来复杂度就上去了。

第三种，也是实际工程里最常用的一种，在消息前面加上一个定长的长度字段。发送方先发送一个固定大小的头部，头部里记录了后面消息体的字节数。比如用四个字节表示长度，接收方先读取那个定长头部，解析出长度，再读取对应长度的字节作为一条完整消息。这个方案既准确又高效，不受消息内容和长度限制，像很多 R P C 框架、 Web Socket 协议，底层采用的就是类似的思路。但这里要提醒你一句，即使你加了长度字段，接收代码依然需要处理半包的情况。什么意思？你读到了四个字节的头部，知道了消息体长度是一千，但这次 read 只读到了三百字节，你就不能急着去处理消息，而要把这三百字节缓存起来，接着读，直到凑够一千字节。反过来，如果一次读了两千字节，里面可能包含了一条完整消息，再加上下一条消息的一部分。

所以真正写接收逻辑的时候，通常要循环读取，每次先从缓冲区里提取定长头部，然后根据头部里的长度判断有没有完整消息体，有就取出来，没有就继续等。这就是所谓的数据包解析状态机，并不复杂，但必须在写代码时考虑清楚。最后总结一下，T C P 粘包不是 T C P 协议的一个故障，而是 T C P 字节流特性带来的天然现象。它本质上就是接收方无法从字节流里自行识别出消息的边界。解决思路万变不离其宗，要么固定长度，要么用分隔符，要么用长度字段，核心目的都是让接收方知道一条消息从哪里开始，在哪里结束。而长度字段加半包处理是目前最通用、最可靠的做法。理解了这一点，你在以后阅读任何网络框架的收发代码时，就会发现他们做的所有封装，几乎都是在和消息边界这四个字打交道。
