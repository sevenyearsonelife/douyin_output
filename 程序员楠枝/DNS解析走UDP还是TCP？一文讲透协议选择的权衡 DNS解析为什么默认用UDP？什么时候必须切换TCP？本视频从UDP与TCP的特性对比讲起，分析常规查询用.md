D N S 解析到底是走 T C P 还是 U D P？这个问题看似简单，但答案并不唯一。今天这篇内容我们就来把事情讲透，为什么正常情况下 D N S 都用 U D P？什么时候它又必须切换成 T C P？以及这个选择背后涉及的数据包大小、可靠性和网络安全的权衡。先说 D N S 本身是干什么的。D N S，域名系统，职责是把人类好记的域名，比如三 w 点 e x a m p l e 点 c o m 翻译成计算机能理解的 I P 地址。你每次打开网站，第一步几乎都是 D N S 解析。既然解析这么频繁，传输方式的选择就极其关键。我们对比一下 U D P 和 T C P。U D P 是无连接协议，数据直接发出去，不做确认，没有握手过程，速度快，开销小。

T C P 是有连接协议，需要三次握手建立连接，确保每个数据包都收到，可靠性高，但延迟和开销更大。如果 D N S 用 T C P 做每一次常规解析，每一次查地址都要先握手、建连接、再传输、再确认，这个开销在互联网的规模下是灾难性的。你点开一个网页，背后可能有十几个子资源要解析，那网页加载速度会肉眼可见的变慢。所以 D N S 明文解析的主流传输协议是 U D P，端口五十三。常规查询通常只涉及一个请求和一个响应，数据包非常小，U D P 的无连接特性让查询可以非常轻量的完成，一次往返就够了，这正好匹配 D N S 查询的短交互特点，这是 U D P 的天然优势。但 U D P 的问题是不可靠，数据包丢了就丢了，于是 D N S 走 T C P 的场景也随之而来。第一种场景，响应数据太大。

经典 D N S 规定 U D P 响应最多五百一十二字节，超过就得截断，有标志位告诉你包被截断了。虽然 E D N S 零协议把这上限提到了一千二百三十二字节甚至更大，但 U D P 包一旦超过 M T U，也就是最大传输单元，通常一千五百字节，就会被 I P 分片。分片包在网络中容易丢失，而且容易被人利用做放大攻击或缓存投毒，风险很高。所以当 D N S 查询的响应特别大，比如包含大量 D N S S e c 签名记录时，解析器发现响应被截断或者包太大，就会自动改用 T C P 重新查询。T C P 没有包大小限制，可靠传输保证了数据的完整性，这是第一种。第二种场景，区域传送。

D N S 服务器之间同步数据时，要把某个域名的整个区域文件从一个主服务器复制到从服务器，这数据量很大，而且必须保证完整准确，一条记录都不能少。所以区域传送必须走 T C P，这也很好理解，大文件传输要求高可靠性，这正是 T C P 的强项。第三种场景也是近年来最受关注的，加密 D N S。传统 D N S 走 U D P 是明文传输，任何人都能看到你在查询什么域名，容易被劫持或监听。为了安全，行业推出了 D N S over T L S 和 D N S over H T T P S，也就是 Do T 和 D O H。

这两者都建立在 T C P 之上，Do T 用专属端口八百五十三，D O H 直接走 H T T P S 的四百四十三端口，因为 T C P 的连接管理能力强，能承载更长的会话，而且 T L S 需要可靠的流传输，所以加密 D N S 同时放弃了 U D P。D O H 还有个额外好处，它混在正常的 H T T P S 流量里，防火墙很难精确识别和封锁。而 T C P 的延迟问题通过长连接和复用得到很大缓解，每次查询不必重新握手。这里还要说一个实际网络里的现象，U D P 丢包带来的体验问题。W i F i 或者移动网络下，U D P 流量常常被限速或者丢包，很多操作系统上的 D N S 解析器都有超时重试机制，当 U D P 查询迟迟没有响应，会等上一两秒，然后自动改成 T C P 重试。

所以你会偶尔遇到这样的。情况，某些网络环境下，网页第一次打开很慢，刷新一下就好了，这中间很可能就发生了一次 DNS 从 UDP 切换到 TCP 的隐性过程。总结来看，DNS 解析不是单纯的二选一，常规查询走 UDP，求的是快；响应变大或者需要区域同步时走 TCP，求的是吻合全；加密时代走 TCP 上的 TLS 或 HTTPS，求的是安全；未来还有 DNS over QUIC，它基于同样无连接的 UDP，但自带加密和可靠性，又在向既要快又要安全的方向演进。理解这个变化，你就能明白，协议的取舍从来不是绝对的，而是网络环境、数据规模和安全需求共同作用的结果。
