后端如何设计一个直播间弹幕系统？先明确弹幕系统的定位，它的本质是超高吞吐、低延迟、高并发写入的实时消息分发系统。一场热门直播，峰值可能每秒涌入几十万甚至上百万条弹幕，同时有上千万人在线观看。和普通聊天室不同，弹幕没有强一对一属性，也不要求每条都永久保存。它是典型的瞬时消费、大量广播场景，因此设计重点要放在链路上，而不是数据仓库上。后端设计从协议选择开始，常见的方案有两种：Web Socket 和 H T T P 轮询。Web Socket 是主力，因为它是全双工长连接，服务器能主动把消息推给用户，延迟低到百毫秒级。H T T P 轮询则适合降级场景，比如某些弱网环境连不上 Web Socket 时，客户端退回定时拉取接口。

但注意，轮询会放大服务器压力，所以降级时一般只拉取最近几秒的滚动消息，并且拉取间隔不能太短，否则流量会成倍涨。接下来是整个系统最核心的部分，消息的接收和广播。假设用户发了一条弹幕，请求先到接入层，接入层是一组无状态的 Web Socket 网关服务器，它们只负责维持客户端连接和收发字节。网关收到消息后，第一件事不是直接转发，而是做合法性校验，内容长度、敏感词、频率限制。校验通过，这条消息就被推送到一个统一的入口，也就是消息队列。这里为什么要用消息队列？因为弹幕的写入峰值极高，如果让所有网关直接写数据库，数据库必然被击穿。消息队列起到削峰填谷的作用，后端服务从队列里消费消息，再执行真正需要的逻辑，比如存一份到消息历史表，同时把消息路由到对应的直播房间。存储怎么设计？

弹幕历史记录不需要强事务，通常用性能高的 No S Q L 数据库，或者直接用支持追加写入的日志型存储。关键点是按直播间 I D 加时间做分区，这样进入直播间时拉取历史弹幕只需一次范围查询。但历史存储只服务进来的人，它不参与实时分发。实时分发路径是这样的：后端服务从队列消费到消息后，把弹幕数据发到一台对应直播间的分发器，分发器维护着一张房间在线表，记录这个房间当前有多少个 Web Socket 连接，分布在哪些网关节点上。为了精准发送，后端需要知道某个用户连在哪台网关，这样才能把弹幕推给那台网关，再由网关推给用户。

这种设计叫按连接路由，避免给全网所有网关广播，但这样还不够高效，真正的弹幕系统会用上 Redis 或类似的分布式缓存，维护直播间网关节点、连接列表的映射关系，每条弹幕只需转发给这个房间涉及的节点，而不是所有节点。同时 Redis 还能用来做房间级别的计数、限流和在线人数统计。说到限流，这是弹幕系统后端最容易忽略又最致命的部分。如果没有限流，一个用户拿脚本每秒发几百条弹幕，整个房间都会被刷屏。所以后端必须在网关层做单用户限流，比如每个用户每两秒只能发一条。同时在服务端做全局限流，比如这个直播间每秒最多接受一万条弹幕，超过的直接丢弃。更精细一点，还可以按用户等级、用户举报状态设置不同优先级，主播和管理员的弹幕优先进入广播队列。那么弹幕的广播到底是推还是拉？

主流做法是推拉结合，实时消息用 Web Socket 直接推送，保证秒达，而在进入房间时，客户端先通过 H T T P 拉一次最近的历史弹幕，比如最近一分钟内的消息，这样既能快速填充屏幕，又避免了服务器对离线用户积压数据。再看消息丢失和数据一致性问题，弹幕系统允许偶尔丢消息，但绝不能容忍系统崩溃。所以消息队列里的数据要持久化，这样消费方宕机时可以重新拉取。而广播给用户的过程允许部分消息因网络波动丢失，用户不会感知到严重问题，因为大。弹幕本来就是高频信息，丢失一两条不影响体验，这给了设计者很大的容错空间。还有一点，多房间的隔离，弹幕系统必须保证一个房间的流量洪峰不影响其他房间，常见做法是按直播间 I D 做分片。

比如把不同房间的消息路由到不同的 Kafka 分区，或者不同的 Redis 槽位，这样千万人围观的大主播只会压满一个分片，其他中小主播的房间依然正常。整个链路走下来，你可以这样理解：网关负责连接，队列负责缓冲，消费者负责逻辑，分发器负责路由，Redis 负责状态，数据库负责历史，每个环节都能独立扩容，每个环节都只做一件事。比如高峰期你可以把网关节点加到一百台，消费者进程调到五十个，但数据库一台都不变，因为写入已经被队列和批量处理弱化了。最后说说弹幕系统要关注的三个关键指标，一是端到端延迟，就是用户发出到其他人看到的时间，目标通常在一秒以内。二是入站吞吐，即每秒能接收多少条合法弹幕，这决定了能否支撑住极端场面。三是系统的优雅降级，当负载超过上限时，系统选择丢弃部分非核心弹幕，还是直接拒绝新用户连接。

成熟系统一般会优先保证主播发言和连麦消息不丢，普通弹幕可以降速。另外还要考虑客户端断线重连后如何补拉消息，一般会在重连后的第一次拉取中带上断线期间的弹幕。所以后端设计直播间弹幕系统，本质上是在设计一条高吞吐管道，你不需要让每一条数据都百分之百交付，但你要让绝大多数消息在正确的时间到达正确的人，并且整个管道在承受极端脉冲流量时不塌方。做好协议选择、消息队列、连接路由、限流和降级这五件事，弹幕系统的基本盘就稳了，其余的一切都是在这个框架上不断优化延迟和机器成本。记住一句话，弹幕系统设计的好不好，不看平时发消息顺不顺，看的是突然千万人涌进同一个直播间的那十秒钟，你的后端还稳不稳得住。
