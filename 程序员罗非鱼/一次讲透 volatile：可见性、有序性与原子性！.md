什么是 Java 里的 volatile 关键字？简单说，它是一个修饰变量的关键字，用来告诉编译器和 CPU，这个变量可能被多个线程同时访问，别自作主张地优化它。它到底解决了什么问题？为什么面试里几乎必问？因为它牵扯到并发编程里两个最底层的麻烦：可见性和有序性。先讲清楚它不是什么。很多人以为 volatile 能保证线程安全，其实它只保证可见性和有序性，不保证原子性。也就是说，它不能替代锁。理解这一点是理解它全部行为的前提。那什么是可见性？在现代多核 CPU 里，每个核心都有自己的缓存。线程读写变量时，往往先动自己核心的缓存，而不是直接读主内存。这就导致一个线程改了值，另一个线程可能还在看旧值，永远看不到变化。

volatile 的作用就是，对一个 volatile 变量的写，会立刻刷回主内存，读的时候会直接从主内存重新拉取。这样一来，一个线程的修改，其他线程马上能看见。它是怎么做到的？在底层，JVM 会在 volatile 写操作前后插入特定的内存屏障。写之前插入 store-store 屏障，写之后插入 store-load 屏障。读操作前后也有对应的屏障。这些屏障不是空操作，它们会限制 CPU 和编译器的重排序，并强制刷新或失效缓存。在 x 八六架构上，volatile 写通常编译成带 lock 前缀的指令，这个前缀会触发缓存一致性协议，把其他核心里对应的缓存行标记为失效。再讲有序性。编译器和 CPU 为了性能，会调整指令执行顺序，只要不改变单线程的结果就行。

但在多线程下，这种重排序可能让另一个线程看到半成品状态。volatile 通过内存屏障禁止特定类型的重排序，保证屏障两侧的指令不会乱序穿过。一个经典例子是双重检查锁的单例模式。如果实例字段不加 volatile，另一个线程可能拿到一个构造还没完成的对象。加上 volatile 后，这个隐患就被堵住了。那它为什么不保证原子性？因为像 i 加加 这种操作，本质是读、改、写三步。volatile 只能保证每一步读到的都是最新值，但两步之间可能被其他线程插进来。两个线程同时读到五，各自加一写回六，结果就少加了一次。要解决这个，得用 synchronized 或者 Atomic Integer 这类原子类。所以总结一下，volatile 是一把轻量级的同步工具，代价小但不万能。

它适合一个线程写、多个线程读的状态标志位，比如开关变量。凡是涉及复合操作、需要互斥的场景，还是得靠锁。理解它的边界，比记住它的定义更重要。
