什么是分库分表后的分页查询？简单说就是当数据被分散到多个数据库或多张表之后，你仍然想按顺序取出第 N 页的数据，这时候查询该怎么做？它比单表分页复杂得多，因为数据不再集中在一处，页码也不能直接对应到某一张表上。今天我们就把它讲清楚，为什么普通分页会失效，常见的几种解法各自适合什么场景，以及实际使用时要注意哪些坑。先看单表分页为什么简单。假设一张表有一亿条数据，你执行按时间倒序取第十页，每页二十条，数据库可以直接利用索引定位到偏移量，跳过前一百八十条，再取二十条。整个过程只查一张表，顺序和页码是天然对齐的。但分库分表之后，数据可能被拆到四个库，每个库四张表，一共十六个分片。你想要的第十页数据可能分散在多个分片里。如果每个分片各取第十页再合并，结果一定是错的，因为每个分片的前十页加起来远多于全局的前十页。

这就是第一个核心难点，页码是全局概念，而数据是局部分布的。那怎么办？第一种思路叫全局偏移，也就是把每个分片的前 N 页都查出来，在内存里归并排序，再取真正的第 N 页。比如你要第十页，就让十六个分片各返回前两百条，汇总后排序，取第一百八十一到两百条。这个方法逻辑正确，但代价很大。页码越深，每个分片要返回的数据越多，内存和网络开销急剧上升，所以它只适合浅分页，比如前几十页。第二种思路是禁止跳页，只允许上一页、下一页。它不依赖页码，而是记住上一页最后一条记录的排序值，下一页就从那个值之后继续取。比如按时间倒序，上一页最后一条时间是某个时刻，下一页就查所有分片中小于这个时刻的数据，各取前二十条，归并后再取二十条。因为每个分片只返回少量数据，深度翻页也不会变慢。代价是用户不能直接跳到第一百页，只能顺序翻。

第三种思路是二次查询，也叫改写偏移。先让每个分片按条件取前 N 条，归并后确定全局第 N 页的最小排序值，再拿这个值回到各分片，查出所有大于等于它的数据，最后精确归并。它能在支持跳页的同时控制数据量，但实现更复杂，需要两次查询，还要处理排序值重复的边界情况。还有一种常见做法是用搜索引擎或专用中间件，把需要分页的字段同步到 Elasticsearch 这类系统，由它来承担全局排序和分页，数据库只负责按主键批量取详情。这样分页性能好，也支持复杂条件，但引入了数据同步延迟和额外运维成本。最后要提醒几个容易踩的坑。第一，排序字段必须全局唯一且稳定，否则不同分片返回的顺序可能不一致，导致数据重复或遗漏。第二，深分页本身在单表里也很慢，分库分表不会让它变快，只会更复杂。

第三，如果业务能接受，尽量用游标分页替代页码分页，它在分布式场景下最稳。第四，任何跨分片归并都要考虑内存上限，不能无限制的堆数据。总结一下，分库分表后的分页，本质是把局部结果拼成全局顺序。浅分页可以用全局偏移，深度翻页优先用游标，需要跳页且数据量大时考虑二次查询或搜索引擎。选哪种取决于你的页码深度，是否能接。接受顺序翻页以及愿不愿意引入额外组件。理解了这个权衡，你就不会在分页这件事上被分片数量牵着走。
