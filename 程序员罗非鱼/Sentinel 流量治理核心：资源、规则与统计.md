什么是 Sentinel？简单说，它是一套面向分布式系统的流量治理组件，核心任务是保护服务不被突发流量打垮。很多人第一次听到这个名字，会以为它只是一个限流工具。其实限流只是它最基础的能力之一。接下来我会讲清四个问题：Sentinel 到底解决什么问题？它的核心概念有哪些？它怎么判断一个请求该放行还是拦截？以及在实际系统里它通常怎么用，有哪些边界条件？先看它解决的问题。一个服务上线后最怕的不是没有流量，而是流量突然超过它能承受的上限。比如秒杀活动开始的一瞬间，请求量可能是平时的几十倍。如果没有保护机制，线程池被占满，响应变慢，上游调用超时，故障会沿着调用链一层层扩散，最后整个系统雪崩。Sentinel 要做的就是在入口处判断这个请求现在能不能进来，能进就放行，不能进就按预设策略拒绝、排队或降级处理。

它的核心概念有三个。第一个是资源，指的是被保护的对象，可以是一个接口、一个方法，也可以是一段代码。第二个是规则，指的是对这个资源设定的保护条件，比如每秒最多允许多少请求。第三个是槽位链，这是 Sentinel 内部的处理结构。一个请求进来后会依次经过不同职责的处理节点，每个节点负责一件事，比如统计、限流、熔断。这种设计让功能可以灵活组合，也方便扩展。那它怎么判断放行还是拦截？关键在于实时统计。Sentinel 会持续记录每个资源的调用情况，包括请求数量、响应时间、异常比例等。当请求到达时，它拿当前统计值和规则做比较。以限流为例，如果规则是每秒一百次，而当前这一秒已经处理了一百次，新来的请求就会被拒绝。熔断的逻辑不同，它关注的是错误。

如果某个资源在统计窗口内异常比例过高，Sentinel 会主动切断对这个资源的调用，让请求快速失败，避免继续消耗资源。等过一段时间再放少量请求试探，如果恢复正常就重新放行。实际使用中，Sentinel 通常接在服务的入口位置，比如在 Web 应用里，它可以拦截进入的 HTTP 请求。在微服务调用里，它可以保护被调用的下游接口。规则可以写在代码里，也可以放到配置中心动态调整，这样不用重启服务就能改变限流阈值。它还会提供实时的监控数据，让你看到每个资源的通过量、拒绝量和响应时间，方便定位问题。不过要注意几个边界。第一，Sentinel 保护的是单个服务实例，如果部署了多个实例，每个实例各自统计，总量控制需要配合集群限流模式。第二，规则本身要合理，阈值设得太低会误伤正常请求，设得太高又起不到保护作用。

第三，限流和熔断只是稳定性手段，不能替代容量规划和性能优化。它们是在系统已经接近极限时争取时间，而不是让系统凭空变强。总结一下，Sentinel 是一套以资源为核心、以规则为依据、以实时统计为判断基础的流量治理组件。它通过限流、熔断、降级等手段，在流量异常时保护服务，防止故障扩散。理解它的关键，是抓住资源、规则和统计这三个要素，以及它们之间如何配合做出放行或拦截的决策。
