有了 Cookie 和 Session 为什么还要用 JWT？这个问题很多人第一反应是 JWT 更先进，但真相没那么简单。今天我们就把这三次技术选择背后的逻辑、场景和代价一次讲清楚。先明确概念：Cookie 是浏览器里存的一小段文本，本质是客户端存储；Session 是服务器内存或数据库里存的一份用户状态，本质是服务端存储；而 JWT 全称 JSON Web Token，是一段自带信息的签名令牌，本质是无状态凭证。Cookie 负责放在哪，Session 负责记什么，JWT 负责证明你是谁。那为什么有了前两个还要用 JWT？核心原因是 Session 的状态存储在分布式时代撑不住了。

传统单机部署下，用户登录后，服务器把 Session ID 写进 Cookie，下次请求带着这个 ID，服务器查一下自己的内存就知道你是谁，这没问题。但一旦你的服务有多个节点，比如负载均衡后面挂了十台服务器，用户第一次请求落在 A 机器，第二次请求被分到 B 机器，B 机器没有这个 Session，用户就被当成未登录了。解决办法叫 Session 粘滞或集中式 Session 存储，比如用 Redis 统一存 Session。这能解决问题，但引入新麻烦：每次请求都要查一次 Redis，网络开销增加，Redis 挂了全部用户掉线。而且 Session 数据量一大，存储和运维成本直线上升。JWT 的思路完全不同，它把用户信息直接编码进令牌里，服务器不存任何状态。

用户登录成功后，服务端生成一个 JWT 返回给客户端，客户端之后每次请求都带上这个 JWT，服务端拿到后只需要用密钥验证签名是否有效，再解析里面的内容就知道用户是谁、有什么权限。整个过程不查数据库、不查缓存、不依赖任何共享存储，这就是无状态的含义。服务端不需要记住你，你拿着令牌来，我验一下签名就认你。但 JWT 不是免费的午餐，它的第一个代价是无法主动失效。Session 存在服务器里，你想踢用户下线，删掉那个 Session 就行。JWT 在客户端手里，只要没过期，服务器没有能力让它作废。你改了密码，旧 JWT 还是有效的，用户被禁用了，他手里的 JWT 还能继续用一段时间。所以 JWT 通常要设一个较短的过期时间，比如十五分钟，再配合一个 Refresh Token 去续期，这又引入了刷新令牌的管理复杂度。

第二个代价是体积。JWT 把用户信息直接塞进令牌里，通常比一个随机的 Session ID 长很多，每个请求都带着这个大头，网络传输开销增加。如果你把太多信息塞进去，可能超过 Cookie 的大小限制，就得改用 Local Storage 或者 Authorization 头来传，这又带来跨域和 XSS 攻击面的问题。相比之下，Session ID 只是一个短字符串，Cookie 自动携带，实现简单。那到底什么时候该用 JWT？最典型的场景是跨域、跨端、无共享存储。比如你有一个移动 App、一个网页、一个第三方开放 API，他们都访问同一套后端服务。用 Session 你得让所有端共享同一个 Session 存储，还得处理 Cookie 在非浏览器环境下的兼容问题。

用 JWT，客户端拿着令牌走天下，后端只管验签，天然适合这种多端接入的架构。另一个典型场景是微服务，每个微服务都验证 JWT，不需要每个服务都去连一个 Session 服务，减少了耦合和延迟。但如果你做的是传统 Web 应用，用户量不大，服务端部署在单机或少量机器上，Session 加 Cookie 依然是最简单最可靠的选择。它的优势是可控性，能主动踢人，能实时查询在线状态，能精确控制会话生命周期。很多后台管理系统、银行网银至今还在用 Session，不是因为技术落后，而是因为安全审计和权限控制要求高。最后给你一个判断框架：如果你的系统是多端、分布式、对实时失效要求不高，JWT 是更合适的选择。如果你的系统是单端、集中式，需要严格会话管理，Session 依然是更稳妥的方案。

技术没有银弹，JWT 不是替代品，而是针对 Session 在特定场景下的短板做出来的另一把工具。理解这个差异，比记住 JWT 更好这个结论重要得多。
