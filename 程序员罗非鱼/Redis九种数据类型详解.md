什么是 Redis 的九种数据类型？简单说，Redis 不只是一个缓存，它更像一个数据结构服务器。你往里面存的不只是字符串，而是九种各有脾气的数据结构。理解这九种类型，才算真正理解 Redis 能做什么、不能做什么，以及为什么它在高并发场景里这么能打。我们先从最基础的字符串开始。字符串是 Redis 的起点，也是其他类型的地基。它能存文本、数字，甚至序列化后的对象。它的价值在于原子操作，比如 incr 自增，秒杀系统的库存扣减就是靠这个原子性保证不会超卖。如果你需要计数器、分布式锁或者简单的缓存，字符串就够了。接下来是哈希。哈希相当于一个对象，一个 key 里塞多个 field，你可以只修改对象里的某个字段，不用整个序列化再写回。

比如存用户信息，name、age、email，改年龄时只改 age 字段，省流量也省时间。哈希特别适合存结构化数据，是 MySQL 行记录的天然映射。然后是列表。列表是有序的字符串集合，可以从左或右推入弹出。它天生就是消息队列的雏形，lpush 加 brpop 能实现阻塞读取，这就是最简单的可靠消息队列。列表还适合做时间轴，比如你的微博动态，按时间顺序排列，左边推入新内容，右边读取。集合是另一个方向，它无序但成员唯一。它的看家本领是集合运算，交集、并集、差集。比如你可能认识的人，就是拿你的好友集合和别人的好友集合做交集。抽奖系统里，把用户 ID 加进集合，srandmember 随机抽一个，保证不重复中奖。有序集合在集合的基础上加了一个分数，按分数排序，这是 Redis 最聪明的类型之一。

排行榜就是它的主场，每个用户一个分数，随时更新，随时按排名取前 N 名。而且它底层是跳表加哈希表，插入、更新、查询都是对数级复杂度，百万级别的排行榜，毫秒级响应。接下来三种是 Redis 5.0 之后引入的。第一个是位图，它本质上还是字符串，但按位操作。你可以用一个 bit 表示一个状态，比如用户一年三百六十五天的签到记录，一个用户只需三百六十五个 bit，不到五十字节。一亿用户一整年的签到数据也就五百兆左右。统计连续签到天数，用 bitfield 和 bitcount，效率极高。然后是 HyperLogLog，它的名字很吓人，但用途很朴素，做基数统计。所谓基数，就是去重后的数量。比如统计一个页面的 UV，每个用户 ID 进来就 pfadd 一次，最后 pfcount 一下，就能得到大约的独立访客数。

它的误差在百分之零点八一以内，但省内存省到离谱，不管你有多少数据，每个 key 最多只用十二 KB。如果你能接受大约的 UV，它是完美方案。最后是地理空间类型，它基于有序集合实现，但把经纬度编码成分数，专门用来算距离和找附近的人。geoadd 存入位置，geosearch 找半径五公里内的餐厅，按距离排序。外卖、打车、社交打卡，都是这个类型在撑腰。现在你把这九种类型放在一起看，就会发现 Redis 的设计哲学。每一种类型都是为一种特定问题场景量身定做的。字符串解决计数和缓存，哈希解决对象存储，列表解决队列和时间线，集合解决关系和去重，有序集合解决排名和权重，位图解决海量布尔状态，HyperLogLog 解决海量去重计数，地理空间解决位置查询。但这里有一个重要的提醒，类型只是工具，怎么用才是关键。

用错了类型，性能会急剧下降。比如用集合去模拟排行榜，每次排序都是全量计算，用字符串去存一个对象的多个字段，每次修改都要整个读出来再写回去，网络开销翻倍。所以真正的 Redis 高手拿到需求后第一件事不是写代码，而是问自己这个场景的数据结构本质是什么？是计数？是关系？是排名？还是位置？然后再从这九种类型里选出最合适的那一个，或者几个组合使用。总结一下，Redis 的九种数据类型不是九个孤立的工具，而是一整套解决不同数据形态的思维框架。字符串是基础，哈希是对象，列表是序列，集合是关系，有序集合是排名，位图是状态，HyperLogLog 是统计，地理空间是位置。理解了它们各自的能力边界和适用场景，你就能在任何高并发系统里找到最合适的数据存储方案。这才是 Redis 真正值钱的地方。
