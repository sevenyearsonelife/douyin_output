什么是 MySQL 回表？简单说，当查询走二级索引时，二级索引的叶子节点通常只保存索引列和主键值。如果查询还需要其他列，MySQL 就得拿这些主键值再到聚簇索引里查完整行，这一次额外的查找就是回表。回表本身不是错误，但它意味着更多随机读写。数据量大、缓存不命中时，查询会明显变慢。所以减少回表的核心不是消灭所有回表，而是让高频、重要的查询尽量少回，或者把回表代价降下来。先分清哪些情况不回表。用主键查一行，本来就在聚簇索引上，不叫回表。如果查询需要的列，二级索引里全都有，也不用回表，这叫覆盖索引。所以最直接的办法就是设计覆盖索引。比如经常执行查询，条件是城市等于杭州，按年龄排序，只返回姓名。可以建立城市、年龄、姓名三列联合索引，城市做等值匹配，年龄用于排序，姓名作为返回列。

这样索引里已经包含所有需要的数据，MySQL 读完索引就能返回结果，不必再查主键。但覆盖索引不能随便堆列，它会让索引变大，占用更多磁盘和内存，插入、更新、删除也要维护更多索引页。所以要先找频率高、收益大的查询，再决定覆盖哪些列。一个通用原则是避免 SELECT 星号，只取真正需要的字段。返回列越少，越容易覆盖，网络传输和排序内存也更省。第二个办法是合理使用联合索引和最左前缀。把 WHERE 里的等值条件放在前面，再放排序或范围条件，最后放用于覆盖的返回列。比如联合索引是状态、创建时间、用户编号，那么按状态过滤、按创建时间排序时，就能顺着索引读，减少扫描和回表。这里要注意，范围条件后面的列通常很难继续用于精确定位，所以索引列顺序要结合真实查询模式，而不是只看列多不多。

第三个办法是利用索引条件下推，也就是 MySQL 五点六以后支持的 ICP。假设索引里有姓名和年龄，查询条件是姓名以张开头，并且年龄等于十八。没有下推时，存储引擎可能先按姓名找到主键，再回表取出整行，交给服务器层判断年龄。有下推时，年龄这个条件会尽量在二级索引上先过滤，不符合的行根本不回表。它不改变索引结构，但能减少无效回表次数。用 EXPLAIN 看到 Using index condition 通常说明这个机制在起作用。第四个办法是减少需要回表的行数。很多慢查询不是回表本身慢，而是回表太多。更精确的 WHERE、合理的 LIMIT、避免一次取几十万行，都能直接减少回表。深分页尤其典型，LIMIT 十万零十，先扫大量索引再回表，代价很高。可以改成延迟关联，先用覆盖索引查出这十行主键，再拿主键去原表取完整数据。

这样子查询只走索引，真正回表只有十次。还有一个辅助手段是 MRR 多范围读。它不减少回表次数，而是把一批主键排序后再批量读取，降低随机 I/O 的代价。是否生效要看版本、查询和优化器选择。最后记住，减少回表的最强工具是覆盖索引，其次是索引下推，减少返回行数和延迟关联。但索引不是越多越好，必须权衡写入成本、存储空间和优化器选择。实际优化时，先开慢查询日志，找到高频慢 SQL，再用 EXPLAIN 看是否走索引，是否出现 Using index 或 Using index condition，最后结合数据分布和业务读写比例做决定。这样减少的才是真正有价值的回表。
