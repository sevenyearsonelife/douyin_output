什么是 Ribbon？在微服务架构里，当一个服务需要调用另一个服务时，Ribbon 就是那个帮它决定到底该找哪一台机器的组件。它是 Netflix 开源的一个客户端负载均衡器，后来被 Spring Cloud 集成，成为早期微服务调用链里的关键一环。这期内容会讲清三件事：Ribbon 到底解决什么问题？它的负载均衡是怎么工作的？以及为什么现在它逐渐被替代？理解了它，你就能看懂微服务里服务发现和负载均衡这两块拼图是怎么咬合的。先说它要解决的问题。假设订单服务要调用用户服务，而用户服务为了扛住流量部署了五台机器。订单服务如果写死某一台的地址，那台机器挂了就全盘失败，其他四台也白白闲着。所以需要一个机制，在每次发起调用时，从可用的机器列表里挑一台。这个挑一台的动作就是负载均衡。

Ribbon 做的正是在客户端这一侧完成挑选。这里有个关键区别，负载均衡分两种，一种是服务端负载均衡，比如 Nginx，请求先到统一的入口，由它转发到后端某台机器。另一种是客户端负载均衡，调用方自己拿到所有可用机器的清单，自己决定发给谁。Ribbon 属于后者，它的优势是调用方掌握全部信息，可以灵活选择策略，也少了一层网络跳转。那 Ribbon 怎么知道有哪些机器可用？这就离不开服务发现。通常它会和 Eureka 这类注册中心配合。每台用户服务启动时，把自己的地址注册到 Eureka。Ribbon 定期从 Eureka 拉取这份清单，缓存在本地。当订单服务要调用时，Ribbon 就从本地缓存里挑一台，直接发请求。整个过程不需要额外的中间代理。挑哪一台是由负载均衡策略决定的。

Ribbon 内置了多种策略，最常用的是轮询，也就是按顺序一台一台来，简单均匀。还有随机策略，随机挑一台。还有加权响应时间策略，响应越快的机器被选中的概率越高。另外还有可用性过滤，它会先剔除掉多次调用失败的机器，避免一直往坏节点上撞。这些策略可以组合使用，也可以自己实现接口来定制。除了选机器，Ribbon 还负责一些调用层面的细节。比如重试，某台机器调用失败后，它可以自动换一台再试。比如超时控制，避免请求一直卡住。这些能力让调用方在面对部分节点故障时，仍然能保持整体可用。不过要强调一个前提，Ribbon 的这些能力都建立在它能拿到准确的服务清单之上。如果注册中心的信息过期，或者网络分区导致清单不一致，那再好的策略也可能选到已经下线的机器。所以它的效果依赖服务发现体系的健康程度。

那为什么现在提 Ribbon 越来越少了？因为 Netflix 在二零一八年前后把 Ribbon 置入了维护状态，不再积极开发。Spring Cloud 也随之调整，推荐用 Spring Cloud Load Balancer 来替代。新的方案更轻量，和 Spring 的响应式编程模型配合更好。所以如果你现在做新项目，可能不会直接用 Ribbon，但它的设计思想，也就是客户端负载均衡加服务发现这套组合，依然广泛存在于今天的微服务框架里。总结一下，Ribbon 是一个客户端负载均衡器，它从注册中心获取可用服务清单，在本地按策略挑一台机器发起调用，并支持重试和超时等容错能力。它解决的是微服务之间找谁调用、怎么分摊流量、节点故障怎么办这三个问题。理解它的工作机制，也就理解了微服务调用链里最基础的一层。
