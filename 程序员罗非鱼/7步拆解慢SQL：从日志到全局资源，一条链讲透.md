什么是慢 SQL？它不是一种固定类型的 SQL，而是执行时间超过阈值的查询。慢日志、性能视图或 APM 把它记录下来，我们就叫它慢 SQL。接下来用一条链讲清七步：从日志里发现它，再看 SQL 和执行计划，然后看等待、资源和并发，最后回到全局容量与业务影响。理解这条链才能避免看到慢就加索引的误判。第一步，先确认它是否真的慢。看慢日志阈值、采样比例和统计口径。有的系统阈值是一秒，有的两百毫秒。同一条 SQL 在缓存命中、主从不同节点、不同参数下，耗时可能差很多。阈值太低会淹没日志，太高会漏掉问题。先排除记录误差和偶发抖动，再决定是否深入。第二步，拿到完整 SQL 和绑定参数。很多慢查询不是 SQL 文本本身，而是某个参数导致扫描行数暴增。比如分页翻到很深，时间范围突然拉大，in 列表变长，或者发生隐式类型转换。

还要看执行次数，单次慢和总耗时高是两种问题，后者常常由高频小查询累积而成。第三步，看执行计划。重点不是只看用了没用到索引，而是看访问方式、预估行数、实际行数、连接顺序和临时表、排序。预估行数和实际行数差很多，常说明统计信息不准、条件选择性差或数据倾斜。执行计划是理解数据库准备怎么执行，不是最终结论。第四步，看等待事件。SQL 在等什么？是在等磁盘 I/O、锁、日志刷盘、网络，还是在等 CPU 调度？如果大量时间花在等锁，优化索引未必有用。如果等 I/O，可能是缓冲池命中低、回表多或数据量超内存。等待事件把慢翻译成具体资源，而且要结合时间线看，不能只看瞬时快照。第五步，看数据量和索引结构。表有多大？活跃数据占多少？索引选择性如何？是否存在回表、排序、函数计算导致索引失效？还要看更新频率和统计信息更新时间。

组合索引要注意最左前缀和范围条件后的列失效。索引不是越多越好，写多读少的表，多加索引会放大写入和存储成本。第六步，看并发和连接层。同一条 SQL 单跑很快，并发一上来就慢，可能是连接池、线程池、锁竞争、缓存穿透或热点行更新。还要看事务边界，长事务会持锁、拖住清理，让更多查询排队。连接池排队时间要单独监控。此时单条 SQL 优化只是局部，必须看并发模型。第七步，回到全局资源与业务链路。看数据库 CPU、内存、磁盘 I/O、网络、连接数，也看上下游应用发压、缓存命中、消息积压、报表任务、主从复制。慢 SQL 往往只是症状，根因可能是容量不足、流量突增、架构耦合或业务参数失控。如果根因是容量，优化 SQL 只是延缓问题。最后用同口径压测和上线观察验证，确认优化真的有效，且没有把风险转移到别处。

总结一下，七步不是七个孤立技巧，而是一条排查链。先定义慢，再定位 SQL 和参数，接着还原执行计划与等待，随后看数据、索引和并发，最后回到全局资源。每一步都在缩小范围，也都在提醒你，慢 SQL 是系统问题的入口，不是终点。
