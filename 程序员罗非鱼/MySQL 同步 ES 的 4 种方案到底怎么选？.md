什么是 MySQL 同步 ES？简单说就是把 MySQL 里的数据变化准实时的复制到 Elasticsearch，让 ES 承担搜索和分析的职责。MySQL 擅长事务和精确查询，ES 擅长全文检索和聚合，两者配合能各取所长。接下来我会讲清四件事：为什么不能直接双写，四种主流方案各自怎么工作，它们分别适合什么场景，以及选型时要盯住哪些条件。先说为什么需要同步。用户下单后要按商品名搜索订单，这种模糊匹配 MySQL 的 like 查询会全表扫描，数据量一大就撑不住。ES 倒排索引能毫秒级返回结果，但数据必须写进 ES 才能被搜到，而业务写入只发生在 MySQL。于是问题变成，怎么把 MySQL 的变更可靠地搬到 ES？第一种方案，同步双写。在业务代码里写完 MySQL 紧接着写 ES。

优点是实现最简单，延迟最低，写完立刻能搜到。但问题也很明显，两次写入不在一个事务里，MySQL 成功 ES 失败就会出现数据不一致。ES 抖动或超时会拖慢主流程。多语言、多服务场景下每处都要写一遍，维护成本高。它只适合写入量小、对一致性要求不苛刻的边缘场景。第二种方案，异步双写，也叫 MQ 解耦。业务写完 MySQL 后发一条消息到消息队列，由独立消费者写 ES。相比同步双写，主流程不再被 ES 的延迟和故障拖住，消费者失败还能重试。但它引入新风险，消息可能丢失或重复，需要消费端做幂等。消息顺序也可能乱，导致旧数据覆盖新数据。所以关键条件是消息队列要保证至少一次投递，消费者按主键做覆盖写，并且尽量按同一主键分区保证顺序。第三种方案，定时任务扫表。

用定时任务每隔几秒扫描 MySQL，把更新时间大于上次扫描点的记录同步到 ES。它不侵入业务代码，实现简单，适合存量数据初始化。缺点是延迟取决于扫描周期，通常秒级到分钟级，高频更新时容易漏掉中间状态，靠时间戳字段还怕时钟回拨和同秒并发写入。它适合对实时性要求不高、数据量中等的场景。第四种方案，订阅 binlog，这是目前最主流的做法。MySQL 会把所有变更写进 binlog，工具伪装成从库去订阅，比如 Canal、Debezium，解析出增删改事件后投递到消息队列，再由消费者写入 ES。它完全解耦业务，不增加主库查询压力，能拿到变更前后的完整数据，还能保证顺序。代价是架构链路更长，需要维护 binlog 格式为 row、订阅组件和消息队列，还要处理全量加增量的衔接，避免同步过程中丢数据或重复。

对比一下，同步双写最简单但最脆弱，异步双写缓解了耦合，但要自己解决消息可靠性。定时扫表最省事，牺牲实时性。binlog 订阅最重，但可靠性和实时性最好，也是大厂标配。最后说选型要看什么。第一看实时性要求，秒级以内基本只能选 binlog 或异步双写。第二看一致性容忍度，能接受最终一致就别做同步双写。第三看团队运维能力，binlog 链路需要有人维护中间件。第四看数据规模，千万级以上优先 binlog。无论选哪种，都要保证写入 ES 时以 MySQL 主键做唯一键，实现幂等覆盖，并监控同步延迟和数据量差异。记住一句话，没有最好的方案，只有匹配当前约束的方案。
