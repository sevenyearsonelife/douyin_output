有了线程，为什么还需要协程？这是很多程序员在接触高性能编程时都会问的问题。今天这条视频我会先讲清楚线程和协程的本质区别，然后解释协程到底解决了线程解决不了什么问题，最后用一个真实场景告诉你什么时候该用协程，什么时候还是得老老实实用线程。先看线程，线程是操作系统管理的最小执行单元，它由内核调度，每个线程都有自己的栈空间和寄存器上下文。线程之间的切换需要从用户态切换到内核态，再由内核决定下一个该跑哪个线程。这个过程叫上下文切换，它是有成本的，一次切换大约需要几微秒，听起来不多，但如果你的程序里有成千上万个线程，光切换开销就能把 CPU 吃满。那协程是什么？协程可以理解成用户态的轻量级线程，它不归内核管，而是由程序自己控制调度。

协程的切换不需要陷入内核，只需要在用户态保存和恢复几个寄存器，成本能比线程低一到两个数量级。更重要的是，协程可以自己决定什么时候让出执行权，所以它天然适合用在 I 斜杠 O 密集型的场景里。为什么 I O 密集型的场景需要协程？我给你拆解一下。假设你要写一个爬虫，同时抓取一万个网页。如果用线程，你可能要开一万个线程，每个线程都在等网络响应，CPU 大部分时间都在做无意义的切换。如果用协程，你只需要开几个线程，每个线程上跑几千个协程。当一个协程发起网络请求后，它不需要傻等，而是主动让出 CPU，让其他协程去干活，等数据回来了再回来继续处理。这样 CPU 利用率高，内存占用也小。那是不是说有了协程，线程就没用了？不是，协程本身不能并行，它只是并发。真正让多核 CPU 同时跑任务的还是线程。

协程跑在线程上，一个线程同一时刻只能执行一个协程。所以如果你的任务是纯计算密集型的，协程帮不上什么忙，线程或者进程才是正确的选择。协程的优势是在大量等待、大量连接、大量请求的场景里，把等待的时间让给别的任务用。真实世界里，像 Nginx、Redis 这类高并发服务器早就用了类似协程的模型。Go 语言的 Goroutine 本质就是一种协程，配合调度器跑在线程池上。你用 Go 写一个高并发服务，不用手动管线程，调度器会帮你把成千上万个 Goroutine 分配到几个线程上执行。这就是协程的价值，它让程序员能用同步的思维写异步的代码，同时把并发能力提升几个量级。最后做个总结，线程是操作系统级别的并发单位，适合 CPU 密集和需要真正并行计算的任务，但线程切换开销大，创建数量有限。

协程是用户态的并发单位，切换成本极低，适合 I O 密集和海量连接场景，但它不提供真正的并行。两者不是替代关系，而是互补关系。现代高性能架构里，通常是用线程承载并行，用协程承载并发。理解了这层关系，你在设计系统时就知道该在什么层面解决什么问题了。
