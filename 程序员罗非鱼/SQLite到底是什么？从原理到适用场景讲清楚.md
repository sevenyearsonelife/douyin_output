什么是 SQLite？简单说，它是一个非常轻量的关系型数据库，但它和大多数人印象里的数据库不太一样。它不需要单独安装一个服务器，也不需要启动一个后台进程，而是直接以一个文件的形式存在，程序读写它就像读写普通文件一样。理解这一点是理解 SQLite 全部特点的起点。接下来我会讲清几件事：SQLite 到底是怎么工作的，它为什么会被用在几乎每一部手机和每一个浏览器里，它适合什么场景又不适合什么场景，以及它有哪些容易被误解的地方。先看它的基本结构。传统数据库，比如 MySQL 或 PostgreSQL，通常是一个独立的服务进程，应用程序通过网络连接它，把 SQL 语句发过去，数据库处理完再把结果返回。SQLite 没有这个中间层，它是一个库，被直接链接进你的程序里。

你的程序调用它提供的函数，它就去读写磁盘上的那个数据库文件。也就是说，数据库引擎和应用程序运行在同一个进程里。这个文件本身是跨平台的，格式稳定，从二零零四年到现在都没有变过。那为什么这种设计很重要？因为它解决了一个很实际的问题。很多程序其实并不需要一整个数据库服务器。比如手机上的一个记事本应用，它要存几百条笔记，需要能查询、能排序、能保证数据不损坏。如果为它跑一个数据库服务，成本太高也太复杂。SQLite 让这些程序用很小的代价就获得了事务、索引、SQL 查询这些能力。它最核心的价值就是在不需要客户端服务器架构的地方，提供一个完整、可靠、零配置的关系型数据库。再来看它内部是怎么保证可靠性的。SQLite 最被称道的是它的原子提交和崩溃恢复能力。它使用一种叫预写日志的机制。

简单说，修改数据时不是直接改原文件，而是先把改动写到一个日志文件里，确认写完之后再合并回主数据库。这样即使程序在写入过程中突然断电或崩溃，下次打开数据库时，它能根据日志判断这个事务是完整提交了，还是只写了一半。如果只写了一半，就回滚掉，保证数据库不会处在一个损坏的中间状态。这就是所谓的 ACID 特性中的原子性和持久性。对于没有专人维护的嵌入式场景，这一点极其关键。那它适合用在哪里？典型场景有几类。第一类是移动端和桌面应用。安卓和 iOS 系统内部都大量使用 SQLite，浏览器用它存书签、历史记录和缓存。第二类是嵌入式设备，比如路由器、汽车系统、机顶盒。这些设备资源有限，没有条件跑独立数据库服务。第三类是小型的网站或原型开发，访问量不大时，SQLite 完全够用，而且部署简单。第四类是数据分析。

很多人把大量数据放进一个 SQLite 文件里做本地查询，因为它读取效率高，又不需要安装任何东西。但它也有明确的边界。SQLite 的并发写入能力有限，同一时间只允许一个写操作，其他写操作要排队。如果很多客户端需要同时频繁写入，比如一个高并发的 Web 服务，SQLite 就会成为瓶颈。这种场景应该用客户端服务器型数据库。另外，它没有内置的用户权限系统，数据库文件的访问控制完全依赖操作系统的文件权限。它也不适合超大规模数据集，虽然理论上能存很大，但单文件管理几百 GB 并不是它的设计目标。所以判断标准很简单：如果写入并发不高，部署环境简单，数据量在合理范围内，SQLite 是极好的选择。反过来就要考虑别的方案。最后澄清一个常见误解。有人觉得 SQLite 太简单，不算真正的数据库。这是不对的。

它完整支持事务，支持大部分 SQL 标准，支持索引和触发器，可靠性经过了极其严格的测试。它不是玩具，而是一个经过精心设计的，在特定约束下做到极致的工程作品。它的哲学不是功能最多，而是在嵌入式和本地场景里，把正确性、稳定性和零维护做到最好。理解了它的定位，你就能判断什么。时候该用它，什么时候不该用。
