什么是 JWT？全称 JSON Web Token，是一种把用户信息打包成字符串，并用签名保证没被篡改的令牌格式。它由三段用点号连起来的文本组成：头部、载荷、签名。头部声明类型和签名算法，载荷放具体数据，签名用来验证前两段有没有被动过手脚。很多人听到的说法是，有了 JWT，服务器就不用存 session 了，天然支持分布式，特别先进。但你去翻主流网站，会发现他们的登录态大多还是一串看不懂的随机字符串。准确的说，主流网站大量使用 JWT，只是很少把它当做长期的登录凭证。下面我们说清三件事：它到底是什么？缺陷在哪？真实系统怎么组合使用它？先说结构。JWT 的头部和载荷只是 Base64URL 编码，不是加密。任何拿到令牌的人都能把它解开，看到里面的用户 ID、角色、过期时间。

所以在载荷里绝对不能放密码、手机号这类敏感信息。签名只保证完整性，不保证保密性。那它为什么看起来很美？因为无状态。服务器验证签名就能确认令牌是自己签发的，不用查数据库。用户从一台机器换到另一台，服务不用共享 session，扩容很方便。这在服务数量多、跨域、跨组织的场景里确实是优点。问题出在“无状态”这三个字上。状态不是消失了，而是被塞进了令牌本身，并且一旦签发就无法收回。用户点了退出登录，或者账号被封、密码被改，只要令牌还没过期，它就依然有效。想让它立刻失效，只能维护一张黑名单，而黑名单本身就是状态，绕一圈又回来了。第二个问题是过期时间的取舍。设的短，用户体验差，要频繁刷新；设的长，泄露后的窗口就长。很多教程干脆设七天甚至三十天，等于把风险放大。第三个问题是存储位置。

放在 localstorage，任何一段注入的 JavaScript 都能读走，XSS 一旦成功，令牌直接失手。放在 cookie 里可以加 HTTP Only，脚本读不到，但又带出 CSRF 问题，需要用 SameSite 等属性配合。这里没有免费午餐，只有权衡。第四个问题是体积和杂项成本。JWT 比一个随机 ID 大得多，每个请求都要带上，流量和解析开销都更高。再加上密钥轮换、时钟偏差、算法配置错误，比如某些库允许算法写成 none，或者混淆对称与非对称算法，都会变成真实漏洞。那主流网站到底怎么做的？他们的登录态通常是服务端 session，浏览器只拿一个不透明的随机 ID，真正的用户数据存在 Redis 之类的存储里，服务器一查就知道是谁，想踢谁就删掉那条记录。简单、可撤销、体积小。

JWT 真正发光的地方是短生命周期的凭证传递。比如 OpenID Connect 里的 ID Token，用来向第三方证明这个人刚刚登录过。比如 API 访问令牌，有效期只有几分钟到一小时。再比如微服务之间、跨公司之间的调用，服务 A 相信服务 B 签发的令牌，不需要共享数据库。这时候无状态就是优势，过期快也就不是问题。再配合刷新令牌、轮换、重复使用检测，才能把安全性补回来。所以结论不是 JWT 被吹过头了，别用，而是把 JWT 当成长期登录态，等于把一个为跨域、短时、多方信任设计的工具，硬塞进它不擅长的位置。理解它的边界，比记住用 JWT 很潮重要得多。
