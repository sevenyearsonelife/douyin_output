什么是负载均衡？简单说，它把大量访问请求分发给多台服务器处理，用户只访问一个地址，背后却可能有一组机器共同服务。它的目标不是让单台机器更快，而是让整个系统更稳，更容易扩展。接下来会讲清它的核心流程和常见算法，也会说明四层和七层的区别，健康检查、会话保持和部署形态同样会放进真实场景里解释。先说它是什么，负载均衡器通常位于客户端和后端服务器之间，对外提供统一入口，比如域名、虚拟 IP 或监听端口。请求到达后，它按规则选中一台后端，再转发过去。后端可以是一组网站服务器、应用服务器、缓存节点，也可以是数据库代理。对用户来说，后面有多少台机器并不重要，重要的是访问体验像在用一个服务。为什么需要它？因为单台服务器有上限，CPU、内存、连接数、磁盘 I/O，任何一项先到瓶颈就会变慢甚至拒绝服务。

流量会高峰，业务会增长，机器也会故障。如果只有一台机器，它一挂服务就中断。负载均衡把请求分散到多台机器，既能水平扩展，用增加机器换吞吐，也能在部分机器故障时继续服务。它还能配合发布，把新版本先切一小部分流量，确认没问题再扩大。要注意，它主要解决入口流量分配和可用性，不能自动治好代码慢、慢查询或数据库瓶颈。它怎么工作？核心流程可以拆成四步：接收请求、选择后端、转发请求、返回响应。选择后端靠算法，轮询最简单，按顺序轮流发。加权轮询适合机器配置不一致，性能强的多分一些。最少连接会把新请求交给当前连接较少的机器，适合请求耗时差异大的场景。一致性哈希常用于缓存，让同一个用户或同一个键尽量落到同一台机器，提高缓存命中率。还有最短响应时间、随机等，没有万能算法，关键是匹配业务特征。

健康检查是保命机制，它定期探测后端，比如发 HTTP 请求或建立 TCP 连接，连续失败就标记不可用，不再转发，恢复后再放回，这样能减少用户打到坏机器上的概率。但探测太敏感可能误摘正常机器，太宽松又可能把请求送给已经出问题的节点。阈值、超时、重试次数都要按业务调整。再看四层和七层，四层主要看 IP 和端口，处理 TCP 或 UDP 流量，速度快、开销小，但看不到 HTTP 内容。七层能解析 HTTP，可以根据域名、路径、请求头、Cookie 做路由，还能做 TLS 终止、限流、灰度发布和 API 网关功能，代价是处理更复杂，性能开销更高。实际系统常组合使用，外层做四层入口，内层做七层路由。会话保持也很关键，如果应用把登录状态存在单台服务器内存里，用户下次被分到另一台机器就可能掉线。

解决办法有两种，一是让负载均衡器做粘性会话，把同一用户固定到同一后端，二是把会话外移到 Redis 这类共享存储，让后端尽量无状态。后者扩展性更好，但增加了对共享存储的依赖。部署形态很多，可以用硬件设备，也可以用 Nginx、Haproxy、Envoy 等软件，还可以用云厂商的负载均衡服务。DNS 轮询也能做简单分流，但故障切换和精细控制较弱。微服务里还有客户端负载均衡，由调用方自己选择实例。无论哪种，负载均衡器自己都不能成为单点，通常要做主备或集群，跨可用区部署。真实场景里，电商大促会把流量分到多台 Web 服务器，视频网站会把请求分到不同边缘节点，API 网关会在微服务之间做路由和限流，数据库读写分离会把读请求分到多个只读副本。一个简单例子，网站原来一台机器，后来增加到三台。前面放负载均衡器，轮询分发。

某台机器宕机，健康检查把它摘掉，用户几乎无感。但也要知道限制，它不保证业务一定正确，重试可能带来重复下单，所以接口最好幂等。配置不当可能把流量集中到少数机器，引发雪崩。跨地域调度还要考虑网络延迟和数据一致性。总结一下，负载均衡是分布式系统的入口调度层，它做三件核心事：分发请求、感知故障、支持扩展。理解算法、四层七层、健康检查和状态管理，才能把它用对。它不是魔法，而是把单机问题变成集群问题后，必须认真设计的一层基础设施。
