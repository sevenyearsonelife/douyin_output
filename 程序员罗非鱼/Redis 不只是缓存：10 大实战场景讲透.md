什么是 Redis？很多人把它等同于缓存，更准确地说，它是一个以内存为核心的数据结构服务器，提供字符串、哈希、列表、集合、有序集合、位图、HyperLogLog 和 Stream 等结构。它的命令执行以单线程为主，所以单条命令具备原子性，这也是很多技巧成立的基础。把这层看清，你会发现它能承担的不只是加速查询。接下来用十个实战场景讲清它解决什么问题，怎么落地，边界在哪里。第一个场景是缓存，这是最主流的用法，把数据库热点数据放进 Redis，读请求先查缓存，未命中再查库并回填，同时设置过期时间。要处理穿透、击穿和雪崩，常用空值缓存、互斥重建和过期时间打散。

第二个场景是分布式锁，多个服务实例竞争同一资源时，可以用 S E T key value N X P X 超时获取锁，用唯一值标识持有者，再用 Lua 脚本校验后释放。它能解决大部分互斥问题，但强一致场景要谨慎，锁续期和故障切换需要额外设计。第三个场景是限流，固定窗口用 I N C R 加过期时间，滑动窗口用有序集合按时间戳计数，令牌桶可用 Lua 保证原子性，目的是保护数据库、下游接口或第三方服务，避免突发流量打垮系统。第四个场景是计数器与排行榜，I N C R 能做文章阅读数、点赞数，有序集合按分数排序，天然适合实时热榜。注意高频写入可先聚合再落库，避免把 Redis 当唯一事实源。第五个场景是会话共享，用户登录后把 Session 写入 Redis，多个应用实例都能读取，服务就可以无状态扩容。

关键是设置合理过期时间，并处理 Redis 故障时的降级登录策略。第六个场景是轻量消息队列，List 能做简单队列，Pub Sub 适合实时广播，但不持久。更完整的是 Stream，支持消费组、确认和消息回溯，适合日志分发、异步任务等对可靠性要求中等的场景。第七个场景是延迟队列，把任务内容和到期时间写入有序集合，后台轮询 score 小于当前时间的任务并执行。它适合订单超时关闭、延迟通知，但精度取决于轮询频率，任务多了要分片。第八个场景是分布式 I D 和签到，用 I N C R 生成趋势递增的序列号，适合订单号辅助、活动编号。签到用位图，一个用户一年只需少量字节，查询和统计都很快。

第九个场景是地理位置，Redis 的 G E O 结构支持添加坐标、计算距离、查询附近的人或门店，外卖、打车、社交推荐都能用，但复杂路径规划仍应交给专门地理系统。第十个场景是统计去重，HyperLogLog 用极小内存估算 U V，适合海量独立访客统计，位图适合活跃用户、签到等布尔状态，集合适合需要精确成员判断的小规模去重。总结一下，Redis 快，核心是内存访问和高效数据结构，但快不等于万能，内存成本高，持久化有取舍，分布式锁、队列和统计都有语义边界。集群模式下，跨 key 的事务、Lua 和多键操作还会受分片限制，设计键名时最好让相关数据落在同一哈希槽。把它当工具箱，根据一致性、丢失容忍和规模选型，才能让系统真正快得稳。
