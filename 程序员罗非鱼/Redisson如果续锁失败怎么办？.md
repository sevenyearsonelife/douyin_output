什么是 Redisson 的续锁失败？简单说就是你用 Redisson 给某个共享资源加了一把分布式锁，锁有个默认的三十秒有效期，业务还没跑完，你得在锁过期前给它续命，也就是续锁。但如果续锁这个动作本身失败了，锁就可能在业务执行到一半时突然失效，别的线程就能趁虚而入抢到同一把锁，造成数据错乱。今天我们就讲清楚续锁为什么可能失败，失败后 Redisson 到底会怎么做，以及我们作为使用者应该怎么应对。先来理解续锁的机制。Redisson 的看门狗，也就是 Watchdog，会在你获取锁之后启动一个后台定时任务，默认情况下它每十秒检查一次，如果锁还在持有中，就把锁的过期时间重新设置为三十秒。这个机制保证了你只要没主动释放锁，业务方法还在跑，锁就一直有效。

但这里有个关键前提，就是续锁操作必须真正到达 Redis 服务器，并且被成功执行。那续锁失败的原因有哪些呢？最常见的是网络抖动，比如你的应用和 Redis 之间出现了短暂的连接超时，或者 Redis 主从切换期间请求没被正确路由。第二种可能是你手动关闭了看门狗，或者你自己设置了 leaseTime，也就是锁的固定租期。如果你指定了 leaseTime，Redisson 就不会启动看门狗，锁到期就自动释放，谈不上续锁。第三种是线程被阻塞，比如 G C 停顿或者业务代码里做了长时间等待，导致看门狗线程本身没机会执行续锁命令。那么续锁失败之后 Redisson 会怎么处理？这里要分两种情况。第一种续锁失败发生在锁还没过期的时候，Redisson 的看门狗会尝试重试，默认重试次数是三次，每次间隔一点五秒。

如果重试后还是失败，它会放弃续锁，但不会主动释放锁，锁会在剩余的有效期结束后自动过期。第二种情况更危险，续锁失败时锁已经过期了，那么锁就被 Redis 自动删除，其他线程就能立刻获取同一把锁。这时候你原来的业务线程还在继续跑，但它已经不再持有锁了，这就是典型的锁失效问题。Redisson 本身并不会因为续锁失败而中断你的业务代码，它只是安静地放弃了续锁。所以问题最终落到我们开发者身上，怎么避免或者应对续锁失败？第一道防线是配置合理的重试参数。Redisson 允许你调整看门狗的续锁间隔和重试策略，把重试次数适当调大，比如五次，重试间隔缩短到五百毫秒，能在网络瞬时抖动时提高成功率。但要注意重试次数太多反而会加重 Redis 压力，所以要根据你的网络质量来平衡。第二道防线是业务侧设置合理的锁超时时间。

如果你的业务逻辑本身很快，比如几百毫秒就完成，那续锁失败的影响很小，锁过期就过期了。但如果业务可能跑几十秒甚至几分钟，你就不能完全依赖看门狗。这时可以考虑在业务代码里主动加一个锁有效性的校验，比如在关键操作前调用 isHeldByCurrentThread 方法，确认锁还在自己手里。如果发现已经丢了，就立即抛异常或回滚。第三道防线也是最稳妥的方案，是使用 Redisson 的自动续锁和业务心跳结合的方式。你可以把业务逻辑拆分成多个小步骤，每个步骤完成后检查锁状态，如果发现锁快过期了，就手动调用 renewExpirationAsync 方法强制续锁一次。这样即使看门狗失效，你也有兜底手段。最后还要说一个容易忽略的点，续锁失败不等于锁被别人抢走，锁只有在过期后才会被其他线程获取。

所以如果你在续锁失败后，但锁还没过期前主动释放锁，那是最安全的选择。Redisson 允许你在 finally 块里调用 unlock 方法，但前提是你还持有锁。如果锁已经过期，unlock 会抛出 IllegalMonitorStateException，这个时候你只需要捕获异常，然后放弃操作即可。总结一下。锁失败是分布式系统中的正常风险，Redisson 的设计是尽力而为，但它不会为你的业务结果兜底。你要做的是理解看门狗的重试机制，合理配置参数，在业务关键节点主动检查锁状态，并且接受一个事实任何分布式锁都不是百分之百可靠的。最终一致性要靠业务代码的幂等设计和容错逻辑来保证。记住，锁只是工具，安全边界永远在你自己手里。
