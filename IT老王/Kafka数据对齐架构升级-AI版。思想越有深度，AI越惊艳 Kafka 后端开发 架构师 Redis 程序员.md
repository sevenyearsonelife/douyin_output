这次啊，我被 AI 狠狠的上了一课。好，在之前的视频当中，我是相当自信的给大家分享了一套基于 Redis 去优化 Kafka 的 offset 的技术方案，用来解决 Kafka 不丢消息但是容易丢业务数据的问题。还蛮以为最后代码写出来了，这个方案就算是过了。后来呢，我随手把方案扔给了 Germany，让他看看这个方案是否完美，并且有没有大厂真实用过这套类似的方案。结果一通交流下去，他随手就给我指出了一个非常核心的小问题，并且给出让人惊艳的解决方案，不光让整个方案的逻辑更加优雅了，更是和大厂的经验不谋而合，瞬间把整个方案的格局拔高到了一个让我拍案叫绝的地步。这次我就把这个过程跟你分享分享，相信也能让你思考一下程序员到底应该怎么对待 AI 这个庞然大物。我是楼兰，关注我，IT 路上一起进步。

那么现在看这个非常典型的业务场景，假设我们在做一个复杂的电商系统，用户的订单信息会源源不断的发到 Kafka，然后呢在下游有一堆的异步系统在同时消费这些订单数据进行不同的业务处理，大家的消费速度呢肯定是有快有慢的。比如核心交易业务要处理订单后续的交易动作，业务复杂，最终还要存数据库，处理速度慢的要死。而搜索推荐的业务只要把订单数据整理一下扔到 ES 里就行了，处理速度飞快。

平时大家各跑各的，大家速度不一致问题也不大，但业务总是要梳理的呀，到了每天晚上十二点，财务系统要求停，我要拉取全量数据去进行日中对账了，这时候天塌了，ES 速度跑得太快呀，可能把明天十二点零五分的订单都消费进去了，而 MySQL 因为跑得慢，还在吭哧吭哧处理今天晚上十点五十分的订单，数据在时间上是完全混乱的，财务一核对发现搜索系统里面有一万笔订单，但核心交易库里面只有九千九百五十笔，差了五十笔，财务就会以为系统出了大 bug，资金流失了，但实际上数据根本就没有丢，仅仅是因为 MySQL 消费它慢了十分钟。这往小了说是对账失败的问题，往大了说那就是这些下游消费者完全都是脱缰野马，你根本不知道他们到底处理到了什么程度，一旦出问题了，那就是有抓耳挠腮的份了。这就是几乎所有 MQ 场景都会遇到的异构数据对齐的问题。

最初基于我自己的理解和经验，我其实是有一套基础的解决方案的，具体细节在之前视频当中分享过，感兴趣的朋友可以去找来看看。简单来说就是放弃 Kafka 自带的 offset 的提交，由我们自己去把各个业务线的消费进度实时记录到 Redis 里，然后取所有消费者里最慢的那个进度记为统一水位线。那怎么解决十二点数据对齐的问题呢？我的想法是这样的，到了十二点整，系统去 Redis 里抓取跑得最快的那个消费者组的 offset，把这个位置记录下来作为全员对齐的目标进度。接下来所有消费者只要消费到了这个目标进度就主动调用 pause 方法停下来，直到等到消费速度最慢的那个消费者组，他也慢慢消费到了这个目标进度，系统检测统一水位线赶上了这个目标进度，这才认为数据已经对齐了，然后等待对账结束后大家再一起恢复进入下一个账期。

当时我觉得这个方案逻辑闭环简直完美，甚至已经开始信心满满的封装 SDK 工具包了。后来我随手把这个方案发给了 Germany，随便问了一下他，你帮我看看这套方案有什么优化空间吗？结果 AI 毫不留情的给我指出了一处致命伤，就是从外部干预数据流永远都做不到精准。你想啊，Kafka 它拉取消息的时候都是一批一批的往内存里面拽的，假设你定住的目标 offset 是一万，但消费者在拉取的时候可能一网下去直接就把九千八到一万零五百的数据全部拉进了本地内存里面，这时候你再去对比外部的 Redis，发现超标了，但数据已经进来了呀，这些多出的数据要扔掉还是把这批数据拆开处理，无论怎么搞，代码都会变得非常的恶心，最终你根本切不出一个精准平滑的数据界面。那随后我当然继续追问怎么办呢？

AI 给了我一个非常惊艳的升级方案，这套方案的核心思想参考了大数据流式计算框架 Flink，非常巧妙的把外部控制变成了数据流内部的自我驱动，而且真实的对应上了大厂的很多真实案例。这种神级的升级方案整体呢概括为两个核心，一个是添加数据挡板，还有一个是水位线裂变。这到底是什么样的神级方案呢？如果你看过我上一期的视频，现在把两个方案一对比，绝对会让你大呼过瘾，咱们接着往下看。刚才我们说到靠外部状态去控制消费者，那就像是看着 GPS 开车了，GPS 有延迟，你一脚刹车踩下去，车早就冲过线了，根本停不住，那怎么才能精准刹车呢？AI 给出的第一把利器。

叫做数据挡板，这个概念对很多朋友来说可能比较新奇，但它其实是大数据计算框架 Flink 里的一个核心机制，它的原理非常巧妙，既然从外部控制不准，那我们就把控制指令直接混进数据流里面去，具体怎么做呢？到了晚上十二点，我们直接往 Kafka 的 topic 里发送一条特殊的挡板消息，消费者只要消费到了这条挡板消息，就知道要停下来等待其他消费者了。但这里有一个非常关键的架构设计，这个挡板消息它是用来控制消费进度的，那它就绝对不能和业务消息混在一起，要是因为你添加了这个挡板消息，导致所有下游的消费者的业务代码里都要增加一个莫名其妙的 if 判断，那写业务的兄弟绝对是要骂娘的。怎么做到对业务的完美隔离和零侵入呢？首先在发这个挡板消息的时候，消息体也就是 value 应该是空的，但是在消息的头部可以打上一个特殊的挡板标签。

接下来在消费者端就要配置一个底层的 intercept 拦截器，在进入业务处理之前就完成对挡板信息的处理，一旦消费者遇到了挡板信息，直接在拦截器就处理掉了，完全不会流进后面的业务逻辑里面，这样呢业务人员根本就不用知道挡板的存在，而且整个进度的控制不是通过外部的时间调度，而是通过消费者正常处理的数据流来控制的，数据流自己告诉系统在哪里停，这样切出来的数据进度就能整齐自然，完全不用担心外部控制时间不精准的问题。知道消费者什么时候开始对齐了，那接下来怎么知道数据有没有对齐呢？这就引出了 AI 给我的第二把利器，水位线裂变。在基础方案里啊，我们在 Redis 里只记录一个最慢的统一水位线，在终极方案里面，这个水位线裂变成两个，上水位线和下水位线。

刚才拦截器拦截到挡板消息的时候，就可以记录下这个挡板消息的 offset，这个 offset 的偏移量就作为上水位线，表示这是全员对齐的目标天花板，把它直接存入到 Redis 当中，而另外那个记录着最慢消费者进度的统一水位线就变成了下水位线，它代表着系统的真实兜底进度。接下来整个系统的运作就非常自然了，跑得快的消费者一头撞上了数据挡板，就会被拦截器按下暂停键乖乖等待，而跑得慢的消费者离挡板还远着，就会继续拉取正常的业务数据，并且不断的推高下水位线，直到跑得最慢的那个消费者也抓到了那条挡板消息，这时候下水位线就终于赶上了上水位线。

当系统检测到这两个水位线重合的时刻，就意味着今天所有的业务线都已经把挡板前的数据处理完了，这时候系统就可以非常自信的打上一个 checkpoint 的检查点，通知财务系统数据已经对齐完毕了，可以开始对账了。接下来只要等到对账结束，系统就可以向所有的消费者发送 resend 恢复的指令，大家一起冲向下一个账期。最终呢在 AI 的配合下我也成功封装出来 SDK 工具包，并且在业务场景当中验证通过了。当然方案梳理到这个程度，其实代码到底是自己写还是 AI 写，你发现这其实就已经不重要了，因为这个时候你已经成竹在胸了。这就回到开头那个话题了，我们到底应该怎么去对待 AI 呢？等着 AI 抄了老鸟的后路，还是任由 AI 切断新手的打怪升级路线？

其实通过这次经历我也感觉到，面对 AI 它不是非黑即白的，不要一想到 AI 编程 web coding，那就是当一个甩手掌柜，只管给它扔需求，自己脑子就不转了，你这是在亲手裁掉自己。但反过来不用 AI 写代码，也不必跟 AI 老死不相往来，像我经常劝大家不要盲信 AI，然后就有很多人给我贴无法编程还有老登的标签，但其实关于 AI 我用的比绝大部分程序员都要多。在这个时代拒绝 AI 确实就是在拒绝进化，AI 真正的价值不是替你干活，而是淬炼你的思想，就像我这一次这样的，把它就当成朋友，当成导师，当成最挑剔的对手，去讨论、去挑战、去迎接更好的 AI 以及更好的自己。
