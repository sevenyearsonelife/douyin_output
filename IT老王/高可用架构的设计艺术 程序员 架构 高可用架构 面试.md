这个视频内容深度全面硬核，记得点赞关注收藏，不然就找不到了。另外如果有什么问题，欢迎发到评论区，我是楼兰，IT路上一起进步。这高可用的第一招叫做冗余，也就是大家最常听到的加机器，但加机器不是瞎加，你要会加还得要会管。咱们现在看一个最初初始的状态，你有一个 Tomcat 在跑业务，这个时候如果这个 Tomcat 崩了，或者所在的服务器断电了，你的业务是不是就彻底挂了？这叫做单点故障，怎么办呢？加机器啊，我们要再部署一台 Tomcat，现在你就有两台机器了，一台挂了另一台还在，但新问题也就来了，用户发出的请求怎么知道该去访问哪一台呢？用户不可能自己去试 IP 地址对吧？

于是我们需要在两台 Tomcat 前面加一个统一的入口，比如 Nginx 来做负载均衡，流量先到 Nginx，再通过 Nginx 的反向代理分发给后面的 Tomcat，看似完美了对吧？但你仔细琢磨一下，后面的 Tomcat 是安全了，可前面的 Nginx 只有一台呀，如果这台 Nginx 挂了，那路不就断了吗？后面就算有一万台 Tomcat 也没用啊，这不又回到了单点故障了吗？所以终极的冗余是这样的，光加 Tomcat 还不够，Nginx 也得一起加，Nginx 至少还得搞两台，一主一备，主的干活，备的待命。但如果主 Nginx 崩了，怎么让备用的 Nginx 上岗呢？我们可以再引入 Keepalived 来当保安，它会提供虚拟 IP 漂移的机制，也就是 VIP 的机制，来保证 Nginx 能快速进行主备切换。

这个 VIP 啊平时会绑定在主 Nginx 上，Keepalived 会像保安一样盯着主 Nginx，每秒检查一下 Nginx 的状态，一旦发现主 Nginx 挂了，这个 VIP 就会在几毫秒内自动漂移到备用的 Nginx 上，而用户发的所有请求都只要关注 VIP 就可以了，中间完全感觉不到 VIP 进行了切换，这样就形成了一套完整的冗余架构。当然在实际项目中，你也并不一定限定于 Keepalived 加 Nginx 的组合，还有很多其他的组件也能达到这样的效果，但最终记住这一招的核心思想，冗余不是瞎加机器，而是要消灭所有的单点故障，每个环节都有备用，就不怕突然崩溃了。

应用层搞定了，接下来是系统的心脏，数据库，这里更麻烦，应用服务挂了重启就行，因为它是没记性的，我们称为无状态，但数据库是有记性的，就是有状态，这就不能像网关层那样，用户随便访问哪个库就行了，那这种情况下怎么去做高可用呢？对于数据库通常我们会做主从复制，主库负责写数据，从库负责读数据，但这里有个致命的漏洞，如果半夜三点主库突然挂了怎么办？数据库是系统的脑子呀，记着所有用户的数据，那主库一崩，总不能等运维从被窝里爬起来打开电脑手动把从库改成主库吧？这一通操作下来半天时间就过去了，公司损失多少钱咱先不说，那运维兄弟的奖金那是肯定要泡汤了。

所以这第二招叫自动故障转移，我们要去找一个永不睡觉的监工，Redis 可以用 Sentinel 哨兵，MySQL 也可以用 MHA，它们都是服务端自主切换的工具，他们会二十四小时盯着主库，一旦发现主库崩了，几秒钟就选个健康的从库当新的老大，其他从库也自动跟随新的老大，全程不需要人来动手，停服不存在的，把人工抢救变成自动愈合。这才是高可用的分水岭。你有遇到过数据库崩溃的噩梦吗？评论区可以说说你们的处理方法是什么样的。前两招解决的是自身生生病的问题，但这第三招是为了解决外界压力的问题。比如说搞秒杀活动或者遭到了恶意攻击，流量瞬间暴涨十倍，你的服务器就像早高峰的地铁，如果所有人硬往里面挤，结果就车门被挤坏，谁也走不了，系统直接雪崩。

这时候架构师必须学会弃车保帅，这招叫做限流，常用的算法像令牌桶或者漏桶，原理很简单，我就发这么多张门票，有票的进来，没票的直接在门口拦着，快速返回失败。虽然拒绝了一部分用户，但至少保住了系统没被压垮，让剩下的人能够正常使用。同理，在微服务里，如果你的服务A调用了服务B，而B卡死，服务A如果傻傻的等，就会把自己的资源也耗尽，最后A也跟着一起，这叫做级联故障。这时候就需要熔断，就像家里的电路保险丝一样，一旦发现下游服务不行了，直接跳闸，后续请求不再调用下游，而是直接返回一个默认值。扛不住就别硬扛了，限流保系统，熔断防雪崩，这是高可用的基本素养。接下来你以为服务加了冗余就稳了吗？道高一尺魔高一丈，如果我再极端一点，如果你们机房的光纤被挖掘机挖断了怎么办？如果机房发生了火灾、地震怎么办？

同一个机房的机器全没了，你做再多的冗余都是白搭，因为这是物理层面的一锅端。所以真正的互联网大厂绝不会把鸡蛋放在同一个机房的篮子里。在同一个城市里可以找两个不同的机房分别部署服务，一个机房崩了，另一个机房就能随时顶上，这叫做同城双活。在不同的城市里分别部署服务，北京有机房，上海也有，深圳也有，平时大家一起分担流量，一旦北京机房彻底失联，流量可以自动切换到上海或深圳的机房，这叫做异地多活。但注意了，这种异地多活的方案可不是简单的把服务部署多份就可以了，因为物理距离远了，信息传输一定会有延时，这个时候如何保证两地数据一样快、一样准，这可是架构设计的硬骨头。没有真正动过手的朋友千万别吹牛了，把难点老老实实说出来，这样反而才会显得你懂行。总之这一招的核心思路就是只有物理层面的隔离才能抵御物理层面的毁灭。
