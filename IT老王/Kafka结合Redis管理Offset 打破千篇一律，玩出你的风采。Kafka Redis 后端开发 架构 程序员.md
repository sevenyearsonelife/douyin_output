现在代码都让 AI 写了，那咱们程序员以后还能干点啥呢？我一直强调做架构，但架构怎么做呢？今天这个 Kafka 结合 Redis 优化 offset 管理的方案，或许能够给你打个样。提到 Kafka 和 Redis，这两个你都熟悉吧？把 Kafka 当消息中转，把 Redis 当做缓存，这都是基础常识了。其他的什么环境搭建啊、客户端 API 啊，这些细节问题扔给 AI 都能给你整的明明白白的。但真实项目里，技术从来不是单打独斗的呀。怎么样把各种技术巧妙的融合在一起，共同解决并优化各种业务问题，这才是最有价值的地方，而这也恰恰是程序员真正值钱的地方。

比如通常一个复杂点的项目啊，都会涉及到很多个数据源，有些业务数据可能要存 MySQL，有些统计类的数据可能要存 HBase，还有些搜索相关的数据可能又要存 ES，那怎么兼容这么多的业务场景呢？那通常都是用 Kafka 来做个解耦，既能提高数据流转的效率，又能保证业务灵活互不影响。但这样的场景真的是上个 Kafka 就完事了吗？消息丢了怎么办？数据不一致怎么办？不同业务的消息处理速度不一样，又怎么处理？这些问题都需要解决呀。这次我们就不去聊枯燥的代码了，花几分钟我给你拆解一下企业的真实方案，看看高手是怎么样一步步挖掘问题、解决问题，并最后兜底的。我是楼兰，关注我，IT 路上一起进步。咱们先来看第一个最要命的问题啊，怎么保证 Kafka 的数据不丢？你可能会想，是不是面试八股那一套又又来了？

但是打住，消息不丢在项目开发当中这都是不值一提的标配了。真实业务当中最容易造成数据丢失的反而是另一个问题，就是消息与业务是脱节的。消息不丢不代表数据不丢。Kafka 能够很容易的保证生产者发送过来的消息一定会进入消费者处理，但是它管不了你下游的业务代码怎么写啊。你的业务最终是要存 MySQL、存 ES 的，但万一某一个业务线的数据库发生了一下抖动，或者写的业务代码有点逻辑问题，消息最终消费了，但业务数据却丢丢了，这才是最头疼的问题。那怎么破呢？很多项目中的基础解决方案就是把 Kafka 的消费进度 offset 放到 Redis 自己来管。实际上 Kafka 的消费者不光是可以按照默认的模式，有哪些消息就消费哪些消息，还可以自行指定消费进度，从某一个指定的 offset 开始消费，像这样的。

既然底层脚本都支持，那客户端的 API 也是能够轻松实现这样的效果的，就算你不会，问问 AI 也能轻松解决。有了这个基础，接下来的思路就很直接了，不管多少个消费者组，在 Redis 里记录业务的统一消费进度，这个进度只管业务推进到了哪里，而不仅仅是去关注消息消费到了哪里。下游不管是存 MySQL 的还是存 ES 的，每次消费前都去 Redis 里看一眼当前的这个统一进度，然后大家都从这个统一进度开始消费，拿同一批数据各自去处理。接下来重点来了，只有当 MySQL、HBase、ES 这些所有业务都处理成功了，我们才去 Redis 把这个统一进度往前推一步。

只要业务上能够做到幂等这种基础要求，那即便中间服务崩溃了，不不用管消息消费到了什么进度，下次重启还能够接着之前的数据进度继续处理消息，这样呢业务数据的安全性就得到了极大的提高。到这儿你是不是觉得这个方案很简单啊？就是换一下 offset 而已，可以直接找 AI 要代码了。但是如果你征集的就上生产，那后面的各种坑就足够你和你的 AI 喝一壶了。比如一个最简单的问题啊，不同业务的消息处理速度那是完全不同的呀。像一些核心业务的数据要存 MySQL，业务本身就很复杂，还得要走事务，那麻烦着呢，处理同一批消息可能要好几秒。但是，一些统计类的业务数据就是把数据收集起来往 ES 那边一扔就完事了，这可能几毫秒就处理完一批数据了。

这时候一个死局就出现了，ES 把这一批数据跑完了，他兴冲冲的想去拉下一批数据，但他去 Redis 里一看傻眼了，因为 MySQL 还在那儿慢吞吞的墨迹呢，Redis 的统一进度根本就没有往前推。那这个时候 ES 这个消费者组应该怎么办呢？再拉一次吗？那数据全重复了呀，那干等着吗？等 MySQL 跑完了统一进度去更新了，再去拉起下一批消息吗？那这样你引入 Kafka 的意义是什么呢？本来是为了异步解耦提升吞吐量的，结果整个系统的处理速度还是被最慢的那个 MySQL 死死拖住了，Kafka 的高并发优势就被彻底的废掉了。问题出来了，那些真正的高手会怎么破这个局呢？

这里分享一种很常见的大厂方案，就是在 Redis 里把游标一分为二，我们给下游的每一个业务，也就是消费者组，单独建一个拉取游标，记录当前消费者组消息拉取到了哪一条。这时系统跑起来就成这个样子了。ES组跑得快，他一口气拉到了一万，那把自己的拉取游标就更新到一万，一路狂奔，谁也不用等。MySQL组呢跑得慢，它的拉取游标才推到了五十，大家各拉各的，Kafka的性能优势就彻底释放了。而Redis组那个统一消费进度呢，它依然只盯着最慢的MySQL组，MySQL组跑到了五十，它才推到五十，它代表着全系统绝对安全已经彻底消化完的数据位置。那接下来怎么让ES组和MySQL组的进度一致呢？

比如平时大家都跑得爽啊，可到了每天晚上十二点，啊系统说停，我要核对今天的数据了，你去系统里面一看，坏了，ES组跑得太快了，把明天凌晨两点的数据都算进来了，而MySQL组呢的慢，今天的数据都还没算完，数据在时间上就彻底撕裂了，那这个还怎么去统计啊？这时候就可以引入大厂的一个终极杀招，watermark水位线机制以及账期设计了。在业务上可以引入一个账期的概念，不再需要保证每一笔消息的进度一致，只要保证在一个账期内各个消费者组能整体保持消费进度一致就可以了。在技术上可以在Redis增加记录一个watermark水位线，就取当前所有消费者组里那个最大的拉取游标，比如ES组跑得最快，游标拉取到了一万，那这个watermark就记到一万，这个就是账期内的数据边界了。

接下来各个消费者组在拉取下一批消息前，就必须去Redis里拿自己的那个拉取游标和这个watermark进行比较。比如MySQL组一比较，哎发现自己的拉取游标才到五十，距离watermark的一万还差得远呢，于是MySQL继续吭哧吭哧拉取数据，处理数据，并且推进Redis里那个统一消费进度。而而ES组呢发现自己的拉取游标到了一万这个边界，watermark也是一万，那ES组就必须主动刹车，调用Kafka原生的consumer点pause方法，保持心跳，暂停拉取。要等到什么时候呢？当他发现Redis的消费进度也达到了一万，和watermark保持一致了，这时候他就知道所有业务数据的处理速度已经跟上来了，就可以继续下一个账期的消息了。

而从系统整体来看，只要发现Redis的统一消费进度和watermark一致了，就知道数据处理进度保持一致了，这时候就可以打下一个checkpoint做个标记，然后通知所有暂停的消费者组，调用resume方法恢复消息拉取，大家一起进入下一个账期。听到这里方案基本成型了，那是不是接下来就交给AI写代码的事情了？还没完呢，如果你是一个有经验的架构师，你脑子里一定会冒出最后一个问题，这么复杂的双层游标对比水位线，还有主动启停防雪崩，自己梳理起来都费劲，如果交给每个业务线自己去开发，那绝对是满地的bug，天天排错。要是再加上各种AI写出的代码五花八门，那就更加没完没了了。所以作为有经验的程序员，最后还有非常重要的一步就是封装。

其实回头看看整套方案，你会发现这些watermark啊，统一消费进度啊，账期比对啊，都是跟下游具体的业务代码没有关联的，也就是说是解耦的，所以你完全可以封装成一个标准的SDK，对业务代码零侵入。写业务代码的兄弟只要调一下你的方法，拿到消息了就写业务方法去处理就可以了。你想想看，要是这么一套对接所有核心业务线的数据全程维护在你的手里，整个业务系统靠着你的SDK才能够运转，后续哪个业务线有问题了也等着你来对接，会是什么样的感觉？是不是尾巴都要翘到天上去了？至于最终代码是不是AI写的，这还重要吗？你看这就是我说的思路，程序员可以不是热门的行业，热门的行业也不是你能够追得上的，就像别人说的，要是扫大街能够发财，你绝对连扫把都抢不到，所以最终程序员这个职业热不热不重要，关键是你这个人燃不燃，这才重要，你说呢？
