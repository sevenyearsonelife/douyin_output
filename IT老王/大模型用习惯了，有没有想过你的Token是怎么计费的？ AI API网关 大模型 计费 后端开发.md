像 DeepSeek 这样的计费页面你应该很熟悉吧？你每调用一次大模型呢，报表上的三项核心数据就会隔一段时间更新一下。如果现在让你来负责开发这个计费看板，你会怎么做呢？现在写代码当然是用 AI 了，但问题是你怎么给 AI 提需求呢？你总不能直接说，帮我做个计费功能，实时统计用户的金额、请求数、token 消耗吧？毕竟这可不是简单的增删改查了呀，它一头连着底层的大模型，另一头连着的可是用户钱包里的真金白银，一分钱都不能错。在让 AI 帮你写代码之前，你脑子里至少得要有一套全局的架构设计，去摸清楚要调度哪些基础资源，再梳理明白有哪些关键步骤，然后再去指挥 AI 写代码吧。但问题是，这么个看起来很简单的架构到底要怎么设计呢？

当然方案设计你也可以问 AI，你现在就可以用你的方式去问问 AI，看看它给出的答案是什么，然后带着你的答案来看看接下来我给你拆解的大厂架构，来评论区分享一下差距在哪里吧。我是楼兰，关注我，IT 路上一起进步。我们先从整体架构来看，任何请求进来最前面肯定需要一个 API 网关，负责鉴权以及请求转发。如果是普通的 API 业务呢，网关把请求转发过去拿到结果的同时顺手把计费做了，整个流程非常简单。但在大模型场景下，这个简单的模型根本就行不通。为什么？因为大模型的请求接入和 token 计费是有着巨大时间差的，大模型是流式输出的，token 呢是一段一段往外蹦的，如果用户跑了一个超长上下文的复杂推理任务，大模型可能要耗时几分钟，甚至是几个小时，这时候网关能傻傻的同步等它处理完再去记账吗？

这会把网关的连接池直接打满，导致后面的请求全部排队，甚至整个系统都会假死，这肯定不行。所以网关后面需要加一层 MQ，比如最经典的 Kafka，用来做业务解耦，同时进行流量削峰。现在整体架构变成了这样，网关收到请求立即放行转发，如果后面的大模型能够正常接收请求，那就可以更新 API 请求数了。等后面大模型吐 token 的时候，网关再把消耗的 token 信息打包成一条计费日志，直接扔给 Kafka 做消息中转，扔完就不管了，绝不阻塞网关的性能。然后呢再由后端的消费者程序去订阅 Kafka 里的消息，进行真正的后台数据统计与扣费，这样呢一套基本的骨架就形成了，接下来我们就可以专注考虑后端消费者程序怎么进行实时数据统计了。

很多朋友会说，这还不简单，读到一条日志看一眼当前的时间，发现今天是九月二十号，那就把数据加到二十号的账单里，这不就完事了吗？这种按服务器当前时间来算账的方式叫做 processing time 处理时间，但是在大模型场景下，这会引发一个极其诡异的 bug，就零点跨日。我们前面说过，API 请求数和 token 消耗是分开记录的，假设用户在九月二十号晚上二十三点五十九分发起了一个复杂的超大请求，网关立刻在二十号记录了一次 API 请求，但是大模型吭哧吭哧吐 token 一直吐到了二十一号的凌晨，如果按处理时间来算，这批跨日产生的 token 就会被算进二十一号的账单里，结果就是客户第二天打开看板一看，二十一号的 API 请求数是零，但 token 消耗却有好几万。

要是你遇到这种明明没发请求却疯狂扣钱的账单，你会认账吗？估计是没耐心听客服的解释的，直接打电话就要骂街了。所以想要算对账，我们必须进入第一层思维，选择 event time 事件时间。在架构设计时，你必须要求网关在生成每一条 token 日志的时候，主动把最初那个请求发生时的时间戳打到业务报文里向后透传，下游的计费引擎必须抛弃自己的服务器时钟，只认报文里自带的那个时间戳，不管大模型的 token 是几点吐出的，也不管日志在 Kafka 里躺了多久，这笔消费永远属于请求发生的那一天。只有这样请求数和 token 数才能对齐，计费逻辑才有了一个正确的基石。统一了用 event time 之后呢，紧接着就会面临下一个非常现实的业务问题，我们到底什么时候结束计算，把最终的统计结果推给前端？

时间刚刚走到二十一号的凌晨零点零分，前端看板正等着刷新二十号的最终账单呢，这时候你的计费引擎面临一个两难的选择，你要不要立刻关闭二十号的计费窗口把账给结了？如果你立刻关窗结账，那别忘了二十号晚上二十三点五十九分发起的那个请求，大模型这会儿还在吭哧吭哧往外吐 token 呢，如果你把窗口关了，这些数据就会丢失，那公司直接就会损失资产。但如果你不关窗一直等着，那前端看板上二十号的柱状图就。永远卡在那里出不来最终结果。为了解决这个矛盾，流计算引擎就必须引入第二层思维 watermark 水位线机制。说白了它就是一种基于概率的妥协，也就是有策略性的等一等。我们通过监控可以发现，百分之九十九的大模型常规请求从发起到读完 token 整个过程一般不会超过五分钟，那好，我们就把 watermark 设为五分钟。

到了零点零分的时刻，系统不关窗继续等，直到什么时候呢？直到系统收到了一条自带时间戳为零点五分一秒的新日志，系统一看连零点五分发起的请求都已经处理完了，它在心里减去这五分钟的 watermark 缓冲期，认为当前绝对安全的时间戳已经走过了零点，来到了零点零分一秒。注意直到这一刻安全时间才真正越过了零点的边界，系统这才正式接板，理论上二十号的 token 应该都已经全吐完了，都在这儿了，关窗结账，把最后的数据推给前端。刚才我们讲到五分钟的 watermark 机制能够完美兜底百分之九十九的常规请求，但是大模型场景下总有极端情况，比如用户在跑一个几十万字的超长文本总结，导致最后那百分之一的 token 足足过了半个多小时才吐出来，这时候怎么办？我们能把 watermark 延长到半个小时吗？

绝对不行，如果你等半个小时，意味着前端看板上的所有数据永远都要延迟半小时才能刷新，为了百分之一的特殊请求让百分之九十九的正常数据陪跑，这在业务上是完全得不偿失的，所以死等行不通，我们就必须转换思路。流计算引擎呢给出了第三层思路 allow lateness 允许迟到机制，它的核心逻辑就六个字，先发车后补票。当五分钟的 watermark 时间一到，系统不再等了，立刻结账，把当前统计到的二十号的数据先推送给前端展示，但是这个计费窗口并没有真正的焊死，而是悄悄留了一道后门，比如我们设置允许迟到一个小时，在这一个小时内，如果二十号那百分之一的长延迟 token 姗姗来迟了，系统就会通过这道后门重新激活二十号的计算窗口，把这个部分迟到的 token 加上去，然后向前端发送一条更新指令，修正之前的数据。

这种重新计算修正输出的方式当然会降低局部的效率，但是换来的是百分之九十九正常数据的实时性，这笔买卖在业务上是完全可以接受的。有了前面的两大机制，基本上所有预期内的正常数据都能被有条不紊的处理掉，但是一个真正的工业级系统架构必须要有底线思维，就是要留有余地，堵住所有可能出现的极端漏洞。假设真的出现了极其特殊的意外，比如大模型底层卡死了，或者网络大面积故障了，导致某些 token 的延迟超过了一个小时的等待时间，这时候该怎么办呢？这每一条数据背后都是真金白银呢，绝对不能够简单粗暴的丢弃了。那你可能会问了，既然不能丢，那我干脆把 allow lateness 的允许迟到时间拉长到三个小时不就行了吗？绝对不行，这同样是一笔极度不划算的买卖。

你要知道 allow lateness 之所以能后补票，是因为它把这个时间段的计费窗口数据一直保留在服务器的内存里，如果你为了极个别的异常数据把等待时间拉长到三个小时，意味着内存里会堆积海量无法释放的窗口状态，这会给服务器带来灾难级的内存压力，甚至直接把整个计费系统拖垮，主干道走不通怎么办？

流计算引擎给出了最后一道防线 side output 侧输出流，说白了就是在我们的主流程之外单独准备另外一个篮子，当系统发现有些数据迟到的实在太离谱了，连 allow lateness 的后门都已经关上了的时候，它不会把数据丢弃，而是把这些预期外的异常数据全部收集起来，扔进 side output 这个专门的篮子里，之后我们再通过定时的离线脚本或者是人工对账的方式，对这个篮子里的数据进行额外的补充计算，这样既保住了公司的钱，又保住了服务器的内存稳定，这才叫滴水不漏的架构设计。讲到这里其实我们已经不知不觉推开了一扇更大的门，你想既然我们能用 side output 准备一个专门的篮子来装超时数据，那你顺着这个思路往下想，自然就能想到我为什么不能多准备几个篮子把数据分门别类呢？

没错，这就是流计算引擎当中非常优雅的一个特性，数据分流。在真正的 AI 商业化业务里，网关吐出来的数据可是一座金矿，有了侧输出流的机制，我们就可以顺水推舟把同一份原始的 Kafka 数据轻松的分发到更多元的大模型业务场景里去。基于这个思路，大部分的计费引擎就可以自然演化出几个典型的输出流，第一条核心计费主流，负责实时计算 token 的消耗，把真金白银的数据推送到前端。看板和财务系统。第二条，风控审计，把那些触发了敏感词或者调用频率极其诡异的请求单独分流到这个篮子里，直接对接风控系统进行实时拦截或者账号封禁。第三条，性能监控流，专门收集那些首次响应超时或者大模型直接报错的日志。一旦这个流里的数据激增，立刻触发运维报警，这就说明底层的 GPU 算力集群可能出故障了。

第四条，离线归档流，把所有原始的完整的对话报文原封不动的旁路到数据湖里去，不仅能给财务做月底的神都对账，更是算法团队未来进行模型微调最宝贵的语料库。你看，原本只是为了处理极个别异常数据的一个小补丁，顺着业务的脉络，自然而然的就演变成了一个支撑全公司 AI 业务运转的数据中枢，这就是优秀架构的延展性。其实你发现没有，这套被大厂拿来应对大模型的顶级方案，早在大模型诞生之前就已经成型了，只要稍微换一换细节，就是对接 AI 大模型最能打的方案。AI 确实颠覆了写代码的方式，但它根本没有改变做架构的一层逻辑。现在那些 AI 相关的开发岗位抢的也不是会写提示词、会调 API 的 AI 调包侠，而是能把大模型的新特性和这些硬核老架构完美融入的人。你怎么看？接下来评论区见。
