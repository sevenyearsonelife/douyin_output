很多人认为所谓风控啊就是，哦这个交易大于一万呢，我要拦截它，那是过家家。真正的风控规则引擎是当一笔交易发生之后的那十毫秒之内，我就要同时甩给他几百条甚至上千条的规则。当你用支付宝扫码完成一笔交付的几秒钟内，我就要知道他是不是黑名单，是不是异地登录，是不是洗钱，是不是超过了限额。甚至这些规则很多都是需要随时调整的，今天国家出了个政策告诉你老赖不能消费了，明天业务系统告诉你发现了洗钱的新套路，反洗钱的规则变动了，你都得跟着改。每一条规则或许不那么复杂，但是注意是要同时校验，不是排队校验，因为风控只是一个前提，后面还要把大量的时间交给核心交易，要是风控就耽误了半分钟，那这个扫码支付就没法玩了。然后规则引擎需要的是一份体检报告，要看看这几十上百条规则它触发了多少条规则，而不是一个简单的允许交易或者是拒绝交易。

这是规则引擎和一些简单的交易接口的本质区别，这也是极致高并发的代表场景，搞懂这个是前提。如果你连高并发都理解不了，那请刷走吧，后面的内容不适合你。接下来我将抽取出五条具有代表性的真实业务规则来带你逐层闯关，当然这五条业务规则代表的不是简单的业务，并且我明确告诉你这是我简化后虚拟的，真实的业务规则复杂很多。但更重要的是这五条规则代表的是五种不同的数据处理思路，在每一种不同的数据处理思路的指导下，以往你看过的所有高并发的面试八股，比如多级缓存、布隆过滤器等等，都是你真正做业务的基础武器，你可以来试试你能闯到第几关。那么现在热热身，看看第一条规则，交易渠道为低配，且交易手机号等于银行签约手机号放行。

这是一个典型的简单型规则，它的特点就是所有的判断数据都在请求报文里了，交易渠道、交易手机号、银行签约手机号这些固定的数据都是业务系统需要提前获取到的，他们获取到之后再一起发送给规则引擎，规则引擎只需要做一个判断就行了。看懂了这个后，你会不会觉得这个规则太简单了？很多人上来就会说，这就是几个简单的 if else 判断就解决了呀。这里需要注意的是，如果你只写这一条没问题，但如果我有一百条这样的规则呢？一大堆的 if else，你的代码就会变成一坨没人敢动的屎山。这时候别跟我谈什么高深架构，最基础的设计模式你必须得会，并且得会用，策略模式就是必须的。

把每一条规则要封装成一个独立的类，定义统一的接口，输入的业务报文每经过一个规则类处理，输出的报文里就会添加对应的规则处理结果，各种规则随意拔插，改一个规则不会影响到其他规则，而且想用时就接上，不想用时就去掉，怎么实现这种极致的解耦是这一层需要考虑的。这一层呢各种基于 SPI 的扩展机制以及基于 Spring Boot 的 starter 插件开发机制都可以作为参考，这些面试八股的常见方案你还记得多少？不妨在评论区讨论讨论。接下来难度升级，第二条规则，国家导入一。批老赖名单，老赖禁止交易。这类规则我称为数据画像型，它的典型特点是需要在业务报文的基础上增加一些额外的数据因子来参与业务判断。针对这一个规则其实没什么难的，无非就是要增加一步查询老赖名单的操作，把这个操作抽象成一个异步任务就能保证执行的效率。

但是你有没有想过，在这个具体的规则当中，查询老赖名单的过程通常是很慢而且很复杂的，但查出来之后的检查通常是很快而且又很简单的。你把它们两个操作绑定在一起，那是谁都别想舒服。能不能把这两个过程拆分开呢？这就需要引入数据与规则分离的思想，在进入规则引擎之前做一个数据装配器，把所有需要查询的数据提前补充好，这样后面的判断就可以非常省心了。比如这个规则，请求报文里只有用户身份证号，但是很明显业务判断规则只是需要是不是老赖这个业务标识，我就可以在进入规则引擎判断之前，提前根据用户的身份证号查询出他是不是老赖，并作为一个数据因子放到报文里，这样后面的规则校验又回到了一些简单的 if else 逻辑了。比如这里演示一个很简单的规则引擎 Avata 规则引擎的案例哦。

接下来你就可以专心处理数据了，比如选择合适的存储方式，加快计算黑名单数据的速度，比如构建多级缓存，重复利用黑名单计算结果，比如构建缓存一致性策略，及时更新缓存结果等等等等。你会想到如何保证数据缓存一致性呢？评论区说说你的想法和问题。有了规则引擎就万事大吉了吗？咱们来点更有意思的。第三条规则，用户日交易限额五百，超限禁止交易。这不仅需要当前这笔交易的数据，还需要过去这一天所有的交易记录一起参与统计，这怎么做呢？这类规则我称为累计型规则，你肯定不可能临时去读取所有的交易记录再进行统计，那样等你算出结果来黄花菜都凉了。

这类规则就必须引入流式计算的思想，每一笔交易发生时我就要实时更新这个用户的今日消费总额，你可以简单的用 redis 的 incre by，也可以用一些 flink 的 state，总之当新交易来的时候，我要直接读取这个实时统计好的缓存值，加上当前的金额和五百这个阈值进行比较就可以了。这类规则的难点不在于比较，而是在于要以流式计算的方式实时计算每一笔历史交易，不能漏也不能重，还要防止数据延迟。这类复杂的流式计算 flink 通常是首选。我之前介绍过 flink 的水位线机制，用来保证实时数据即便因为网络等原因出现了数据延迟，也能够保证流式计算的数据安全。怎么做的你还记得吗？不妨在评论区说说你的想法。接下来难度继续升级，第四条规则，同一个手机号三天内支付次数超过十次且总金额不超过一百元要封禁十二个小时。

这个规则呢明显是针对那些小额高频刷单的手机用户的，这时候用流式计算就会显得有点吃力，因为条件太复杂，涉及多维度的滑动窗口，你要累加的不是某一个单独的手机号，而是要累加全网海量的手机号，这可是实打实的十亿百亿级别的数据了，这个你没有意见吧？然后针对每一个手机号你要累加多少个数据呢？支付次数、支付金额，这就两个了。这还只是针对这一个具体的规则，再给你加上几十上百条类似的规则，你要累加多少个指标？这种业务场景下就不要跟我说什么 bit map 之类的存储方案优化了，不管你再怎么优化存储空间，都无法控制资源消耗。这类规则我称之为批量计算型规则，这是大数据的主场。我们需要引入 spark 或者 flink 的 window 机制，我们不再处理一瞬间，而是处理一段历史。

系统会在后台默默的对海量历史交易数据进行窗口聚合，用窗口每次处理一个小批次的数据，比如三天内的支付数据，这相对于全量的交易数据就是一个很小的批次了。针对这个批次内的数据进行实时数据聚合，从而判断当前发生交易的手机号是否命中了这个复杂的统计特征，并把这个特征结果放到报文当中，交给风控引擎进行综合的规则判断。例如针对这一个规则，拿到某一个支付数据后，风控系统只要针对这一个手机号实时统计出三天内的支付次数、支付总金额，包括最近封禁时间等等这些数据，并把它们补充到报文中，交给风控引擎进行数据判断即可。最后我们报文中增加输出一个简单的标签，这样呢后面的业务系统就自然能够进行相应的业务判断了。看到了吗？复杂的计算下沉到大数据层，实时的决策依然保留毫秒级响应，这是架构的层次感。

至于这些大数据计算引擎下，他们是如何保证海量数据的高效计算的，沉迷于 CRUD 的你还记得多少？上面几种规则处理思路呢，尽管有简单也有复杂，但基本都属于常规思路。接下来还有很多非常规的规则，就只能按照非常规的思路来优化了。第五条规则，同一个手机号在一天内交易密码连续输错五次锁定账户，注意这个词连续，如果中间夹杂了一次成功登录，计算器就要清零。当然连不连续这个事儿并不是它的关键，要不要连续呢？其实这也是业务一句话的事儿，今天我可以要求连续，明天有可能就调整成不连续了。我知道你看到这个规则肯定又是想到针对手机号做个累加就解决了，但是还是那个问题，针对海量的手机号，你到底要累加多少个数据呢？如果你就只会想着数据库或者 redis 记录状态，然后每次去对比，那你迟早要被海量数据给冲垮了。
