很多朋友问我，现在转 AI Agent 的开发到底要学什么语言啊？我每次都跟他们说，AI 面前语言根本就不重要，但你能用来干什么事情很重要。道理其实很简单，同一个问题你可以指定任何一种开发语言让 AI 很轻松的写出代码来，但写出好的代码和做出真的好用的东西是完全不同的两码事。这什么意思啊？今天我们就来做个很有趣的解剖实验，就拿所有语言都有的这个异常处理逻辑，就是小白都能看懂的 try catch finally 来开刀，看看同样的问题，不同的开发语言都是怎么思考的。看完这几分钟你会发现，其实不同的开发语言展现出的完全是截然不同的世界观。所谓软件开发其实不只是写代码，而是在用不同的世界观解决现实中的问题。讲的有点深奥了，那接下来准备好点赞、关注、收藏，咱们上干货。我是罗兰，关注我，IT 路上一起进步。

咱们先来看一段非常简单的加法代码，就像这样的，try 里面呢我们给变量 x 赋值为一，catch 里面赋值为二，finally 里面赋值为三，那么 x 最后是多少呢？没错，一定是三，因为小学 Java 课里就会告诉我们，finally 关键字就是个拥有特权的 VIP，不管前面代码怎么执行，finally 代码块最终一定会最后执行。但这就完了吗？没有，好玩的来了。我们知道啊，这段代码逻辑其实是需要根据代码的执行情况跳来跳去的，但最终电脑的 CPU 是个直肠子呀，它只会一行一行执行最基础的机器指令，它可看不懂这些 try 啊 catch 这些英文单词。那 Java 是怎么把人类看懂的代码翻译成机器看的说明书呢？

接下来我使用 IDE 里面的一个小插件 JClassLab，来看看这段 Java 代码翻译给 JVM 虚拟机后是什么样子的。像这样啊，这里呢右边翻译出来的 bytecode 就是这段加法代码最终翻译成的字节码。这里我们重点关注 finally 代码块里的 x 等于三这一行，实际上它对应的字节码就是右边的 iconst 三和 istore 一这两行。其中 iconst 三就是定义一个常数三，紧接着 istore 一就表示把这个常数三塞给局部变量表里面第一个变量，也就是我们代码中的 x 了。现在重点来了，大家仔细在右边这排密密麻麻的指令里找一找啊，这对组合总共出现了几次呢？第二行和第三行是一次吧，第十行和第十一行又是一次吧，然后呢第十六行和第十七行还有一次，整整出现了三次，这是什么意思呢？

其实啊这就是告诉你，Java 编译器在背后偷偷摸摸的把你 finally 里的代码呀给复制粘贴了三份，分别堵在了正常执行的 try 代码块后面，异常处理的 catch 代码块后面，以及兜底未知异常的最终出口。那代码运行的时候怎么知道要从哪个出口走呢？这就需要看 class 文件中另一个重要的部分 exception table 异常表了。它就像个交警啊，规定了如果第零到二行报错了，就直接跳转到第七行，意思是 try 代码块里面一旦执行报错，就直接切到 catch 代码块里面去执行。最后一行，如果第七到十行不管出现什么异常情况，都跳到十五行。这里第七到十行实际上就对应的 catch 代码块当中不包含粘贴的 finally 代码块的那一部分。

从这个逻辑可以看到，不管你怎么跳，最终都会撞上提前复制好的那份 finally 代码块，这就是 Java 的 CV 大法。你有没有觉得这个 Java 的做法有点憨呢？其实这是 Java 为了程序稳定做出的一种妥协。早期的 Java 语法当中是有 goto 这样直接跳转的代码关键字的，但是后来人们发现这种跳转指令会让程序执行逻辑变得过于复杂，所以最终为了保持程序稳定就删除了 goto 语法，而处理异常的 try catch finally 也就变成了现在的这个样子。看懂了 Java 的做法，那其他的开发语言呢？他们在面对处理异常这个所有开发语言通用的难题的时候又是怎么做的呢？这就非常好玩了，整个编程界大致可以分为以下几个流派。第一派我称为运行时路由派，代表人物呢是 C sharp。

C sharp 就像个含着金钥匙出生的富二代，他压根就不屑于复制粘贴，你写了一份 finally 编译出来就真的只有一份，那异常逻辑跳转的事情谁负责呢？这就全部交给他背后那个极其强大的管家 CLR 虚拟机，报错的时候管家会接管一切，通过底层的路由机制精准导向了唯一的一份代码。所以这一派的优点就是代码呢非常的干净优雅，缺点就是你必须随身带着这个强大的虚拟机，所以早期的 C sharp 它背后的 .NET 是和 Windows 强绑定的，虽然现在的 .NET 早就跨平台了，但这种带着庞大虚拟机管家的。重型基因，注定了它更适合企业级的重型应用开发。第二派呢，我称为零成本展开派，老大哥 C 加加就是绝对代表了。C 加加可是个狠人，它的字典里压根就没有 finally，它的哲学是谁污染谁治理。

清理代码呢全写在对象的析构函数里，平时不报错它跑得比谁都快，一旦报错了，C 加加运行时会掏出一张异常表，顺藤摸瓜把对象一个个逆序销毁，这叫做栈展开，平时零性能损耗，出事了精准爆破。这种对性能的偏执让它成为高频交易和三 A 游戏的真神，但缺点就是写代码呢会极其的烧脑，写 C 加加代码的难度和 C sharp 那完全不是一个维度。第三派呢我称为延迟队列派，代表人物是现在大火的 Go 语言，Go 的主打一个实用，它连 try catch 都觉得啰嗦，直接用一个 defer 关键字，比如说一打开一个文件，紧接着就写一句 defer 关闭文件，那 Go 的底层是怎么干的呢？它会把你这句关闭代码塞进一个隐藏的延迟队列里，等整个函数跑完了或者崩溃了，它再从这个队列里把任务一个个弹出来执行。

这种做法主打就是一个大道至简，没有那么多弯弯绕绕，所以 Go 的代码写起来非常的清爽，程序员的心智负担也非常的低，加上呢底层处理效率也很高，就特别适合高并发的云原生微服务。不过代价就是底层要维护这个队列会有一点点微小的性能开销。最后呢还有一派我称为甩手掌柜派，代表就是 JavaScript，JS 里面也有 try catch finally，但他说我只管写逻辑，脏活累活我可不管，他把异常处理全部扔给了底层的执行引擎，比如 V 八，V 八引擎会在内存里疯狂运转，动态构建出复杂的控制流图，强行把各种出口粘到 finally 上。这样的做法呢让 JavaScript 代码写起来非常的灵活，那后果就是你写的代码和后面的执行引擎实际上是强绑定了。

这就好比写个前端页面很容易，但你要让这个页面在 P C 端、苹果、安卓甚至各种小程序里面跑的一样的顺滑，那就非常考验技术了，因为换一个引擎底层的处理逻辑可能就完全不同了，主打一个表面岁月静好，底层疯狂适配。所以很多前端开发代码呀写起来非常的灵活自由，但是过度依赖引擎的下场就是一旦代码写的太过的放飞自我了，性能就会出现很神秘的瓶颈。讲到这里啊，我们再回到开头的问题，在 A I 面前各种开发语言真的就没有区别了吗？你看从处理异常这么个小点就能看出来，Java 选择了妥协，所以它非常适合做只求稳定的企业级应用。C 加加拼了性能，所以三 A 游戏底层工具基本都是它的天下。Go 追求极简，所以天生适合做云原生场景下高并发的底层组件。JS 甩锅给了引擎，所以开发很快速，所见即所得那是标配。

你看这根本不是单纯的技术博弈，而是对真实业务和商业背景的博弈。而 A I 本质上是从我们给它的代码里面学习如何编程，它能学会任何语言，却无法学会这种抽象的权衡与取舍。这也才是程序员在 A I 时代永远不会被替代的护城河。这一层你看懂了吗？
