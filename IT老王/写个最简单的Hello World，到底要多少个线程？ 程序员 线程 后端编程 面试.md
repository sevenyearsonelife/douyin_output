这次问你个挺有意思的问题，用 Java 跑一个最简单的 Hello World，你觉得它到底启动了几个线程？一个 Hello World 还能有几个线程吗？不就一个 main 函数吗？说实话，要是冷不丁这么一问，好多干了三四年的老 Java 脑子里也是懵的，因为很多人从打基础开始，路子就走偏了，好好的技术学成了八股。什么进程线程的区别，线程池的核心参数，背的时候头皮发麻，背完之后就全忘了，一到线上遇到程序卡顿，CPU 飙高，除了敲命令重启，根本想不到这些基础的东西。就算现在有了无敌的 AI，需求跟 AI 这么一提，代码刷刷刷就出来了，但真要一问，系统稳定性怎么样啊？并发性能行不行啊？上线访问后人数多了怎么办呢？大部分人心里都是非常发虚的，别说去解决问题了，就是怎么跟 AI 提这些深层次的需求，都不知道怎么开口。

背八股文觉得虚，靠 AI 写并发又觉得慌，说到底就是因为动手玩少了，理论根本没有结合实践。这次就拿这个线程的问题，我直接带你上 Linux 玩一玩，看看一个简单的 Hello World，还有企业级的 RocketMQ，它们到底有多少线程，平时在后台又偷偷忙些什么，花个几分钟顺着捋一遍，你心里那种发虚的感觉自然就没了。我是楼兰，关注我，IT 路上一起进步。大家刚开始学 Java 的时候写的第一个程序肯定就是 Hello World，但是你想过没有，就这么一行打印就完事的代码，到底用了多少个系统线程呢？别猜，我们直接上手。

我这里写了一个最简单的 Java 程序，在 Linux 系统里有一个基础指令 strace，可以追踪应用程序的系统调用日志，我们直接跑一条 Linux 的底层追踪指令，像这样，这条指令的作用就是只要 Java 虚拟机在底层向操作系统申请了一个新线程，那系统就会自动导出一个带线程 ID 为后缀的独立日志文件。敲回车，控制台会打印出 Hello World，然后程序就执行完成了。现在我们来看一下生成了多少个文件，你看一下这一大排啊，从 hello.4411 一直排到了 hello.4425，一下子多了十几个文件，这里一个文件就对应一个线程，也就是说你以为你就写了一个 main 函数，但 Java 虚拟机为了支撑这行代码，前前后后在底层向操作系统申请了十几个线程。

所以你看，多线程从来不是什么高大上的东西，你从写代码的第一天开始，它就一直在你眼皮子底下跑着。那这十几个线程都在干嘛呢？首先最明显的就是 main 线程了，通常对应的就是最大的这个日志文件，在这个案例当中就是 4412 这个文件，你业务代码里打印出的那行 Hello World 提成，就是通过一个叫做 write 的系统调用打印到控制台的。而且从这里看出 main 函数它还不是第一个线程的，Java 的后台有很多的常驻线程，简单挑两个你经常接触的来聊聊。第一个呢，GC 线程，也就是负责垃圾回收的线程，写 Java 大家觉得省心是因为不需要自己手动去申请和释放内存，你在代码里可以随便 new 对象，用完之后就会释放，但是堆内存满了之后谁去清理呢？

就是后台这个 GC 线程，他们平时就在那候着，一旦内存快满了，他们就会被拉起来去扫一遍，把没用的对象给抹掉，内存腾出来，要是没有这几个线程在后头随时兜底，你的程序没跑几下就直接内存溢出了。第二个清理直接内存的线程，如果你用过 Netty，就知道它喜欢用堆外内存，没有 GC，那速度也就飞快，但是堆外内存是直接找操作系统要的，Java 的 GC 线程是管不着它的，那它用完之后怎么释放呢？底层其实就靠一个后台线程在盯着，Java 堆你会给它留一个小小的引用标记，只要你堆里这个标记没用了，后台线程立马就感知到，然后就会去调用底层方法，通知操作系统把那块物理内存给释放掉，这样堆外内存才不会越堆越多把服务器给撑爆。还有像我们平时排查线上问题，敲 jstack，Java 进程怎么把内部信息吐给你呢？

这也是靠后台常驻的一个监听线程在跟你的命令通信，你看把前因后果这么一捋，是不是就顺畅多了？好，你说 Hello World 只是个入门 demo，那真实项目中呢？那些把别人听不懂的三高架构玩到了极致的开源框架呢？一旦跑起来又会有多少个线程呢？我们直接看一个实际的例子，我把阿里开源的 RocketMQ 的 broker 服务在后台启动起来，还是加上 strace 指令把线程日志打印出来，启动好了，我们同样看一下导出来的线程文件，你看这一眼看过去 broker.4138 到最后的 4304，密密麻麻上百个线程，很多人问 RocketMQ 这种大型开源项目代码这么多，到底怎么学才能又快又好？

其实从这些线程的分工去梳理就是最好的方法，RocketMQ 之所以能扛住那么大的消息并发，就是因为它把事情分的特别的细，我挑几个最核心的讲，你听一听就能明白。首先是刷盘线程，消息从客户端发过来，为了快，它不会立刻去往机械硬盘或者是 SSD 里面去写，而是先写进操作系统的内存页里，这样速度是最快的，但是万。一突然断电了，内存里的数据不就全丢了吗？所以后台专门起了一个独立的刷盘线程，这个线程在后台一直循环检查，要么是内存里攒的消息到了几百K了，要么是过了设定的几百毫秒了，它就立马调用操作系统的指令把内存里的这批消息批量的写进磁盘文件里。发消息的只管往内存写，落盘的事情交给后台线程去慢慢干，这样呢两头都不耽误，性能就上来了。

再来就是建索引的线程了，所有业务发过来的消息都会混着写进一个叫做 commit log 的大文件里，那消费者要是只想着拿某个特定 topic 的消息，总不能每次把几个 G 的大文件从头翻到尾吧，那机器肯定卡死了。所以后台还有一个专门分发消息的线程，它在后面一直盯着这个 commit log 大文件，只要发现有新消息写进来了，它马上把这批消息在文件里的位置提取出来，另外写到一个目录索引文件里面去，消费者要查数据直接去翻这个小目录就行了，一秒就能找到，这就是 consumption queue 和 index file 两个索引文件。你看把这些事情一条条摊开来看，多线程到底在干嘛呢？它就是把一个大而化之容易卡住的事情，用不同的线程切成了一条流畅的流水线。你看到没有，为什么就算有了 AI，很多人心里还是发虚？

就是因为以前你只看到了代码这层皮，没有摸到底下骨架到底是怎么动的。很多人说现在 AI 都进入到多 agent 的时代了，以后写代码只要让一堆 agent 帮我们干活就行了，但你仔细想想，驾驭一堆 agent 这跟一个系统里驾驭上百个线程是不是一回事？如果底层的并发模型、数据冲突、隔离设计你完全搞不懂，你根本就指挥不动那成千上万个 AI agent 去稳定的协同。AI 能给你各种标准答案，但遇到复杂的系统瓶颈怎么去优化设计？怎么把老板一拍脑袋说出来的需求做成靠谱的软件产品？这些需要硬核工程底子的地方才是你真正拉开差距的护城河。看清底层的真相，你才会有真正的掌控感。
