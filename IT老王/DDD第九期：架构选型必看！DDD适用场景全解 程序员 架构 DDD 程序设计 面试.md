朋友们，DDD领域驱动设计到底是一个架构的神器还是技术的毒瘤呢？即便现在DDD早就没有之前那么火热了，但是你现在去任何一个技术群里面问一问，我们要不要上DDD领域驱动设计，保证现场立马炸锅。有一派人会把它捧上神坛，说它是解决复杂业务的真理，是高级架构师的标配。另一派人会恨得牙痒痒，说这玩意就是个毒瘤，除了把简单代码搞得谁也看不懂，把开发周期拖长好几倍之外屁用没有。那事实到底怎么样呢？我们这次就来正面聊聊这个问题，你会站在哪一派呢？可以在评论区说说你的想法。咱们先简单说一说DDD到底是个什么东西啊，之前我已经出了八期短视频，一点点去介绍DDD的理论体系以及落地方案。它呢不是一项技术，也不是一个具体的框架，而是一种架构的思想。

简单来说，在没有DDD的时候，我们写代码往往是翻译模式，产品经理说需求，我们把它翻译成数据库表，然后写一堆代码去操作这些表，把这些表的CRUD业务整理好了，一个项目基本上也就完成了。而DDD主张的是代码应该直接反映业务，它要求你在写代码之前，先要像业务专家一样去思考，建立起一个完整的模型，接下来你的代码结构就应该长得和这个业务模型是一模一样的。听起来很美好是吧？但为什么落地的时候有人成了神，有人就成了坑呢？这次我带你穿梭时空，回到DDD的源头，从DDD领域驱动设计这本书开篇序言提到的三个项目入手，从头看一下DDD的故事。听完这三个故事，或许你就能够明白你到底该不该好好去了解一下DDD了。

当然，这期视频不是为了打嘴炮的，而是帮你真正去接触DDD的深层核心，以免错过了这个延续了几十年的架构思想它真正的经典之处，全网绝无仅有。记得点赞关注收藏，不然就找不到了。还有呢，记得在评论区留下你的问题和看法，我是楼兰，关注我，IT路上一起进步。那这三个项目是作者Eric Evans分享的在DDD诞生之初自己亲身经历的项目，这三个项目呢结局截然不同，但即便是已经隔了二十多年，依然是咱们程序员职业生涯的真实写照。

先说第一个项目，这呢是一个Web交易系统，这帮兄弟就是个快枪手团队，凭直觉写代码，什么领域模型设计模式通通不需要，结果呢第一版上线，哎，大获成功，简单实用交付快，老板也很开心，但也正因为这次成功埋下了祸根，老板期望值拉满了，马上要求开发第二版，这时候问题来了，由于第一版完全是面条代码，没有公共语言，没有结构化设计，业务逻辑和代码逻辑就混成了一团，结果就是第二个版本根本交付不出来，整个系统过早的僵化，变成了一个维护成本极高的遗留系统。这其实是不是很多朋友理想的开发模式啊？那我做的就是个用户不过千的垃圾项目啊，什么设计都不如短平快上线来的重要。但这种凭直觉开发的红利，不管是对项目本身还是对你个人来说，到底能够吃多久呢？

再看第二个项目，这个项目是和刚才那个一样复杂，是做贸易的，起初也是小获成功，但不同的是他们非常的轴，非常重视领域模型，在后续的连续加速开发当中，他们不是在堆代码，而是在不断的精进模型，开发人员和业务专家每天都在沟通，代码里的设计直接反映了对业务的理解，结果是每次迭代系统不仅没有变乱，反而更能更灵活了，设计不但没有成为负担，反而让修改。变得更容易了，这其实就是DDD想要达到的一个理想状态。软件它不是死的，它是随着业务的深入而不断进化的一个生物。最后也是最扎心的第三个项目，这个项目呢起点非常的高，它要做一个全球化的企业系统，团队的配置非常的豪华，工具也都是顶尖的，而且他们也非常认真的进行了建模，按理说这把该稳了吧，结果却是屡战屡败，最后泯然众人。为什么？

因为他们犯了一个大忌割裂，有一波精英架构师专门负责画图设计模型，另一波程序员负责写代码，但双方缺乏一致的统一的认知，导致的结果是设计出来的东西没有落地，程序员呢水平参差不齐，也没法保证设计落地的效果。虽然最后也交付了软件，但那个宏伟的目标彻底凉凉，团队也放弃了模型。所以好的建模思想，它也需要DDD这样科学的工具来保驾护航。我们现在但凡说起什么单一职责、依赖反转、开闭原则这些基础的设计准则，很多人都会认同，但是有这些好的准则，就真的能够设计出高内聚低耦合的理想项目了吗？这个故事就会给我们一点点警示。听完这三个故事，我们再来琢磨一下DDD的设计目的到底是针对什么样的业务。DDD的领域驱动设计这本书其实一直贯穿着一个小标题叫做核心复杂性应对之道。什么是核心复杂性？

我可以先来说说这个复杂性是什么，其实复杂性比较好理解，一个很火的技术你不会，那这就是一个具体的复杂性。甲方提出一个莫名其妙的业务需求，你们团队还不清楚怎么做，那这也是一个具体的复杂性。但是这些是核心的复杂性吗？我认为不是，你不会一项技术，你团队有人会啊，团队都不会，那学学也就会了呀，就像你不懂DDD，你看看我的这一套短视频，那也就能理会个大概了呀。项目团队有一个需求不知道怎么设计，可以找产品人员进行业务拆解，实在不行你抄别人的，哦不对，这个不叫抄啊，这叫借鉴同行的，那也是可以的呀。这些不是核心的复杂性，那什么是核心的复杂性呢？我觉得是那些活的、长期的，且在项目设计之初，甚至是某几次重构之初，你根本就无法预料的那些业务演进。

不知道你有没有参加过那些活了十几年的大型互联网项目，我之前就参加过好几个比我女儿年龄都长很多的项目。十年前它可能只是一个简单的Web网站，要么简单的购物、充话费，要么办几个套餐，完成各自的核心业务也就足够了。但是后来VR和AR火了，老板说要搞沉浸式体验，你说你没搞过一些三D渲染和交互场景，那就是掉队了呀。没过两年互联网加火了，要把能力对外输出，要让原本封闭的业务对互联网开放，要构建生态，这时候开放平台成了几乎所有互联网业务的标配，你说你不会搞，那又掉队了呀。紧接着短视频和直播带货又来了，所有的商品流、交易流都要适配直播场景，核心架构又要做大的变样，哪怕是个纯购物网站，你不会做短视频，不会做直播，那又掉队了呀。到现在AI大模型又火了，各个平台又要搞智能体验，搞A Gen的融合，你说你不会AI，又要小心被喷掉队了。

大家发现没有，这每一步的变化最大的共同点就是你在写第一行代码的时候，甚至是你下定决心进行重构的时候，打死。你也想不到未来会变成这样，我觉得这就是核心的复杂性，它不是静态的叠加，而是动态的，未知的技术和业务模式在不断的入侵。面对这种让人防不胜防的变化，你会怎么办呢？可以在评论区聊一聊啊。我觉得如果你只是一个程序员，那还好说，闷头学呗，不过就是学完这个扔掉那个嘛，走到哪儿算哪儿。但你要是一个项目负责人，那就没那么简单了。如果你还是像我们故事当中第一个项目那样，把业务逻辑和技术实现就绑死在一起，那就只能够拉着整个团队来一次大变革，那就做一次重构呗。于是 VR 来了，你要重构一次，直播来了，你要重构一次，AI 来了，你又要再重构一次。

你觉得这是你在带领团队进行技术的革新，但老板只会觉得为什么加个功能越来越慢了，为什么项目总是出现各种各样的 bug？老板还是只会觉得是不是你工作不努力了，是不是我要来个降本增效来刺激一下了。最后呢，哪怕你都干到九九六进 ICU 了，重构的工作量还是只能越来越大，项目还是越来越多的问题。这些核心问题不是靠公司砸钱招人九九六就能够去解决的，而 DDD 的核心价值我觉得就在这里，它强调把核心业务从技术实现里剥离出来，我不管外面的风口是 VR 还是 AR，也不管你是 Web 端还是小程序，核心的交易模型，核心的业务规则，它在任何技术背景，任何业务场景下都是稳定的。只有做到这一点，你的系统才能够兼容那一些不确定的未来。而这也就是我们经常提到的高内聚低耦合的终极形态。

这种终极形态在 DDD 的架构设计支持下，其实就是一种标准形态。感兴趣的朋友可以看看我之前分享的 DDD 的视频啊，连单体架构和微服务都可以通过一个注解轻松切换，那换个技术框架，换个接入场景，那是轻轻松松的事情。说到这儿，你有看过前面几期滴滴的视频吗？看过的朋友可以在评论区说一下你看了哪几期，有什么想要喷的问题没有？让我看看有多少人深受其害。聊完了业务，咱们再来聊聊人和组织。不知道大家有没有发现一个现象啊，在 DDD 最火的那几年，可劲儿去推动 DDD 的往往都是像阿里啊，像美团啊，像爱奇艺啊，包括京东这样的一些巨头公司。比如说蚂蚁金服就推出过一个类似 DDD 的框架啊，Cola。虽然不一定是非常核心的大团队，但团队的出生往往都是名门大派。那为什么会这样呢？是他们闲得慌吗？

当然不是，这是因为他们得了一种病叫做大企业病。随着整个技术团队越来越大，几百上千号人呢维护同一个系统，沟通成本是呈指数级上升的。前端会怼后端，后端怼产品，A 团队改了个字段，B 团队的服务直接挂了，大家都在扯皮，都在推卸责任。于是从中台这样的组织架构到微服务这样的技术框架，整个业界都有一个共同的目标，那就是要划分责任，降低沟通成本。而这个时候 DDD 的战略设计就派上了用场。我之前介绍过 DDD 啊，它的真正核心就是一个叫做 bounded context 限界上下文的概念。这玩意听起来玄乎，说白了就是画地盘定责任。而整个 DDD 的设计思想就是从宏观到微观，从整体架构到每个功能实现，都不断的通过限界上下文形成非常清晰的逻辑边界。

DDD 通过战略设计把一个巨大的系统切分成一个一个独立的上下文，比如说订单上下文、库存上下文、支付上下文。那么在订单这个地盘里，订单团队完完全全自己说了算，他们有自己的通用语言，有自己的模型，在这个边界内，他们可以精益求精。出了这个地盘，大家都通过标准的接口进行对话。而具体到每个上下文的内部，又通过四层架构来实现逐层的解耦，让团队里的每个人也能自己折腾自己的组件。要数据找 repository 仓库，要服务找 domain 领域，要业务找 service 服务。组件和组件之间的沟通通过标准的防腐层接口对话，这样即便内部再怎么折腾，它也不会影响整体的功能稳定。这其实就是在明确责任，战略设计强调如何分工，战术设计强调如何实现。大厂之所以推崇 DDD，就是因为这种责任划分的关系天生适合大组织的团队建设。

它让几百人的大团队也能像几个人的创业团队一样的灵活，不会出现严重的水土不服。那聊这么多呀，我来做个总结。DDD 它是一个神器吗？不是，它和任何技术一样，并不是百分百适合所有的业务场景。如果你的项目只是一些简单的增删改查，或者说生命周期非常的短，上完线就可以把技术人员全部踢走的那种，用 DDD 那就是杀鸡用牛刀，甚至会把自己搞死。但是如果在那些长期的、复杂的、充满不确定性的业务场景里，你把 DDD 用好了，哪怕只是在某个很小的业务场景，都会有非常惊人的表现。这其实和我们程序员的人生是一样的。作为一名程序员，我们大部分的工作时间其实就是做那些简单的 CRUD，都在处理那些琐碎的业务需求。这些工作并不能够体现你的核心价值，大家都能做呀。但是职业生涯的分水岭往往就出现在那几个关键的时刻。

当项目因为业务巨变而摇摇欲坠的时候，当系统因为某一个技术问题而濒临崩溃的时候，或者当公司面临一个前所未有的复杂难题的时候，如果你能够抓住这个机会，利用 DDD 的思想，透过现象去看本质，建立起清晰的模型，带领整个团队从混乱中杀出一条血路，那一刻你就脱颖而出了，你的职业生涯也会因此与众不同。这就是学习 DDD，甚至是那些你工作中暂时用不上的那些技术的真正价值。养兵千日，用兵一时。最后送大家一句话，真正的技术高手不是会用多少框架，而是能在混乱的世界里构建出秩序。最后呢，别忘了点赞、关注、收藏。当然，要是还有什么问题，欢迎在评论区交流。我是罗兰，关注我，IT 路上一起进步。接下来咱们评论区见。
