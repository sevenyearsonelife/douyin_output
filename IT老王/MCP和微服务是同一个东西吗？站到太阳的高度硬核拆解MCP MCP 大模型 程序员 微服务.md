前几天啊，我发了个介绍微服务的视频，反响还不错。但是呢，评论区却炸出来一位真大神啊。这位朋友说 MCP Server 就是微服务，我回复他这俩不是一码事儿啊。结果他来了一句绝杀，就是那是你没有站在架构师的角度。既然都说到这个份上了，我觉得就真的有必要站在架构师的角度来拆解一下这个 MCP 了。现在网上讲 MCP 的，也就是大模型上下文协议的视频满天飞，但百分之九十九点九九都是教你怎么在各种工具里面去配置 MCP 服务，会用就完事了。但这一次既然提到了架构师的高度，那咱们就得来玩点真格的了。我将带你跳出配置文件的表面，从底层协议和架构设计的高度来深度的拆解一下这个 MCP 协议，看看它到底是个什么鬼。

看懂了这期视频，你不仅能够明白它和微服务有什么关系，更重要的是你能看透大模型工具调用的本质，并且或许啊能够带你重新思考一下大模型时代古法编程到底有什么用。硬核拆解 MCP，这期视频内容深度啊你绝对找不到第二家。记得点赞关注收藏，我是楼兰，关注我 I T 路上一起进步。拆解之前要先花半分钟时间来对齐一下一些基础的认知。我们要理解大模型的 Tools 机制，这个是 MCP 的基础。大模型你可以把它看成是一个文科生，他就关在自己的小黑屋里面，没法直接上网。你想让他去查天气，那就得靠 Tools 工具调用机制。大模型输出一段特定格式的 JSON 指令，外部程序呢拿到这个指令去执行，再把执行的结果还给大模型。

这就是工具调用的机制，而 MCP 就是配合这个 Tools 机制，给这个外部程序做了个统一的约定，大家共同约定的一套 Type C 标准接口，只要遵循了这个协议，大模型就能无缝拔插各种外部能力。那么问题来了，这套 Type C 接口底层到底是怎么通信的呢？目前主流的就有两种形式，Stringable HTTP 和 STDIO。顺便提一嘴，早前还有个 SSE 的形式，但因为单向通信等等这些局限呢，现在基本被边缘化淘汰了，咱们重点就看前面两个就行。理论太干了，这次我们直接拿高德地图官方给出的 MCP 服务来举例，大家看看高德地图官网的这个配置信息，它的 Stringable HTTP 形式其实就是给了一个带健全 key 的 URL 地址，这说明什么？

其实这就已经说明了 Stringable HTTP 的本质，其实它就是一个标准的 HTTP POST 的接口。MCP 协议只是规定了这个接口里必须用 JSON 跟 RPC 的格式来完成一些它预先定义好的标准动作。口说无凭，POST MAN 咱们实操来进行验证。你看我向高德的这个 MCP 接口发了一个 POST 的请求，body 里写上标准的 MCP 指令，就这个 method，它是 tools.list，表示我要列出所有的工具。点击发送，下面就会返回了高德支持的工具，比如这个 maps.geo，描述写的就很清楚，将详细的结构化地址转换为经纬度坐标。

拿到工具名了呢，我们就可以来发第二个 POST 的请求，这次我把这个 method 变成 tools.call，表示是调用工具，参数里传给他城市就是长沙市，地址就是东方红广场，点击发送。大家看这个返回结果，经度一百一十二点九四，纬度二十八点一七，精准返回。用理论来破冰，用实操来验证，你看 Stringable HTTP 就是这么简单，一个 POST 接口，一套 JSON 指令搞定。所以你看这个 Stringable HTTP 其实本质上和传统的 Web 编程就是很相似的，而所谓协议呢，更多就是在传输性能上下了一些功夫。比如 Stringable HTTP 协议呢，它可以在必要的时候升级为有状态的长连接，实现更加实时的海量数据传递。当然底层实现的这些具体分享我们就不在这展开了，内容太多，一个短视频肯定是讲不透的。

搞懂了 Stringable HTTP，我们再来看高德官网给出的第二种接入方式 STDIO，官网给的配置呢其实看起来就是一行命令，这个 npx 指令，很多搞 Java 搞 Python 的朋友一看，哟，这就是一个 Node.js 的命令，是不是开发大模型用我们又得去学前端语言了？对，但不够深刻。其实 STDIO 的协议形式就是在本地启动一个进程，基于操作系统的 STDIO 标准输入输出接口来进行传递，而传递数据的协议跟 Stringable HTTP 是一样的，这就是 MCP 协议的核心。这呢是标准答案，但是站在架构视角来看就可以看得更深一点。大家想一下，高德地图那么庞大的算力和数据，它可能。塞进你本地的一个 npx 包里吗？绝对不可能。

这个本地跑起来的 node. js 进程本质上只是个二传手，大模型客户端通过操作系统的 stdio 把刚才那些 json 指令发给一个本地进程，然后这个进程就在底层依然是向高德的远端服务器发送一个 post 请求。其实不光是高德地图是这么干的，但凡复杂点的、有用点的 mcp 服务都需要调用远端服务。到这里你发现没有？发 post 请求这个动作跟编程语言它有半毛钱关系吗？完全没有啊，你用 java、用 go、用 python，甚至你去用 e 语言，只要你能接收标准的输入，能够发 http 请求，你就能写一个 mcp server。而在我们 java 的微服务体系里面发 post 请求互相调用，那简直就是家常便饭嘛。只不过 mcp 是把这些东西又给你封装成了一个新的框架而已。

这里咱们说到了微服务，那就回到开头那个争议了。既然 mcp 底层也是发 http 请求，java 的微服务呢也是发 http 请求，那 mcp 就是微服务这个说法对吗？作为老兵，我负责任的告诉你，这两个东西在架构本质上它完完全全是两码事。微服务解决的是系统架构的扩展与解耦，它是为了让几百号人能够协同开发，为了扛住双十一的千万级高并发，它是系统对系统的这么一种后端逻辑。而 mcp 解决的呢是 ai 与环境的交互标准，它根本不关心你后端用什么注册中心，怎么做负载均衡，它唯一关心的就是大模型该用什么样统一的语言来调用 web 的工具，它是 ai 对世界的一个传感器。如果仅仅因为他们都用了 http 协议，都提供了接口就把他们混为一谈，那就好比是说因为电动车和燃油车都有四个轮子，所以电池就是发动机，这显然是不严谨的。

哎，但话又说回来，把电池说成发动机那是确实不靠谱，但是我把电动车和燃油车都看成是汽车，这样又确实没有什么毛病吧？其实 mcp 和微服务呢又都是可以借鉴标准的 http 协议来进行构建的，从这个角度上来说它又是有互相通信的可能性的。所以如果你有跟踪过现在的新版本一点的 nacos，你会发现这个老牌的注册中心现在也开始支持像 mcp、skil 这些大模型的工作协议。既要从表层看清楚不同技术不同方案之间的差异，又要深入底层发掘它们的共通之处，相互借鉴，兼收并蓄，这才是架构思维的核心。看透了这一层，你还会纠结是去学 java 还是学 python 吗？mcp 其实说白了就是 json 的 rpc 指令加上 post 请求，跟咱们天天写的 c r u d 接口本质上没啥区别。

把微服务的底子学扎实一点，配合个大模型，你自己也能手搓一个 mcp server 出来，这就是架构思维带来的降维打击。这一层你看透了吗？
