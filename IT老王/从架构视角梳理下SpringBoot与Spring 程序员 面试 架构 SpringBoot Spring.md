Spring Boot你天天在用吧？但你有没有停下来想过一个问题，Spring Boot在Spring的基础上到底封装了什么？我见过很多人呢天天背诵什么自动装配的原理，学习各种starter的使用技巧，却真没见过有人来关注过这个Spring Boot的本质问题。甚至在很多程序员眼里，Spring Boot和Spring完全就是一团浆糊，根本就分不清。这也导致了只要遇到版本兼容的问题，绝大多数程序员呢完全是一脸懵。这叫什么？这叫战术上的勤奋，战略上的懒惰。你执着于这些细枝末节，却从来没有站在架构的层面去思考过Spring Boot到底是要解决Spring的什么难点呢？它在宏观上到底做了哪些封装呢？如果你连这个架构思维都没搞懂，那你背再多的八股文也只是个熟练的API调用工。

这一次我带你站在架构师的角度好好梳理一下Spring Boot的设计思想，跟着我的思路走，Spring Boot才真算是入门了。关于Spring Boot太经典了，想说的太多了，这个视频可能有点长，但真的希望你能看到最后，记得点赞关注收藏给自己留个底。我是罗兰，关注我，IT路上一起进步。想要看懂Spring Boot，我们必须找到一条主线。Spring已经很强大了，那Spring Boot要做些什么呢？仅仅只是把启动过程封装成一行Spring Application的run方法吗？其实围绕Spring容器启动前、启动中、启动后各个不同的阶段都有无数需要优化的问题，正是这些问题才让Spring Boot无比的经典。比如在容器启动前，各种乱七八糟的配置怎么去统一管理呢？

容器启动过程中一大堆的初始化代码要执行，你怎么知道它运行到哪个阶段了呢？容器启动后怎么让开发者的感受更好？比如如果报错了，怎么让程序员快速看懂问题在哪？当然具体问题有很多，Spring Boot的所有核心封装就是围绕这三个阶段在展开的，接下来我们一个一个来看。首先是容器启动前，我们都知道Spring跑起来需要大量的配置信息，以前写原生的Spring呢，我们要配一大堆的xml，那Spring Boot是怎么解决这个问题的呢？它没有去死磕怎么解析xml，而是做了一层极其漂亮的架构抽象，它把所有的配置信息封装成了一个统一的Environment对象，而Spring Boot框架会负责将多个加载出来的Environment对象最终合并起来，塞给Spring去加载各种乱七八糟的组件。你说这有啥用？

其实这就是架构设计的魅力。有了这层Environment的封装，Spring Boot就可以理直气壮说，我不管你以前配置写在哪，现在通通给我转移到我指定的application的yml这种默认文件里来。当然这还没完，你应该知道Spring Boot本身就指定了多个不同的配置文件加载的目录与文件，但其实不管配置文件怎么花里胡哨，最终都只是需要加载出Environment对象而已。那我是不是可以从自定义的任意文件里面加载配置呢？哎，只要你想到了，要实现非常的简单。如果你这样尝试过，那可不可以把格局再打开一点？我可不可以通过网络从远程服务器上拉取配置，然后塞进这个Environment里面？

有人抓住了这样的思想，于是Nacos、阿波罗这种分布式配置中心就诞生了，它们可以无缝接入Spring Boot乃至背后的Spring体系，就是抓住了这个架构的扩展点。你看搞懂了这种架构思想，那些高大上的中间件是不是瞬间就没有那么神秘了？甚至你也可以尝试动手去做做自己的配置中心，这可比背诵构建starter的十种技巧有意思多了吧？接下来到了容器启动中，这个阶段有什么痛点呢？这里有两个我觉得最为精妙的设计，一个是自动装配，还有一个就是事件监控。先说自动装配哦，你一定背过相关的面试题，但是你没有想过Spring Boot在这其中做了什么呢？它解决了Spring的什么痛点呢？

Spring框架其实早就支持用@AddConfiguration等一系列的注解来代替xml进行注入了，Spring Boot是怎么在架构上破局的呢？它引入了以Spring Factories为基础的配置文件机制，新版本更新成了import文件，但是底层思想其实是相通的。通过这一层配置文件把分散在各个架包里的零散配置类全部集中到一个固定的配置文件里面，启动的时候我一把梭哈全给你加载进来。但这还不够，一大堆的组件相互之间还有各种依赖，不就乱套了吗？于是Spring Boot在此基础上祭出了真正的杀招，@ConditionOnXXX一系列的条件装配机制。通过条件装配机制，你可以自动管理相关的组件依赖。你引入了Redis的组件依赖，好，那我就自动帮你把Redis Template装配好。

但这个机制其实还有个更强大的功能，在于你可以在没有Redis依赖的基础上就可以去检查项目中有没有Redis相关的核心类，而不像写Java代码一样，没有Redis的依赖你就没法import对应的类，那更别说后面的检查了。这才叫约定大于配置。就是通过框架把行业里的最佳实践当做约定提前写好，从而把你从繁琐的机械的组件拼装工作中彻底解放出来。你要是学会了这种集中管理加条件触发的架构思想，以后去设计公司内部的基础脚手架时，能少走无数的弯路。接下来是事件监控了，打开你的 Spring Boot 的项目啊，在项目里面加入这样的一个类，然后启动你的 Spring Boot 应用，你就能看到很多这样的日志了。这些日志是什么意思呢？

其实就是 Spring Boot 框架在应用启动的过程中不断的往外发布各种广播事件，告诉你应用启动到哪一步了，而你只要做一个监听器就能够接收到这些广播信息。关于这个案例我可以告诉你，只是接收到了 Spring Boot 应用中 Spring 容器加载完成后的少数事件，而在 Spring 容器加载前的一些事件，这个监听器它是接收不到的。这其实就是因为 Add Configuration 是 Spring 框架中的注解，也就只有在 Spring 容器加载完成后才能够生效。至于如何监听 Spring 容器启动之前的事件，你能想到什么办法吗？不妨在评论区说说，看看你这么多年的 Spring Boot 开发经验是不是花架子。接下来 Spring 容器启动完了，并都加载了，这时候 Spring Boot 又做了什么封装呢？

这里简单介绍 Spring Boot 提供的两个封装思路，一个是对异常信息进行封装，二呢是提供应用初始化接口。以前做 Java 应用，一旦容器失败了，控制台就会直接给你甩出几百行红色的异常栈，找个错误能把眼睛看瞎。所以 Spring Boot 封装了一套异常分析框架，端口占用了，数据库连不上了，它拦截到底层异常，直接用大白话告诉你哪错了，下一步该怎么解决。如果你的应用中定制了很多特殊的业务，那为了让运维有更好的体验，最好对每种边界情况定制一个异常类，再定制一个对应的 Failure Analyzer，让运维同学能一眼看懂问题出在哪里。另一个就是大家熟悉的 Command Line Runner 和 Application Runner 这两个接口了。

Spring Boot 会在整个应用启动完成后，主动调用容器当中的接口实现类，完成一些初始化的工作。Spring Boot 框架本身其实并没有提供对应的实现类，也就是说框架本身其实并不需要支持这两个接口，那为什么还要这么做呢？其实这就是架构师们在系统准备就绪的那一刻，把系统的控制权优雅的交还给了开发者。你需要加载缓存字典，你需要跑个初始化的脚本，没问题，实现这两个接口，容器刷新完立刻回调你，既满足了你的业务需求，又不会破坏 Spring 自身的生命周期，这就是架构设计的边界感。为什么要搞这些细枝末节的设计？其实就是一种优秀的架构设计思想。优秀的架构设计必须包含开发者体验，框架不仅要能跑，还要好用，这是架构师的同理心。而这其实也是一个好的程序员成长的必经之路。什么样的代码才叫做好代码？
