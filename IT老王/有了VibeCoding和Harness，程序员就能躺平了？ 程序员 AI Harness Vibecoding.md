这 AI 啊，是现在所有程序员都躲不开的一块心病。在我的各种技术视频的评论区也总是少不了各种拿 AI 说事的评论。这次我就跟大家好好聊聊这个 AI。最近 AI 圈有两个词特别火，一个叫 Web Coding，翻译过来叫氛围编程，另一个叫做 Agentic Harmless，也就是智能体脚手架。你先别去深究这些高大上的词是什么意思啊，但听完总会有那种感觉，就现在 AI 越来越强了，再加上这些神奇的工具和理念，AI 完全可以自己写代码，自己做产品了。那我们程序员以后是不是只要动动嘴皮子，提提需求就可以了呀？那以后剩下的这些程序员们是不是就可以彻底躺平了呢？如果你曾经也这么想，这个视频建议你一定看完。这阵子我是被各种 AI 圈的新闻旧闻给炸平了。

前段时间呢，Anthropic 的一位工程师 Eric Scholtz 做了个演讲，分享了他最近用 AI 做正式项目的一些实操经验。还有软件工程界的老前辈，提出过微服务架构的 Martin Fowler 也分享了如何用好 AI。他们的分享都很强大，也很接地气。梳理完后我知道的一个感受就是在 AI 时代，程序员不但不能躺平，反而要疯狂给自己升维。那这次我就带你把这两个含糊其辞的概念掰开揉碎了，看看在 AI 疯狂进化的今天，咱们普通程序员到底要如何保住饭碗，甚至拿到主动权。记得点赞、关注、收藏，我是楼兰，关注我，IT 路上一起进步。咱们先来聊聊这个 Web Coding 氛围编程，那什么是 Web Coding 呢？

很多人有个误区，觉得用 Cursor、用 Cloud Code 这些工具自动生成代码就是 Web Coding 呢。但 Eric 强调了一个更通俗也更深刻的内涵，就是让你忘记代码的存在，只关注你的产品意图。就像你化身成了一个不懂技术的暴躁老板，对着 AI 疯狂输出需求，给我做一个带支付的页面，按钮要大，颜色要红，然后 AI 噼里啪啦就把代码写好了，跑起来居然还真能用，听起来是不是很爽？很多不懂代码的小白就是靠着这个做出了各种小游戏。但如果你是一个专业程序员，当你把这种只动嘴皮子的模式用到公司真正的商业项目里时，坑就来了。为什么？因为 AI 最大的特点就是不确定性，一旦项目变大了，这团代码对你来说就是一个黑盒。今天它能跑，明天需求一改，AI 加了两行代码，系统就突然崩溃了，这时候你连 bug 都在哪都找不到。

所以 Web Coding 呢难度很大，但并不是说完全不能用。Eric 在踩过了无数个坑之后给出了一个很实战的建议，要把 Web Coding 严格限制在系统的叶子节点上。什么是叶子节点？就是那些最边缘的，不被其他核心功能依赖的模块。比如一个独立的数据导出脚本，或者一个简单的 UI 组件，在这些地方你完全可以放权给 AI，哪怕它代码写的乱七八糟的，只要能跑通，对整个系统也毫无影响。但是对于底层的主干节点和核心逻辑，必须保持人工的深度 review。就像这么多年来 CTO 的首席技术官可以不是技术专家，但是一定要有更清晰的眼光来把控技术的走向。这就引出了我的一个核心观点，在 AI 时代，对程序员的架构思维要求其实更高了。以前咱们的程序员很多时候就是一份工作，老板给多少钱，我就敲多少行代码，拿个需求文档照着写就行。

但是未来能够剩下的程序员，你就得操着产品经理和架构师的心了。你可以不用操心代码具体怎么写，但是当你拿到一个需求以后，脑子里就得先有一张系统的架构图，哪些是叶子节点可以扔给 AI 随便玩，哪些是核心主干必须自己死守，你得要清清楚楚。你还得精心设计输入输出和压力测试，保证不管 AI 代码写的多烂，系统整体运行不会那么容易崩。这种系统级的拆解和把控能力，以往都是技术管理层该操的心，但是随着 AI 更强大，这些问题必然会下放给团队里的每一个人。Web Coding 更加适合做那些一次性生成的边缘性的模块，那如果面对庞大复杂的核心主干项目，咱们应该怎么用好 AI 呢？这就轮到第二个概念出场了，Agentic Harmless 智能体脚手架。

这个概念有个很基础的公式啊，就是 Agent 等于 Model 加 Harmless，也就是说智能体等于模型加脚手架。那也就是说模型就是 AI 的大脑，负责发散和生成，而 Harmless 脚手架就是你给 AI 穿上的紧身衣，负责约束和验证。咱们先说个痛点，大家有没有觉得 AI 写代码其实特别像个神经刀，同样的提示词，今天生成代码完美无缺，明天生成的可能就漏洞百出了。Martin Fowler 一针见血的就指出了这个问题，他说以前咱们写代码不管是 Java 还是 C 加加，只要逻辑对了，编译一百次结果都是一样的，这个叫确定性。但 AI 是个概率模型，它天生就是非确定性的。这种非确定性会带来非常严重的后果，比如你的自动化测试会时而通过时而失败，真正的 bug 会被当做随机噪音。

比如 AI 会不加判断的放大你原本代码里的烂逻辑。再比如一旦出了错，你根本不知道是哪一步推理出了问题，调试起来简直让人崩溃。如果你用之前那种确定性的思维去管理 AI，迟早也会被逼疯。为了对付这个神经刀，Faller提出了两步非常具体的建议。第一个是前馈控制Guiders，在AI动手之前你要给它立规矩，比如写一份详尽的文档，把项目的命名规范，绝对不能用的库明明白白的喂给AI。第二是反馈控制Sensors，在AI写完之后你要有能力自动验证，比如极其严格的类型检查，自动化测试套件，AI只要犯错立马就会被测试脚本打回去重写。这两者缺一不可，只有规矩没有验证，AI根本不知道自己写的对不对，只有验证没有规则，AI就会像没头苍蝇一样不断犯同样的错。这些说法听起来可能有点绕，但如果你平时经常用AI写代码，肯定瞬间就有共鸣了。

大家平时是怎么约束AI不让它乱写代码的？欢迎在评论区聊聊你的独门绝技。在这个模式下，我特别想跟大家分享一个观点，未来我们不再是单纯的打字员，而是带着AI实习生的导师。当AI反复犯同一个错误的时候，你千万不要自己上手去帮他改那两行代码，真正的高手是去修改脚手架，要么去完善提示词规范，要么去加一个自动化的测试用例，让AI在未来永远无法再犯同样的错。这也是为什么我说程序员不能躺平，因为构建环境比写代码更烧脑。这也是为什么Harnes这种东西在阿里腾讯这样的大厂是硬性指标，是规范化的 工作流，而在普通人的眼里，这就只是一个怎么说都对的概念的原因。最后我想换个角度跟大家好好聊聊AI到底对咱们程序员的工作产生了什么深远的影响。

这些大佬的技术分享里其实都隐隐约约的指向了一个极其致命的问题，这也跟我以前多次提出的想法不谋而合，那就是AI打破了程序员的学习循环。以前我们学编程怎么学？其实编程的本质它就是从想法到代码，再反馈并修正的一个学习循环，你每踩一个坑，每调一个bug，你对系统的掌控力就强一分。那现在AI啪的一下把一堆代码甩给你，你不看直接跑，跑通了万事大吉，短期看你的产出效率起飞了，但长期看你对这个系统内部到底是怎么运转的一无所知，一旦脱离了AI，甚至遇到AI解决不了的深层逻辑bug，你连问题都很难看得懂。关于初级程序员会不会被AI淘汰，Martin Fowler很直白的说不知道，但是我们能够知道的是，如果过度依赖AI切断了这个学习循环，那就没有人能够成长成为高级工程师。但这并不是结局，而是改变。

Eric在演讲后的Q A中也表示，AI编程积极的一面在于借助现在越来越强大的AI工具可以更轻松的吸收新的知识，真正的核心变化在于那些懒惰的人不会主动学习，只会得过且过。那对于大部分学又学不进，躺又躺不平的普通程序员来说，我们应该怎么应对这种影响呢？这里有两个经验送给你，第一呢体验大于学习，现在的AI应用圈呢概念大于内容，经验重于能力，不要用以往学传统技术的死办法来学习AI，等着别人给你投喂精心准备的提示词啊工作流啊，不如自己动手去体验体验，只要能帮你解决问题，那就是好工具。就像现在说Spring、Rocket、MQ这些中间件，有的人说经典的不行，有的人却说这是古法编程，怎么说都没问题，只要当你真想要提升系统高并发性能的时候，有法可依，有工具可用，这就够了。

哪怕是Spring AI、Lang Chain、Llama Index这些听起来就头大的AI客户端编程框架也是一样。第二个主动给自己升维，时代真的变了，AI时代确定是一个知识能力高度集中的时代。如果你进不了AI产品竞争的时代红利圈，那你能做的就尽快想好怎么和AI共处。以前那种你给多少钱，我敲多少代码的纯体力活时代已经结束了，未来的游戏规则是谁能站在更高维度去拆解业务，去设计验证机制，去驾驭AI，谁就能够享受AI爆发带来的红利。如果你觉得今天聊的这些内容对你有点启发，记得点赞关注收藏，遇到瓶颈的时候翻出来听听。我是罗兰，关注我，IT路上一起进步。最后呢你在工作中是怎么和AI斗智斗勇的？咱们评论区接着聊。
