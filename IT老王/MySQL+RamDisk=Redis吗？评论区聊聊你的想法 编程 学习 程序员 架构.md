MySQL 加上 RAM Disk，也就是内存盘，就变成了一种纯内存的数据操作。这样是不是可以替代同样是纯内存工作的 Redis 了呢？最近有几个视频聊到了高并发场景的设计，很多时候都在围绕 Redis 做设计。于是就有朋友在评论区提出了这个天才的问题。罗兰，既然 Redis 快是因为它在内存里，那我现在把服务器内存加满，把 MySQL 的数据目录挂载到 RAM Disk，也就是内存盘上面，这样 MySQL 不也就变成了一个内存数据库了吗？那我是不是就可以把 Redis 给优化掉了呢？那这次咱们抛开内存和硬盘的成本不谈，就聊这个逻辑，听起来很完美对吧？都是纯内存操作，凭什么你 Redis 就敢说自己更快呀？这个想法你有没有觉得哪里有不对的地方？可以在评论区先聊聊你的想法，我们共同来探讨一下。

事实上你会发现，讲技术的短视频这么多，你应该从来没有听说过有哪个博主会跟你分享这样的用法吧？因为这根本就不是硬件介质的问题，这还是我经常提到的架构设计与取舍的问题。今天我就带你来抛开表象，对 MySQL 和 Redis 来一次外科手术式的拆解和比较，看完保证你会对 Redis 为什么这么快有一种不一样的理解。我是罗兰，记得关注点赞，IT 路上一起进步。首先我们都要弄清楚，同样是用内存，两者在操作系统眼里的地位是完全不同的。先看 MySQL，当你把 MySQL 放到 RAM Disk 上，你只是骗过了物理层，但没有骗过操作系统。

在 Linux 内核的眼里，RAM Disk 依然是一个块设备，MySQL 去读数据依然要走 VFS 虚拟文件系统，依然要经过文件系统驱动层，而且数据读出来之后，MySQL 还是要把它拷贝到自己的 buffer pool 里，这就导致了双重内存，数据在 RAM Disk 中占了一份，在 buffer pool 又要占一份，中间还隔着厚厚的操作系统的抽象层。再来看 Redis，Redis 是真正的 user space 用户态直读，它根本不走文件系统那一套，在 Redis 眼里，数据就是 C 语言堆内存里的一个个指针，当你执行指令的时候，Redis 拿到内存地址直接就去访问那一个内存块去了。

所以一句话总结就是，MySQL 它是隔着厚厚的玻璃窗看外面的风景，始终还是在用内存模拟磁盘，而 Redis 是真正站在风景里，原生就直接使用内存，这中间的系统调用开销就是一道不可逾越的鸿沟。第二点呢在于他们怎么听懂你的指令。先看 MySQL，MySQL 呢接收的是一些 SQL 语句，这是一种人类的语言。当你发一句 select 语句的时候，MySQL 必须要启动它的大脑，经过解析器、优化器，它要去分析语法，要检查权限，最重要的是要在优化器中计算成本，走哪个索引啊？要不要回表呀？join 顺序怎么排呀？哪怕数据都在内存里，MySQL 光是想明白你要干什么这一步就已经消耗了大量的 CPU 周期。再来看 Redis，Redis 呢使用的是 RESP 协议，它就简单到令人发指。

比如 set key value 这样的指令，在底层的报文就是这样的一种结构。星号三呢表示三个参数，后面接着 dollar 三表示第一个参数的二进制长度，接下来是第一个参数的二进制内容，啊，就这种形式去组成整个指令。这种协议呢是二进制安全的，而且解析它几乎不需要消耗 CPU，Redis 服务端只要拿到这样的报文，它甚至都不需要去构建复杂的语法树，也不需要计算什么执行。计划，直接根据参数位置就能调用对应的 C 函数分发指令了。甚至你可以基于它的 RESP 协议完全自己去开发一套 Redis 客户端，这也很轻松，就像这样。一句话总结就是 MySQL 是在做复杂的阅读理解，而 Redis 只是在做简单的填空题。第三点也是核心中的核心，就是数据结构的设计哲学。

先看 MySQL，MySQL 的 InnoDB 引擎啊，它是基于这个 B 加树构建的，而 B 加树的设计初衷是为了减少磁盘的 I O，所以它会把数据组织成一个一个的 page 页，默认呢每个页是十六 K B，哪怕你只读几个字节，MySQL 也必须加载和维护整个十六 K B 的 page。这种为了磁盘设计的重型结构，在纯内存的场景当中就是纯纯的累赘。再来看 Redis，Redis 的数据结构是为内存定制的，它最大的特点就是动态编码。比如在 Redis 里保存三条简单的数据啊，set k 一呢是一百，set k 二楼兰，set k 三一个很长的字符串。接下来你就可以使用 object encoding 指令就能看到 Redis 底层它是怎么根据数据形式进行变身的。

k 一呢存的是一个纯数字，底层用的就是 int，直接把 value 存成一个 long 类型，不需要分配堆内存。k 二呢存的是一个短字符串，底层用的就是 embstr，这种结构会申请一块连续的内存，把头信息和数据紧挨着放，这能极大的提高 CPU cache 缓存行的命中率。k 三存的是一个长字符串，Redis 中默认超过四十四个字符的就是长字符，当然这个长度是可以配置的，它的底层用的就是 raw 类型，这种类型呢就会像普通程序一样分配一块单独的内存，再创建一个指针指向这块内存。这还只是针对 string 一种业务类型，实际上在 Redis 中针对每种不同的业务类型，比如 hash、list、set、zset 等等，都设计了多种匹配的底层数据类型，以保证底层数据总能按照最优的方案进行保存和检索。

总结呢，MySQL 就是一个大锅饭，不管你吃多少都给你发个大饭盒，也就是一个。而 Redis 则是量体裁衣，通过动态编码榨干了 CPU 缓存的性能。最后我们来聊一聊最大的争议点，线程模型。我们都知道 Redis 是单线程的，那为什么单线程的 Redis 反而能够吊打多线程的 MySQL 呢？我们可以把它想象成两种完全不同的任务场景。先看 MySQL，MySQL 的工作就像是几百个人一起盖大厦，这是一种逻辑复杂性的任务。一个简单的 SQL 语句就要处理事务 ACID，要回滚，要保证数据一致性，还要记各种各样的 log 日志。为了搞定这些，MySQL 就必须用多线程，但人一多，管理成本也就上来了。像第一个锁竞争，两个工人不能够同时抢得起一块砖吧，这就需要有额外的功夫来进行协调。

还一个呢上下文切换，CPU 这个包工头要在几百个线程工人之间切来切去，指挥这个指挥那个，还要不断的还原现场，看看大家都执行到了哪一步了。所以 MySQL 需要在管理和协调上发挥大量的功夫。但 MySQL 每个线程任务时间都很长，所以这些管理消耗在它的整个体系当中还是可接受范围内的。不过对于要追求极致性能的纯内存操作来说，这个消耗就非常可观了。再来看 Redis，Redis 的工作就像是挤地铁，这是一个典型的 I O 密集型的任务，每个任务都极其的简单，拿票、刷卡、开门都是这种模式。这种场景下简化管理的单线程模型更能体现优势，因为在这种模式下每个任务都不需要做任何额外。的协调管理，最快速度去执行就完事儿了。

再配合 I/O 多路复用、EPOLL 技术，它就像在同一个地铁站配置了多台闸机，车还是一个车，但是进来的队列可以有很多个，这样整个系统的运行速度就更高了。所以通常 Redis 的性能瓶颈都不会是它的 CPU，而是网络 I/O。大部分情况下，给它配置更合理的网络结构会比优化数据形式来得更加的有效。那么一句话总结就是，MySQL 因为是任务太复杂，所以不得不启用多线程，导致了昂贵的上下文切换的成本。Redis 呢是因为任务很简单，单线程跑起来反而没有累赘，简单就是极致的快。所以回到开头的问题，把 MySQL 放到内存里面，确实它能够变快，但它永远变不成 Redis。MySQL 的设计初衷就是可靠，它像一个穿着防弹衣的重装步兵，为了事务 ACID 的安全性牺牲了速度。

Redis 的性能初衷则是极速，它像一个轻装上阵的短跑运动员，为了速度剥离了一切重负。虽然他们都做的是这些数据存储的事儿，但在这些任务目标背后是完全不同的设计理念。所以可以看到，我们不要试图用对硬件的战术勤奋去掩盖数据选型上的战略懒惰。给拖拉机换上了法拉利的引擎，它也跑不上 F1 赛道，因为它生来就是为了耕地的。啊，关于我们这次的分享啊，如果你有更多的想法或者是有些什么问题，欢迎在评论区继续沟通。我是罗兰，关注我，IT 路上一起进步。
