Web coding 是什么样的？是不是只要描述清楚需求就能做项目了？是不是主打一个我上我也行？事实到底是怎么样呢？来，一个很常见的问题快速检验一下。假设你们公司现在做一个很常用的智能客服系统，就是用来回答用户的问题。项目第一步需要你来拍板决定到底对接哪个大模型，是选 GPT、Gemini 还是国产的 DeepSeek、通义千问这些呢？你会怎么选？不妨把视频暂停几秒，在评论区先说说你的想法。你可千万别听网上那些评测说 GPT 擅长这个，Gemini 擅长那个就直接拍板做决定了。你这是带着团队做真实的商业项目呢，不是一个人过家家。你要找的是最适合你当前业务的模型，而不是最好最贵的模型。而且现在模型迭代这么快，你怎么能保证今天选出来的模型几个月后它依然是最能打的呢？在工程上到底应该怎么去评测一个大模型应用的效果呢？

这次我就给你拆解一个专业的评测框架 Regas，并带你构建一套完整的工程化评测体系。记得点赞、关注、收藏，我是罗兰，关注我，IT 路上一起进步。在深入聊技术框架之前，我们要先理清一个逻辑，就是在工程上我们怎么去评测一个大模型应用到底好还是不好呢？最简单粗暴的办法当然就是哎拍脑袋人工测了，就像很多短视频博主做评测那样的，自己想几个问题，挨个去问不同大模型，然后人工看一眼答案，感觉哪个顺眼就选哪个。这种方式平时看看热闹还行，但真要拿来做项目决策，那简直就是开玩笑了。为什么呢？首先你拍脑袋想的问题根本代表不了你的客户，真实客户不是按照剧本念台词的机器人，他们的提问千奇百怪，绝不会按照你的套路出牌。然后呢，你没法量化大模型的回答好在哪里，好多少。一旦要对比的模型变多了，那你这套凭感觉的方法就会彻底的崩溃。那要怎么办呢？

你至少要建立一套自动化的评测体系，让机器代替人工来做评测，具体要分四步走。第一步构建测试集，你要准备一批用户常见的问题和对应的标准答案，通常在项目的初始阶段，你可以先预设一些高频的问题，然后请公司的业务专家给出绝对正确的标准答案，这在工程上称为 Ground Truth，这就是你的初始测试集。等项目上线了，再把用户真实的提问不断收集补充进来。第二步自动化批量测试，接下来需要写个自动化脚本，把测试集里的问题通过 API 批量的发给你要测试的大模型用，然后把大模型给出的真实答案全部收集下来。第三步批量打分，拿大模型应用的真实答案和测试集里的标准答案进行批量对比，形成一个整体的评分。这一步最重要的就是要把答案的准确性转换成一个量化的数字评分，用具体的分数来代替你主观的感觉。具体怎么打分呢？

这就要请出今天的主角 Regas 框架了，后面会详细的拆解。第四步持续优化，用户的问题是无穷无尽的，所以评测它也不是一锤子买卖，你需要持续收集线上的真实问题，不断扩充测试集，定期让大模型重新跑测，只有这样你的应用才能跟着大模型一起成长。这是一套最基础的自动化评测体系，你现在的团队是怎么做模型选型的呢？或者你有什么更好的思想，欢迎在评论区交流。整体方案确定了，接下来我们来啃最硬的一块骨头，就是之前第三步留下的悬念，到底怎么给大模型的答案打分呢？如果让你看两段文字，评价哪一段写的更好，你可能还能勉强说出个一二三来，但如果让你精确打分，说这个就要给九十，那个只能给八十五，这估计就非常困难了吧？自然语言的特殊性决定了打分是非常困难的，现在的行业共识就是用魔法打败魔法，让大模型当裁判。那具体怎么构建评分体系呢？

这就需要更加严谨的思路了。这里重点介绍业界最火的 Regas 评测框架，特别是它里面最核心的指标 Answer Correctness 回答准确性。像这个案例，指定用户的问题是苹果 Pro Max 手机怎么退货，大模型给出的回答是我们的 Pro Max 手机支持七天无理由退货，退货运费由买家承担，并且赠送一年延保，而预设的正确答案是支持七天无理由退货，但拆封后不支持，退货运费由买家承担，最终计算出来的回答准确性是零点六八三四九九。那这个分数是怎么来的呢？Regas 在判断答案好不好的时候，会综合考虑两个具体的指标维度，语义相关性和观点匹配度。先说这个语义相关性，它就是在看大模型的答案和正确答案讲的是不是同一回事。比如标准答案是需要重启路由器，大模型说请将网络设备断电后重新开启，字虽然不一样，但意思其实。

是一样的，在工程实现上，我们就会把这两句话转成向量，计算它们的余弦相似度，只要距离够近，就说明大模型没有答非所问。但语义相关只能说明大模型的正儿八经回答这个问题，但是回答到底的好还是不好，那就要请第二个杀手锏出场，观点匹配度了。还是之前那个案例啊，假设客户问，你们的 Pro Max 手机退货政策是什么？专家的标准答案是支持七天无理由退货，但拆封后不支持，退货运费由买家承担。而大模型的回答是我们的 Pro Max 手机支持七天无理由退货，退货运费由买家承担，并且赠送一年延保。这时候要怎么评判呢？观点匹配度的思路分三步走，第一步要拆解观点，让裁判模型把标准答案单独的拆分成一些观点列表，比如说支持七天无理由，拆封后不退，买家承担运费，这就是观点的列表。接着把大模型的回答也同样的做成这样的观点列表。

第二步交叉对比，裁判模型就要开始遍历这两份观点列表，依次进行检测了，会有几种情况，第一种，如果大模型的观点和标准答案对上了，那就放到 TP 列表里面，表示事实重合，比如说支持七天无理由。第二种，如果大模型说了一个标准答案里面没有的观点，那就收集到 FP 列表，表示这是一个幻觉，比如说赠送一年延保。还有第三种，如果标准答案里有的关键信息大模型提都没提，那就收集到 FN 列表，表示观点遗漏，比如说拆封后不退。啊，有了这三个列表之后，接下来进入第三步，套用公式进行计算，要统计这三个列表里的观点个数，综合计算出一个 F1 总分，计算公式是这样的。基础的思路就是你回答准确的就加分，你漏了信息或者自己加戏瞎编，那就要扣分。

比如我们之前的案例啊，TP、FP、FN 的观点都是一，那么计算出来结果就像是这样，得到 F1 的分数呢只有零点五。最后再把前面算出来的语义相关性得分和这个 F1 总分按照权重加到一起，就能得到最终的整体评分。Ragas 默认的计算方式呢是 Answer Correctness，最终等于零点二五乘以语义相似度得分，加上零点七五乘以事实准确度得分。通过这种观点拆解加逐一对比的方式，裁判模型就能精准抓住大模型的遗漏和幻觉，给出一个铁证如山的客观分数。这里让裁判模型去精准提取观点并做连线比对，prompt 提示词非常的有技术含量，这也是 Ragas 最核心的设计。如果你需要这套裁判模型的 prompt 源码分析，在评论区扣个 Ragas。怎么样，这套思路你还能搞定吗？

今天分享的 Answer Correctness 其实还只是大模型评测的冰山一角，针对不同的应用类型，Ragas 框架还提供了非常多有用的指标，而 Ragas 就是把这种工程化的复杂思想封装到了几个简单的 API 之后。那回到视频开头的问题啊，未来的 Web Coding 会怎么样？我觉得就会是这个样子，代码实现会越来越简单，但系统背后的工程思想会隐藏的越来越深，能不能挖掘到这些底层的思想才是决定你实力的关键，这一层你看透了吗？
