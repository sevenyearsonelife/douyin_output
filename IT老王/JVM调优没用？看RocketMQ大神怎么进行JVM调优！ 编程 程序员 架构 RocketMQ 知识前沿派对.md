问大家一个非常反直觉的问题啊，我们写的 Java 代码真的需要去做 JVM 调优吗？百分之九十九的程序员可能会说不需要，因为绝大部分程序员哪怕做了好多年的开发，从来都是在 IDE 里右键运行就完事儿，还调优？能跑就行了，有啥好调的？但是这就带来了一系列可以说是每个程序员从入门就开始一直拖延的巨大矛盾。既然工作中没什么用，为什么面试的时候面试官总喜欢抓着 JVM 调优问个不停呢？既然 JVM 没什么好调的，为什么你去翻看 RocketMQ、 Kafka 这些顶级开源项目的启动脚本，会发现里面写满了密密麻麻的 JVM 参数呢？难道这些开源 Java 大神们还需要炫技吗？还是说他们看到了一些我们作为普通开发者看不见的风险？如果你看烦了各种 Java 的面试题，那么今天这期视频对你一定非常重要。

这次我不聊虚的理论，直接带你去拆解阿里开源的 RocketMQ 生产环境的启动脚本。我要透过这些参数带你去搞清楚一个核心问题，当顶尖高手决定对 JVM 动手的时候，他们脑子里到底在想什么？这可是我压箱底的一期技术视频了，只对热爱技术、热爱人生的有缘人开放，记得点赞、关注、收藏。我是楼兰，IT 路上一起进步。要看懂高手的招数，首先你得认识他们手里的兵器。JVM 调优形式上呢就是调整一些 Java 进程的启动参数，但是有哪些参数可以调呢？不同的 Java 版本这些参数有什么不同呢？千万不要尝试像面试八股那样去背，你是背不住的。你需要知道的是 JVM 参数也是分三六九等的，需要调整什么参数的时候，要会调更要会查。

第一等呢是宪法级的标准参数，就是以单横杠开头的，比如杠 version，不管你是用 JDK 一点八还是 JDK 十七，这些参数永远有效，而且变动非常小。这类参数可以使用 Java 杠 help 查看，其中最为重要的就是杠 cp 参数了，指定 Java 进程所需要的程序目录和 jar 包目录，这是 Java 运行的基础。另外从 JDK 九以后还增加了一系列针对模块化的参数，比如 list modules 列出所有模块，还有 add modules 增加新模块等等。从这里你可以看到模块化机制从来不是 Java 的鸡肋，它跟你写的每一个 Java 程序都有关系。

第二等是行业潜规则级的非标准参数，也就是杠 x 开头的，官方说它非标准，但实际上呢它非常的稳定，所有 Java 版本基本上都支持，变化也不是很大，这是所有程序员的基本功。这类参数可以使用 Java 杠 x 查看，比如大家最熟悉的杠 xms 表示初始的堆大小，杠 xmx 表示最大的堆大小。这里顺便问你一个高端岗位的面试真题啊，JDK 九以后默认使用的是 G One 垃圾回收器，而 G One 逻辑上是不区分固定的老年代和年轻代的，但 JDK 中依然保留了杠 xmn 参数来设置年轻代的大小，那么这个参数有什么用呢？G One 对于年轻代到底是如何控制大小的呢？这个问题比较高端，可以把你的想法发到评论区，我们一起交流。

第三等才是调优的深水区，以杠 xx 冒号开头的不稳定参数，这里全是开关和黑科技，但请注意，既然叫做不稳定，就意味着它跟 JDK 的版本是强绑定的，很多在 JDK 一点八里被奉为神条的参数，到了下一个版本可能就被废弃了，甚至可能导致服务启动失败，并且同样是一个 JDK 的大版本，不同的小版本这些。参数也会有所不同，所以高手调优的第一条直觉永远是看版本下药。那怎么查看当前版本有哪些不稳定参数呢？有一个参数你可以记一下，就是这个 PrintFlagsFinal，这个参数会列出所有最终生效的不稳定参数。可以看到这类参数有很多，但都不是靠记忆能够记得住的。

其实如果你多拿几个 JDK 的版本，都使用这个 PrintFlagsFinal，然后对 G1 关键词进行过滤，过滤跟 G1 垃圾回收器相关的参数，你会发现一个很有趣的规律。虽然同为 G1 垃圾回收器，但是随着 JDK 版本的升级，G1 相关的参数却越变越少了。这其实就是 G1 算法在不断优化的结果，G1 会越来越强调自适应，减少程序员手动调优的工作量。而这个故事就不是几个面试八股能够讲明白的了。明白了参数的等级，我们再来看看 RocketMQ 的 runserver 点 sh 这个脚本，这就是 RocketMQ 启动它的 nameserver 服务的核心的调参脚本。这段代码完美展示了什么叫上帝视角的调优。这个脚本最核心的脚本调优部分呢其实并不复杂，就是这样的。

可以看到他做的第一件事就印证了我们刚才说的检测 JDK 的版本，脚本逻辑很暴力，如果你的版本小于九，走上面这一套配置，如果是九以上，那就走下面这一套配置。这说明在高手眼中，JDK 一点八和后面的 JDK 九加其实是两个完全不同的物种。关于 JDK 一点八和 JDK 九加有哪些核心的变化呢？你能列出几个来吗？欢迎在评论区交流。我们重点看他是怎么去调优 JDK 一点八的，这里面藏着 RocketMQ 团队对业务的极致经验。经验一，提前布局内存，扼杀抖动。看这个配置，他把堆内存的初始大小和最大大小都设置成了四个 G，初始堆和最大堆必须设成一样大，为什么？因为高手不允许 JVM 在运行的时候忽大忽小的调整内存，每一次调整都是性能损耗，稳定压倒一切。

经验二，反常规的内存布局，注意这个参数杠 Xmn 二 G，总的堆内存是四 G，他既然把新生代设置成了二 G，占比达到了百分之五十，教科书教我们要设成三分之一啊，RocketMQ 为什么要反着来呢？这就是懂业务，RocketMQ 它是消息中间件，消息的特点是朝生夕死，把新生代搞大一点，就是为了让这些短命的对象在新生代你就彻底干掉，坚决不让他们流传到老年代，因为一旦进入老年代，那就是 Full GC 的地盘，那是系统的灾难。经验三，激进的清理策略。对于 JDK 八，他选择了 CMS 回收器，但改了一个关键的阈值，这是 CMS 开始进行初始标记的内存阈值，默认是百分之九十二就开始回收，那 RocketMQ 改成了百分之七十，这意味着什么？

意味着提前动手，普通人是等垃圾堆满了再倒，高手是看着快满了就倒，虽然倒的频率高了，但每次倒的快，系统就不会容易产生卡顿。而对于 JDK 九加可以看到，它虽然改用了 G1 垃圾回收器，但是也把开始进行 GC 的内存阈值给调小了，这种提前动手的思想还是一致的。看完了 RocketMQ 的启动脚本，其实不仅仅是学会了几个调优的参数，更重要的是要理解这些参数背后的调优思路。RocketMQ 就给所有人生动的分享了一套通用的调优三部曲，这三步不仅仅是操作指南，更是高手为了预防未来风险而布下的三道防。螃蟹。第一步，规划地盘，也就是内存布局。我们为什么要像 RocketMQ 那样去精细计算新生代大小呢？这是为了防止对象早衰。如果你的新生代规划的太小，那些本该在年轻时就死掉的短命对象，就会因为挤不下，被迫晋升到老年代。

一旦老年代被这些垃圾堆满，那就会触发 Full GC 导致系统卡死。所以充分的内存规划本质上是在物理层面隔离风险，让对象死在他该死的地方。如果是做 Web 服务，对象短命就应该加大新生代；如果是做本地缓存，对象长寿就应该加大老年代。把理论和业务相结合，Java 调优才不会那么枯燥。第二步，选对管家。对 Java 来说，百分之九十的调优工作都集中在 GC 上。但这一步不是简单的选个 G1 或者 CMS 就完事了，而是要匹配业务的性格。如果你的系统是个支付接口，用户对延迟极度的敏感，那你必须选择 G1 或者是 ZGC，哪怕牺牲一点 CPU 资源也要保证不卡顿。如果你的系统是离线报表，只求跑得快，那 ParNew GC 可能才是王者。对于 GC 算法，是为了在硬件资源有限的情况下，把系统的业务性能压榨到极致。

第三步，装上监控。大家看 RocketMQ 脚本的最后啊，不管在哪个版本，它都精心布局了 GC 的日志文件，同时还限制了日志文件的数量和大小。这样可以防止日志把磁盘写满，但更重要的是为了可观测性。高手的调优从来不是一次性的，而是根据日志逐步迭代，小步快跑的。学会分析 GC 日志能让你拥有一双透视眼。比如通过日志发现老年代的使用率每天在缓慢的上涨，虽然现在没有崩，但你能预测出一周后就会出现 OOM 内存溢出。这种从日志中看见未来的能力才是调优的最高境界，它能让你在故障发生前就把隐患消灭掉。这套调优三部曲虽然并不一定是所有 Java 程序都适用的万能招数，但至少你学会了这一套从开源框架中提取出来的独门秘籍，行走江湖肯定就比别人多一层信心了。

然后回到开场的那个问题，既然 Java 写了代码就能跑，为什么大神们还要费尽心机去调优呢？现在答案可以揭晓了。普通程序员和顶尖高手的区别其实往往还不在技术本身，而在于思维的方式。普通人是救火队员，只会等着线上 OOM 了，服务崩了，只才会急着急忙慌的去重启服务，然后匆匆忙忙，连滚带爬的查日志，病急乱投医。而高手是建筑师，他们在代码运行之前就已经通过对业务的深刻理解，把资源的规矩立好了，维护系统的稳定性那是从从容容，游刃有余的小事。而这种未雨绸缪的掌控感何尝不是你的人生秘籍呢？希望大家看完这期视频能关掉那些八股文，去看看自己手头项目的启动脚本，把这种未雨绸缪的思维带到你的工作里，这才是技术进阶的必经之路。然后记得点赞、关注、收藏，并把你的想法以及遇到的问题发到评论区。我是罗兰，关注我，IT 路上一起进步。
