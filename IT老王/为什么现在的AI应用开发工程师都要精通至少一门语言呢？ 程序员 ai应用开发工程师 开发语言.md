朋友们，你们有没有想过一件事情，就是为什么现在这些 AI 应用开发工程师的岗位招聘要求上都会加上一条精通一门开发语言，通常都是 Java、Go、Python 至少精通其中一门，为什么呢？你说这些东西我反正是 Web Coding，我不用写代码，我一样都可以做开发，我甚至自己写项目写的贼溜，那为什么要你去精通呢？有些朋友会觉得说，那是不是为了我能够 review 那些 Web Coding 生成的代码呀，至少看看 AI 写的这些代码有没有问题？但其实不是这样的，你真正做过一线开发你就知道，当业务体量上来了之后，别说新手了，老手都没有时间去看那么多代码，尤其现在 Web Coding 生成的代码，大部分都是又臭又长，你根本没有时间去看，那为什么还非非要你去精通一门开发语言呢？那怎么看你是自己是不是精通？

这次趁着中秋休息，我也回老家去参加了一次朋友聚会，都是一些开发经验丰富的编程老鸟了，有以前的同事朋友，还有一些跟了我很久的老学员。当然大家聊的最多的也就聊着聊着编程聊 AI 了，结合他们的很多一线的故事和体验，对于 Web Coding 我也有了一些新的思考，也确实有不少的收获，我觉得或许这些经验可以对你有一点点帮助，让你去衡量一下自己是不是符合现在的这些 AI 应用开发工程师的热门要求。首先你要清楚一个事情，就是如果你不懂任何一门开发语言的话，别人其实是很难跟你沟通清楚业务需求的。啊，你说业务需求这个事儿本来也不是程序员管的，是那个产品团队他们管的，他们分析好需求，你就照着做就完事了。

虽然是照着做，但你要知道企业级编程一定是个团队作战，它不是一个人瞎玩，很多时候既然是团队作战，就有很多团队内部的一些约定俗成的规则，或者说哪怕是不正式的，但就是这样推行下去的规则，你必须自己去悟自己去做。你如果越界了，那你这个事情就是错误很大的，会给团队带来很大的麻烦，而这个过程不会有人跟你一字一句讲清楚的，也不会有一个 AI 说帮你把这条条框框分析的清清楚楚，因为很多东西就是不正式的。像有个朋友讲了一个他非常无语的案例，他们做了一个项目，中间有一个需求是要加一个新的功能，那本身这是很正常的嘛，你就前端加个菜单，后端加些新接口，这事就完了对不对？但是一个哥们做了一个非常看起来很牛逼的事情，就是用 Web Coding 从头到尾写了一套新的体系，结果让团队陷入了大半年的时间都在为这个错误买单，什么意思呢？

就是因为他们这个项目就是从前端这个菜单构建了一整套的权限体系已经成型了，从前端菜单权限到这个页面上的一些控件权限，再到后端接口的权限，本身权限系统是非常成型的，你只要照着个权限系统加上一些东西，把这些业务代码加进去就完事了。结果这哥们反正是 Web Coding，他也不管，直接从头到尾写出了两另一套新的体系，这就变成什么？一个项目里面两套独立的体系，你让这个项目还怎么玩？你让后续还怎么维护？你让其他人怎么去做后面的业务系统？而且你写的这一堆东西让别人改，谁有时间给你去改这些东西？

这就是因为你对自己的业务边界不清楚，即便用了 Web Coding，你也赶不上一个老鸟的一个这个工作方式，还有一个可能更加刺激你的一个事情，你要知道你写的代码好不好其实并没有那么重要，但是你写的代码靠不靠谱这个很重要，因为现在的企业级开发，不管是用什么语言，本质上都已经不再是专注于用自己这门语言开发了，而就是跟各种中间件框架打交道。你要存数据有数据库，你要做缓存有 Redis，你要做消息中转有 MQ，很多时候你写的代码好不好，并不体现在你自己的这一些业务代码上，而就是体现在你周边这些各个框架的理解了。所谓的好的代码并不是说我这个代码有多牛，而是说我能够把这周边框架的性能发挥出来。

比如说有个朋友他们一个项目就这样的，用 Kafka 做一个消息中转，Kafka 的后端有很多的数据源，有像数据库啊，有像缓存啊，还有一些他们的这些大数据体系很多的数据源，那各个数据源之间就要做数据的同步，那怎么保证数据一致性？这个过程当中你说你用 Web Coding 能写出什么样的好的方案吗？

其实这事本身很简单，你有经验你只要想到我是可以把 Kafka 的 offset 移到 Redis 里面自行去控制消费的进度，那么我就可以根据周边数据的一致性情况来控制这个消息是要重新消费，还是说直接跳过，这事就完了呀，那接下来你要做的事儿就是按照 Kafka 的框架把这个 offset 拿出来管理就行了，这一点点代码体现不出那什么难度，你熟悉 Kafka 其实很简单，没有什么的难度，那你用 Web Coding 写和你自己写本身没有多大的区别，但是你如果稍微越界了这个事儿后果就很严重了，这也是我们后面经常聊的一件事，就你要知道企业级开发永远是带着镣铐在跳舞，它跟你自己去个人玩，或者你用 Web Coding 做自己的小工具，这完全不是一码事儿。

就像我之前聊这个 Spring Boot 的一个复刻的这个事情，我在网上出了一些视频，有很多朋友各种各样的反馈，我们这次聚会聊到这个话题，那很多人态度出奇的一致。就这件事情本身是很重要的，因为在很多企业当中，对于开源框架的态度一定是非常克制的。你既不能不用，也不能够完全照搬。万一这个开源框架有一点点问题怎么办？你项目还玩不玩？所以通常对这个开源框架，很多团队都是非常谨慎的。但是会有一个边界，对于开源框架或者这些中间件这些东西，即便要改造，它不会放到业务团队去做，通常会有一个框架组或者是架构组来做这些事情，提供最基础的帮助。而且Web Coding去复刻Spring Boot这件事来说，对任何团队其实都是非常重要的。

尤其对框架团队来说，它不仅是体现出了团队对于Spring Boot的深度挖掘，而且还是体现出这个Web Coding过程当中对大模型能力的把控程度。这样的话，你只有有了这样的基础演练，才能保证我做的这些东西是真正有用的，不容易把整个团队引向一个错误的方向的。所以这事其实是非常重要的，但是这里面就有一个边界。那你如果要改这些开源框架，要去深度挖掘这开源框架，一定是放到框架组，在你有深刻的了解掌握之后，你才可以去动，你不会放到业务团队里面去做。那如果你是在一个业务团队里面写代码，你要是敢在项目里面贸然用上一点自己写的Spring Boot，甚至是都不说那么大的框架了，你仅仅是学学Spring的那种底层反射满天飞的代码形式，你就看看别人会不会对你爆粗口就完事了。

你对自己做的事情边界是不清楚的，你写的这些代码写的越好，给团队带来的麻烦反而越大。所以这就是为什么在AI时代，依然要求工程师要吃透至少一门编程语言，因为语言只是皮囊，在AI时代用什么语言都不重要，但是这些语言背后底层的架构思维和工程的操守，这个才是你的骨肉，是你真正去吃饭的东西。在这个时代呢，有能力抓得住机会，那叫做得天独厚。没有能力，当你赚上了一个好的机会，这也还算是一种本事。有能力，但是没有好的机会，还可能说一句你生不逢时，至少相信你下次还能东山再起。但是如果你既没有过硬的能力，又抓不住眼前的那些机会，那个不叫遗憾，你的淘汰那是理所当然。
