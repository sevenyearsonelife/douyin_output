我是罗兰，关注我，IT 路上一起进步。要搞懂架构的演进，我们先得回到根儿上，一条消息在 Kafka 里到底是怎么流转的？很多人面试张口就来什么 topic、partition、broker，但这仨的逻辑关系百分之九十人都没讲透，今天我直接拆成两层让你一眼就看明白。首先呢是逻辑层，也就是 topic 主题，说白了就是个分类标签，比如订单日志、用户行为日志，生产者发消息，消费者取消息都只认这个标签。但 Kafka 是扛海量消息的呀，如果所有消息都堆到一台机器上，那直接就炸锅了。所以这就到了物理层，也就是 partition 分区，这才是真正存储数据的核心。Kafka 会把 topic 切分成多个 partition，磁盘上就是一个个独立文件夹，再分散到不同的 broker 服务器上。

这里有个面试必问的技术点大家一定要记住啊，Kafka 把消息写入到 partition 对应的点 log 文件里时，用的是顺序追加写 append only，不管你的硬盘是机械的还是固态的，顺序写的速度都快到离谱，这也是 Kafka 快的核心原因之一。所以整个流转过程可以简化为三步，第一步，生产者根据算法，比如说哈希取模，决定把消息发送到哪个 partition。第二个，broker 收到消息直接追加到磁盘文件的末尾。第三步，消费者像读磁带一样的根据 offset 的偏移量顺序读取。看懂了这个模型，你就能够理解 Kafka 集群要解决的核心问题了，一个 topic 的数据分散在那么多台的 broker 上，每个 partition 还有多个副本，那消息写入的时候到底听谁的呢？怎么决定谁是主谁是备呢？

如果机器挂了，谁来指挥主节点进行切换呢？这就引出了咱们今天的主角，集群机制，这是核心中的核心。在 K Raft 出来之前，Kafka 是怎么管这摊子事的呢？他请了个外援，就是 ZK，这是老架构的皇权时代。这里有两个关键的选举过程大家一定要分清楚啊，第一个关键点，谁是集群的大脑，也就是 controller 的选举。Kafka 集群启动的时候，几百台 broker 会同时冲去 ZK 上抢着创建一个叫做 controller 的临时节点，这就好比大家抢椅子，谁先坐上去谁就是 controller，这个 controller 权力巨大，整个集群的状态全归他管。

第二个关键点，谁来处理数据，也就是 partition leader 的选举，每个 partition 都有多个副本，但是只有 leader 副本才能够处理读写请求，其他的 follower 只是默默的同步数据。这时候重点来了，那 leader 是怎么选出来的呢？这个 leader 不是 broker 自己说了算的，而是由 controller 指定的，controller 会一直盯着 ZK，一旦发现某个 broker 挂了，controller 就会去查元数据，看这台挂着的机器上有哪些 partition 的 leader，然后 controller 从剩下的数据同步正常的 ISR 列表里面挑一个作为新的 leader，选好之后再把结果写入到 ZK 并通知给其他的 broker。

这种机制下，ZK 就像是皇宫里的军机处，存储了所有的元数据，而 controller 就像是宰相，他时时刻刻都得盯着军机处。但这也带来了一些致命的问题，依赖太重且恢复太慢。一方面，ZK 天生就不太适合存太多的数据，Kafka 的集群规模一旦变大了，ZK 就容易成为性能瓶颈。另一方面呢，主节点切换太慢了，要是有上千个 partition，controller 一挂，新的 controller 上位就得从 ZK 上把所有分区元数据全部拉一遍，加载到自己的内存里面，这期间集群直接是不可用的，在大厂里面这几秒的故障就能出大事故。老架构的痛点摆在这了，Kafka 这才花了好几年的功夫，费劲巴拉的搞出了个 K Raft，直接开启 Kafka 集群的革命时代。

别被 K Raft 这个洋文名字吓到了，其实你吃透了 ZK 的集群，K Raft 一句话就能搞懂，它就是把 ZK 里的元数据拿回来，当成普通的日志存在 Kafka 自己身上。对比 ZK 时代，K Raft 改了三件事。事情每一件都直击痛点，尤其是第二件。第一啊，元数据存储方式大改。以前元数据是 ZooKeeper 里的 ZNode 节点树，现在 KRaft 内部搞了一个特殊的 topic 叫 cluster metadata。集群里发生的所有事情，创建 topic、broker 上线、节点挂了，这些全封装成了事件消息，写到这个内部 topic 的日志里，这就是核心思想，元数据即日志，用自己最擅长的方式存元数据，直接把外部依赖给砍了。第二点，Controller 选举彻底重构，这是重中之重。

在 ZooKeeper 时代，谁当 Controller 靠的是抢，谁手快谁当，非常的随机。但在 KRaft 模式下，直接在配置文件里指定三台到五台的机器当做 voter 投票节点，相当于改成了内阁制。这些投票节点内部都跑着 Raft 共识协议，自己选出 active Controller 主控制器，谁当老大规则说了算，再也不凭手速了。第三呢，决策机制全面升级，技术最深的地方也就在这里。ZooKeeper 时代的 Controller 它是独裁者，它自己做了决定写到 ZooKeeper 里面就行了。

现在基于 Raft 协议，主 Controller 做的任何决定，比如选 partition 的 leader，就必须生成一条日志同步给其他备用的 Controller，只有当大多数备用 Controller 都收到了这条日志，这个决定才算生效。这样带来最大的好处就是热备，备用 Controller 参与投票的同时，内存里时刻都保存着最新的元数据日志，一旦主 Controller 挂了，备用的立马就能顶上，根本不需要去别的地方拉数据，因为数据就在它自己脑子里，这就把集群恢复时间从分钟级直接干到了毫秒级，这才是真正的高性能。讲到这儿啊，开头问题的答案就明了了，卡夫卡为什么要重复造轮子呢？因为他发现自己最擅长的能力是处理日志，既然我能把业务日志处理的又快又稳，那为什么不用同样的方式来处理我自己的元数据日志呢？

这就是 KRaft 的本质，用自己最擅长的武器解决自己最大的难题。其实这也是卡夫卡给我们的启示，做技术的，尤其是现在 AI 满天飞的时代，很多人都怕焦虑，都怕被取代，于是瞎跟风，什么火就学什么，像无头苍蝇一样的乱撞，最后啥都学的不精。但卡夫卡这次的架构升级给了我们一个非常重要的启示，别总依赖外部的 ZooKeeper，也别跟风盲目追风口，真正的护城河从来不是会多少新工具，而是找到自己最擅长的核心能力，哪怕只是写好一段代码，优化好一个 circle，吃透一个中间件，然后就把这个长处发挥到极致。当你能像卡夫卡一样用自己的核心能力来管理自己的人生的时候，任何时代的风浪都击不垮你。今天的 KRaft 核心架构都讲透了，内容比较硬核，建议大家多看两遍，记得来个点赞关注收藏，回头慢慢品。
