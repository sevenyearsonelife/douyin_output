在 AI 时代，体现你能力的永远不是你写代码的速度，而是你的技术广度和对业务的架构深度。就拿最简单的定时任务来举个例，假设业务场景是这样的，每隔十分钟就需要触发一个定时任务去扫描一次数据库里的异常订单，给老板发报警短信，这样的场景你会怎么设计呢？很多人第一反应就是这还不简单，Quartz、Z、Spring 的 Add Schedule 注解都可以，这不是轻轻松松吗？但你细想一层，生产环境呢通常是要部署多个服务的，如果部署了三台机器，一到时间同时触发任务，老板不就瞬间收到三条短信了吗？那这还能玩吗？哎，你这才反应过来要防并发，那就加个分布式锁吧，谁先想到了谁发，这就保证了最多一个在执行。但到这一层还没完，如果抢到锁的那台机器发生了故障，短信没发出去就宕机了怎么办？

它占着位置不干活，另外两台机器就只能干瞪眼，这下老板又连一条短信都收不到了。这其实就是保证最少一个在执行。你看，你把问题思考的有深度一点，接下来找答案其实就不是一件难事了。你可以把你的这些想法整理整理，直接发给 AI，一个企业级的分布式单例方案就成型了。那接下来我们就来看看有哪些解决这个分布式单例问题的思路呢？我来说说我的，你也可以问问你的 AI 分享一下你的思路，在评论区我们多交流交流。我是楼兰，关注我，IT 路上一起进步。既然明确了我们的目的是要防重复又要防死机，那我们的思路这就打开了。第一步呢，我们可以先去解决死机锁死的问题。最自然的思路就是给这个锁加个心跳，这就很容易让人想到 Redis 去配合 Redisson 的看门狗机制。

在 Redis 里写入一个 key 作为分布式锁，谁写入了这个 key 就判定拿到了锁，就可以去执行定时任务了。写入的时候记得要给这个 key 设定一个过期时间。机器抢到锁之后呢，后台就会开一个看门狗的线程，只要这台机器的 JVM 进程还活着，它就不断的去 Redis 里给这个锁延长过期时间。这样呢，就算这台机器出现了故障，一段时间后锁就会自动释放，其他那些替补的机器也就能够抢到锁继续接管任务了。但是朋友们，这里还有一个非常容易被忽略的细节，替补的机器不能够无限制的等下去。我们的定时任务呢是每十分钟执行一次，如果因为网络抖动等特殊的原因，替补的机器在第九分钟才抢到锁，那么这时候如果它再去执行定时任务，那就会和下一个十分钟的定时任务撞车，就会导致系统资源严重的竞争。如果这种延迟不断的累计，整个系统都可能会被拖垮。

这就是体现你思考深度的地方了。普通程序员只能够想到我一定要把这个任务完成，但有经验的程序员会想的更深，在很多业务场景下，放弃比迟到更重要，宁可漏发一次报警，也绝对不能让系统雪崩。所以我们必须引入一个时间窗口退出的机制，比如规定有效竞争期是五分钟，抢到锁的第一时间就要看看时间，如果超过了五分钟的有效期，那就直接退出，把资源留给下个周期的任务。有兜底，有边界，这才是一个完整的闭环，这套方案也才基本成型了。加上这个退出机制之后，这套 Redis 方案呢看似完美，但如果你思考的更深一层，Redis 其实有个硬伤，Redis 它是 AP 架构的，主从同步是异步的，如果主节点刚把锁分配给了机器 A，还没有把数据同步给从节点，然后自己就宕机了，那从节点就会上位变成新的主节点，重新开放写请求的权限。

但尴尬的是，这时候它肚子里还没有刚才那把锁的数据，此时机器 A 去抢锁，那么新的主节点就立即批给他了，结果就是机器 A 和机器 P 同时拿到了锁，脑裂了，老板又收到了两条重复的短信。这就引出了第二套思路，强一致的 Zoonkeeper 占坑法，三台机器都不断的尝试去 Zoonkeeper 上抢着创建一个临时节点，谁写成功了，谁就能够去执行定时任务。而由于 Zoonkeeper 的临时节点是和客户端的 TCP Session 是绑定的，客户端的服务如果一宕机，TCP 连接就会断开，临时节点就会被 Zoonkeeper 自动删除掉，这时候其他替补的机器就能继续写入临时节点，重新抢占锁了。

而且呢，由于 Zoonkeeper 底层它是基于 ZAB 协议的强一致同步，所以绝对不会出现之前使用 Redis 的时候，在极端情况下，两台机器同时抢到锁的情况。早期的 Kafka 选主其实就是这么干的。当然抢到节点之后依然要判断那个五分钟的退出窗口，不过 Zoonkeeper 虽然严谨，但是它太重了，为了一个业务系统的定时任务去维护一套高可用的 Zoonkeeper 集群，那运维成本就太高了，能不能不依赖任何外部组件呢？哎，顺着这个思路，下一个方案就出来了，Raft 内部共识算法，我们可以让这三台机器啊自己建个群去投票，谁票多谁就是 leader，负责发短。

剩下的就是 follower 负责监听，leader 会不断的给 follower 发心跳，一旦 leader 死机了，机心跳断开，follower 在随机的超时时间内没有收到心跳，就会立刻发起新一轮投票，选出新的 leader 接管任务。不需要 Redis，也不需要 Zookeeper，系统自己就可以实现完美的内聚和自洽。像 Kafka、RocketMQ、Nacos 等都有类似的机制。具体实现的时候呢，也有 Sofa J Raft 这样的现成内库来降低实现的难度。你看，只要思路清晰，一系列的方案自然而然就出来了。但加锁防并发这只是程序的本能，你要能考虑到宕机兜底和时效边界，这个才是真正体现了你的架构深度。而这样的架构深度从哪里来呢？

如果你脑子里有的是 Redis、Zookeeper、Raft 这些基础，很多方案其实自然而然就借鉴出来了，这就是你的技术广度。当你同时具备了这两点，你再去用 AI，你的提示词就不再是许愿式的自嗨，而是架构师级别的方案设计了。当然，如果机器刚把短信发出去，还没更新数据库就死机了，那替补上来又发了一次怎么办？那就是幂等性要解决的问题了，咱们下期再说。
