做过微服的朋友是不是全卡过这个坑啊？就网关它到底是选 Nginx 还是选 Spring Cloud Gateway？而且除了这两个主流的网关产品，还有一大堆网关产品在等着你呢。为什么一个网关要有这么多产品和框架都来做呢？网关到底应该怎么选呢？还有网关到底要怎么搭建？企业中的网关到底是怎么玩的？其实关于网关产品啊，Nginx 和 Spring Cloud Gateway 是两个不同的技术路线。Nginx 代表的是以底层 C 语言为代表的高性能解决方案，通常以 Nginx 加上一系列 Lua 脚本扩展为主，衍生出了像 OpenResty、API Six、Kong 等一大批网关产品。

而 Spring Cloud Gateway 则主要代表自定义的网关解决方案，通常是以 Netty 和 Reactor 响应式编程等性能框架为基础，进行业务服务定制。但是这两个路线看起来都完全没有 Spring 那么简单美观。选 Nginx 吧，性能确实强，但是想搞点复杂的健全逻辑还得去啃 Lua 脚本，维护起来太痛苦了。选 Spring Cloud Gateway 吧，它是 Java 写的，改代码方便，但性能跟 C 语言写的 Nginx 相比呢，确实又差了一个量级。那网关到底应该怎么构建呢？那今天这条视频我就把这两条路线的底层逻辑给你扒的明明白白，教你一套大厂都在玩的双层网关架构。不管是优化项目还是备战面试，学会这套思维，微服务网关这块你直接封神。记得点赞关注收藏，不然以后真要用的时候就视频就找不到了。

另外有什么问题欢迎在评论区留言，我是罗兰，关注我 I T 路上一起进步。我们先要把基础打牢，别一上来就选工具，先得想明白微服务架构里网关到底是干什么的。网关通常是微服务系统的统一门面，也是最先和客户打交道的一个后端服务。如果没有网关，你的客户端不管是手机 A P P 还是网页，都得直接去连接后端的几十个甚至上百个微服务，这会带来一系列巨大的灾难。第一个坑呢，安全裸奔，订单、用户、核心服务直接暴露在公网，黑客扫一眼就知道怎么搞你，这不是给人送人头吗？第二个坑呢，代码耦合，客户端得记住每一个服务的 I P 和端口，后端稍微扩容或者迁移一下，前端就得跟着改，前端兄弟绝对会拿刀砍你。第三，重复造轮子，健全、限流、日志监控这些通用的逻辑，难道你在每个微服务里都要重写一遍吗？这就是纯纯的浪费时间。

所以网关的核心作用就是微服务系统的统一门面，它把所有的请求收拢，对外只暴露一个入口，路由转发、安全认证、流量控制这些通用的功能全归它管，一夫当关万夫莫开，这就是它的核心意义。既然都要守大门，为什么会有 Nginx 和 Spring Cloud Gateway 这两个流派呢？核心区别就两个字，定位。我们一个一个来说，先说 Nginx，这是老熟人了，搭建互联网产品基本上都离不开它，它的核心优势就一个，性能拉满。它是 C 语言开发的，采用多进程和 Epoll I/O 多路复用模型，这意味着什么？意味着它处理网络连接的效率极高，同时内存占用还非常的少。

说白了就是轻装上阵干苦力，处理图片和 CSS 这样的静态资源，做反向代理、负载均衡这些纯流量层面的活，Nginx 就是神，哪怕你只有一台配置一般的服务器，几万并发也能轻松扛住，一点也不费劲。但是呢 Nginx 有个致命的短板，扩展性差。程序员的职责就是要折腾，如果你想在 Nginx 里写业务逻辑，比如解析 J W T 令牌，或者根据用户 I D 做灰度发布等等，那你就得用 OpenResty 去写 Lua 脚本，而这个 Lua 脚本呢，调试起来那是相当的麻烦，做 Java 的有一个算一个，维护个几千行的 Lua 代码直接崩溃。一旦业务逻辑变复杂，Nginx 的维护配置就是一场噩梦。再看 Spring Cloud Gateway，这里简称 S C G，它是 Spring 全家桶的亲儿子，专门为微服务诞生的。

它底上的核心呢是 Netty 和 Reactor，虽然也是异步非阻塞模型，性能在 Java 领域呢已经算是拔尖的，但毕竟中间隔了一层 J V M，Java 的虚拟机，跟贴着操作系统跑的 Nginx 比呢，吞吐量肯定是有差距的，这是天生的短板，没法比。那为什么我们还需要它呢？就是因为它灵活，它非常的灵活。S C G 呢是 Java 写的，这意味着你可以用你最熟悉的 Java 代码去写过滤器，想干。什么都简单。要查数据库进行鉴权吗？几行代码的事情。想要调用 Redis 做动态限流，直接就可以对接。而且 SCG 呢天生集成了 Spring Cloud 的强大生态，可以集成 Sentinel 就实现熔断降级，集成 Nacos 就能做动态路由，规则改变就能立刻生效，应用都不用重启了。

总结一下，Nginx 呢是流量专家，主打的就是高性能高并发，但是呢业务逻辑比较死板，即便有很多产品来做了一些封装，但始终对它的功能扩展还是比较受限制。SCG 呢是业务专家，主打的高扩展强逻辑，就是性能受到 JVM 的限制。搞清楚了各自的优劣，最完美的架构方案也就呼之欲出了，那就是流量网关加业务网关的双层架构。这一段是今天的重头戏啊，全是生产环境能用的干货，赶紧记笔记。第一层流量网关 Nginx，我们把 Nginx 部署在最外层，直面互联网，让它去干那些最脏最累最耗资源但逻辑最简单的活。比如第一，SSL 和 TLS 卸载，HTTPS 的加解密非常的消耗 CPU，让 C 语言写的 Nginx 去干，解密之后把 HTTP 请求转给后面，别累着 Java 了。

第二呢，静态资源托管，前端的静态页面图片直接在 Nginx 这一层返回，根本不需要把请求打到后端的 Java 服务上。第三，WAF 防护，防 SQL 注入，封禁恶意 IP，Nginx 在最前面挡刀，把脏流量全拦在外面。甚至在做秒杀这样面试必问的高并发场景时，你也可以在 Nginx 中直接查 Redis 库存，要是商品已经被秒完了，直接在 Nginx 就可以返回秒杀了，可以减轻后端百分之八十以上的流量压力。第二层业务网关 Spring Cloud Gateway，它专门就来接 Nginx 洗过的干净流量，让它专心干那些需要动脑子的精细活，别让它干苦力。比如第一种复杂的鉴权，解析 token 啊，校验用户权限啊，这些复杂的逻辑就用 Java 来写顺手多了。

第二呢，动态路由，根据请求头把流量分发到不同的微服务版本，做蓝绿发布、金丝雀发布都可以。第三，接口聚合，把多个微服务的结果拼装在一起返回，减少客户端请求次数，体验感直接拉满。为什么要这么分呢？其实 Java 程序员就必须清楚啊，Java 应用最怕的是什么？就是 GC 垃圾回收抖动。如果我们把 SSL 握手、海量静态资源请求这些高频低效的活都扔给了 SCG，那么 JVM 的内存压力会非常的大，频繁的触发 Full GC，整个网关就会卡顿。让 Nginx 在前面扛住压力，给 SCG 创造一个稳定的运行环境，这就是架构设计的智慧。这套架构啊看起来简单，改几个配置就行，但落地的时候全是坑，我挑了三个最致命的，全是重点。

第一个，网络链接配置必须要优化，Nginx 到 SCG 这一段呢一定要走内网，而且直接走 HTTP 协议，别再搞一次 HTTPS 了，内网是可信的，没必要再浪费一次加解密的性能。第二呢，高可用设计不能够偷懒，Nginx 要是挂了，整个系统直接瘫痪，所以 Nginx 前面通常还要挂一个 LVS 或者 Keepalived 去做高可用的 VIP 漂移，SCG 呢也要部署多台，前面通过 Nginx 做负载均衡，这些麻烦事缺一不可。第三，配置千万别写死了，Nginx 的配置文件上线后就尽量不要动了，要动配置的地方全移到 SCG 里，尽管 Nginx 也能快速重启加载配置文件，但毕竟会对流量产生抖动。

然后 SCG 的路由规则千万别写死在 application. yaml 里面，一定要结合 Nacos 或者是阿波罗配置中心，这样你上线新的服务或者做流量切换的时候，在配置中心改一下，网关自动刷新，用户完全无感知，这是生产环境的基础玩法。那今天的核心干货就到这儿，再给你完整的撸一遍，Nginx 做外层流量网关就扛高并发做基础防护，SCG 做内层业务网关处理复杂业务逻辑，双层配合刚柔并济，这就是微服务网关的最优解。其实这套 Nginx 加 SCG 的架构啊不仅仅是技术方案，也藏着我们程序员的职场生存法则，Nginx 就像是我们的硬实力，无论。论环境多么恶劣，我们都要有扎实的基本功，要能扛得住高并发的压力，守得住系统的底线，这是我们立足的根本。

Spring Cloud Gateway 就像是我们的软实力，在复杂的业务场景中，我们要懂得变通，要有清晰的逻辑，能灵活调整资源，解决复杂的问题，这是我们向上的阶梯。其实做技术也好，混职场也罢，底线要稳，身段要活，只有硬实力够刚，软实力够柔，才能在瞬息万变的技术浪潮里游刃有余。这次网关架构你听透了没有？你们公司用的是什么网关？踩过哪些奇葩的坑？评论区聊一聊，互相避坑。当然也记得点赞、关注、收藏，我是罗兰，关注我，IT路上一起进步。接下来我们评论区见。
