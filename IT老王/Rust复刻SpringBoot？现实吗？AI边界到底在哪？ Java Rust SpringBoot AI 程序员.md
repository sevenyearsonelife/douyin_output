我发现现在很多人呢真的是把 A I 在当成哆啦 A 梦在用了，感觉有了 A I 的加持，手搓个流浪地球推动器出来，那都算是限制想象力了。前几天我发了个讲 Java 的 Spring Boot 的视频，评论区有位大哥直接给我来了个降维打击啊，他说 Java 早就过时了，Java 能做的 Golang 甚至是 Rust 都能做，现在有了 A I 只要我愿意，随手就能用 Rust 给你复刻一个 Spring Boot 出来，分分钟吊打你。各位你们觉得这位哥们狂吗？Spring Boot 这么大的企业级框架，他随手就能复制出来，还 Rust、Golang 随便挑，是不是有很多朋友也会觉得确实是这么回事啊？

毕竟 A I 什么代码写不出来，但今天作为一个老程序员，我还真就跟他较这个真了，咱们就真到 Rust 的生态里去转转，看看有了 A I 加持，用 Rust 到底能不能复刻出一个 Spring Boot 来，顺便看看这 A I 编程的边界它到底在哪里。我是楼兰，关注我，IT 路上一起进步。首先咱们看看技术层面，复刻 Spring Boot 这个事儿呢都不用 A I 加持，互联网还早就有了一批猛人已经行动起来了，比如这个 SummerRS，前身就叫 Spring RS，后来为了避嫌就改成了 SummerRS，应该算是 Rust 生态里复刻 Spring Boot 最成功的了吧。

作者绝对是个狠人，Spring Boot 能复刻的他都给复刻出来了，他使用 Rust 的宏指令来模拟 Spring 中的注解，完整实现了 Spring 中核心的 IOC 依赖注入系统，同时还实现了完整的 Web MVC 路由功能，可以通过路由宏快速定义 GET 和 POST 的接口，整个开发体验呢非常接近 Spring Boot，它还实现了 Spring Boot 非常具有代表性的自动装配机制，可以按需自动加载一些常用的插件，不用手动堆砌大量的初始化代码，就连 Spring Boot 的多环境配置功能它也完美的复刻了出来，可以同时提供 DEV、TEST、PROD 三套配置文件，可以在不同环境中快速切换配置文件，甚至还提供了多个功能插件，对标 Spring Boot 的各种 Starter，比如你看这个 Summer Redis、Summer Nacos、Summer X L Job，还有 Summer SA Token 等等，这些插件是不是一看就是满满的熟悉感？

还有这个 P R E D O，这也是一个类似于 Spring Boot 的 Rust Web 框架，它实现了 Spring 最为核心的依赖注入功能，可以通过这个 Singleton 宏来进行单例标记，同时也支持自动依赖注入、接口多实现绑定等功能，不过它的插件生态就几乎是个空白了，而且项目体量也很小，只适合做一些小型的接口项目。

另外还有一些其他的框架，但整体完成度就差的比较多了，就复刻 Spring Boot 这件事来说，看起来感觉是挺繁荣的，但是一旦深入 Spring Boot 真正的核心深水区，这些 Rust 框架普遍就不太够看了，比如 Bean 的完整生命周期、循环依赖的解决方案、三级缓存，还有 SPI 资源扫描、AOP 面向切面编程，以及我之前介绍过的事件发布与监听机制等等，这些框架就集体哑火了，在业界生态里呢基本就是 Demo 级别的。你可能会说这是不是因为开发量不够，只要有 A I 帮忙提提效，往下做下去是不是很轻松呢？

但现实很骨感，因为这些项目真正触碰到了语言层面的天然鸿沟，Rust 语言主打的是轻量高性能，Java 主打的就是稳定可扩展，天然路数就不对，比如 Spring 的很多核心魔法都依赖于运行时反射，就是在程序跑起来以后再逐步去增加一些新的功能，比如动态代理在 Spring 中就是一个基础标配，但是 Rust 是强编译的，也就是在编译过程中所有功能就通过硬编码的方式固定下来了，压根就没有实现运行时反射的功能，你是一根筋，人家是见招拆招啊，你 A I 再强大也没法跨过 Rust 语言的规定，实现 Rust 支持不了的功能吧？

再比如生态，Spring Boot 有庞大无比的 Starter 全家桶，但凡好用点的功能都会随手提供一个集成 Spring Boot 的 Starter 插件，这是几十年生态积累下来的，但在 Rust 领域呢，所有依赖都要自己实现，你看 SummerRS 自己实现的那一堆插件就知道了，费那么大劲实现的插件数量也赶不上 Spring Boot 的一成功力吧？所以 Rust 注定适合做一些高性能的底层插件，在企业级应用这个赛道，给你十个 A I 你也干不过 Spring Boot，更别说取代 Java 了。这就是 A I 编程的第一层差距，基础开发语言的差距，只要 A I 还只能在人类的技术规则内工作，它就甩不掉规则的历史包袱，至于你说未来 A I 用二进制编程了，至少目前那还仅仅只是个科幻。

但 A I 真正的边界或许还不在语言层面，人的认知才是对 A I。哎，最大的限制。我当时就问这位大哥，就算你现在用 Rust 写出来一堆类似的东西，那 Spring Boot 这么多功能点，你怎么测试验证呢？结果他的回复直接让我大跌眼镜，你看这好长一段。我让 AI 写几千个测试用例，端到端测试，真要想做，我搞一百个子智能体，几天就能从写完到测完，还直接发 GitHub，把所有情况测完就能上线。因为测试驱动开发，不管代码怎么写，所有可能情况总是能够测完的。还特地给我强调，不开玩笑，也没有半点夸张，那个自信都要溢出屏幕了。看着是不是挺像那么回事？还测试驱动开发呢？但搞笑的也就在这里，测试驱动确实挺牛，但至少你得知道你要测什么吧。这框架代码可不是简单的业务代码，每一行框架代码的背后逻辑都是盘根错节的。

Spring Boot 为什么这么牛？可不仅仅是因为它的功能花里胡哨，是因为它处理了无数非常复杂的边界条件、循环依赖、并发冲突等等各种各样你可能根本都没听过的问题。如果你自己都不懂架构，连这些问题是什么都不知道，你就敢让 AI 给你写几千个测试用例，还直接测完发 GitHub，你还让不让其他使用者活了吧？还有一用到 AI，你就只想到一个暴力穷举，这么大的工程体量，还让 AI 又写又测又修复的，那且不说现在的 AI 它能不能吃得下这么大的上下文，就光这个 token 消耗的钱，怕是地主家也烧不起吧。要知道你这还仅仅只是个测试呢，你真当 AI 是个打个响指就能用的无限算力了？这就是 AI 编程的第二层差距，人的认知差距。

回到 Rust 复刻 Spring Boot 这个事情上来说，或许真的有顶级大牛能够另辟蹊径去实现，但至少这位朋友是根本撑不起这么宏大的工程的。你控制不住 AI，就没法发挥 AI 的极限。所以 AI 的边界在哪？其实 AI 的边界就是屏幕前你我的认知边界。现在 AI 编程确实很牛，但是有的人用它写出的是像 CodeX、Worker Buddy 这样改变行业的牛逼工具，但有的人哪怕给他一百个 AI，他写出来的照样是一堆混口饭吃的无用代码而已。AI 或许能帮助你，但改变不了你，能改变你的只有你自己。你说呢？接下来咱们评论区见。
