很多人刚接触 Redis 时都会有个疑问，Redis 单机性能那么强，一秒钟能处理几万次请求，为什么还要搞主从复制？一台真的不够用吗？答案是，在真实的业务环境里，一台确实不够用。主从复制的本质就是给 Redis 安排分身，让一台服务器专门负责写入新数据，多台服务器负责读取和备份。那单机到底会卡在什么瓶颈上？主从之间是怎么配合分工的？这种模式又有什么解决不了的硬伤？今天我们把这条链路彻底理清。先说单机为什么会不够用，主要面临两个致命风险。第一个是单点故障，哪怕 Redis 本身再稳定，也扛不住物理层面的意外，比如机房断电、网线被挖断或者服务器硬件损坏。一旦这台唯一的机器宕机，整个系统的缓存服务就全瘫痪了。第二个是性能天花板，虽然 Redis 读写都很快，但单台机器的 C P U 核心数和内存容量是有物理上限的。

当遇到大促或者热点事件，海量用户同时来查询数据，单台机器依然会排队卡顿。为了解决这两个问题，主从复制把原本一台机器干的活拆分给了一个团队。在这个团队里，原始数据的服务器叫主节点，拷贝数据的服务器叫从节点，它们的核心分工叫读写分离。主节点专门负责接收和处理写请求，比如新增、修改或删除数据，而从节点只负责读请求，也就是查询数据。这样一来，查询的压力就被分摊到了多台从节点上，系统的并发处理能力直接翻倍。同时，从节点手里有一份完整的数据副本，相当于做了实时的热备份。那主节点的数据是怎么实时跑到从节点那里的呢？这个过程分为两步，当从节点刚加入团队时，主节点会把自己内存里的所有数据打包成一份快照，完整发送给从节点，这叫全量同步。等从节点把家底都补齐后，双方就进入日常协作模式。

主节点每执行一条新的写命令，就会立刻把这条命令传给从节点，从节点跟着执行一遍，这叫增量同步。通过这种机制，主从之间的数据就能保持高度一致。不过这里有一个非常常见的误解，很多人以为只要不断增加从节点，Redis 的性能就能无限提升。实际上从节点只能分担读的压力，解决不了写的瓶颈。因为所有的写操作依然只能由唯一的主节点来处理。如果你的业务场景是写多读少，比如频繁的更新库存、记录海量日志，那主节点依然会被压垮，加再多重节点也没用。除了写操作的瓶颈，主从复制还有两个天然的硬伤。首先是延迟问题，数据从主节点通过网络传给从节点是需要时间的，如果网络抖动或者主节点太忙，从节点的数据就会比主节点慢半拍，导致用户刚写完数据却立刻查不到。

其次是故障转移问题，如果主节点真的宕机了，从节点虽然手里有数据，但它默认自己是从属身份，不会自动站出来接管写请求，这时候依然需要人工介入去修改配置。所以回到最初的问题，一台 Redis 确实不够用，但主从复制也不是包治百病的万能药。它完美解决了数据备份和读并发的问题，是 Redis 高可用架构不可或缺的地基。但也正是因为它在自动故障转移和写并发上的局限，才促使后来演化出了哨兵模式和集群架构。理解了主从复制的分工与边界，你也就看懂了 Redis 整个高可用体系的演进起点。
