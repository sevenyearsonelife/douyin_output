有了 Docker 为什么还要 K8s？很多刚接触后端开发或运维的人都有这个疑问。简单来说，Docker 是一种容器技术，负责把程序和它需要的环境打包在一起运行。而 K8s，全称 Kubernetes，是一个容器编排平台，专门用来管理海量的容器。打个比方，Docker 是把货物装进标准集装箱，保证到哪儿都能卸货，而 K8s 是管理成千上万个集装箱的自动化港口调度系统。那 Docker 到底解决了什么痛点？当容器多到一定程度时会发生什么灾难？K8s 又是怎么接手这个烂摊子的？今天我们把这条技术演进线彻底理清。要理解 K8s，得先知道 Docker 立下了什么汗马功劳。在 Docker 出现前，程序员最怕听到：“在我的电脑上明明能跑，怎么到你那儿就报错了？

” Docker 通过容器技术，把代码和运行环境实时打包在一起，做成了一个个独立的集装箱。这解决了程序打包和单机运行的问题，只要服务器装了 Docker，集装箱拉过去就能直接跑。但 Docker 只管造箱子和在单台机器上跑箱子，它不管这些箱子怎么分配，怎么运输。如果你的系统只有几个小服务，用 Docker 完全够了。但现实中的大型互联网项目往往有几百上千个服务，每天要更新几十次，还要部署在几十台甚至上百台服务器上。这时候如果全靠人工去管理这些 Docker 容器，就是一场灾难。哪台服务器空闲，该把新容器放哪？某个容器突然崩溃了，谁来重启？突然来了十倍的用户流量，怎么在几分钟内手动启动几百个新容器？靠人敲命令根本管不过来。这就是 K8s 出场的原因。

K8s 在行业里被称为容器编排系统，它的核心任务就是接管成百上千台服务器，把它们变成一个巨大的资源池。当你要部署一个新服务时，你不需要自己去挑哪台服务器，只要告诉 K8s：“我需要运行三个容器，每个需要二 G 内存。” K8s 这个港口调度塔就会自动扫描整个集群，找出资源最充裕的机器，把容器稳稳地放上去。这在技术上叫自动调度。除了分配任务，K8s 还能自己当监工。在庞大的服务器集群里，硬件故障或网络波动是家常便饭。如果没有 K8s，一个容器挂了，可能直到用户投诉，运维人员才发现并手动去修。而 K8s 有强大的自愈机制，它会时刻盯着每一个容器的健康状态，一旦发现某个容器死掉了，或者它所在的服务器宕机了，K8s 会立刻在另一台健康的服务器上自动拉起一个一模一样的新容器，保证服务不中断。更厉害的是应对流量洪峰。

遇到电商大促或者突发热点事件，访问量瞬间暴涨，K8s 可以根据你设定的规则，监控到 CPU 或内存使用率飙升，然后在几十秒内自动复制出几百个新容器来分担压力。等半夜流量褪去，它又会自动把这些多余的容器销毁，把服务器资源释放出来。这种不用人干预的弹性扩缩容，是大型系统扛住高并发的底气。不过 K8s 虽然强大，却不是什么项目都必须用的神器。K8s 本身非常复杂，学习和维护成本很高。如果你的团队只有两三个人，项目也就是个日活几千的小程序，或者只是几个简单的内部工具，那直接用 Docker 配合一些轻量级的部署脚本就足够了。强行上 K8s 不仅享受不到它的调度优势，反而会被它繁杂的配置和运维工作拖垮。杀鸡不需要用牛刀。所以 Docker 和 K8s 从来不是谁替代谁的关系，而是完美的上下游分工。

Docker 实现了应用级别的标准化，让程序可以到处运行，而 K8s 实现了基础设施级别的自动化，让成百上千台服务器像一个整体一样工作。看懂。而这层分工，你就真正理解了现代云原生架构的底座。
