有了线程池，为什么还要虚拟线程？线程池明明已经能复用线程了，难道还不够用吗？其实线程池解决的是复用和管理昂贵的平台线程，但并没有改变线程本身相对笨重的事实。虚拟线程的出现是为了降低高并发场景下大量阻塞任务占用线程资源的成本。那线程池到底卡在了哪里？虚拟线程又是怎么做到既轻量又能承载海量并发任务的？它是不是在所有场景下都能无脑替换线程池？今天我们把这几个问题讲透。要理解虚拟线程，得先看看我们以前用的普通线程，也就是平台线程。你可以把平台线程想象成餐厅里的全职服务员。在传统的模型里，每来一个网络请求，系统就派一个专属服务员去处理。如果请求一直在处理数据，服务员就很忙。但如果程序遇到了网络等待或数据库查询这种阻塞操作，这个服务员就只能干站着等。

因为平台线程通常和操作系统底层线程一对一对应，它一旦阻塞，这个线程在等待期间就不能继续处理其他任务。为了控制线程数量和资源消耗，开发者会使用线程池，也就是限制服务员的总数，请求多了就在门外排队。但这依然存在一个问题，当大量线程都在等待 I O 时，后面的任务只能继续排队，系统的并发能力也就受到了线程数量的限制。虚拟线程就是来打破这种一对一使用方式的，它是由 Java 虚拟机自己管理的轻量级线程，不再直接对应一个固定的操作系统线程。打个比方，虚拟线程不再绑定专属服务员，它更像是一个个独立的服务任务，而底层的平台线程变成了相对少量的共享跑腿员。当一个虚拟线程开始执行时，它会被挂载到一个跑腿员身上。一旦遇到可以挂起的阻塞操作，虚拟线程通常可以从跑腿员身上卸载下来，把自己挂起，让这个跑腿员继续去处理其他虚拟线程。

等数据库的结果回来了，虚拟线程再重新挂载到可用的跑腿员上继续执行。这种机制可以理解为 M N 映射，也就是用相对少量的平台线程去承载大量的虚拟线程。这种设计带来了两个直接的好处，首先是资源开销更低。平台线程需要维护操作系统线程栈等资源，大量创建时成本比较高，而虚拟线程轻量得多，因此 J V M 可以同时管理非常大量的虚拟线程。其次是代码终于变简单了。过去为了提高高并发场景下的资源利用率，程序员经常需要写复杂的异步回调或者响应式代码，代码写得像迷宫一样，调试起来也比较痛苦。有了虚拟线程，很多场景下可以继续使用简单、符合直觉的同步阻塞写法，也就是一个任务对应一个虚拟线程，同时获得很高的并发处理能力。不过虚拟线程并不是万能的，它有一个明确的适用边界。

它之所以能发挥巨大威力，前提是任务会频繁遇到阻塞，也就是所谓的 I O 密集型任务，比如 Web 服务、爬虫、数据库读写。但如果你的任务是 C P U 密集型，也就是需要 C P U 一直做复杂的数学计算、图像处理或者加密解密，中间几乎没有等待，那虚拟线程就没有多少资源可以让出来。这时候增加大量虚拟线程并不会让计算本身变快，真正的并行能力依然受 C P U 核心数限制。所以在纯计算场景下，使用传统线程池控制并行任务数量往往是更合适的选择。线程池是在有限的平台线程资源里做排队和复用，而虚拟线程是通过把任务和底层线程解耦，用更低的成本重新实现一任务一线程的编程模型。看清了这两者的分工，你就能明白技术的演进不是为了淘汰旧工具，而是为了让复杂的并发问题重新回到更简单的写法。
