写 Java 代码时，控制台一飘红，很多人第一反应都是报错了。但在 Java 的世界里，报错其实分成了两大阵营，Exception 和 Error。它们虽然都继承自同一个老祖宗 Throwable，用来表示程序出了问题，但设计目的完全不同。Exception 是程序能预料并处理的意外，而 Error 是程序根本扛不住的灾难。那它们具体差在哪？为什么有的报错编译器逼着你处理，有的却只能眼睁睁看着程序崩溃？今天我们把这两个概念彻底理清。先说最核心的差异，严重程度和能不能救。Error 代表的是系统级或 JVM 虚拟机级别的致命问题，比如内存被彻底撑爆了的 OutOfMemoryError，或者方法递归太深把栈塞满的 StackOverflowError。这就像汽车的发动机直接炸了，程序除了原地崩溃什么也做不了。

所以面对 Error，程序通常不需要，也不应该去尝试捕获它。而 Exception 代表的是业务逻辑或外部环境引起的意外，比如要读的文件突然不见了，或者网络断了。这就像汽车轮胎扎了钉子，程序完全可以通过备用方案，比如重试或者提示用户，让流程继续跑下去。这就引出了一个很多初学者容易踩的坑。既然都是报错，那我写个 try catch，把所有异常都实时捕获住，程序不就永远不崩溃了吗？实际上，如果你去强行 catch 一个 Error，比如内存溢出，就算你捕获到了这个信号，JVM 也已经没有多余的内存让你执行后续的补救代码了。所以 Error 的正确应对思路不是在代码里兜底，而是在写代码前就做好规划，比如合理分配内存，限制递归深度，从根源上避免它发生。

说完了不可控的 Error，Exception 这边的情况要更细致一些。Exception 内部其实还分成了两派，受检异常和非受检异常。受检异常，也就是 Checked Exception，是编译器强制要求你处理的。最典型的就是读写文件时的 IOException。如果你不写 try catch 捕获它，也不在方法上声明抛出，代码根本编译不通过。这相当于编译器在强制提醒你，外部资源不可靠，你必须提前想好对策。而非受检异常，通常也叫运行时异常，比如最常见的空指针异常 NullPointerException。这类问题编译器不会强制你处理，因为它们多半是代码逻辑没写严谨导致的。对付它们最好的办法是通过规范的代码和单元测试来避免，而不是靠满篇的 try catch 去掩盖逻辑漏洞。

简单来说，Error 是脱离程序员控制的天灾，Exception 是代码需要优雅处理的人祸。分清它们不是为了应付面试背几个名词，而是为了在写代码时建立正确的风险意识，知道哪些意外必须提前规划兜底，哪些灾难只能靠严谨的设计去预防。
