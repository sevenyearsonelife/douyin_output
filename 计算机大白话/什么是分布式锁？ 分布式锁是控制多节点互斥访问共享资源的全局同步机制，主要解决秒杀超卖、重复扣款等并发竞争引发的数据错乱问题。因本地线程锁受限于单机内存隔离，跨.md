什么是分布式锁？简单来说，它是分布式系统里用来控制多台机器互斥访问同一份数据的同步机制。你可以把它当成一把跨越多台服务器的全局排队锁。当你的系统从一台机器扩展到几十台机器时，怎么保证大家修改同一份数据时不打架？为什么以前代码里写的普通锁突然失效了？这把全局锁又是靠什么机制撑住高并发的？今天我们把这几个核心问题一次性讲透。先看看如果没有它，系统会惹出什么麻烦。假设你在做一个电商秒杀活动，库存只剩最后一件。如果两个用户的请求同时打到了两台不同的服务器上，这两台服务器去查数据库发现库存都是一，于是都执行了扣减操作，结果就是一件商品卖给了两个人，这就是典型的超卖。或者在支付环节，因为网络卡顿，用户连点两次，系统没拦住，直接扣了两次钱。分布式锁要解决的，就是这种多节点并发竞争同一份资源时的数据错乱问题。

很多刚接触后端开发的人会有个误解，觉得在代码里加个普通的线程锁，比如 Java 里的 synchronized，不就能保证同一时刻只有一个人操作了吗？这在单台机器上确实管用，这种锁叫本地锁。但本地锁的管辖范围仅限于当前这一台机器的内存。当你的服务部署在十台机器上时，每台机器都有自己独立的内存和进程，机器 A 加的锁，机器 B 根本看不见，这时候本地锁就彻底失效了，必须请出能跨机器协调的分布式锁。那分布式锁是怎么让多台机器乖乖排队的呢？它的核心逻辑是引入一个外部共享存储来当裁判，所有机器在操作数据前，都必须先去这个裁判那里抢钥匙，抢到钥匙的机器才能去修改数据，没抢到的只能在门外等。这里有两个必须满足的硬性条件，第一是互斥性，也就是同一时刻只能有一台机器拿到钥匙。

第二是防死锁，如果拿到钥匙的机器突然宕机了，钥匙不能永远被霸占，必须设置一个过期时间，时间一到自动释放，让后面的机器能继续用。既然需要一个外部裁判，业界通常用三种工具来造这把锁，它们各有各的脾气。第一种是基于数据库，利用数据库的唯一约束或行锁来实现，优点是线程不用额外搭组件，缺点是性能较差，扛不住高并发。第二种是基于 Redis，这也是目前最主流的方案，利用 Redis 的单线程特性和特定命令来抢锁，速度极快，非常适合秒杀这种高并发场景。第三种是基于 Zookeeper，它利用临时顺序节点来排队，优点是强一致性，哪怕机器挂了也能可靠释放，适合对数据准确性要求极高的金融级场景。不过分布式锁也不是万能的，它在一些极端场景下也会失效。

比如在使用 Redis 锁时，如果你的业务代码执行时间太长，超过了锁的过期时间，锁被自动释放了，但业务还没跑完，这时候另一台机器又抢到了锁，就会导致两台机器同时操作数据。为了解决这个问题，成熟的框架通常会引入看门狗机制，在业务没执行完时自动给锁续期。另外在 Redis 主从架构下，如果主节点刚写入锁就宕机了，数据还没同步给从节点，从节点升级为主节点后，其他机器可能会再次抢到同一把锁。所以在要求绝对严谨的场景下，通常需要换用更可靠的方案。从单机时代的本地锁到微服务时代的分布式锁，本质上是因为系统的物理边界变大了，我们需要一个更高维度的协调者来维持秩序。理解了分布式锁，你也就理解了分布式系统中最核心的矛盾，如何在追求高性能的并发处理时，守住数据一致性的底线。
