在 MySQL 里，长事务被称为潜伏的性能杀手。很多开发同学以为只要 SQL 写得快就不会有问题，但其实长事务和慢查询完全是两码事。那长事务到底是指什么？它为什么可能让整个数据库系统雪崩？它又是通过哪几种隐蔽的方式拖垮服务器的？今天我们把这几个核心问题讲透。首先，什么是长事务？其实 MySQL 并没有规定一个统一的时间标准。简单来说，一个事务开启后，如果明显超过正常业务所需时间，却迟迟没有提交或回滚，就可以认为是长事务。这里有个常见误解，很多人把长事务等同于慢查询，其实不是。慢查询是一条 SQL 本身执行的慢，而长事务可能是里面的每条 SQL 都飞快，但你在两条 SQL 之间去调用了一个耗时的外部接口，或者做了一段复杂的业务计算，导致整个事务迟迟不提交。

这就好比你在超市收银台结账，扫码很快，但你突然接了个十分钟的电话不付钱，后面排队的人就全被堵死了。这种占着位置不提交的行为，引发的第一个致命问题就是锁竞争与阻塞。在数据库里，修改数据通常是需要加锁的，长事务一旦修改了某行数据，相关的锁就可能一直持有到事务提交或者回滚。这时候如果其他业务也需要修改这行数据，就只能在外面等待。如果并发量大，等待的队伍会越来越长，不仅系统响应时间变慢，还可能增加死锁发生的概率，最终导致大量请求超时，整个业务链路出现连锁阻塞。第二个问题更隐蔽，就是 undo log 和历史版本不断堆积。MySQL 为了保证事务能够回滚，并且让其他查询通过 M V C C 看到一致的历史数据，会把修改前的旧版本保存在 undo log 中。

正常情况下，当这些历史版本已经不再被任何活跃事务需要时，后台的 purge 线程就可以逐步清理。但如果有一个长事务迟迟不结束，它的 read view 可能一直需要访问较老的数据版本，于是部分历史版本就不能及时回收。时间一长，undo 和版本链会越积越多，不仅占用更多磁盘空间，还可能让查询历史版本的成本越来越高。第三个问题，尤其是在长事务同时包含大量写操作时，还可能加剧主从延迟。在很多公司里，写操作在主库，读操作在从库。主库事务提交后，会把对应的 binlog 交给从库进行同步和回放。如果一个事务一次更新、删除了几十万甚至几百万行数据，等它最终提交以后，从库就需要处理大量的 binlog 事件。如果从库回放速度跟不上，就可能出现几秒甚至几分钟的复制延迟。

这时候用户刚下完单去查订单，从库里的数据可能还没同步过来，直接影响业务体验。所以你看，长事务的危害从来不是孤立的，它可能从长期占用锁资源开始，到拖慢 undo 历史版本的回收，再到大事务场景下加剧数据同步压力，是一条完整的性能风险链。理解长事务，本质上就是要明白数据库的事务是为了保证数据一致性，而不是用来包裹整个业务流程的。把大事务拆小，把耗时的网络调用和复杂计算尽量移出事务，才是让数据库轻装上阵的真正解法。
