当多个用户同时修改数据库里的同一条数据时，如果不加控制，就会发生丢失更新。比如商品只有一件，两个人同时下单却都成功了。为了解决这种并发冲突，数据库引入了锁机制。而在 MySQL 中，最常被提到的就是乐观锁和悲观锁，它们到底有什么区别？底层分别是靠什么撑住的？在实际业务中又该怎么判断用哪个？今天我们把这两个概念彻底理清。很多人刚接触这两个词，会以为它们是 MySQL 里两把具体的物理锁。其实这是一个常见误解，准确的说，悲观锁和乐观锁并不是某种特定的锁实体，而是两种处理并发冲突的思想与策略。悲观锁主要依赖数据库自带的锁机制来实现，而乐观锁通常是程序员在应用层通过代码逻辑自己实现的。我们先看悲观锁，它的核心思想是先锁门再操作。它悲观地认为，只要我去修改数据，就一定会有别人来跟我抢。

所以在读取数据准备修改的那一刻，它就会直接给这条数据加上一把排他锁。这就像商场里的单人试衣间，你进去把门一反锁，外面的人不管多着急，都只能在走廊排队等着，直到你试完出来释放锁，下一个人才能进去。在 MySQL 中，这通常是通过在查询语句后面加上 for update 来实现的。这种机制非常适合写操作频繁，数据冲突概率极高的场景，比如银行转账或者秒杀扣减库存，宁可让大家排队，也绝不能让数据出错。那乐观锁呢？它的态度完全相反，核心思想是先操作后检查。它乐观地认为，大家平时都在各自读数据，真正同时修改同一条数据的概率很低。所以它在读取数据时根本不加锁，而是给数据表加一个版本号字段。这就像多人在线协作编辑一份文档，大家同时下载了版本号为一的文件开始修改。当你点击保存时，系统会去检查数据库里的版本号是不是还是一。

如果是，说明没人改过，你的修改成功，版本号变成二。如果数据库里的版本号已经变成了二，说明别人抢先提交了，你的这次操作就会失败，只能重新加载最新版本再改。这种方式省去了排队等待的时间，非常适合读多写少、冲突较少的场景，比如修改个人资料或者文章点赞数。不过这两种策略都有各自的失效边界。如果在一个冲突极其频繁的场景里错用了乐观锁，比如几万人同时抢购一件商品，大家每次保存时发现版本号都变了，就会导致程序疯狂重试，最终耗尽系统资源甚至崩溃。反过来，如果在读多写少的场景里滥用悲观锁，大量原本不需要等待的查询请求也会被强行阻塞，导致数据库连接池被排队占满，系统响应变得极其缓慢。乐观锁和悲观锁并没有绝对的高级与低级之分，悲观锁用排队等待换取了数据的绝对安全，乐观锁用冲突重试换取了系统的吞吐效率。

看懂了它们背后的假设与代价，你就能在面对不同的业务并发时，选出最合理的那把锁。
